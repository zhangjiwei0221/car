## 1. 最终目标与边界

### 1.1 [用户要求] 要交付什么

输入一张 TXT 目标图，点击批量生成，在有限预算内得到一关：

1. 棋盘行列、车辆容量、车序和障碍合理；
2. 玩家会卡住，但主要不是黑、窄、背板或末段锁死；
3. 中段尽量持续经历暂存 **3/4**，压力有起伏；
4. 玩家能通过思考释放暂存压力，最后通关；
5. 生成不能靠无限局部搜索耗数小时。

### 1.2 不把什么当成功

- 找到一条全知解 ≠ 好关；首通低 ≠ 好关；峰值高 ≠ 好关。
- 单个 seed 或单张图成功 ≠ 泛化；有界搜索没找到 ≠ 无解；`unknown` ≠ 没有释放。
- 时间到时输出“当前最好” ≠ 目标已达成；目标未达必须落库为未达。
- 目标图本身不适合时，应给策划修改建议，不承诺所有图都能做成同一种好关。

### 1.3 当前最终验收的四层

| 层 | 当前证据 | 尚未证明 |
|---|---|---|
| 硬合同 | 可解、守恒、独立回放、行列≥6、容量审计 | v523推荐图仍发现aboveMax=1，存在漏网路径 |
| 结构 | 免费段、选择、partial、棋盘、低压力吃满最终证据 | 指标仍是代理，不能代替真人审美 |
| 目标体验 | 中段3/4、显著释放、释压动作可回放、多路线 | release unknown、路线覆盖和可学习性 |
| 真人体验 | 目前主要依赖 PlayerSim 和用户偶发反馈 | 尚未系统盲评，不能宣称“好玩已公式化证明” |

### 3.3 瞬时模式与总流程的关系

用户确认的目标规则是“车辆进入暂存后，从该车最左空槽映射的起点，优先吃掉曼哈顿最近的小人”。因此当前瞬时模式施工主线为：

```text
规则契约 → instantPlayout切车 → 每色容量计划 → 摆盘车序
→ 完整体验 → 失败驱动修复 → 目标化障碍 → 多图/UI/真人
```

它与 P0~P6 不是两套计划：第1步和第3步落实P0容量合同；第2~4步落实P2/P3；第5~6步落实P1/P2；第7步落实P4；第8步落实P5/P6。总流程仍是最终验收与冻结标准。

## 4. 所有后续实验必须遵守的工作流

### 第0步：写预登记

每次实验先写：`假设 / 唯一变量 / 图与seed / 预算 / 主指标 / 保护指标 / 通过与否决条件 / 回滚点`。没有预登记，不跑大搜索。

### 第1步：固定样本，不先调参

- 至少包含：一个已知成功保护、一个近失、一个远失败、一个结构失败、一个留出图/seed。
- 校准集与留出集分开；不能看结果后换图、换seed或挑阈值。
- 重要对照保留旧—旧重复：墙钟预算本身会造成hash漂移，不能把所有差异都归因于代码。

### 第2步：先跑旧版基线

保存旧版逐关：hash、结构、完整体验、路线、容量、board、wall、rounds、失败主因。没有旧数字，不允许写“改善”。

### 第3步：只改一个因素

- 一次只改一个动作：一个容量变量、一个车序交换、一个障碍单元或一个搜索排序规则。
- 生成与修复仍走同一`produceDispatch/runFlowOnce`产线；禁止另写只在实验里有效的假产线。
- `boxSizeMin/Max`、`capNormMin/Max`不得被逻辑偷拆或越界。

### 第4步：完整重解与保护

每个候选至少检查：可解、每色守恒、独立回放、棋盘≥6、aboveMax、belowMin不恶化、障碍语义、完整体验、已有成功hash/pass。

### 第5步：预算内给结论

- 近失败才局部修；远失败换基底；局部耗尽换seed；总预算耗尽如实未达。
- `unknown`单独保留，不写成0，也不自动放行。
- 记录实际墙钟与超时；不把单轮时间乘容量臂或后处理重复放大。

### 第6步：通过后才扩大样本

顺序固定：**精确复现 → 单变量小实验 → 已知成功保护 → 多图独立seed → 真实UI/落库 → 真人校准**。

### 第7步：留档与回退

- 工具输出JSON/JSONL；日志固定“问题/证据/改动/验证/遗留”。
- 生产改动升版本、语法检查、补丁、Git小提交；失败方案也保留候选和否决理由。
- 默认不通过就回退，不把“指标更合理”当作接受搜索退化的理由。

## 5. 剩余实验的详细执行卡

## P0．先补硬合同：容量越界谱系追踪

**问题**：v523推荐图出现1辆26px车，用户上限19；旧新都有，说明不是重试造成。

**实验**：

1. 固定推荐图/88001及生成配置，dump最终候选及每次容量变换前的快照。
2. 沿“切球→归一化→容量臂→棋盘溢出→障碍后处理→trapPost（历史名P7）→最终best”逐段重新计算`capacityEvidence`。
3. 找到第一次出现aboveMax的阶段；只修该阶段的夹紧或候选拒绝，不在最终出口简单删车削像素。
4. 检查是否同级worker/branch配置不同导致最终`r.config`与实际容量臂不一致。

**通过**：同一关不再越界且每色守恒；已有成功hash/pass不变；若只能淘汰该候选，必须如实未达而非硬修。

**否决**：需要破坏每色像素总量、缩放用户区间或隐藏审计才能“通过”。

## P1．释放证据unknown：先修评价覆盖，再改关卡

### P1.1 状态覆盖

**假设**：当前只试前2个高压状态，可能漏掉真正释放点。

- 收集`curvePass=true + release unknown`关，标出显著释放事件与已尝试状态。
- A臂当前maxDecisionStates=2；B臂只增加状态覆盖，不增加单动作搜索预算。
- 记录found/unknown、实际命中状态、评价耗时。

**通过**：至少一个unknown变成found且回放有效，已知found不退化；随后用释放事件指导状态排序，而不是永久暴力增加状态数。

### P1.2 动作排序

**假设**：参考动作之后按棋盘顺序取前几个备选，可能漏掉能完成/能解锁的释压动作。

- 固定P1.1仍unknown的状态；只改备选排序：即时降压、可完成、解锁贡献、长期搜索证据分别记录。
- 不增加maxAlternatives或节点预算，避免把排序改善与加预算混淆。

**通过**：同预算found增加、unknown减少，最终回放全过；不能只提高短期降压却导致最终无法通关。

### P1.3 预算分配

- 只有前两项证明“覆盖/排序不是根因”后，才比较350ms/节点预算的阶梯。
- 报告found增益与额外毫秒；若线性加时间仍无收益，回生成侧修供给/车序，不继续烧评价预算。

## P2．失败驱动的压力与容量组合规划

### P2.1 先按诊断分派，不混治

| 诊断 | 动作 | 禁止 |
|---|---|---|
| 远压力不足 | 换切法/基底/供给规划 | 在近失容量微调上耗时 |
| 近压力不足 | 少量关键车±px重解 | 扩大到所有车或无限串阶段 |
| 显著释放缺失 | 查供给同步与车序 | 只抬高峰值 |
| release unknown | 先做P1评价覆盖 | 直接判关差或自动通过 |
| 结构失败 | 按具体结构门修，不用体验曲线抵消 | 用74.5%体验绕过其他结构失败 |

### P2.2 每色候选容量集

对每色c建立整数候选：

- 约束：`Σ capacity(c,j) = pixels(c)`，包含管道queue；车辆数、用户上下界、belowMin和微型车角色分别记录。
- 小色不因面积小被排除；若解锁贡献、唯一供给、等待和偿还高，可成为关键债车。
- 为每色保留多个角色方案：免费供给、关键债车、释放车、普通车；不要求所有车都“大”。

### P2.3 全局联合而非跨色偷像素

- 每色内部独立守恒；**跨色联合指联合选择每色方案，不是把A色像素转给B色**。
- 以少量Pareto候选做beam：压力覆盖、有效释放、选择宽度、车数/棋盘、首行观感、成本分别评分。
- 每个组合都重新求解；静态债务评分只用于剪枝，不能直接验收。

**首轮通过条件**：至少一个当前近失败基底完整转化，且已知成功不退化；否则保留规划器为分析工具，不接默认生产。

## P3．车序、首行与棋盘观感

### P3.1 局部车序实验

- 从双时间线找“供给已就绪但被迫等待”“债务同时到期”“释放车早于债务”的位置。
- 每次只交换一对车或移动一辆；重新求解并比较压力曲线与释放动作。
- 不复活已否决的全局代理排序。

### P3.2 首行同色观感

- 记录`row0MaxSameColor`、最长同色连、首行颜色数、首行立即可装满选择。
- 用户不绝对禁止首行同色，因此先做人看对照：同色多但功能合理 vs 强制打散但压力变差。
- 只有真人/体验都支持时才把观感权重接入候选排序，不能为好看牺牲核心压力。

### P3.3 棋盘与黑块

- 保持行列≥6；比较同容量同车序下的少量盘型，不把扩大棋盘当万能修复。
- 黑块拆成结构墙、管道、车少补位；优先修根因，不机械追求15%。
- 保护：可解、容量、freeLow、释放、首行选择与黑块比例同时报告。

## P4．目标化障碍：最后做，按功能单元做

### P4.1 先写功能目标

障碍必须回答：“在哪一步，制造什么债务/选择，预期何时释放？”没有这句话就不放。

### P4.2 数量与位置

1. 在基础车序/容量已接近目标但仍有明确缺口时运行。
2. 从激活图、需求时间线和高压状态生成少量候选位置。
3. 每次只加一个最小功能单元；数量由“第一个有效单元”逐步增加，不由随机比例决定。

| 类型 | 合适实验 | 不接受 |
|---|---|---|
| 数字冰 | 延迟某车到目标债务窗口；冰值由相隔取车数决定 | 随意冰10~20、只看峰值、末段封关键色 |
| 锁链 | 让两个供给同时进场，形成可规划的暂存选择 | 用连锁溢出或后期锁死制造难度 |
| 管道 | 调整供给时序/隐藏信息，单独评估公平 | 用管道藏关键债、规避容量或黑块问题 |
| 黑块 | 仅结构/形状必要 | 为压力随机补墙、成片填盘 |

### P4.3 必做消融

- 同一基底：无障碍 vs 一个单元；容量和车序不变。
- 命中后再做“移除该单元”复核，证明效果确实来自它。
- 记录可解、3/4曲线、释放、末段压力、路线分布、PlayerSim死因和实际耗时。

**否决**：只提高峰值/首通死亡、只在末段堵死、移除后无差别或靠unknown才能通过的障碍。

## P5．多图、性能与真实UI验收

### 固定报告口径

- 图集预登记为校准/留出，至少含ready/review、不同颜色数、不同前沿与不同尺寸。
- 指标：目标通过率、结构通过率、有效→无效、aboveMax、体验distance、release found/unknown、P50/P90墙钟、超时、轮数、重试次数。
- 小样本只写x/N，不伪造P95；后续样本足够再报告分位数。

### 真实UI必查

1. 页面版本与脚本query正确；worker与headless配置一致。
2. 无高速noCandidate；可停止；长轮/最终评价耗时如实记录。
3. 每关落库，批次最终COMPLETED/STOPPED明确；目标未达不计合格。
4. JSONL包含体验、路线、最终结构、容量、重试和失败原因。

## P6．真人校准与最终冻结

### 先小样盲评，再扩大

- A/B隐去版本，随机顺序；包含旧基底、生成器候选和明确反例。
- 记录：是否看懂暂存压力、在哪一步知道如何释放、是否靠背板、是否感到公平、是否愿意再玩。
- 同步保存真人操作回放与buffer曲线，检查机器认定的“释放点”是否真是玩家思考点。

### 真人反馈如何回写生成器

- “简单但首通低” → 查免费前期、背板和隐藏信息，不直接加峰值。
- “卡住但想不到释放” → 查选择可见性、解锁因果和供给时序。
- “首行丑/同色多” → 进入P3观感实验，不改目标体验门迎合。
- 真人结论与代理冲突时，保留代理为待校准，不宣称公式胜过体验。

### 最终冻结条件

1. 硬合同全部通过，无aboveMax漏网；目标体验与释放回放通过。
2. 预登记多图留出集达到事先约定的命中和耗时目标，已知成功无回退。
3. 真实UI批量、落库、停止、预算与版本全部一致。
4. 障碍可解释且经消融；观感经用户确认。
5. 真人能识别并执行预期释放，未表现为纯背板/末段锁死。
