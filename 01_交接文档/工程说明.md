> ## ⚠ 当前能力边界（2026-10-22，用户明确）
>
> **生成器能做出来的，是「难关」，不是「好关」。**
>
> - ✅ 能保证：关卡可解（全知求解通关）、有压力（全知峰 4~5 / 覆盖率 7~58%）、可批量出关
> - ❌ 不能保证：好玩。**"好关卡"至今没有定义，也没有任何指标在衡量它。**
>
> 手里只有两个量：`全知峰 maxBuffer`（最优解要欠几个槽）和
> `覆盖率 buf34Pct`（20~80% 暂存≥3 的占比）。**这两个都是难度刻度，不是质量刻度。**
>
> 缺的量（一个都没算过）：选择丰富度 / 决策影响力 / 学习曲线 / 废牌率。
>
> 另：**球序没有被任何机制保证**——切球给了颜色顺序、摆盘忠实映射，
> 但混色（mixRate 0.6）会把后面的车提前拉进前面的行（首行出现"该色可达 0"的废牌）。
> 求解器不控制球序，它只验证可解性。
>
> 详见工作日志 279 节。

## 1. 这个工程是做什么的

给手机游戏「车接小人」（蚂蚁拿块玩法）**批量生产可玩关卡**。

- 输入：一张像素图（TXT 像素矩阵，一格一个颜色号）
- 输出：一关 `toprow / blocks / maprow / mapcol / spools` 结构的 JSON，可直接放进游戏客户端的 `bin/` 目录
- 中间：切球 → 选盘 → 摆障碍 → 放车 → 求解 → 评估 → 择优/兜底

核心矛盾（整个工程都在围绕它调）：

```
车太碎 → 车多盘大、开局全是免费车 → 没有压力
车太大 → 车少盘小、每辆都能一口吃下 → 也没有压力
压力 = 中段（30~80% 进度）手里"攒着几张吃不完的票"持续得够久
```

## 3. 技术架构

### 3.1 代码组成（`02_工程/完整主bin快照_20261012/bin/js/`）

| 文件 | 职责 |
|---|---|
| `generator.js` | 生成主逻辑：切球、选盘、铺盘、卡点树、验收编排（最大，1.3 万行） |
| `app.js` | 界面与批次调度：参数装配、线程池、日志、结果条、落盘 |
| `solver.js` | 求解器：6 遍（贪心×2 / 三步树×2 / 噪声×2），产出取盒序列与压力采样 |
| `solver-strategy.js` | 选步策略：贪心打分、三步前瞻树 |
| `playersim.js` | 玩家模拟：不同"手痒程度"的 10 局，含死因埋点 |
| `simulator.js` | 规则内核：棋盘可达/激活、消除 flood-fill、锁链/冰判定 |
| `analysis.js` | 审核：卡点审计、难度分 |
| `utils.js` | 关卡解析、游戏格式转换 `toGameFormat` |

### 3.2 两条产线

| 流程 | 入口 | 特点 |
|---|---|---|
| **旧流程**（生产用） | `generatorFlow:'old'` → `produce()` | 切球定车数、棋盘按盒数反推、结构组合轮换 |
| 新流程 | `produceFixed()` | 按"结构/层"铺盒，**不认容量区间**（历史遗留，仅纠偏/兜底误用过） |

> 红线：**一个会话只能走一条产线**。任何"重产一次"的分支（纠偏 `bandFixOnce`、兜底）都必须走 `runFlowOnce()`，
> 否则会出现"你设 30~60，结果满盘 8~25"的事故（v314）。

### 3.3 一次生产的数据流

```
TXT 像素图
  → genApplyFixed（参数装配）
  → produceDispatch（K 轮产线）
      → produce（单轮：造 14 个候选 + 卡点树）
          → generateFromBlocks → pickBoxSplit（切球）→ buildBoard（选盘/障碍/放车）
          → Solver.solve（首解 6 遍）
          → evaluateGeneration（覆盖率/峰窗/玩家/死因）
          → goodV3Of（六条门槛，历史判据；现行看结构门）
  → portfolioBetter（择优）→ bandFixOnce / 兜底
  → 落盘 + 界面回显
```

## 4. 产物与数据格式

### 4.1 关卡 JSON（客户端可直接用）

```json
{ "toprow": 40, "blocks": [[色号…]], "maprow": 5, "mapcol": 7, "spools": [[…]] }
```

- `blocks`：目标图像素矩阵（色号，0 = 空）
- `maprow/mapcol`：车场行列
- `spools`：每格一辆车 `{id, count, type:[…], param:[…]}`；`type` 里 5=锁链、6=问号、7=数字冰，11~14=管道

### 4.2 批次产物目录

```
输出文件/<批次名>/
├─ 合格关卡/<图名>.json           ← 合格关
├─ 不合格关卡/<图名>__超时兜底.json
├─ 生产文档/
│   ├─ 关卡数据/<图名>.json       ← 调试数据（含 audit/perf/solve）
│   ├─ 逐关记录.jsonl             ← 每关一行（结果/棋盘/难度/性能）
│   ├─ 分析报告.csv
│   ├─ 生产报告.md
│   └─ 批次配置.json
├─ txt图/ 不合格txt图/
```

### 5.2 跑一批

1. 面板 1 导入 TXT（可多选）
2. 面板 2 设：**生成模式**（按时间 / 按目标）、**每图搜索时间**（2/3/5/8/10/15 分钟，时间模式用）、

> **两种模式**：按时间 = 到点输出手里最好的一关；按目标 = 不达标就一直换种子重做，
> 点「结束」后最多等约 35 秒，输出当前最好的一关（不是什么都不给）。
> 目标模式下「每图搜索时间」变灰，单轮固定 20 秒。

## 7. 指标：旧六条 vs 新六指标

### 7.1 旧六条（goodV3，已降级为“旧判据”）

| 指标 | 定义 |
|---|---|
| **覆盖率** `band3Pct` | 进度 30~80% 区间里，暂存 ≥3 的采样点占比 |
| **峰窗** `midLateMax` | 同区间的暂存峰值（旧合格带 3.2~4.8） |
| **尖峰** `band4Pct` | 同区间暂存 ≥4 的占比（默认不卡） |
| **玩家通关率** `playerPassPct` | 5 种手痒度 × 2 种子 = 10 局，不给复活 |
| **死因** `deathCauses` | 链 / 冰 / 管道 / 形状 / 断供 |

> **口径（2026-10-22 核对）**：全知求解器与玩家模拟器都走「起点距离优先」消除
> （`solver.js:111` `useSlotStart:true`），**不是圈号**；仍用圈号的是 `demandCurveOf`（算冰值/切球近似）。
>
> **v364 起旧六条不再决定合格**；v366 起只作为报告里的「旧判据（仅供参考）」和搜索早停的辅助。
> 不要再把“峰窗 3.2~4.8 / 覆盖率 / 玩家通关率”当成质量定义。

### 7.2 新六指标（质量刻度，当前状态）

| 指标 | 想量什么 | 状态（v370） |
|---|---|---|
| **F 前沿宽度** | 切球前沿平均能同时暴露几种颜色 | ✅ 已算：`frontierWidthOf`；报告 F |
| **W 选择宽度** | 每一步“可吃满”的选项数 | 🟡 部分：`choiceCurve.medFull/lowPct`；报告 W；质量线用 W 中位≥2、W≤1≤35% |
| **T 陷阱密度** | 策略间分歧步数 ÷ ≥2 决策点（v0 代理） | ✅ P1 已出数（v371）；真反事实 P3 |
| **R 后悔率** | 最优进度 − 10 局平均进度（pp） | ✅ P1 已出数（v371） |
| **U 废牌率** | 10 局都没碰过的盒 ÷ 总盒数 | ✅ P1 已出数（v371）；失败局偏高 |
| **J 公平度** | 死亡里由隐藏信息（管道/问号）造成的比例 | 🟡 部分：`deathCauses` 里管道占比；质量线 >20% 判偏黑 |

新口径：**硬门 2 条（可解 + 守恒）→ 可玩；六指标 + 四玩家 → 质量**。
质量阈值等 P1/P2 跑出分布再定，不拍脑袋。

### 14.2 容量自动推导

工具：[`03_工具/难度关系/容量推导.js`](../03_工具/难度关系/容量推导.js)

```
m      = 需求块中位数（每解锁一次新露出多少像素）
下界   = 1.5m      低于它 → 一步装满 = 白给
上界   = 4.5m      高于它 → 等太久 = 容易死锁
白给车 = Σ floor(开局该色暴露量 / 容量)，目标 1~2 辆
```

实测：006（m=9）→ 带 32~40，取 36，白给 2，冰 0~1；
015（m=10）→ 无可行带（要 ≥72），取 45 + 冰 3，或改图让开局只露 2~3 色。

### 14.3 障碍数量（修正后）

| 障碍 | 数量（30~40 步关） | 约束 |
|---|---|---|
| 数字冰 | **4~8 块**，分 4~5 个时点 | 第 0 行 ≤1；同一时刻 ≤2 块生效 |
| 锁链 | **2~4 对**（4~8 辆） | 同时 ≤2 对；一对 = “现在色 + 以后色” |
| 管道 | **1~3 条**（每条 2~4 辆） | `H/N` 10~25%；默认 0，管型才开 |
| 黑块 | **1~4 块** | 只封捷径，不封唯一路；不 2×2 |

> 关键区分：**全关总数**可以多，**同一时刻同时生效的债务源 ≤3 个**
> （车容量债 / 冰锁 / 链配对 / 管道未知）；超过 3 个，玩家无法归因。

### 14.4 关卡类型与轮换语义

| 类型 | 主要压力源 | 默认障碍 |
|---|---|---|
| 无（纯容量） | 容量 + 需求块 | 0 |
| 冰型 | 时机锁 | 冰 4~8 |
| 链型 | 被迫垫付 | 链 2~4 对 |
| 管型 | 信息未知 | 管 1~3 条 |
| 混合 | 两类组合 | 各取本类型 60% |

- **“每种占一份”= 批次份额 ≥1/4，不是“每种只做 1 关”**；
- 40 关一批 → 每种 ≥10；5 关一批 → 每种 1；3 关一批 → 按顺序轮换，不保证每种都出现；
- 类型**先只写入记录**，暂不参与生成；以后再做定向生成。

### 15.7 结构门 v2 定义（v462）

| 指标 | 算法 | 门槛 | 防什么 |
|---|---|---:|---|
| 可解 | 全知求解器通关 | 必须 | 死局 |
| 守恒 | Σ盒容量 = 彩色像素 | 必须 | 生成错误 |
| J | 管道+问号死亡 ÷ 全部死亡 | ≤20% | 隐藏信息杀 |
| 可选中位 | 每步 `moves.length` 的中位数 | ≥2 | 单线/没选择 |
| 被迫步 | `moves.length≤1` 的步占比 | ≤20% | 太多强制单线 |
| partial步 | `moves.length−full≥1` 的步占比 | ≥20% | 全是 full |
| 吃满中位 | 每步 `full` 数的中位数 | ≤2 | 多个 full 白给 |
| freeLow | `full≥2 且 free≥4` 的步占比 | ≤30% | 全程随便点 |
| 最长免费连 | 连续 `full≥2 且 free≥3` 的最长步数 | ≤5 | 连续白给段 |

说明：

- `free` 是当前缓冲剩余格数，`full` 是当前能吃满的选项数；
- 首通（贪心）只报告，不进结构门；
- J 只代表管道/问号，不代表冰/链/形状的公平性；
- 结构门只防畸形，不单独保证“难”。
