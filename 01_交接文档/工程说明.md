## 1. 这个工程是做什么的

给手机游戏「车接小人」（蚂蚁拿块玩法）**批量生产可玩关卡**。

- 输入：一张像素图（TXT 像素矩阵，一格一个颜色号）
- 输出：一关 `toprow / blocks / maprow / mapcol / spools` 结构的 JSON，可直接放进游戏客户端的 `bin/` 目录
- 中间：切球 → 选盘 → 摆障碍 → 放车 → 求解 → 评估 → 择优/兜底

核心矛盾（整个工程都在围绕它调）：

```
车太碎 → 车多盘大、开局全是免费车 → 没有压力
车太大 → 车少盘小、每辆都能一口吃下 → 也没有压力
压力 = 中段（30~80% 进度）手里"攒着几张吃不完的票"持续得够久
```

## 3. 技术架构

### 3.1 代码组成（`02_工程/完整主bin快照_20261012/bin/js/`）

| 文件 | 职责 |
|---|---|
| `generator.js` | 生成主逻辑：切球、选盘、铺盘、卡点树、验收编排（最大，1.3 万行） |
| `app.js` | 界面与批次调度：参数装配、线程池、日志、结果条、落盘 |
| `solver.js` | 求解器：6 遍（贪心×2 / 三步树×2 / 噪声×2），产出取盒序列与压力采样 |
| `solver-strategy.js` | 选步策略：贪心打分、三步前瞻树 |
| `playersim.js` | 玩家模拟：不同"手痒程度"的 10 局，含死因埋点 |
| `simulator.js` | 规则内核：棋盘可达/激活、消除 flood-fill、锁链/冰判定 |
| `analysis.js` | 审核：卡点审计、难度分 |
| `utils.js` | 关卡解析、游戏格式转换 `toGameFormat` |

### 3.2 两条产线

| 流程 | 入口 | 特点 |
|---|---|---|
| **旧流程**（生产用） | `generatorFlow:'old'` → `produce()` | 切球定车数、棋盘按盒数反推、结构组合轮换 |
| 新流程 | `produceFixed()` | 按"结构/层"铺盒，**不认容量区间**（历史遗留，仅纠偏/兜底误用过） |

> 红线：**一个会话只能走一条产线**。任何"重产一次"的分支（纠偏 `bandFixOnce`、兜底）都必须走 `runFlowOnce()`，
> 否则会出现"你设 30~60，结果满盘 8~25"的事故（v314）。

### 3.3 一次生产的数据流

```
TXT 像素图
  → genApplyFixed（参数装配）
  → produceDispatch（K 轮产线）
      → produce（单轮：造 14 个候选 + 卡点树）
          → generateFromBlocks → pickBoxSplit（切球）→ buildBoard（选盘/障碍/放车）
          → Solver.solve（首解 6 遍）
          → evaluateGeneration（覆盖率/峰窗/玩家/死因）
          → goodV3Of（六条门槛）
  → portfolioBetter（择优）→ bandFixOnce / 兜底
  → 落盘 + 界面回显
```

## 4. 产物与数据格式

### 4.1 关卡 JSON（客户端可直接用）

```json
{ "toprow": 40, "blocks": [[色号…]], "maprow": 5, "mapcol": 7, "spools": [[…]] }
```

- `blocks`：目标图像素矩阵（色号，0 = 空）
- `maprow/mapcol`：车场行列
- `spools`：每格一辆车 `{id, count, type:[…], param:[…]}`；`type` 里 5=锁链、6=问号、7=数字冰，11~14=管道

### 4.2 批次产物目录

```
输出文件/<批次名>/
├─ 合格关卡/<图名>.json           ← 合格关
├─ 不合格关卡/<图名>__超时兜底.json
├─ 生产文档/
│   ├─ 关卡数据/<图名>.json       ← 调试数据（含 audit/perf/solve）
│   ├─ 逐关记录.jsonl             ← 每关一行（结果/棋盘/难度/性能）
│   ├─ 分析报告.csv
│   ├─ 生产报告.md
│   └─ 批次配置.json
├─ txt图/ 不合格txt图/
```

## 5. 操作手册

### 5.1 起服务

```bash
cd 02_工程/完整主bin快照_20261012
python3 -m http.server 8060        # 本工程固定用 8060
# 浏览器打开 http://127.0.0.1:8060/bin/index.html

### 5.2 跑一批

1. 面板 1 导入 TXT（可多选）
2. 面板 2 设：卡点覆盖率门槛（默认 45%）、球容量区间（默认 30~60）、每图搜索时间（默认 3 分钟）、希望主死因（默认不限）
3. 点「批量生产」→ 每关跑完，目标图上方出现结果条、棋盘下方出现「生成过程」

### 5.3 看结果

| 位置 | 内容 |
|---|---|
| 结果条 | 合格/不合格、覆盖、尖峰≥4、玩家通关率、主死因、峰窗、棋盘、车数、容量、用时 |

| 导出制作过程 | 单文件 HTML：颜色统计 → 棋盘/障碍 → 每格车容量 → 压力曲线 → 判定 |
| 日志 | 「本关参数」「搜索规模」「好关v3」「贪心线」等 |

```

## 6. 参数说明（界面上每个旋钮）

| 界面 | config 字段 | 作用 | 备注 |
|---|---|---|---|
| 卡点覆盖率门槛 | `targetBand3Min` | 30~80% 里暂存≥3 的采样占比下限 | 最常卡人的一条 |
| 球容量 上/下限 | `boxSizeMin/Max`、`capNormMin/Max` | 每辆车容量的硬区间 | **用户输入，任何缩放都算 bug** |
| 每图搜索时间 | 推导 `portfolioK / timeBudgetMs / candidateCount` | 3 分钟 = 4 轮 × 45 秒 | 合格早停，时间只是上限 |
| 希望主死因 / 占比 | `targetDeathCause / targetDeathCauseMin` | 只收"主要死于某类障碍"的关 | 默认不限 |
| 只要难关 | `hardOnly` | 只认真实卡点，不认"趋势过平" | — |

## 7. 指标与六条门槛

| 指标 | 定义 |
|---|---|
| **覆盖率** `band3Pct` | 进度 30~80% 区间里，暂存 ≥3 的采样点占比 |
| **峰窗** `midLateMax` | 同区间的暂存峰值（合格带 3.2~4.8） |
| **尖峰** `band4Pct` | 同区间暂存 ≥4 的占比（默认不卡，≥5% 才算门槛） |
| **玩家通关率** `playerPassPct` | 5 种手痒度 × 2 种子 = 10 局，不给复活 |
| **死因** `deathCauses` | 链 / 冰 / 管道 / 形状 / 断供 |

六条门槛全过才算**合格**；不过就换候选，最后输出"最接近"的一关。

| 10-21-23 | ✅ 合格 | 5×7 | 33 | 2 | 0 | 4 | 298s |

**汇总**：合格 6 / 10（60%）；棋盘 5×6 ~ 6×8；车 24~38；黑块 1~15（v338 之前那几批偏多）；

## 10. 约定与红线

1. **版本号**：改 `bin/index.html` 三处（`?v=NNN` 13 处、`<title>`、`<h1>` 徽标）与 `css/style.css?v=NNN`
2. **补丁**：关键改动写进 `02_工程/补丁/补丁_XXX_vNNN.patch`
3. **容量区间是用户输入**：任何"缩放/对半拆/目标车数"都必须让路（踩过两次：v330、v337）
4. **验收必须用真关卡复现**：先写临时脚本跑出数字，再改；单种子对比已误导 ≥5 次
5. **一个会话一条产线**：纠偏/兜底必须走 `runFlowOnce`
6. **删文件前先 `ls -la` 确认路径**（历史上误删过一次工作日志）

## 11. 已知问题（截至 v339）

| # | 问题 | 现象 | 方向 |
|---|---|---|---|
| 1 | 覆盖率双峰 | 要么 80~90%，要么 20~25%，门槛 45 时大批落空 → 兜底 | 门槛降到 35~40；或重新建模"压力靠什么抬起来" |

| 4 | 客户端关卡上限 | 桌面客户端 1~5 已换新关，但上限仍 549，打完第 5 关进旧关 | 改 `棋盘分组配置.csv` 第 4 列 |
