## 0. 一句话目标

把当前“评价框架已接通、局部样本可成功、但泛化未证明”的生成器，按证据逐阶段推进到：

**可解、守恒、容量不越界、棋盘优先行列 ≥7、车序和压力结构可控、释放可回放，并通过多图、独立 seed、真实 UI 和真人校准的关卡生产系统。**

## 1. 用户硬要求

1. 输入 TXT 像素图，批量生成客户端可直接使用的关卡 JSON。
2. 每色车辆容量之和必须等于该色像素数，包含管道 queue。
3. 用户输入的 `boxSizeMin/Max`、`capNormMin/Max` 不得被缩放、对半拆、按目标车数偷拆或静默改写。
4. 棋盘行、列均不得小于 6，最大 9×9。
5. 棋盘选择应优先 `min(rows, cols) >= 7`。
6. `6×6`、`6×7`、`7×6` 只作为经过数据验证后的兜底形态。
7. 7×8、8×7、7×9、9×7 是不同形态，必须覆盖并分别报告，不能只测一个方向后声称转置等价。
8. 目标体验不是“首通越低越好”：
   - 中段多数时间应承受暂存 3～4；
   - 应存在玩家能理解的显著释放；
   - 释放动作必须能接完整后缀并最终通关；
   - 不靠末段锁死唯一关键色、隐藏关键债务或纯背板制造难度。
9. 一个会话只走一条产线。纠偏、兜底、重产必须走 `runFlowOnce()`，不得另写 `produceFixed` 分支。
10. 所有关键改动必须有真实关卡前后数字、多个 seed、语法检查、版本、补丁、工作日志和可回退提交。

3. 不把用户未提交改动、临时 Chrome 目录或旧实验文件混入当前改动。

### 实验中

1. 先跑旧版基线。
2. 只改一个主要因素。
3. 用真实关卡，不用静态推断替代重解。
4. 保留所有变体 JSON/JSONL。
5. unknown 保持 unknown。
6. 单 seed 只用于定位。

### 结束后

1. 至少做 4 seed 复核，或在里程碑中说明不适用原因。
2. 检查已知成功是否回退。
3. 检查容量、守恒、可解、棋盘。
4. 生产代码改动必须升版本。
5. 跑：

   ```bash
   node --check 02_工程/完整主bin快照_20261012/bin/js/generator.js
   node --check 02_工程/完整主bin快照_20261012/bin/js/app.js

   node --check 02_工程/完整主bin快照_20261012/bin/js/gen-worker.js
   ```

6. 更新 `bin/index.html` 三处版本和全部 JS/CSS `?v=NNN`。
7. 写补丁到 `02_工程/补丁/`。
8. 工作日志追加固定五段：
   - 问题（原话）；
   - 证据；
   - 改动；
   - 验证（改前后数字）；

   - 版本；
   - 参数；
   - 已知问题；
   - 当前生成状态。

## 6. Goal 模式执行规则

1. 从 M0 开始，不跳到尺寸策略或障碍。
2. 每完成一个里程碑，先确认通过条件，再进入下一个。
3. 若里程碑失败：
   - 写清负结果；
   - 回退默认；
   - 记录“不得重复”；
   - 再决定是否需要用户裁决。
4. 若同一根因连续两轮仍无法定位：
   - 停止增加预算；
   - 加入只读诊断；
   - 不用更多随机搜索掩盖。
5. 若下一步需要突破用户硬合同、修改客户端 bin、删除数据或改变验收标准，必须停下来向用户确认。
6. 不为了“完成整个目标”而把未达标关卡标成合格。
7. 达标立即停；总预算耗尽时如实返回当前最好并标明未达项。
8. 最终交付时必须提供：
   - 当前版本；
   - 已完成里程碑；
   - 改前/改后数字；
   - 多图与独立 seed 结果；
   - 已知失败类别；
   - 回退点；
   - 仍需真人校准的边界。
