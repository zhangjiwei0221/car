# 主流程总图

> 本次批准写入范围：`codex助理/毛线汽车/**`

## 1. 推荐正式链路

```text
用户启动
  |
  v
node 网页启动器/启动.js
  |
  |-- 选择 8000-8060 的空闲端口，或使用用户指定端口
  |-- 拉起 网页启动器/生产服务.js
  |-- 打开 http://localhost:<port>/bin/index.html
  v
bin/index.html 生成器页
  |
  |-- 导入 N 个 TXT 目标图
  |-- getGenConfig() 读取 UI 参数
  |-- batchProduce() 建立 easySlot / BOSS slot / worker pool
  |-- genPersistProbe() 探测 /api/production/ping
  v
有本地生产服务？
  |
  |-- 是：/api/production/start 创建 输出文件/<批次名>-MM-DD/
  |       每关生产完先 POST /api/production/result 或 /error
  |       服务写盘成功后，网页才派发下一关
  |
  |-- 否：回退为内存模式，全部结束后生成 ZIP，用户手动下载
  v
Web Worker 池
  |
  |-- gen-worker.js importScripts(utils/simulator/solver/playersim/analysis/generator)
  |-- 每个 worker 接收 {cmd:'produce', index, blocks, config}
  v
AntSolver.Generator.produce(blocks, config)
  |
  |-- produceDispatch()
  |-- 默认 new_fixed -> produceFixed()
  |-- 可通过 generatorFlow:'old' 或 FLOW='old' 回退旧流程
  v
生成核心
  |
  |-- 目标图解析与前置闸门
  |-- 候选参数采样
  |-- 建棋盘 / 障碍 / 管道 / 盒队列
  |-- 结构性卡死检查
  |-- 全知求解器筛选
  |-- 玩家模拟与难度评分
  |-- 卡点树分支强化
  |-- 审核分档与兜底
  |-- v126 最终候选多轮难度标定
  v
produce result
  |
  |-- app.js genBuildRec() 汇总生产侧记录
  |-- genPersistPayload() 转程序端干净关卡 + debugData
  v
生产服务落库
  |
  |-- 合格：合格关卡/ + txt图/
  |-- 不合格：不合格关卡/ + 不合格txt图/
  |-- 文档：生产文档/批次配置.json、生产状态.json、逐关记录.jsonl、分析报告.csv、生产报告.md
  |-- 调试：生产文档/关卡数据/<名>.json
```

## 2. 生成核心内部层级

`produceFixed()` 是当前默认主路径，核心意图是“多候选 + 卡点树 + 审核兜底”：

```text
TXT blocks
  |
  |-- blocksFromTXT()
  |-- 入口模式判定：fourSide / bottomOnly / fourSideInstantChain
  |-- 碎色率闸门 fragmentMaxRate
  |-- bottomOnly 时先做底部入口可达性检查
  v
候选循环
  |
  |-- 每个候选采样区间参数 sampledConfig
  |-- buildStructureCandidateFixed()
  |-- planObstacleSlotsFixed()
  |-- fillStructureFixed()
  |-- structuralDeadlockCheck()
  |-- Solver.solve() 多策略筛选
  v
基础可解候选
  |
  |-- evaluateGeneration()
  |-- computeDifficulty()
  |-- chokepointAudit()
  v
卡点制造/分支
  |
  |-- choke types 抽取
  |-- 换球、稀有色、大盒、聚集、窄路、锁链/冰/问号组合等
  |-- 分支后重解 + 重新审核
  v
候选排序
  |
  |-- 合格优先
  |-- 简单关·趋势过平次之
  |-- 兜底候选保底
  v
finalizeProduce()
  |
  |-- v126 difficultyRounds 多轮玩家路线标定最终难度
  |-- 救援成功路径强制重解析最终 level，避免 stale parsed/result
```

## 3. 输出流向

正式逐关落库输出在 `输出文件/<批次名>-MM-DD[-N]/`：

```text
输出文件/<批次>/
  ├── 合格关卡/                  程序端干净 JSON
  ├── txt图/                      合格源 TXT
  ├── 不合格关卡/                不合格但有结构的 JSON
  ├── 不合格txt图/               不合格或前置闸门跳过源图
  └── 生产文档/
      ├── 批次配置.json
      ├── 生产状态.json
      ├── 逐关记录.jsonl
      ├── 分析报告.csv
      ├── 生产报告.md
      └── 关卡数据/<名>.json     完整内部 board/solve/audit/debugData
```

服务不可用时的 ZIP 兜底输出结构不同：

```text
ZIP/
  ├── 关卡/
  ├── txt图/
  ├── 求解数据/
  ├── 关卡数据/
  │   ├── 关卡数据.json
  │   ├── 分析报告.csv
  │   └── 生产报告.md
  └── 索引.csv
```

## 4. 两条离线/历史链路

- `bin/generate_node.js`：面向 20x20 小图的 headless 批量生产脚本，默认输入 `txt图/20x20图纸_9关`，输出 `output/20x20关卡包_9关`。
- `bin/finalize_node.js`：面向 20x20 包补齐/修复，默认目标 20 关，做内部 board 与 round-trip 双重求解校验。
- `bin/js/_prodrun.js` + `_prodmerge.js`：旧临时并行生产/合并脚本，含 `/Users/red/...` 硬编码路径，不能视为当前可移植主流程。
