# 蚂蚁拿块 · 最短距离计算逻辑

> 用途：把「蚂蚁吃目标图像素时的最短距离」这一件事单独讲透——距离是什么、怎么算、用在哪、和「可达性」有什么区别。
> 依据：当前正式代码 `bin/js/simulator.js` / `bin/js/playersim.js` / `bin/js/utils.js`。
> 性质：逻辑说明文档，本文件不改任何代码。
> 关联：起点映射与整条消除顺序见 `目标图起点与消除顺序_程序端对接.md`；本文只聚焦「距离」这一维度。

---

## 0. 一句话结论

**这里的「最短距离」= 曼哈顿距离（L1）**：目标图上某个像素 `(r,c)` 到「该蚂蚁球固定起点 `(sr,sc)`」的
`|r-sr| + |c-sc|`。它是**直线格距、无视一切障碍**，只用来给「可以消的像素/可以推进的球」排优先级，
**不做绕障寻路**。「能不能消」由另一套**可达性 BFS** 决定；「先消哪个」才由距离决定。两者是两回事。

---

## 1. 先分清两个概念：可达性 vs 距离

| | 可达性 (Reachability) | 距离 (Distance) |
|---|---|---|
| 回答的问题 | 这个像素**现在能不能消** | 能消的里面，**先消哪个** |
| 算法 | 4 邻 BFS / flood（尊重墙、空腔、由外向内溶解） | 曼哈顿直线格距（`|Δr|+|Δc|`） |
| 是否绕障 | 是（连通性即路径存在性） | 否（穿墙直算，只是排序权重） |
| 主要函数 | `outsideReachSeed` / `reachableCell` / `computeExteriorOpen` / `canConsumeReach` | `keyOf`(带 start) / `eatNearest` / `peekNearestDist` |

核心：**先用可达性筛出「本轮候选像素集合」，再在候选里用曼哈顿距离挑最近的先吃。** 距离从不负责判断「消得到消不到」。

---

## 2. 距离怎么定义（公式）

设蚂蚁球的固定起点为 `start = {r: sr, c: sc}`，目标像素为 `(r, c)`：

```text
distance(r, c) = |r - sr| + |c - sc|      // 曼哈顿距离 / L1 / 网格直线格数
```

- 坐标系：数组 `r=0` 是**顶行**，`r=rows-1` 是**底行**；`c=0` 最左。
- 距离恒为非负整数，单位是「格」。
- 不含对角线（只走上下左右的格差之和）。
- **不考虑**中间是否隔着未消像素、黑块、管道——它不是真实爬行路径，只是排序标尺。

---

## 3. 起点 `start` 怎么定（距离的基准点）

距离必须有基准点。基准点就是**这颗球入场时占到的暂存槽位映射到目标图底部的坐标**，每球一个、入场即固定。

```js
// simulator.js: slotStartCoord / playersim.js: slotStart
col   = floor( slot / bufferLimit * cols )   // 按槽位比例横向铺开
start = { r: rows - 1, c: clamp(col, 0, cols-1) }   // 行恒为底行
```

- 蚂蚁从**底部**进入，所以 `start.r = rows-1`（恒定）。
- `slot` 取暂存区**最左空槽**（`leftmostFreeSlot`）；`bufferLimit` 默认 5。
- `bufferLimit=5, cols=55` 时：槽 0/1/2/3/4 → 起点列 0/11/22/33/44。
- 球一旦入场，`start` 写进它的暂存条目**终身不变**；哪怕左边槽腾空也不改。
- 详见 `目标图起点与消除顺序_程序端对接.md` 第 2 节。

> 因此「最短距离」是**相对每颗球各自起点**算的，不是相对一个全局固定点。同一像素对不同球的距离不同。

---

## 4. 距离用在三处

### 4.1 选像素：一颗球本轮先吃哪个同色像素

函数：`floodFillEliminate(..., start, ...)`（`simulator.js` 约 335 行起）。
每消一个像素都要在「当前可达的同色候选」里按排序键取最小者。排序键 `keyOf`（生效版本）：

```js
var SOURCE_SPAN = AREA * (AREA + 1);            // AREA = rows*cols
function keyOf(r, c, source, depth) {
  var base = source * SOURCE_SPAN + depth * AREA + tieOf(r, c, source);
  if (start) return (Math.abs(r - start.r) + Math.abs(c - start.c)) * (4 * SOURCE_SPAN) + base;
  return base;                                   // 无 start = 理论口径，见 §5
}
```

优先级从高到低（键值小者先消）：

1. **离起点的曼哈顿距离**——权重 `4 * SOURCE_SPAN`，压倒后面一切；
2. 入口源 `source`：底(0) → 左(1) → 右(2) → 顶(3)；
3. 依赖波深度 `depth`：从入口进来经过几层；
4. 同波内次序 `tieOf`：底/顶按左→右，左/右按下→上。

即：**曼哈顿距离是第一关键字**，只有距离完全相等时，才用「入口源 + 依赖波」这套「由外向内」的次序打破平手。

并发玩家模拟里的等价实现是 `eatNearest`（`playersim.js`）：在该色可达像素集合里取曼哈顿最小，平手时**取最底(r 大)、再最左(c 小)**：

```js
var d = Math.abs(r - ar) + Math.abs(c - ac);
if (d < bestD || (d === bestD && (r > bestR || (r === bestR && c < bestC)))) { ... }
```

### 4.2 多球调度：本 tick 哪颗球先推进

同色多球共享像素池，先动手的球会抢到争用像素，所以要给球排序。用 `peekNearestDist`（**只探测距离、不消除**）：

```js
// simulator.js peekNearestDist：离“我自己的起点”最近的、可达的同色像素的曼哈顿距离
d = start ? (Math.abs(r - start.r) + Math.abs(c - start.c))   // 带起点：曼哈顿
          : ((rows - 1 - r) * cols + c);                       // 无起点：由底向上、再靠左的理论序
```

- `autoReleaseBuffer`（求解/手动）与 `playersim.run` 的消除阶段都据此排序：
  **每轮先让「离自己起点最近的可达同色像素」更近的球消**，平手按入列先后（暂存索引 / `key`）。
- 单球时跳过排序（省去全图扫描，行为等价）。
- 注意：`peekNearestDist` 会先用 `reachableCell` 过滤，只统计**可达**的同色像素；找不到可达像素则返回 `Infinity`（该球本轮排最后、实际吃不到）。

### 4.3 道具 / 复活：无视可达性的「按距离直取」

死锁救场（`playersim.js` 的 `useItemPS` / `revivePS`）走的是**跨越阻挡**的距离直取——
把目标色的**全部未消像素**（不经可达性过滤）按距离排序后从近到远消掉：

```js
for (所有未消的该色像素) px.push({ r, c, d: |r-ar| + |c-ac| });
px.sort((a, b) => (a.d - b.d) || (b.r - a.r) || (a.c - b.c));  // 距离↑ → 最底 → 最左
```

这是与 §4.1/§4.2 的唯一区别：**救场时距离仍是曼哈顿，但不再要求像素可达**（相当于道具能穿墙消除），
用于强行腾空暂存槽 / 清理棋盘残留盒。平手规则同样是「先最底、再最左」。

## 5. 两套口径：带起点(曼哈顿) vs 无起点(由外向内)

距离相关代码都有「传 `start` / 不传 `start`」两条分支：

| 口径 | 触发条件 | 距离定义 | 用在哪 |
|---|---|---|---|
| **起点距离优先** | `useSlotStart=true`（传入 `start`） | **曼哈顿** `|Δr|+|Δc|` | 手动游玩、玩家模拟、以及当前求解器（见下） |
| **理论由外向内** | 不传 `start`（`start=null`） | 非曼哈顿，用 `dEdge` / `(rows-1-r)*cols+c` 编码的「贴边、由外向内、底优先、左优先」次序 | `floodFillCount` 等纯计数、旧理论口径 |

无起点口径的排序基（`floodFillEliminate` 的 `base`，或 `peekNearestDist` 的 else 分支）本质是：

```text
dEdge = min(rows-1-r, c, cols-1-c)        // 到最近“开口边”的格数（顶边不计入优先）
优先级：dEdge 小（越靠外）→ 底部(r 大) → 左侧(c 小)
```

它衡量的是「离外部开口多近、由外向内第几层」，是一种**结构性次序**，不是到某个起点的直线距离。

> 现状提示：`createState` 里 `useSlotStart` 的注释写「默认关(求解器/生成)」，但实际 `solver.js` / `playersim.js` / `app.js` / `utils.js` 都传或默认 `true`——**正式运行走的是曼哈顿起点口径**。注释过时，实现为准（详见对接文档 §10）。

## 6. 复合优先级：为什么说「距离压倒一切」

`keyOf` 里曼哈顿距离乘了 `4 * SOURCE_SPAN`（`SOURCE_SPAN = AREA*(AREA+1)`），
远大于「入口源 + 依赖波 + 波内次序」三项之和的取值上界。因此：

```text
键 = 曼哈顿距离 × (很大的权重)  +  由外向内的依赖波次序
```

- 距离差 1 格，键值就相差一整个 `4*SOURCE_SPAN`，任何依赖波差异都翻不过来。
- 结论：**先严格按离起点的曼哈顿距离分层，同距离内再按「由外向内的依赖波」定序。**
- 后果（重要）：起点选错（比如程序端用「底部正中」而非槽位映射点）会**整体改写消除序列**，
  不是细微误差——因为距离是压倒性的第一关键字。

---

## 7. 平手规则汇总

所有「距离相等」时的兜底次序一致：**先最底行（r 大），再最左列（c 小）**；再平手则按依赖波 / 入列先后。

| 场景 | 平手兜底 |
|---|---|
| `eatNearest`（玩家选像素） | `r` 大优先 → `c` 小优先 |
| `keyOf`（求解选像素） | 依赖波 `source(底→左→右→顶) → depth → tieOf` |
| `peekNearestDist`（球间排序） | 暂存索引 / `key` 小优先（先入列先动） |
| 道具/复活直取 | `r` 大优先 → `c` 小优先 |

## 8. 可达性如何界定（距离的前置筛选）

距离只在「可达候选」上比较，所以必须先懂可达性：

- **初始已消种子** `outsideReachSeed(blocks, rows, cols, bottomOnly)`（`utils.js` 约 460 行）：
  从「贴外边的空格」BFS 铺开成初始 `eliminated`。**封闭空腔不与外部连通 → 不可达**，不会从孔洞内壁凭空开始消。
  - 默认：四边都是外部开口；
  - `bottomOnly`：只有底边开口，上/左/右当墙 → 目标图只能**自底向上溶解**。
- **单像素可达判定** `reachableCell(elim, rows, cols, r, c)`：
  `(r,c)` 在棋盘边界，**或**任一 4 邻已被消除，即算可达。
- **外部连通空洞** `computeExteriorOpen(s)`：从「贴边且已消」的空格做 BFS，得到与外部连通的空洞集合，
  供同一 state 下所有盒的 `canConsume` 复用。
- **能否一次消完** `canConsumeReach(s, box, open)`：从「贴边 / 贴外部空洞」的同色像素起，沿同色 4 连通扩散计数，
  达到 `need` 即返回 true（等价于 flood 的布尔结论，但不整图拷贝）。玩家用它做「乐观估计」。

一句话：**可达性 = 4 邻连通 + 由外向内 + 封闭空腔不算；距离 = 在可达候选上算曼哈顿。**

---

## 9. 为什么用曼哈顿，而不是「绕障最短路」

- 距离的职责是**排序**（先吃哪个），不是**判定**（吃不吃得到）——判定已由可达性 BFS 承担。
- 蚂蚁在目标图上按可达性逐格溶解，视觉上「就近先消」；曼哈顿直线格距最贴近「离入口最近的像素先被吃到」的直觉。
- 曼哈顿是 O(1) 计算、无需寻路，放进每消一格都要跑的排序键里代价极低；若改成绕障测地距离（BFS 最短路），
  每个候选都要一次 BFS，性能不可接受，且与「可达即可消」的规则重复。
- 因此设计上刻意让「距离」保持廉价的直线格距，把「路径是否存在」交给可达性——两者解耦。

## 11. 注意事项（读码避坑）

1. `floodFillEliminate` 内有**两个同名 `keyOf`**：前者 `keyOf(r,c)`（静态最近边，含 `dEdge`）因函数提升被后者
   `keyOf(r,c,source,depth)` 覆盖，是**死代码**。真正生效的是 §4.1 的四参版本。
2. 同函数里的 `reachable(r,c)` 也无调用点；实际可达性由 `edgeSource` + 空洞 BFS（`accessKey`）承担。
3. 距离权重 `4 * SOURCE_SPAN` 是「压倒依赖波」的关键常量，改它会改变距离与结构次序的相对强弱。
4. 道具/复活的距离**不过可达性筛选**（`useItemPS`/`revivePS` 扫的是全部未消同色像素），这是它能「穿墙救场」的原因；
   常规消除（§4.1/§4.2）永远只在可达候选上算距离。
