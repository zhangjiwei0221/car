### 核心设计

拼接里的操作分两类，记录方式不同 —— 这一点是本轮的关键判断：

- **像素类**（涂色 / 直线 / 边框 / 填充 / 图层换色 / 稀少颜色替换）：只改某几个图层的
  blocks，沿用「整层像素快照」（原有做法）。一次直线动几十上百格，逐格记反而更大；
- **结构类**（放上部件、从部件列表移除、生成背景/包围/分隔、新建或清空画布、新建空白图层、
  复制/移除/合并图层、改层序、拖动与方向键移动、改名、固定/隐藏、导入部件）：
  动的是**图层清单本身**（增删换序）与各图层的几个字段。这类**没法**用整层像素快照退回
  —— 新加的图层不在旧快照里、被删掉的更不在 —— 所以记一份**结构快照**：
  图层对象的引用 + 当次的位置/名字/固定隐藏等字段值。

结构快照只存引用、不复制像素，依据是本模块里图层的 blocks 一律「换成新数组」而不是原地改
（`core.js` 的 `paintCells`/`fillRegion` 返回新数组）。审计中发现**唯一一处例外**：
稀少颜色替换原先逐格原地改 `e.layer.blocks[r][c] = target`，会让旧引用跟着变、撤销点失效，
本轮顺手改成按图层分组后走 `paintCells` 整体换新数组再写回（结果像素完全一致）。

### 具体改动

- 撤销栈改成一个，条目带 `kind`：`blocks`（像素）/ `struct`（结构）；重做栈独立，撤销一步就把
  「撤销前的当前状态」压进重做栈；
- 结构类操作统一走 `composeSnapBefore(what)`：**先拍快照再动手**，保证撤销点一定是动手前的状态；
- 方向键连按用 `coalesceKey` 合并成一步（相邻 1.5 秒内），挪十格只需撤一次；
- 「生成背景+包围+分隔」用 `composeSnapGroup` 并成**一步**；包围一个都没生成时用
  `composeDropLastSnap` 丢掉这一步空撤销；
- 图层换色、包围生成等「可能什么都不改」的分支改成**先判断再压栈**，不留空撤销步；
- 拖动摆位在 mousedown 时记位置快照、mouseup 有实际位移才压栈（没挪动不留撤销步）；
- 快捷键：拼接工作台内 **Ctrl/⌘+Z** 撤销、**Ctrl/⌘+Shift+Z** 或 **Ctrl+Y** 重做；
  焦点在 input/textarea/select 里时不接管（不抢浏览器自己的文本撤销）。常规视图不受影响，
  仍走它自己那套编辑撤销；
- 界面：工作台顶栏新增 `btnComposeUndoTop` / `btnComposeRedoTop`（带「还能撤几步」计数），
  「⑤ 在画布上画」里的按钮改名「↶ 撤销 / ↷ 重做」；两处共用 `syncComposeHistoryButtons()`；
- 日志措辞如实说明撤掉了什么、还剩几步、怎么重做（例：`↶ 已撤销：放上「方块3」（画布 20×20，0 个图层）`）。

拿这批真实产物一测，**上一轮我写的拼接口径过于乐观**：

| --- | --- | --- | --- | --- |
| 财神爷 | 20×20 | 272 | 20×20 | 100% |
| 蜗牛 | 55×55 | 1166 | 41×36 | 48.8% |
| 熊猫 | 55×55 | 2309 | **54×55** | **98.2%** |

- 唯一同尺寸的一对（蜗牛+熊猫）直接叠加**重叠 1132 格 = 蜗牛的 97.1%**；
- 三张外接面积合计 4846 格 **>** 55×55 的 3025 格；实心像素 3747 格 = 画布的 123.9%。

上一轮文档里写的是「图纸都是同尺寸、原坐标、空处为 0，所以拼接就是逐格取非 0」，
验证用的是我人为矩形切半、左右互补的两块。**结论本身没算错，但会让人以为拼接已经不缺什么** ——
实测表明真正可用的拼接**必须支持把部件平移到指定位置**。该更正已同步改进 `使用说明.md` §13.6
并注明原因。核查脚本：`_kiro临时/09.15-拼接需求核查/_探拼接可行性.js`。

### 摆放与合法性彻底分开

用户口径（原话）：部件「默认是单独的主体，互不影响，**可叠加**」，但
「可叠加状态只存在于编辑过程中，类似于美术先临时摆放，**而不是输出后的合法图**」。

据此把两件事拆开，这是整个模块的核心设计：

- **摆放期一路不拦**：`composeFlatten` 永远能出图，叠加只被**高亮**出来，不阻止任何操作；
- **出图前才把关**：`composeAudit` 回答「能不能当正式图纸交出去」，
  `composeExportTxt` / `composeToLib` 一律先过这道闸。拦的时候点名
  「「A」×「B」N 格」而不是只报个总数 —— 只报总数用户没法下手改。

### 位置只用偏移表示

图层结构是 `{ id, name, blocks, rows, cols, offR, offC, locked, visible }`，
**位置只由 `offR/offC` 表示，拖拽不动像素**。于是拖来拖去是无损的，拖回原处完全还原；
冲突检查与出图都由偏移现算。回归里专门验了「挪走再挪回，拍平结果逐格一致」。

命中测试有个容易踩的坑：**只认非 0 像素**，且从数组末尾往前找。
若按外接矩形判定，一个带大片空白的部件会吃掉它矩形内的所有点击，下面的图层再也选不中；
遍历方向则必须与 `composeFlatten` 的覆盖顺序、图层列表的展示顺序保持同一套，否则
「看到的最上层」和「点到的那个」会不是同一个。

### 绘制工具（需求⑥）

作用对象是**当前选中的那一个图层**（用户需求⑤「单个图层编辑」）。
空白画布上**直接落笔即可**，没有可画图层时会自动补一张「绘制层」——
这一点见下面「追加轮①」，是用户实机试用后提的。
「新建空白图层」建出来的是画布尺寸的全 0 图层，也是「自制边框」的载体：画完可
「把选中图层导出为模块 TXT」，再从②导入回来当部件反复用（对应用户需求⑥末段）。

六种边框形态（`BORDER_KINDS`，命名与用户原话逐字一致）：
田字格 / 口字型 / 斜线型 / Z型 / L型 / N型。每种都按**语义部件**分组，供局部替换 ——
用户明确举例「田字格可以看作四个小口，做局部的替换和设计」，所以田字格的 parts 就是
外框 / 中间十字 / 左上口 / 右上口 / 左下口 / 右下口，可以只把左上那一口换色。

**两处靠回归逼出来的实现问题**（都不是数字好看不好看的事）：

1. `lineCells` 原按「每个中心点铺 width×width 方块」加宽 → **端头会外扩**。
   后果不只是格数：田字格的中间十字就是用它画的，线宽 >1 时**十字会戳出外框**。
   已改为**只沿垂直于线的方向加宽**。
2. 改完发现**粗细不一致**：口字型走 `ringCells`（往内画），线宽 3 是实打实 3 格；
   而 L/N/Z 的贴边线居中加宽后外侧被裁掉，只剩 2 格。同一个 width 给出不同粗细，
   用户会以为工具算错。已在 `borderShape` 内加 `edgeLine()`：**贴 box 边的线一律向内侧加宽**，
   中间十字仍居中加宽；末尾再统一把 parts 裁到 box 内（斜线端点在角上时垂直加宽必然溢出一圈）。

连续涂色**一笔只压一次撤销**（拖一条长线应当一次撤回，而不是撤几十次）；
直线与边框都是「拖范围 + 松手才落笔」，拖动期间画半透明预览，避免反复撤销试错。

### 追加轮①：空白画布上直接可画

用户实机试用后提的：「手动涂色/直线/填充/边框等功能需要能在空白画布上直接可操作」。

主干实现要求「先选中一个图层」才能画，于是在一张刚建好的空白画布上，用户必须先手动点
「新建空白图层」才能落笔 —— 这一步纯粹是手续，意图明摆着就是「在这张画布上画」。
另外**画布都还没建时点画布是静默 `return`**，点了毫无反应，用户只能自己猜哪里不对。

改法是新增 `composeEnsureDrawTarget()`：需要画的时候把可画的地方准备好。
关键在于它**不是一律自动建**，而是分三种情况：

| 情况 | 处理 | 为什么 |
| --- | --- | --- |
| 没有任何选中的图层 | **自动建一张画布尺寸的空白「绘制层」**并选中 | 意图明确就是在这张画布上画。建完即选中，所以后续每一笔都落同一层，**不会每画一笔多出一层** |
| 选中的图层被**固定** | 仍然拒绝，提示解固或另起一层 | 用户有意锁了它。自动新建会让他以为画上去了却找不到 |
| 选中了**多个** | 仍然拒绝，提示先单选 | 意图指向若干已有图层，自动新建只会更乱 |

自动建的图层叫「**绘制层**」、手动建的叫「空白图层」，日志措辞也不同 ——
否则用户会奇怪图层列表里怎么凭空多了一层。「铺满整张画布」按钮走的是另一条路径，
也一并改成同一口径。没建画布时改为给出明确提示。

验证：`_验空白画布直接画.js` **59 项 0 失败**，其中一半专门验「自动建不能失控」
（连续 5 笔只建 1 层、换工具仍同一层、固定/多选时不建、move 工具完全不受影响）。

> 这一轮还暴露了两个测试桩没跟上实现：`_验拖拽与图层.js` 与 `_验绘制接线.js` 都缺
> `composeEnsureDrawTarget`，全套回归时直接 `ReferenceError`。前者补了假实现（它只验移动那一路），
> 后者把真函数抽进来（「铺满整张画布」这条路径要验真代码）。
> 另外为避免手拼一长串脚本路径被 shell 转义坑到，加了 `_kiro临时/09.15-拼接需求核查/_全套回归.sh`。

### 追加轮②：修三个实机缺陷（事件收尾 + 画布居中）

用户实机试用后报了 3 条：①边框仍然无法使用 ②手动涂色跟随鼠标、会误触 ③画布没居中。

**①②是同一个 bug。** 事件绑定处只写了

```js
document.addEventListener('mouseup', function () { if (cpS().drag) onComposeMouseUp(); });
```

`cpS().drag` **只是「移动图层」那一种拖拽态**。涂色用的是 `paintDrag`、直线与边框用的是 `shapeDrag`，
而且 canvas 上**根本没挂 mouseup**。后果：

- 直线/边框的 `shapeDrag` 永远收不到收尾 → **永远不落笔**（用户说的「边框无法使用」）；
- 涂色的 `paintDrag` 永远不被清除 → 松手后鼠标一进画布就接着画，看起来就是「跟随鼠标赋色」。

既有目标图那套本来就是 `if (S.edit.dragging || S.edit.paintDragging)`，两种态都判上的 ——
拼接这边漏了。改法：加 `composeDragging()` 统一判断三种态，canvas 与 document 都挂 mouseup，
再补一道 `ev.buttons === 0` 兜底（在浏览器窗口外松手时连 document 都收不到 mouseup）。

**③ 的原因是 CSS 优先级之外的东西**：本文件 CSS 第 120 行有全局 `canvas { display: block }`，
而我给容器写的是 `text-align: center` —— 那对 block 元素不起作用。既有目标图用的是
`.canvasWrap > canvas { margin: 0 auto; }`，且注释里已写明「不用 flex+justify-content:center，
因为图比容器宽时会把左边缘顶到滚不到的地方」。改为沿用同一口径。

**为什么上一轮 771 项回归没抓到①②**：那些测试都是直接调 `api.up()` 这类内部函数，
**绕过了事件绑定这一层** —— 验的是「函数逻辑对不对」，没验「事件到底挂没挂、挂的条件对不对」。
本轮补的 `_验事件收尾与居中.js` 换了验法：在 DOM 桩里真跑 `init()` 拿到**真实注册的监听器**，
再用「按下 → 移动 → 松手」的真实事件序列驱动，并覆盖三种松手情形
（画布内松手 / 拖到画布外松手 / mouseup 完全丢失）。**42 项 0 失败。**

> 过程中还修了 DOM 桩本身的一个缺陷：桩把 `innerHTML` 当普通属性存，而真实 DOM 里给
> `innerHTML` 赋值会清掉全部子节点。于是 `box.innerHTML=''; box.appendChild(...)` 这种写法
> 在桩里会让 children 一轮轮累加，「读列表内容」拿到的是历次渲染的叠加 ——
> 本轮就因此误判了 3 项「移动图层」。已改成 accessor，赋值时清子节点。

## 上一轮改动：区域内同色选取与去毛边 + 纯美术编辑模式（`ANT-ARTTOOL-EDGE-TRIM-20260915`）

用户用上一轮的功能实际抠了 3 张图（`实验关卡/主体图纸库_3张_20260915-110230/`：财神爷 20×20/272 格、
蜗牛 55×55/1166 格、熊猫 55×55/2309 格），然后提了 4 条优化。本轮基于**这 3 张真实产物**做需求核查，
核查结论直接决定了功能形态 —— 而不是照需求字面猜。

### 开工前核查：推翻了两个想当然的方案

| 想当然的做法 | 实测否掉它的数据 |
| --- | --- |
| 「去毛边」= 形态学腐蚀，剥掉主体最外一层 | 外轮廓一层占比：蜗牛 **10.6%**（124/1166）、熊猫 **14.7%**（340/2309）、财神爷 **22.1%**（60/272）。**主体轮廓会跟着被削**，这不是「去毛边」而是「啃主体」 |
| 熊猫那些栅栏/花盆用「只留最大连通块」一键清掉 | 熊猫非 0 像素共 24 块，**最大块 2206 格里就包含了栅栏、花盆、脚下** —— 它们与熊**是连通的**。其余 23 块合计仅 103 格（4.5%），是右上/左上散落的小花。最大连通块**清不掉用户说的栅栏** |

真正的缺口是选区运算上**缺一档**。以熊猫的描边色（色 33 深灰）为例：

| 手段 | 在熊猫图上选中 | 问题 |
| --- | --- | --- |
| 同色块（四连通同色） | 最大 **89** 格 | 太小。深灰共 573 格却碎成 **94 块**（蜗牛更碎：267 格 → **73 块**、最大块仅 24 格），一次够不着整条边缘 |
| **区域内同色（本轮新增）** | **68** 格（左右边缘带 ∩ 深灰） | **正是要的** |
| 按色选（全图同色） | **573** 格 | 太大。会把**主体轮廓的 505 格**一起选中，剔除后主体被毁 |

描边色同时构成边缘杂物和主体轮廓，这才是用户说「shift和alt的加减工具只能加减不同的颜色」的根因 ——
缺的不是修饰键，是「先圈范围、再在范围内取该色」这个运算。

### 实现：把早就写好的 intersect 接出来

`maskCombine` 的 `intersect` 模式在上一轮（任务 AS）就实现了，只是**没接到界面**。本轮：

- **选区叠加方式从 3 种扩到 4 种**，并做成**界面可见的单选**（替换 / 加选 / 减选 / **交集**）。
  没给交集配修饰键：mac 上 `Ctrl+click` 会被系统当右键菜单、`Cmd` 与浏览器快捷键冲突，
  两者都不适合当拖拽期间长按的键。修饰键 Shift/Alt 保留并**优先于界面选择**（临时覆盖，松手即恢复），
  这样老习惯不被破坏。
- **`core.js` 新增 2 个语义化封装**：
  - `maskFromColorInRegion(blocks, color, region)` — 区域内同色，`region` 为 null 时退化为全图。
    做成命名函数而不是让调用处各写一遍 `maskCombine(region, maskFromColor(...), 'intersect')`，
    是为了把「region 为空怎么算」这个边界固定在一处。
  - `maskFromSmallComponents(blocks, maxSize)` — 所有 ≤N 格的非 0 连通块，用来一键清零碎。
    与「只留最大连通块」的分工：后者只留第 1 块（第 2 大块再有用也会被清），这个按**尺寸阈值**判，
    能留下次大的有效部件。熊猫图主体 2206 格、其余 23 块单块最大 37 格，阈值 40 一次清净。
- **「选区内颜色」面板每项加了「只选」按钮**。该面板本来就列出了选区里有哪些色、各多少格，
  点一下就等于「套索范围 ∩ 该色」，不用切工具也不用记叠加方式 —— 这是「区域内同色」最省力的入口。
  条目主体的点击**仍然是**既有的「选区内替换颜色」，靠 `data-pick` 早退 + `stopPropagation` 隔开，
  没有改掉原有用法。

### 一个会静默出错的边界：交集 + 没有选区

`maskCombine(base, add, mode)` 在 `base` 为 null 时直接返回 `add` 的副本。于是「叠加方式=交集」
但当前还没有选区时，点一下「按色选」会**静默变成全图该色** —— 正好是用户想避免的那个结果
（熊猫图 573 格，主体轮廓 505 格会被一起选中，一剔就毁）。

处理方式是在 `applySelection` 里**显式拦截**：说明「交集需要先有一个范围」、指出下一步该干什么、
**选区保持原样不动**。同时给交集补了日志（前后格数）与「交集为空」的明确提示，
避免用户以为工具坏了。按住 Shift/Alt 时不受此拦截影响（那时走的是加选/减选）。

### 需求④：纯美术编辑模式与卡片折叠

### 选区统一成掩码，而不是四种选法各写一套

`js/core.js` 新增「主体提取：选区掩码层」整节（1435 → 1637 行，插在 `cellsInRect` 之后，全部已挂导出表）。
掩码是 `{rows, cols, bits:Uint8Array}`，下标 `r*cols+c`，与既有 `connectedComponents` 同一套口径。

四种选法各自只负责「产出掩码」，后续的加减组合、剔除、统计、描边全部共用一份实现：

| 函数 | 对应界面 | 关键取舍 |
| --- | --- | --- |
| `maskFromRect` | 矩形框选 | 自动归正上下界并裁到画布内 |
| `maskFromPolygon` | 套索 | 射线法取格中心；**轨迹格强制选中**——否则细长条选区因「内部无格中心」会整条丢 |
| `maskFromSameColorRegion` | 同色块 | 四连通同色 flood fill，「磁吸」的实际对应物 |
| `maskFromColor` | 按色选 | 全图同色，不要求相连 |

`maskCombine(base, add, mode)` 支持 `replace/add/subtract/intersect`（对应直接选 / Shift / Alt），
**不改入参**，**尺寸不一致直接抛错**而不是静默算错。

剔除是 `applyExtract(blocks, mask, mode)`：`outside` 只保留选区内（提取主体）、`inside` 挖空选区内（删杂物）；
被剔处写 `0`；**保持原尺寸**；返回 `{blocks, rows, cols, mode, removed, kept, before, after}`，
`removed` 只统计原本 >0 的格。

图纸条目 `toArtPiece(blocks, meta)` → `{type:'artPiece', version, key, rows, cols, blocks, bbox,
pixelCount, colors, colorCount, source:{sourceName, ops, extractedAt}, note}`。
**全空图抛错，不静默入库**。一张 20×20 图纸约 1.2 KB JSON（关卡条目约 54 KB）。

### 为什么保持原尺寸、空处写 0

这两条是拼接能不能成立的前提，不是随手定的：都保持同尺寸、主体留在原坐标，
合并就只是**逐格取非 0**，不需要平移换算。若裁到外接矩形或挪到左上角，拼接时要反算偏移，多一层易错换算。
空处写 `0`（用户第④条决定）让图纸仍是格式正常的 TXT，能被本工具和其他读该格式的地方直接读回。

### 三处「按外接矩形判定」被改成走掩码

`S.edit.selection` 原本是矩形 `{r0,c0,r1,c1}` 且是选区的**权威**。引入不规则选区后，
凡是仍按矩形判定的地方都会**允许在「矩形内但选区外」落笔或替换** —— 这类错误不会报错，只会静默改错像素。
因此把权威改成 `S.edit.mask`，`selection` 语义收窄为「mask 的外接矩形」，仅供既有面板显示尺寸，
并同步改掉四处判定：`paintAllowed`、`performColorReplace` 的 `scope==='selection'` 分支、
`renderSelectionColorsPanel`、`renderCloseCheckPanels`。

### 图纸库与关卡待导出库物理隔离

图纸走**独立** `localStorage` key（`antArtTool_pieceLibrary_v1`，关卡库是 `antArtTool_exportLibrary_v1`）。
理由：`exportLibraryBatch` **无条件**读 `e.originalLevel` / `e.reconstructedLevel`，
图纸条目混进去会让整次批量导出抛错。

即便如此仍给 `exportLibraryBatch` 加了一道**条目类型守卫**：非关卡条目跳过并**如实报出**
（图纸条目会提示改用主体提取里的导出），既不静默丢弃也不让整批失败。
两库已物理隔离，这道守卫针对的是手改 localStorage、旧版残留这类情况——失败模式是「整次导出带一个看不懂的报错全挂」，值得堵。

### 自动选法的实测覆盖面（写进界面，不做过度承诺）

拿 `20x20图纸_44关/` 全量 44 张实测：

- **「选四角同色块」一击能剔 ≥25% 的只有 20/44**；剔不到 5% 的 5 张（`130` 3%、`128` 2%、`125` 1%、`5` 1%、`790` 1%）；
- 边缘形态实际分三类：①单一背景色铺满外圈（`2.txt`：色 14 共 153 格连成 1 块）
  ②背景色被打断成噪点（`108.txt`：色 25 有 168 格却切成 **10 块**，从 (0,0) 只连到 5 格）
  ③无背景密铺纹理（`125.txt`）；
- **「最大连通块 = 主体」在这批素材上不成立**：44 张**每张都是 400 格全非 0**，
  整图四连通只有 **1 块**，按了等于没按。它的实际用处是**收尾**（已剔出空白后清残留），不是入手第一步。

结论：**手动选区（矩形 + 套索）是主力，自动选法只是加速器**。这句话与上面的数字一并写在页面面板上，
比例过低时按钮直接提示「这张图自动选法帮不上」，而不是让人以为点了就好了。

> 这一条推翻了我自己在本任务早期的两次判断（先认为「最大连通块=主体」可行，

## 这个工具解决什么

美术需要知道「玩家玩到 50%–90% 这段进度时，目标图上被消掉的是哪一块」，好在那个位置改色、改图案。
本工具导入关卡后按真实求解路线回放，把你指定进度区间内消除的像素**描边框出来**（只描边，不覆盖原图颜色）。

## 启动

双击 `一键启动.command`。它会在项目根目录起一个本地静态服务并自动打开页面。

也可以直接用浏览器打开 `index.html`，但那样 Web Worker 会被浏览器拦截（`file://` 限制），
求解只能在主线程跑，求解那几秒页面会卡住——功能不受影响，只是不流畅。工具会自动检测并在日志里说明。

## 用法

1. **导入**：两种方式，都按内容自动识别类型、按文件名同名索引配对
   - **选择文件**：一次多选若干文件
   - **选择文件夹**：选一个目录，递归读取全部子目录，整批导入（例：`输出文件/348关工具导入包/`）
   - 识别的三类：
     - `xxx.txt`：目标图像素矩阵（首行「像素矩阵」+ 空格分隔数字）
     - `xxx.json`：正式关卡本体（`{toprow, blocks, maprow, mapcol, spools}`）
     - `xxx.solve.json`：求解数据，**可选**
   - 去掉扩展名后名字相同即视为同一关（`.solve.json` 当成一个整体扩展名）。
     `.txt`/`.json` 以外的文件（`.DS_Store`、csv、md、图片…）自动忽略并计数。
   - 只有 TXT 时可以看图但不能求解；只有关卡文件时目标图取自其 `blocks`；两者都有时会做逐像素一致性校验。
   - 导入完成后显示「共 N 关 / 三件套齐全 / 缺关卡 / 缺求解 / 缺TXT」，列表上方有过滤框（348 关也能快速定位）。
   - 批量导入**只做配对与索引**，不自动求解、不自动跑多路线。
2. **求解路线**
   - 导入了求解数据 → 直接取其中的真实 `pickOrder`，由工具按真机口径重放（不重新求解，秒开）。
   - 没有求解数据 → 点「现场求解」，走正式完整全知入口 `AntSolver.Solver.solve`
     六遍编排 `0 → g2 → tree → tree2 → n1 → n2`，任一遍通关即止。
   - 未通关的关卡不出区间结果（不伪造路线）。
3. **进度区间**：填上下限百分比（或点 50–90 / 50–60 / 10–20 等快捷按钮）→「定位区域」。
4. **多路线复核**（按需，自己点）：最多取 3 条不重复的可通关路线，区分稳定 / 高频 / 浮动区域。
5. **显示**：像素尺寸、按连通块分别描边、淡化区间外像素、格线、标出区间前已消除范围。
6. **导出**：当前视图 PNG、区间定位 JSON（含实际吸附区间、连通块、区域像素下标）。

## 固定口径（不要随手改）

| 项 | 口径 |
| --- | --- |
| 进度 | **已完成盒数 ÷ 总盒数**（与审核评分体系一致） |
| 冰块耐久 | **3**（官方关卡本体不存耐久，`fromGameFormat` 默认还原 2，工具导入后显式改写为 3） |
| 暂存上限 | 5 |
| 区间区域 | 回放到下限存状态 A、到上限存状态 B，取 **B − A**（不保存每步完整目标图副本） |
| 回放口径 | `Simulator.createState(level, { useSlotStart: true })`，与 `Solver.runSolver` 内部一致（solver.js 注明「与手动游玩一致…真机规则」） |
| 数据定性 | 「基于正式关卡 JSON 重新求解的标准复核路线」，**不声称**还原生产时未保存的原始路线 |

### 进度吸附

盒进度是离散的，不一定存在正好 50% / 90% 的时刻。工具把你输入的上下限吸附到**最近的实际可达盒进度**，
并同时显示「用户要求区间 / 实际采用区间 / 对应完成盒数 / 对应步序号」。

等距并列时（例：51 盒关卡要 50%，25/51=49.02% 与 26/51=50.98% 距离完全相同）规则固定为：
**下限取更低的进度（同进度取最早那步），上限取更高的进度（同进度取最晚那步）**。

### 与阶段2 求解包数据的已知口径差异

`临时求解包-348关/输出/求解数据/*.solve.json` 里的 `replay.steps` 与 `defaultInterval` 是**旧回放口径**产出的
（建状态时漏传 `useSlotStart`），逐步消除像素与逐步完成盒数都与真机口径不同（总像素、总步数、pickOrder 不受影响）。
因此本工具**不采信**这些文件里的 `replay.steps`，只取其 `pickOrder` 自己重放。
只有在「导入了求解数据但没导入关卡文件」时才不得不退用旧口径逐步数据，此时界面会明确提示。

左右两栏 + 中间主区：左栏是输入类功能（1.导入 / 2.求解路线 / 3.进度区间 / 4.多路线复核），

DOM 顺序是「左栏 → 主区 → 右栏」，与视觉顺序一致，
未用 CSS `order` 做视觉交换（会导致 Tab 键盘导航顺序与视觉顺序不一致）。三栏各自独立纵向滚动，减少单栏内容堆叠过长。

**可悬浮面板**：「编辑改动统计」「5. 显示与导出」「8. 美术编辑」右上角都有「悬浮」按钮，点一下脱离原位变浮层，
拖标题栏移动、拖右边缘/下边缘/右下角放大缩小，再点「收回原位」放回去；位置与尺寸都会记住。
浮层只改自己的定位与尺寸，不影响目标图的绘制与像素坐标换算。
配色改为暖色调（暖棕背景 + 橙色强调色），语义色（成功/警告/失败）保留原有绿/黄/红但换成暖色系色阶。
棋盘区不要求先「定位区域」——只要有一条求解路线（现场求解或导入求解数据）就会显示：
未定位区间时显示开局/末局，定位区间后自动切换成状态A/B对比。

`captureBoard` 选项），不需要为展示单独重放。

多路线复核产生的路线不带棋盘快照（那些只用于区域稳定性统计），勾选后若当前路线没有快照，界面会提示改用标准路线。

## 重构关卡（2026-07-31 起：只有一种方式「完全重新生成」）

「10. 重构关卡」用美术改好的目标图（或导入时原样的目标图）重新构造出守恒、结构合法、全知可解的新关卡。
**页面上只有一个按钮「重新生成关卡」，没有策略选项。**

### 为什么只剩一种

2026-07-30 之前这里有三种可选策略：①保障碍布局换色重配、②完全重新生成、③保结构重切盒。
按需求 `codex助理/codex需求文档/07.31-需求文档/07.31-关卡重构单策略与方案参数纠正.md` §三，
用户决定**只保留②，删除①③**：①③依赖「完全保留原骨架」，而这批 55×55 关卡的骨架容量普遍只有 45~55 格，
新目标图像素略多、或原棋盘没有管道时就装不下，且失败时不允许裁行（裁行会让已规划的冰/问号/锁链坐标失效），
实测 9 次尝试全部失败。①③的实现（`reconstructKeepObstacles` / `reconstructKeepStructureResplit`）
已从 `core.js` 删除，页面上的三个策略单选也已删除。正式 `bin/js/generator.js` 的公开能力没有因此减少。

### 唯一策略的实现口径

- 走 `core.js` 的 `reconstructFullRegenerate(newBlocks, config)`，内部调用正式生产**公开总入口**
  `AntSolver.Generator.produce()`（不是内部的 `produceFixed`），与生成器网页端的正常生产入口完全一致，
  因此结果会带出 `entryMode`（v95 起 `produce` 会分发到纠偏版）与 `flow` 回退信息，一并显示在页面上。
- **不复制任何生成算法**，只调用正式导出函数。
- 失败时原样展示 `reason` / `detail`，不伪造成功、不静默换策略。

### 生效参数以方案文件的 config 为准

- 「6. 导入生成器参数」支持两类文件：生成器网页端导出的方案 JSON、批量生产的 `批次配置.json`。
- 网页方案 JSON 里同时有 `config` 和 `inputs`：**正式生效参数一律取 `config`**，`inputs` 只是页面历史输入状态，
  不参与生成。两者取值不同的字段会在「关键参数确认」区以「字段冲突」标出，导出包的
  `生效的生成器参数.json` 与报告里也会逐条列出。
- 未识别字段不静默丢弃，如实列在页面与导出包里。
- **唯一例外**：暂存上限是玩法固定口径（5），方案给了不同值也不采用，页面会以「被工具强制覆盖」提示。
- 点重构前，「关键参数确认」区会用中文列出这次真正会生效的参数（参数来源、底部消除、盒容量、暂存上限、
  黑块 / 冰块 / 锁链 / 问号、棋盘范围、窄路缺口），未导入方案时显示工具默认值并注明来源。

### 棋盘尺寸适配（修掉「超额补黑块」）

旧行为是先随机挑棋盘尺寸再补黑块填满，盒子少而棋盘大时会补出远超 `blackPercent` 的黑块。
现在 `bin/js/generator.js` 的 `chooseBoardDimsFixed` 改为按盒数分档挑选：优先「盒 + 预留管道空间」刚好装得下的
尺寸（`pipeRoom = max(3, 盒数×25%)`，避免把所有盒都塞进管道撞上管道容量上限），装不下才放宽，
并要求形态「列 > 行 且 列 - 行 ∈ {1,2}」；确实无合法形态时退回原随机行为并置 `shapeRelaxed` 标记如实上报。

### 障碍参数核对与浮动容差（2026-07-31 整改后）

Codex 审查（`2026.07.31-03-Codex审查结果.md` 的 P1-3）指出：原来页面用「实际 > 目标 + 5 个百分点」判黑块超标，
这个 +5 是 Kiro 自定的、没批准过、而且容差本身不显示给用户看。用户裁决是
**「批准可以加浮动兜底，包括其他障碍参数也可以浮动 5%」**，所以整改方向不是删掉容差，而是把它正式化：

- `core.js` 新增 `obstacleCheckOf(level, cfg, slots)`，逐项算 **目标 / 实际 / 偏差 / 是否在容差内**，
  四项为黑块、冰块、问号、锁链；容差常量 `OBSTACLE_TOLERANCE_PP = 5`、`CHAIN_TOLERANCE_GROUPS = 1`
  与说明文字 `OBSTACLE_TOLERANCE_NOTE` 一起导出，页面、单关报告、批量报告三处同源同口径。
- **分母与正式生成器逐一对齐**（定向核实 `bin/js/generator.js`）：
  黑块 `floor(棋盘容量 × blackPercent/100)` → 分母 = 棋盘容量；
  冰块 `floor(棋盘盒格数 × icePercent/100)`、问号同理 → 分母 = 棋盘上 `t==='box'` 的格数；
  锁链 `totalChains = chainCount` → 按组数比，不是比例。管道队列里的盒只有 `{color,count}`，
  不带 `ice/chain/q`，故不计入冰块/问号分母。
- **窄路额外障碍单独算**：开启窄路后，每个缺口会额外加一组锁链（`generator.js` 里 `var ng = 90`，组号 90 起）
  和一个 `src='narrowGap'` 的冰块，**不占 `chainCount` / `icePercent` 配额**。
  把它们并进配额一起数会得出「chainCount=3 却有 5 组锁链」这种假超标——这正是本轮回归第一次跑出来的现象。
  现在锁链按组号 90 分界拆开，冰块按 `obstacleSlots.ice` 的 `src` 拆开，窄路那部分只报数、不参与判定。
- **拿不到数据就不判定**：冰块来源明细只在 `generateFromBlocksFixed` 的返回值里，
  走卡点变体分支产出的关卡不带 `obstacleSlots`。这时该项标 `judged: false` 并写明原因，
  **既不算通过也不算超标**，避免误报。这是取舍：实测 3 关里冰块常常落在未判定状态，
  要让它稳定可判需要在 `generator.js` 里把 `obstacleSlots` 透传过卡点变体分支——
  属于本轮批准范围外的改动，**未做**，已提请用户决定。
