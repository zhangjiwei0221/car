一句话结论

  • A · 按日程切（生产默认）：总债 0px、峰值 0 辆。 盒子大小永远等于它能吃到的量——切球本身一点压力都不产生，紧张感全部来自后面的摆位和障碍。
  • B1 · 按层切 + 碎车合并：总债 94px、峰值 4 辆、最长解锁延迟 10 步、 碎车 0 辆（合并前 22 辆）。这些债是"排坏了"排出来的，不是设计出来的。
  • C · 动态排序（干净基线）：切法与 B1 完全相同，只改服务顺序——总债 2px、峰值 1 辆、最长解锁延迟 2 步。 债从 94px 降到 2px。
  • D · 动态排序 + 债务节拍：在 C 的干净基线上，15%/60%/80% 各把一辆"颜色还没露脸"的车提前（3 笔）—— 总债 21px、峰值 1 辆、最长解锁延迟 5 步。 没有超上限。
  • 这条链怎么读：A 是"顺其自然"（零债，压力全在后端）；B1 是"按结构切但排得糙"（债是事故）； C 是"切法不变、把顺序理顺"（债归零，这是设计压力的必要前提）；D 才是"把债故意做进去"。 没有 C，就分不清哪些债是该有的、哪些是排错的。

六、术语对照（"矿脉"到底叫什么）

我们口语里的更专业的说法定义
矿脉同色连通域 / 色块（same-color connected component）4-连通、颜色相同的最大像素集合；与怎么走、怎么切无关
层依赖深度 / 剥离层（peeling depth）色块邻接图上，从"外部可达"出发的 BFS 层号
包壳关系区域邻接图（region adjacency graph）两个色块 4-邻接，就连一条边
序号贪心消除日程（greedy elimination schedule）某一条走法下的像素次序，换走法就变
债务 Δ解锁延迟（unlock latency）实际轮到它的位置 − 理论最短位置
车 / 盒请求（demand：颜色 + 容量）一辆车 = "我要 N 个 c 色像素"
取盒序服务顺序（service sequence）这些请求被满足的先后
"矿脉"是我起的比喻，容易让人以为图里真有"脉"。它的实体就是同色连通块——以后报告里我用"色块 / 依赖层 / 解锁延迟"。

七、这份报告不能告诉你什么

  • 看不到棋盘：车摆在哪个格子、哪一格先解锁，会决定"这辆车此刻能不能点"。61 那种死法（暂存里 4 个颜色全被埋）是切法 + 摆位一起造成的。
  • 看不到障碍：冰/链/管道/墙都会改"菜单什么时候出现哪辆车"，这里一概没有。
  • 看不到真人：干跑用"圈序"（动态外圈→由下到上→由左到右）这一条固定规则；真人会挑。
  • 所以它只回答一个问题：这个切法本身，会把债务做成什么样。棋盘与障碍是下一层的事。
