# 难度关系量化（只读工具）

> 回答一个问题：**「目标区需求」和「棋盘区供给」的关系，能不能量出来？**
> 能。量出来的不是「每辆车的路径长度」，而是三个可直接设计的数：
> **每步可点几辆 / 每步有几辆能一次吃满 / 吃满≤1 的步占多少**。

## 用法

```bash
# 单关全报告
node 关系量化.js <关卡.json 或 目标图.txt>

# 批量出一行 CSV（不打印明细）
node 关系量化.js *.json --csv

# 摆位实验：同一副车局部打乱 / 整体随机重排 / 整体平移
node 关系量化.js 关卡.json --window 2,4,6,8 --permute 20 --sweep 10
```

输出解释：

| 字段 | 含义 |
| --- | --- |
| 目标出现日程 | 每个颜色第一次「够一辆车吃」时的进度%（纯目标图，与棋盘无关） |
| 供给深度 | 一辆车至少要先拿掉几辆才轮到它露头（0-1 BFS：空位=0、车=1、黑块/管道=墙） |
| 扇出 unlocks | 拿掉这辆，会让几辆车从不可点变可点 |
| 耦合·差 | 车的供给深度 − 它的颜色层。负=车来得比颜色早，要背债 |
| 债务曲线 | 贪心玩家每一步之后的暂存占用（半满车的数量） |
| **每步能吃满** | 当前可点的车里，颜色暴露量 ≥ 车容量的有几辆 ← **这是压力的主指标** |
| 审核口径峰窗 | 用生产同一套 `Analysis.chokepointAudit` 算的卡点区峰窗 |

## 实测（40x40 / 35x35，样本见 `样本_关系量化.csv`）

| 档 | 每步可点 | **每步能吃满** | 吃满≤1 的步 | 卡点区峰窗 |
| --- | ---: | ---: | ---: | ---: |
| 合格（有卡点） | 3.1~5.7 | **0.9~1.7** | 44~81% | 3.5~4.0 |
| 简单·趋势过平 | 6.7 | **1.93** | 46% | 3.0 |
| 不合格（太松） | 7.7~8.4 | **2.7~7.1** | 2~21% | 0~2.0 |

**规律**：每步能吃满 ≈ **1 辆** 时，玩家几乎每步只有一个正确选择 → 有压力；
≈ 2 辆以上 → 总能找到能装的 → 趋势过平；= 0 → 被迫背债 → 峰窗冲到 5。

## 摆位到底有多大的用（实测结论）

同一副车、只改摆放：

| 实验 | 结果 |
| --- | --- |
| 在暴露序上局部打乱 ±2 / ±4 / ±6 / ±8 位 | **峰窗完全不动**（109 恒 4 / 156 恒 3），可解 6/6 |
| 整体环形平移 0~10 位 | **峰窗完全不动**（因为只切断了首尾一对相邻关系） |
| 完全随机重排 | 109 只有 **3/20 可解**，其余全部解不出来 |

→ **摆位是「约束」，不是「旋钮」**：粗粒度颜色序不能乱（乱了直接死关），
但把颜色序排对之后，微调格子位置对压力几乎没有影响。
真正决定压力的是：**车的清单（颜色块怎么切、每辆容量多大）** ＋ **棋盘尺度（前沿宽度）**。

## 已知边界

- 债务曲线用「贪心玩家」近似，比真机稳健玩家略激进；压力下限看 `[压力·全知]` 那条。
- 管道/问号/数字冰只按引擎现成规则走，没有单独建模。
- 供给深度只算静态可达（不考虑锁链/数字冰的阶段性锁），极少数带链的关卡会偏乐观。

## 一句话结论

**压力 = 每步能吃满几辆。** 想加压就让它靠近 1，想放松就让它到 2 以上；
（注意：这是方向性信号，不是充分判据 —— v238 新产出的合格关只有 23~43%，大盘同样能压到峰窗 4。）
把车摆在哪里影响很小（±8 位内峰窗不动），真正动压力的是**车的容量与颜色清单**和**棋盘前沿宽度**。
