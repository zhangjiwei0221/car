## 0. 一句话定义

正式版不是“不断换 seed，直到撞出高压关卡的难关搜索器”，而是一个
**故事驱动的关卡编译器**：

> 从目标图提炼可解锁区域与容量合同，先定义玩家应经历的债务、选择与释放，
> 再把这段体验编译成车辆依赖、棋盘结构、障碍语义和可回放证据，
> 最终直接输出无需人工修改即可使用的关卡。

核心变化：

```text
旧：生成候选 → 求解 → 看压力像不像好关 → 换 seed 继续撞

新：定义体验剧本 → 构造车辆/棋盘/障碍 → 验证玩家确实会经历这段剧本
```

求解器从“发现关卡的发动机”降级为“验证与找旁路的质检器”。  
压力曲线从“生成目标”降级为“预期体验是否按计划发生后的温度计”。

## 1. 为什么必须换代

当前工程已经证明了不少底层能力：容量守恒、可解、路线回放、PlayerSim、
目标落库和多图 UI 都能工作。但这些能力组合起来，仍然是候选筛选逻辑，
没有真正控制关卡如何讲故事。

### 1.1 当前模式的根本问题

1. **成功依赖搜索命中**：同一图、同一配置换 seed 就可能从通过变成失败。
2. **压力指标倒置因果**：先要求 buffer 升高，再猜是什么障碍造成的，
   而不是先决定玩家为何愿意承担债务。
3. **障碍缺少语义**：冰、链、管道经常是在结果不达标后追加的修正量，
   而不是某个具体体验节点的表达方式。
4. **球序没有真正翻译成棋盘语言**：车单可以计划，但玩家最终看到什么、
   为什么愿意选某辆车、下一步从哪里释放，都没有被显式控制。
5. **验收对象漂移**：开发结果在 00199/00028，正式目标仍引用 006/008/014，
   局部命中不能自然积累成总 Goal 的完成度。
6. **压力不等于正反馈**：玩家可能只是被卡住，并没有理解自己为什么卡住、
   也没有看到值得追求的解救机会。
7. **不能直接交付**：即使机器指标通过，仍可能需要人工调棋盘、障碍或容量。

### 1.2 已确认终止的方向

- **混合容量填盘实验终止投入**。它一次同时改写目标车数、棋盘、黑块、管道、
  容量和修复开关，既刻意又无法归因，不进入正式版主线。
- 不再以增加冰/链数量作为主要质量修复手段。
- 不再以“换更多 seed、拉长搜索时间”作为首选转化方式。
- 不再把“中段 buffer 3/4 达标”单独视为关卡设计成功。

## 2. 正式版产品定义

### 2.1 输入

至少包含：

- 一张目标像素图；
- 用户给定的容量硬区间 `boxSizeMin/Max`、`capNormMin/Max`；
- 棋盘尺寸策略；
- 黑块、管道与障碍策略；
- 期望体验强度或剧本偏好；
- 可接受的生成预算。

### 2.2 输出

每次输出必须同时包含：

1. 可直接导入客户端的关卡 JSON；
2. 一条明确的目标体验剧本；
3. 计划路线及真实回放；
4. 每个债务、选择、释放节点的证据；
5. 每个障碍的角色、目标节点与移除消融结果；
6. 容量、逐色守恒、棋盘和可解审计；
7. 旁路检查、可恢复性检查和失败原因分类。

### 2.3 成功定义

“生成成功”不等于找到一条可解路线。正式版成功至少包括：

- **硬合同成功**：守恒、容量、棋盘、可解、规则一致；
- **剧本成功**：预期债务、选择、解救和收尾在计划位置真实发生；
- **公平成功**：玩家有理由选择预期动作，失误后有机会理解和恢复；
- **自由度成功**：玩家不是只能照抄唯一路线，但也不能完全绕过核心思考；
- **交付成功**：批量输出无需人工修改即可使用；
- **泛化成功**：多图、多 seed、不同容量合同中都能稳定工作。

## 3. 设计原则

### 3.1 先写体验，再生成关卡

每一关先生成一份“体验剧本”，再生成具体棋盘。剧本至少回答：

- 玩家开局应先学会什么？
- 哪一步会出现第一笔债务？
- 玩家为什么愿意承担这笔债务？
- 哪个动作会释放它？
- 债务到释放之间允许等待多久？
- 第二笔债务如何变化，而不是重复同一动作？
- 最后一笔压力如何收束？

### 3.2 求解器只验证，不主导设计

求解器负责：

- 回放计划路线；
- 检查原计划是否仍然可解；
- 寻找可能绕过剧本的旁路；
- 检查玩家犯错后是否有恢复路线；
- 给出 `unknown / budget_exhausted / no_route / route_found` 的准确分类。

求解器不负责：

- 用任意高压路线替代计划路线；
- 靠扩大搜索掩盖结构错误；
- 用“找到一条路线”证明体验符合设计。

### 3.3 压力是剧情的验收结果，也是卡点目标

正式版首先控制事件：

```text
愿意承担的债务 → 可理解的等待 → 可发现的释放 → 状态改善的正反馈
```

然后才测量：

- buffer 何时升高；
- 3/4 占比多少；
- 峰值多大；
- 显著释放幅度多少。

压力指标用于判断剧本是否真实发生，而不是反过来驱动障碍堆叠。

这里要区分两件事：

- 不能把“整图中段3/4占比”当成随机搜索目标，用障碍和seed硬撞；
- 计划中的卡点必须明确要求暂存达到3或4，否则所谓故事只是路线正确，
  并没有形成真正需要玩家思考的压力。

因此压力按“窗口”验收，而不是只看全局平均：

- 每个计划卡点记录哪些车占用暂存、为什么无法立即完成；
- 卡点至少让暂存达到3或4，且其中至少一项是未完成债务或锁链承诺；
- 玩家必须面对可解释的取舍，不能只因唯一动作被强迫；
- 释放必须来自目标区域中的真实动作，并让压力明显下降；
- 全局`midBuffer34Pct`继续作为报告指标，但不能替代逐窗口状态证据。

### 3.4 棋盘负责讲故事

目标图不是“颜色像素总量”，而是有空间关系的区域图。  
棋盘不是“把车塞进格子里”，而是把计划中的取车顺序翻译成：

- 什么区域先暴露；
- 哪辆车先可点；
- 什么车被什么挡住；
- 哪个动作会打开下一段；
- 债务形成后，玩家从哪个方向看到解救机会。

### 3.5 引导，但不把玩家绑在轨道上

正式版追求“有预期的多条合理路线”，不是唯一解。

- 允许 2～4 条符合设计思想的路线；
- 这些路线可以动作不同，但都应经过核心决策；
- 不允许一条更简单路线完全绕过债务与释放；
- 不靠未提示的隐藏信息逼玩家失败；
- 不把玩家第一次合理尝试直接做成不可恢复死局。

## 4. 体验剧本模型

### 4.1 五个基础节拍

每关不强制固定五段，但正式版第一版建议使用以下五类节拍：

| 节拍 | 目的 | 必须被控制的行为 | 可观察结果 |
|---|---|---|---|
| 教学 `teach` | 建立规则与操作信心 | 玩家完成少量清晰动作 | 低债务、连续正反馈 |
| 债务 `debt` | 让玩家主动承担第一笔等待 | 选择一辆当前只完成一部分的车 | buffer 上升、目标区域部分打开 |
| 释放 `release` | 让等待转化为可理解的进展 | 选择对应区域/关键车完成债务 | buffer 明显下降、下一区打开 |
| 变奏 `variation` | 用不同空间或障碍重复核心思维 | 第二次做选择，而非重复首个动作 | 新的债务方向或新的释放方式 |
| 收尾 `finale` | 用已学规则完成最后压力 | 结合前两类决策完成最后一组 | 压力收束、没有末段神秘锁死 |

进度区间只作为初始建议，最终值必须由样板与真人反馈校准：

- 教学：约 0%～15%；
- 第一债务：约 15%～35%；
- 第一释放：债务后 1～3 步内；
- 变奏：约 45%～75%；
- 收尾：约 75%～100%。

### 4.2 每笔债务必须回答的问题

```text
为什么现在选它？
为什么它暂时完成不了？
玩家如何看出这是暂时债务？
哪块目标区域或哪辆车可以释放它？
释放机会何时、以什么空间形式出现？
如果玩家不选它，有什么合理但次优的结果？
```

任何无法回答这些问题的“卡点”都只是阻塞，不是体验设计。

### 4.3 “心甘情愿”的四个条件

1. **收益可见**：预期债务车当前能消掉有吸引力的一部分目标。
2. **代价可见**：车容量、剩余需求和暂存占用都能被玩家推断。
3. **希望可见**：债务后 1～3 步内存在可识别的释放方向。
4. **选择可解释**：玩家有其他动作，但预期动作在打开局面或当前收益上更合理。

正式版应避免：

- 选之前完全看不出会欠；
- 欠下以后完全看不出怎么救；
- 只有背板才知道正确动作；
- 合理路线第一步就无解；
- 预期动作是明显亏本、靠强迫玩家踩坑制造“难度”。

### 4.4 故事原子与“强制”的合法性

五节拍只是整体节奏，不是每一关的唯一实现方式。正式版允许以下故事原子
单独出现或组合出现：

| 故事原子 | 体验含义 | 允许的实现 |
|---|---|---|
| `voluntaryDebt` | 玩家看到收益，主动接受暂时收不满 | 当前只能消掉部分目标的债务车 |
| `groupDebt` | 一个锁链组中有已完成车和未完成车，整组共同等待 | 2 连或 3 连锁链组；两辆立即收满、一辆留下债务 |
| `reservedDebt` | 先把当前不需要的颜色锁起来，后续回来偿还 | 一组或多组有明确后续需求的锁链组 |
| `forcedGate` | 棋盘通路被挡住，玩家必须先处理指定车 | 深层车、结构性阻挡、可达性门 |
| `hollowEntry` | 从目标图边缘缺口进入，逐层剥离并打开内部主题 | 边界区域 → 内部区域 → 更深主题区 |
| `delayedGate` | 关键车在计划时刻前不可取 | 数字冰、管道或时空组合 |
| `reveal` | 清掉外围后才看到关键区域 | 被包住的小区域、同色单像素高光 |
| `choice` | 两条路线都能推进，但代价和收益不同 | 多色入口、多个锁链组、两个可解区域 |
| `repair` | 后续动作释放先前债务 | 新区域补齐旧车需求 |
| `finale` | 用已学规则完成最后一段 | 组合此前的故事原子 |

因此，正式版不要求每一关都有自由选择，也不要求每个动作都能不承担代价。
强制门、预留债务和单点揭示只要**可见、可解释、可恢复**，都是合法故事。

反过来，任何障碍是否需要，不取决于“冰/链用得多不多”，而取决于它是否承担了
上表中的某个角色，以及移除它后对应体验是否发生明显变化。

## 5. 用棋盘讲故事

### 5.1 从目标图生成需求区域图

目标图先编译为 `DemandGraph`：

- 颜色总量与容量可行性；
- 每色可消除区域；
- 区域之间的暴露/解锁关系；
- 当前可见需求的颜色与数量；
- 某些动作会打开哪些新区域；
- 哪些小区域可能是关键解锁点。

同一颜色可能被切成多个区域节点，不再只保留一个总像素数。

### 5.1.1 机制分析以 TXT 为准，图像只作人类审阅层

从生成合法性来看，TXT 像素矩阵已经足够，因为它包含：

- 行数、列数和每个位置的色号；
- 目标区域形状；
- 颜色连通关系；
- 可消除的依赖关系；
- 0 背景和特殊色区域。

原图或渲染图用于人类识别“高光、轮廓、人物部位”等视觉语义，不应参与容量计算。
如果要把某个区域标成“眼睛高光”或“主题区域”，应作为可选语义标注，
不能改变同色容量守恒和消除规则。

### 5.1.2 单像素与高光

目标图中的单像素可以直接成为故事节点，但必须区分：

- 它与大区域同色：作为空间上的 `reveal` 或最后收尾像素；
- 它是独立颜色：需要容量合同允许 1 像素微车，否则不能强行生成；
- 它从开局就可见：通常不构成揭示；
- 它被主题区域包围、外围清掉后才可达：可以作为有意义的延迟揭晓。

### 5.2 选择棋盘的方向趋势

目标图的区域关系应选一个可解释的总体趋势，例如：

- 从上往下；
- 从下往上；
- 从外向内；
- 从一侧向另一侧；
- 围绕中心逐层展开；
- 按目标图形自身的轮廓分段。

趋势不是强制的一条线，而是让玩家感觉“局面正在朝某个方向展开”。
每次选择都应产生局部进展，并打开下一步的可见目标。

### 5.3 行程规划

为剧本选择一条或多条区域主线：

```text
区域 A → 债务 A → 解锁区域 B → 完成 B → 回补 A → 进入区域 C
```

行程规划负责：

- 选择关键区域；
- 安排区域暴露顺序；
- 控制每一步玩家可见的颜色；
- 避免剧情尚未发生就暴露全部答案；
- 让重要债务和释放点有连续的空间解释。

### 5.4 把球序翻译成车辆依赖

计划取车顺序 `A1 → B1 → A2` 必须落成棋盘约束：

- `A1` 在对应节拍开始时可见；
- `A1` 的容量大于当时可见 A 区需求，形成预期债务；
- `B1` 在 `A1` 完成后可见，或只需再解一层；
- `B1` 消除后打开新的 A 区；
- `A2` 打开后能够完成先前债务；
- 其他车不能提前同时打开大量 A 区，使债务在选中前消失。

这张依赖关系是一张有向图，棋盘必须满足：

- 节点可取得顺序；
- 解锁边；
- 可见性边；
- 禁止提前打通的旁路约束；
- 预期释放的最晚出现时间。

### 5.5 曼哈顿距离必须进入计划

瞬时连锁模式下，实际消除不是“取 A 色车就消除规划中的 A 区域”。车进入暂存槽后，
槽位映射到目标图底边起点；当前可达同色像素按与起点的曼哈顿距离排序，
并按快照批次结算。

因此计划单位不能是：

```text
A 色 → B 色 → A 色
```

而必须是：

```text
A 车(cap=40, slot=0, start=底边第0列)
→ 消掉 A 的右下区域 A2 的 16 像素
→ A2 留下 24 债务
→ 打开 B1
→ B 车(cap=30, slot=1, start=底边第1列)
→ 消掉 B1
→ B1 暴露 A 的右上区域 A3
→ A2 被释放
```

每个计划步骤至少记录：

- 车色与容量；
- 进入的槽位；
- 槽位映射的起点；
- 实际消除的像素 trace；
- 命中的目标区域 ID；
- 消除后新暴露的区域；
- buffer 变化和还需偿还的债务。

曼哈顿距离不是噪声，而是棋盘叙事的一部分。同一颜色的不同区域必须视为不同的
故事节点，不能只存“颜色总像素”。

### 5.6 棋盘编译器

`BoardCompiler` 不直接“随机摆车”，而是求解一组约束：

**必须满足**

- 车辆容量与逐色守恒；
- 关键车在正确时间可取得；
- 关键目标区域在正确时间可见；
- 预期债务在选中前没有被其他动作提前抵消；
- 预期释放区域在允许窗口内出现；
- 不存在直接绕过核心债务的低成本旁路；
- 不使用未知信息制造无提示死局。

**尽量满足**

- 首行/首层有可理解的颜色方向；
- 开局面板有 2～3 个合理选择，而不是十辆白给车；
- 车辆位置与目标区域方向一致；
- 后续车层有可读的递进关系；
- 黑块、管道和其他障碍形成结构，而不是补洞。

### 5.7 双图联合规划

正式版不能先独立摆好棋盘，再用求解器看目标图是否碰巧可玩。目标图和棋盘必须联合规划：

1. **目标像素图**决定当前颜色需求、区域可达性和动作后的暴露；
2. **棋盘车辆图**决定哪些车当前可取、以什么顺序打开、进入哪个槽位；
3. **暂存状态**决定后续车辆起点和可同时容纳的锁链组；
4. **障碍状态**修改可用时机和通路；
5. **求解器**只验证计划状态转移并寻找旁路。

一次完整规划状态至少包含：

```text
targetState:
  eliminated[r][c]
  reachable[color][region]
  remaining[color]

boardState:
  cells
  activated[r][c]
  iceCounters
  chainGroups
  pipeQueues

bufferState:
  items[color, capacity, progress, remaining, slot, start, link]

storyState:
  currentBeat
  plannedDebt
  plannedRelease
  elapsedSteps
```

车辆依赖的一部分来自棋盘激活图，像素依赖的一部分来自目标区域暴露图；
两者通过“取这辆车会在目标图上消掉哪些像素”的边连接起来。

### 5.8 联合约束公式

把第 `k` 个计划动作记为 `a_k`，至少包含车辆、容量、槽位、锁链组和预期目标区域。
令 `E_k` 为执行后的目标像素消除状态，`B_k` 为棋盘车辆/激活状态，
`T_k` 为真实消除的像素 trace。

目标侧：

```text
T_k = InstantChainConsume(E_{k-1}, a_k.color, a_k.capacity, start(a_k.slot))
E_k = E_{k-1} ∪ T_k
debt_k = a_k.capacity - |T_k|
```

其中 `T_k` 不能由规划器任意指定，必须来自当前 `Simulator` 的真实消除结果。

棋盘侧：

```text
a_k.car ∈ pickable(B_{k-1})
if a_k is a chain group:
    all group members are pickable
    freeSlots(B_{k-1}) >= groupSize
B_k = activate(remove(B_{k-1}, a_k), a_k)
```

剧情侧：

```text
regions(T_k) ∩ expectedRegions(a_k) != ∅
debt_k ∈ allowedDebtRange(a_k.beat)
if a_k creates debt:
    ∃ j ∈ [k+1, k+maxReleaseDelay]:
        newReachable(E_j, a_k.color) >= remainingDebt_k
```

旁路侧：

```text
所有未被计划允许的提前动作，要么不可取，
要么不能同时满足“高收益 + 提前解锁关键目标 + 低 buffer 代价”。
```

锁链组侧：

```text
groupEnter = all members enter together
groupRelease = all members.progress == member.need
```

因此计划验证不能只看“最后可通关”，必须逐动作核对这些状态转移。
任何一条不匹配，都要记录是目标区域漂移、棋盘阻挡错误、槽位变化、
锁链组溢出还是障碍没有承担语义。

### 5.9 切球、车数与棋盘尺寸的联合可行性

容量、车数和棋盘不能各算各的。对每种颜色 `c`，总像素为 `N_c`，
用户容量区间为 `[Cmin, Cmax]`：

```text
该色最少车数 = ceil(N_c / Cmax)
该色最多车数 = floor(N_c / Cmin)
```

如果某色的最少车数大于最多车数，说明这组容量区间无法把该色精确拆完。
这不是生成器可以自行缩放容量的理由，必须报告为容量冲突，或者由用户明确调整输入。

总车数也不是 `总像素 / 平均容量`，而应来自每色区间的联合分配：

```text
totalCarsMin = Σ ceil(N_c / Cmax)
totalCarsMax = Σ floor(N_c / Cmin)
```

棋盘 `R × C` 的可用车位数还要扣除黑块、管道占格和其他永久阻挡：

```text
boardCarSlots = R × C - blackCells - pipeCells
```

若还有管道 queue 藏车，则必须把显式 queue 容量计入总车数和供给时序，
不能把管道当作免费的补空格。

#### 裁决规则

当目标车数与棋盘格数冲突时，只允许有以下明确方案：

1. 调整容量区间；
2. 调整棋盘尺寸；
3. 允许少量结构性黑块；
4. 使用有剧情作用的管道；
5. 判定当前目标图不适合该棋盘/容量组合。

禁止静默采用“目标车数 = 棋盘格数”来反推并改变用户容量下限。

#### 棋盘大小的实际情况

“行列优先 7 以上”是尺寸偏好，不是硬门；用户已明确不强制行列必须为 7 以上。
更不应把它理解成“棋盘越大越好”。

- 车太少时，大棋盘只能靠黑块或管道填空，反而破坏体验；
- 车太多时，小棋盘放不下，必须扩盘或使用管道；
- 只有在故事需要的层数、车位和可见选择都存在时，扩盘才有价值。

因此流程应是：

```text
用户容量区间
→ 每色可拆车数区间
→ 目标图中的故事车辆角色
→ 所需车位/槽位/障碍
→ 在满足最小边≥6的合规棋盘中选择最合适的尺寸；7以上仅优先
```

如果目标图在当前容量下只能产生约 37 辆车，而 7×7 有 49 个车位，
就不能宣称“7×7 + 0黑 + 0管道”是天然可行的；必须显式选择：

- 接受约 11～12 个结构性空格/障碍；
- 由用户明确放宽容量下限以增加车数；
- 允许 7×7 以下的回退盘；
- 或判定这个组合不适配。

#### 实验图 006 的初步结果

`实验关/关卡6/35x35拼接图纸_006.txt`：

- 35×35，1225 个彩色像素，13 色；
- 同色连通块 234 个，最长依赖层 6；
- 开局暴露 3 色：31 号 76px、5 号 30px、30 号 30px；
- 深层色只有 4 号色（约 5% 像素，3 层）；
- 现有自动预检给出容量带约 `[31,40]`、选择值 36，但 `exactFeasible=false`，
  4/13/14/33/34 等颜色无法在该带内精确拆分；
- 用当前 `InstantPlayout` 按 `[31,40]` 实际做一次近似容量规划得到 37 辆车，
  其中只有 8 色精确、5 色无法精确、6 辆车低于下限；这不是可用于“7×7 满盘零黑”的干净方案；
- 因此这张图不能直接在“31～40 + 7×7 满盘 + 0黑”的前提下当成无冲突样本。

仅用于说明容量与棋盘关系的候选方案（不是自动修改用户输入）：

| 容量区间 | 每色精确可分时的总车数 | 能精确对应的示例棋盘 |
|---|---:|---|
| `[31,40]` | 存在非精确颜色，当前实际近似为 37 辆 | 7×7 会留下约 12 格，需要黑块/管道/空位策略解释 |
| `[20,40]` | 37～55 | 7×7 = 49 可精确 |
| `[18,40]` | 37～61 | 7×8 = 56 可精确 |
| `[16,40]` | 37～71 | 7×9 = 63、8×8 = 64 可精确 |

这些只是独立读实验中的容量—棋盘关系。任何区间变化都必须由用户明确确认。

这里的结果只是初步容量/棋盘体检，不是最终剧本结论。实际还需用用户指定的
容量区间、槽位起点和曼哈顿 trace 重新计算。

## 6. 障碍语义系统

正式版不再使用“冰 12 个、链 6 组”这种以数量为中心的主目标。  
障碍数量是编译结果，不是产品目标。

| 障碍 | 语义角色 | 合理用途 | 禁止用途 |
|---|---|---|---|
| 数字冰 | 延迟 | 延迟一辆关键车，让债务或释放发生在预期窗口；数字提示等待成本 | 随机加厚、无解释拖延 |
| 锁链（2/3 连组） | 绑定承诺/回报 | 组内可包含两辆立即收满的车和一辆收不满的车，形成整组共同等待 | 为凑组数随机连接无关车辆 |
| 管道 | 硬阻挡 + 分阶段揭晓 | 永久占格阻断通路；暂存关键车并在出口释放，拿过出口后形成新的局部可达源 | 隐藏必要信息、掩盖容量错误、当作免费空格 |
| 黑块 | 空间塑形 | 控制可见方向、阻挡旁路、塑造区域轮廓 | 补满空格、制造黑墙 |
| 问号 | 有线索的未知 | 前后存在可推断线索时增加决策 | 把隐藏答案本身当难度 |

### 锁链组的特别说明

当前规则支持锁链组为 2 连或 3 连，整组一起进入暂存，只有组内所有车完成才一起离场。
因此一个 3 连组中“两辆立即收满、一辆留下债务”是完全合法的 `groupDebt`：

- 两辆完成车不会先释放，而是和未完成车一起占住暂存；
- 玩家看到的是一个整体承诺，而不是三个互不相关的球；
- 第三辆被后续目标区域释放后，整组一起离场，形成明显正反馈。

这种组可以作为叙事单元，不应按“三个普通障碍”统计。需要额外记录：

- 组大小；
- 每辆车入场前可消像素；
- 每辆车入场后的剩余债务；
- 组内完成几辆、等待几辆；
- 整组需要几个暂存槽；
- 是否存在完成车因未完成成员而被迫滞留的明确体验。

### 6.1 障碍绑定格式

每个障碍至少记录：

```text
beatId：服务于哪个体验节拍
role：delay / bind / reveal / shape / obscure
ownerCar：影响哪辆车
targetZone：对应哪个目标区域
expectedEffect：预期改变哪个玩家行为
removalResult：移除后剧本是否失效
```

### 6.2 移除消融

所有语义障碍必须通过移除消融：

- 移除后预期债务消失或错位；
- 移除后预期释放消失或提前；
- 移除后玩家可明显绕过核心决策；
- 若移除后什么也不变，该障碍是装饰，不保留。

```text
目标图 TXT
  ↓
SourcePreflight
  ↓
DemandGraph + CapacityContract
  ↓
StoryPlanner
  ↓
CarRolePlanner
  ↓
BoardCompiler
  ↓
SemanticObstacleCompiler
  ↓
StoryVerifier
  ├─ 计划路线回放
  ├─ 旁路检查
  ├─ 可恢复性检查

  └─ 障碍消融
  ↓
RepairController
  ├─ 容量不可行 → 回退合同/建议改图
  ├─ 区域不匹配 → 重选主线
  ├─ 车辆不可达 → 局部重摆
  ├─ 债务不出现 → 调整容量/可见需求
  ├─ 释放不可见 → 调整区域暴露或关键车

  ↓
```

### 7.1 建议核心对象

#### `StoryPlan`

- `beats`：教学、债务、释放、变奏、收尾；
- 每个节拍的进度窗口；
- 预期债务量与持续时间；
- 预期释放幅度与延迟；
- 允许的选择数量；
- 允许的未知信息量。

#### `CarRolePlan`

- `debtCar`：预期制造第一笔债务的车；
- `keyCar`：解锁释放区域的关键车；
- `releaseCar`：完成债务的车；
- `supportCar`：维持正常推进和分支；
- `decoyCar`：合理但次优的选择，不允许直接绕路。

#### `BoardPlan`

- 车辆格位；
- 前置依赖；
- 目标区域暴露顺序；
- 首层可见动作；
- 禁止旁路；
- 障碍挂载点。

#### `StoryEvidence`

- 计划节拍与实际节拍对齐；
- 计划动作与实际动作；
- 债务形成与释放状态；
- 替代路线与旁路；
- 障碍消融；
- 不可解/未知/超预算分类。

### 7.2 搜索策略

搜索保留，但只作为约束求解和局部修复：

1. 先按容量和区域依赖判断是否存在剧情；
2. 先构造满足依赖的棋盘；
3. 只对失败约束做局部搜索；
4. seed 只用于同等合规候选的微小变化；
5. 不允许用搜索时间替代剧情可行性。

修复应优先回答“哪条因果边断了”，而不是“再换一个 seed 看看”。

### 7.3 实现顺序

建议按以下顺序实现，不直接从随机生成器改成一个复杂全局求解器：

#### 第一步：只读 Target Atlas

输入 TXT，输出：

- 颜色连通区域；
- 每块像素的坐标、区域归属、边界和相邻颜色；
- 每个动作在真实消除规则下的像素 trace；
- 每个像素从当前状态是否可达；
- 底边起点的区域距离；
- 容量合同和微车风险。

这一阶段不改棋盘，只确认“这张图能提供哪些故事原材料”。

#### 第二步：Story Plan

先人工或规则生成一份明确剧本：

- 选择目标区域；
- 安排债务车、锁链组、深层门和高光揭示；
- 标出预期路线和每个动作的 buffer；
- 不先设置冰链数量。

#### 第三步：目标路线精确回放

用当前 `Simulator` 的瞬时连锁规则模拟：

- 每辆车的槽位；
- 每个槽位的起点；
- 曼哈顿排序后的实际像素 trace；
- 锁链整组入场；
- 每个动作后的目标暴露变化。

如果实际区域与计划不符，先修正剧本，不换 seed。

#### 第四步：棋盘约束构造

车辆图使用以下约束：

- 计划车辆在正确时间激活；
- 前置车未处理前，后续车不可取；
- 锁链组所有成员在计划窗口可激活；
- 取组时有足够空槽；
- 深层门确实阻挡主路径；
- 旁路存在时，旁路收益低于主计划。

棋盘不是按颜色总量顺序填格，而是按“动作依赖和车辆角色”布局。

#### 第五步：语义障碍绑定

把冰、链、管道、黑块、问号作为动作前后的状态变化挂到剧情节拍上。
每个障碍必须能回答：

```text
它延迟了哪辆车？
它让哪一个动作进入计划窗口？
它让玩家多承担了哪一笔债务？
它移除后哪一段故事改变了？
```

#### 第六步：真实验证

至少执行：

- 计划路线回放；
- 目标区域 trace 对账；
- 旁路搜索；
- 锁链组 buffer 可行性；
- PlayerSim；
- 障碍移除消融；
- 容量、逐色守恒和客户端导入。

失败分类不能统一写成“目标未达”，至少区分：

```text
capacity_infeasible
target_region_mismatch
manhattan_region_drift
debt_not_formed
release_too_late
chain_group_overflow
forced_gate_unrecoverable
board_activation_bypass
obstacle_padding
```

### 7.4 正式版分析工具的输入与输出

第一版分析工具先做只读报告，不直接生成关卡。

#### 输入

```json
{
  "targetTxt": "实验关/关卡6/35x35拼接图纸_006.txt",
  "ruleMode": "instantChain",
  "capacity": {
    "mode": "user",
    "min": 31,

  },

    "pipeMode": "auto"
  },
  "storyTemplates": ["groupDebt", "forcedGate", "reveal"]
}
```

`capacity` 必须来自用户输入；预检只能建议，不能自行修改。

#### 输出一：Target Atlas

`target-atlas.json` 记录：

- 尺寸、背景和每色像素总量；
- 每个同色连通区域；
- 区域边界、相邻区域和空间中心；
- 依赖层和初始暴露区域；
- 每个区域在不同底边起点下的曼哈顿候选顺序；
- 容量合同和无法精确拆分的颜色。

#### 输出二：Capacity Board Feasibility

`capacity-board-feasibility.json` 记录：

- 每种颜色的最少/最多车数；
- 总车数区间；
- 每个棋盘尺寸的车位占用；
- 0 黑、黑块回退、管道 queue 三种策略；
- 是否存在合规棋盘（默认最小边≥6，7以上优先）中满足容量和占用要求的组合；
- 若不存在，给出最小的显式冲突原因。

#### 输出三：Story Candidates

`story-candidates.json` 记录：

- 可形成 `groupDebt` 的锁链组；
- 可形成 `forcedGate` 的深层车或阻挡路径；
- 可形成 `reveal` 的单像素或小区域；
- 每个候选的槽位、起点、目标区域和预期债务；
- 当前容量/棋盘下是否可执行。

#### 输出四：Human Report

`story-preflight.md` 用人类可读方式展示：

- 这张图能讲哪几种故事；
- 哪种故事需要哪些容量/棋盘让步；
- 哪些区域是噪声，哪些是关键揭示；
- 当前输入是否适合进入剧本编写。

#### 原始 006 初步报告

第一轮看到的主要信号：

```text
35×35 / 1225 px / 13 色 / 234 个同色连通块 / 6 层
开局暴露 3 色
深层色仅 1 个（4号）
自动容量带 [31,40] 不能精确拆完所有颜色
```

这说明它可以作为“短债务、强制门、单点揭示”的实验图，
但不应当被直接假定为“能自然做长期多阶段债务”的图。
234 个组件也要求分析器把相邻小碎片聚类成空间区域，
不能把每个 1px 组件都当成独立故事节点。

## 8. 正式版验收

### 8.1 四层门槛

#### A. 硬合同

- 全知可解；
- 容量和逐色守恒；
- 棋盘尺寸合规；
- 黑块、管道和障碍落位真实；
- 调用前配置审计；
- 计划障碍与实际障碍分别记录。

#### B. 剧本合同

- 预期教学、债务、释放、变奏、收尾全部发生；
- 债务产生于设计车辆与设计区域；
- 释放发生在允许窗口内；
- 计划路线可独立回放；
- 实际路线偏离计划时能给出可接受解释。

#### C. 公平与自由

- 预期动作有可见收益和可见希望；
- 不依赖隐藏答案；
- 第一次合理失误后存在恢复路线；
- 允许 2～4 条符合核心思考的路线；
- 不存在低成本完全绕过核心债务的路线。

#### D. 直接交付

- 批量输出不需要人工改棋盘、障碍、容量或路线；
- 客户端 JSON 可直接加载；
- 多图多 seed 达到双方确认的稳定通过率；
- 生成耗时 P50/P90 在可接受范围；
- 通过真人校准，用户明确确认可玩且值得玩。

### 8.2 建议记录的新指标

最终阈值留到样板和真人讨论后再冻结，先记录以下指标：

- `beatHitRate`：计划节拍实际命中率；
- `debtTriggerStep`：预期债务实际产生步骤；
- `releaseLatency`：债务产生到释放的步数；
- `releaseAmplitude`：释放带来的 buffer 改善；
- `choiceWasReasonable`：预期动作是否有可见收益；
- `recoveryAvailable`：合理失误后的恢复路线；
- `routeFreedom`：符合核心思想的路线数量；
- `bypassDetected`：是否出现无意义旁路；
- `obstacleNecessity`：移除障碍后剧本是否失效；
- `manualEdits`：交付前人工修改数，目标应为 0；
- `unknownRate`：预算/未知比例。

### 8.3 不再接受的“通过”

- 只有压力曲线漂亮，但玩家不知道为什么被卡；
- 只有单一路线，且必须靠背板；
- 只有单图单 seed 命中；
- 障碍移除后结果不变；
- 生成后仍需人工补车、调容量或改棋盘；
- 用更多 seed、更长搜索或更多障碍勉强转化。

## 12. 待讨论决策

### 12.1 已确认的机制澄清

- 锁链组可以是 2 连或 3 连；一个 3 连组内“两辆立即收满、一辆收不满”是合法的
  `groupDebt`；
- 多组预留债务可以作为故事，只要每组有明确的后续需求和可恢复路径；
- 深层车挡路可以形成 `forcedGate`，不要求每一步都是自由选择；
- 管道和黑块都可以形成硬性阻挡；区别是黑块只负责永久空间塑形，
  管道还带有队列、延迟释放和出口开启语义，必须按两种不同机制单独验收；
- 目标图中的单像素高光可以是 `reveal`，前提是它靠外围清除后才可达；
- 曼哈顿距离和槽位起点必须进入目标区域计划，不能只计划颜色顺序。

1. 正式版最终是“自动关卡编辑器”“可人工编排故事的编辑器”，还是两者结合？
2. 正式验收集采用哪些图和 seed？是否继续保留 006/008/014，还是切换为 00199/00028 加新的留出集？
3. 一关允许几条符合核心思想的路线？“唯一预期路线”和“2～4 条路线”如何定？
4. 玩家第一次合理失误后，恢复窗口要求几步？
5. 五节拍是否作为默认结构，还是允许不同关卡类型使用不同剧本模板？
6. 数字冰、锁链、管道、黑块、问号各自允许承担哪些语义角色？
7. 直接可用率的样本量、通过率和 P50/P90 时间上限是多少？
8. 正式版什么时候默认开启，什么时候删除旧路径与混合容量 UI？
9. 是否需要可视化展示“计划路线 vs 玩家路线”，供人工审查和调剧本？

## 13. 非目标

- 不是让所有目标图都能生成同一种“好关”；
- 不是找到一条全知解就交付；
- 不是把所有路线都锁成唯一解；
- 不是用更多障碍、更多 seed 或更长搜索制造难度；
- 不是继续维护一个依赖人工补丁的随机难关搜索器。

## 14. 当前结论

正式版的核心资产不是某个冰/链配方，而是：

1. **需求区域图**；
2. **体验剧本**；
3. **车辆因果依赖**；
4. **棋盘与障碍的语义映射**；
5. **计划路线、旁路和恢复路线的验证证据**。

当这五件事稳定成立，生成器才真正从“碰运气找难关”进入
“可控地讲一段关卡体验”。
