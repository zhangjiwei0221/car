## 十六、方案 B：剧本驱动的关卡构造（2026-11-01 立项）

> 背景：现状已完成 **A（总量难度可控）**——产线能稳定产出 at4 20–30、run4 12–24、峰值 4、可通关的关（8 张量产关）。
> **B（按段指定压力曲线）尚未做**，产出的关形状雷同（前少、中多、后少）。

### 16.1 B 的定义（一句话）

> 输入一段**压力契约**（哪几步要压、压多久、哪几步必须松），输出一关，**逐段符合契约**，而不是只满足总量指标。

与 A 的区别：A 的目标是一个标量（at4 最大），B 的目标是一串带时间位置的约束。

### 16.2 输入格式（压力契约）

```json
{
  "bufferLine": 3,                       // 高压线（buffer≥此值算"压"）
  "segments": [
    { "from": 0.00, "to": 0.20, "max4": 0,  "note": "教学段，不许到高压线" },
    { "from": 0.20, "to": 0.60, "min4": 1,  "note": "第一波债务" },
    { "from": 0.60, "to": 0.80, "max4": 0,  "note": "呼吸段" },
    { "from": 0.80, "to": 1.00, "minRun": 3,"note": "收尾高潮：连续 3 步到线" }
  ]
}
```

- `from/to` 用**步数百分比**（与 H/长度无关，跨关通用）；
- `min4 / max4`：该区间内 buffer≥线的**步数**下限/上限；
- `minRun`：该区间内 buffer≥线的**最长连续**下限；
- 契约先跑**可行性预检**（见 16.6），不可满足就报错，不硬解。

### 16.3 变量（能动的只有这些）

| 变量 | 粒度 | 现有支持 |
|---|---|---|
| 车序（棋盘位置互换） | 每辆 | `OverlapBuild posswap` |
| 每车容量 | 每辆 | `capmove / capswap`（同色内） |
| 链（2–3 辆成组） | 每处 | `chain` |
| 数字冰 param（盒子数倒计时） | 每辆 | `ice`，**已验证单位=盒子数** |
| 墙/黑块 | 每格 | `WallSearch_v742`（删车并容量） |
| 目标图颜色分配 | 每色 | 重映射脚本（保持几何） |

**不可动**：每色容量总和 = 该色像素数（硬约束）；峰值 ≤ 上限；必须 `runSolver` 可通关。

### 16.4 构造流程（三阶段）

**阶段 1｜契约 → 债务计划**（纯计算，不搜索）
把每段契约翻译成"哪一段需要几辆车同时吃不满"：

- `minRun=3` ⇒ 该段至少 3 辆车**同时**处于未满状态，且持续 3 步；
- `max4=0` ⇒ 该段任何时刻不得有 3 辆同时未满 ⇒ 该段的车必须"选中即吃满"。

**阶段 2｜债务计划 → 结构选择**（有向搜索，不是盲爬）
按"该段该不该欠债"决定每个区段的切车方式：

- 该段要欠债 ⇒ 该段的车**容量贴近其颜色的连通块大小**（吃不满就留下来）；
- 该段不许欠债 ⇒ 该段的车**容量小于等于该色的最小连通块**（选中即满）；
- 段与段之间用**数字冰 param** 控制出场时刻（已验证有效）。

**阶段 3｜逐段验收 + 局部修复**
新工具 `WindowCheck_v753.js`：

- 输入关卡 + 契约 → 输出**逐段偏差表**（每段实际 min4/max4/minRun 与目标的差）；
- 偏差 > 0 时，只在**偏差所在段**的车里做局部修复（换容量/成链/上冰），不动别的段。

### 16.5 验收（契约即验收）

```
□ 每段 max4 不超上限
□ 每段 min4 / minRun 达标
□ 全局：峰值 ≤ 上限、可通关、容量守恒、首手 ≥80%
□ 归因：拿掉该段的链/冰，该段压力必须掉（否则判"表演"）
```

### 16.6 可行性预检（重要，避免做无用功）

在动手前先算三个必要条件：

1. **步数预算**：该段步数 ≥ minRun（后 20% 若只有 8 步，minRun=3 可行，=6 就不可行）；
2. **车数预算**：该段可用车数 ≥ min4（一次只开一个主体时通常只有 9–12 辆）；
3. **债务可能性**：该段每个颜色的"最大连通块"是否小于某辆车容量（否则吃不满不可能发生）。

**任一不满足 → 契约不可行，先改契约或改图，不要开搜索。**

### 16.7 里程碑

| 阶段 | 交付 | 预估 |
|---|---|---|
| M1 | 契约格式 + `WindowCheck_v753`（只验收、不改关） | 1 天 |
| M2 | `OverlapBuild --contract <json>`：按契约评分（逐段偏差加权），替代单一 at4 | 2 天 |
| M3 | 阶段 1/2 的"债务计划 → 切车"生成器 | 2 天 |
| M4 | 5 张图 × 3 份契约的批量验证 + 报告 | 1 天 |

### 16.8 已知风险

1. **组合爆炸**：契约越细，可行域越小；M2 可能大量返回"无解"。
2. **契约可能自相矛盾**（如"连续 3 步压、但不许欠 3 辆"）→ 靠 16.6 预检挡住。
3. **局部修复可能破坏别的段**（本会话已验证：局部移动影响整条曲线）→ 修复必须限定在该段的车里。
4. **打碎手段已否决**（毁画面），所以"造债务"只能靠容量贴合与颜色连通块，空间有限。

### 16.9 本会话已证否的手段（不要重复）

打碎（毁画面）、末段冰（不造债）、末段大车（峰值不变）、末段双开（压力不变且毁顺序）、
延后解锁（死锁）、墙/删车（越删越糟）、几何分带（玩家选颜色不选位置）、
按碎片度挑图（无关）、8×8 加车（无效）。

**已确认有效**：颜色按主体独占（目标感）、数字冰闸门（顺序）、上限 4（死亡线）、死亡判定修正（结算后判）。
