## 0. 主线产线 v1.0（2026-11-04 定稿）

> **命名**：这套流程叫 **主线产线 v1.0**。
> `v1.0` = 今天三批（批次_10张 / 批次_第二批 / 批次_第三批）用的版本 **但不硬加管道**。
>
> **管道规则（2026-11-04 用户定）**：
> - **默认不加**（`--pipe 0`）。不是禁止，是**不硬加**。
> - 三个理由：① 现在还没有「加管道是为了什么」的逻辑，硬加就是为加而加；
>   ② 只放 1 辆车时，管道几乎只是把车推后，反而挤占选择面（实测：不是管道就是链子，可选车很少）；
>   ③ 要加就得**一个管道里装 3 辆车**，那是另一套设计，暂不做。
> - 想试仍可 `--pipe N` 手动开（`PipeSearch_v808` 会评估位置；旧 `PipeConvert_v772` 只取左上角，会打崩节奏，别用）。
>
> **已知要修的**：`PipeSearch` 目前把「1 辆车」变管道，应该改成「3 辆车共用 1 个管道」；
> 另外首行的管道不能指向上方（方向要朝棋盘外）。

### 0.3 三个关键参数（缺一不可）

| 参数 | 值 | 为什么是这个值 |
|---|---|---|
| `--order-ratio 0.75` | 0.75 | 按消除顺序（D 值）切车，容量几何递减。0.9 太均匀（没得选多）、0.65 太陡 |
| `--trap-ratio 0.25` | 0.25 | **顺序陷阱**：25% 的颜色切成「1 大 + N 小」。0.15 压力不够、0.35 直接 100% 中段/容错只剩 20% |
| `--edge-big-ratio 0.3` | 0.3 | 边框放大车、内部放小车。**必须按容量排序**，不能按 ratio（见 §0.5 坑 3） |

### 0.4 机制解释（为什么这些参数能造出压力）

**① 顺序陷阱（`--trap-ratio`）—— 这是「会死」的唯一来源**

同色切成 `167 + 27 + 27 + 27 + 27 + 29`：

- 先取 167 那辆 → 开局该色只有 76 可达 → 吃不满 → 占 1 格
- 小车随后把像素吃光 → 167 **永远差一点** → 占死暂存 → 最终爆
- 先取 27 的小车 → 吃满开走 → 167 最后反而能吃满 → 通关

**同一张关，顺序错了就死。** 这就是容错率能从 100% 降到 50% 的原因。

陷阱车容量上限 = `min(该色像素×0.55, 开局可达×1.3)`，避免出现 167/210 这种离谱车。

**② 边框放大车（`--edge-big-ratio`）—— 这是「开局不白送」的唯一来源**

边框 24 格（7×7）是开局全部可见的位置。放大车 = 开局能吃满的选项少 = 第 2 步就得做选择。

K_006 实测：边框 79/60/49/44/44/39/37，内部 8–22。

**③ 按消除顺序切车（`--by-order`）—— 修「没得选」**

不按 (行,列) 切，按 corner 的 D 值切（先消的在前），容量递减。这样最后一辆车很小，吃得满。

### 0.6.1 【重要】`--edge-big-ratio` 曾经完全无效（2026-11-03 修）

原来的写法是 `bigCars = sorted[0..N]` + `restCars = sorted[N..]`，两段拼起来**永远是 sorted 的前 24 个**，
所以 `--edge-big-ratio` 设 0.3 还是 0.9，边框内容一模一样 —— **这个参数从写出来就没生效过**。

修法：**边框 = 最大的 N 个 + 最小的 (24−N) 个**，中间那批放内部。

修好后 40×40 的图立刻能做出来（见 §0.8）。**如果之前调这个参数没反应，就是这个 bug。**

## 0.9 四象限阶段关：可控产线 v1.0（2026-11-05）

> 这条线不是自动搜索，是**人定剧本 + 工具验证 + 配方固化**。
> 适用：一张四象限目标图、四个主体、7×7、39–40 车、9–10 黑，目标是“一个主体一个任务 + 可选债 + 阶段门控”。
> 产物：关卡 JSON + 配方 JSON（可从配方一键重建，见 §0.9.9）。

### 0.9.1 思想：三种债 + 一个保底

| 债型 | 怎么形成 | 玩家感受 | 用法 |
|---|---|---|---|
| **位置债** | 门在主体内部车后面，为了拿门先拿内部车，吃不满 | 被迫背债，但门一到就快速还 | 只保留短门路径（≤3 辆），不堆无关车 |
| **池债** | 同色多车共用一个像素池，剩余容量小的优先，第二辆被饿着 | 拿完发现没吃满，得调整同色车顺序 | 同色 2–3 辆、容量错开；共享色是长池债原料 |
| **主体债** | A 是背景色同时也是主体内色，B 包着 A；先拿 A 背债，拿 B 还债 | 可选，不是被迫；玩家自己选先 A 还是先 B | A 车放侧枝，B 放门/路径上 |
| **保底** | 接近极限时机的冰门（如 20:30 冰27–28） | 选错路线后还有限时补救，能归因 | 只救“安全路线”，不替代主路线 |

配比：框色独占（主体清晰）+ 共享色 4–6 个（长债原料）+ 位置债只留门路径 + 主体债 1–2 对 + 池债 2–3 组。

### 0.9.2 挑图

- 四象限各有独占框色（只在本主体出现；可等于本主体内的一个颜色）。
- `SubjectDetect_v800` 4×100%；每主体 ≥150px；总 1600（40×40）。
- 统计跨 ≥2 主体的共享色：它们是池债/主体债的原料。共享色太少 → 只能做短位置债，后段会平。
- 首手落左下（corner）；四象限齐全；阶梯跨度 ≥30。

### 0.9.3 定阶段与门

- 阶段顺序按主体/象限；每阶段一个框色（门）。
- 门放在“主体内部车后面”，但路径 ≤3 辆；门车不加冰。
- 下一框车在当前主体 **≥70%** 进池（60% 可接受，早一点不致命；别低于 60%）。`StagePlanCheck_v805` 用 60/70 两档跑。
- 未来框色在门槛前不得进可选池（`forbiddenFrameColors` / `forbiddenUntilStep`）。

### 0.9.4 切车与容量

- 每色 `sum(count) == 像素数`；容量是输入，不缩放、不按车数拆。
- 大车给池债/主体债（同色 2–3 辆，容量错开）；小车只做“一拿即满”的钥匙（容量 ≤ 当时可达像素）。
- 不放无职责的 5px 车；车数 39–40、黑 9–10；空格 0（黑格算占位）。

### 0.9.5 摆盘与路线

- 先画“到门的必经路径”：路径上的车就是位置债。
- 再画侧枝：可选的主体债/池债。
- 不要整排黑墙；黑块只用来封口袋/控阶段，不用于“看起来有选择”。
- 20 框车不在最后一格；框车口袋至少留一个“即时钥匙”（如 `23:16`）和一个“限时保底”（如 `20:30` 冰27）。

### 0.9.6 债务设置（每笔都要写清楚）

对每笔债记录：颜色/容量/位置/入口步/入口进度/还款车/还款步/占用槽数。

| 债型 | 入口进度 | 还款 | 目标 |
|---|---|---|---|
| 位置债 | 20–50% | 门或门后第一辆 | 1–3 步内还，不拖 |
| 池债 | 第二辆 ≤50% | 前一辆吃完 + 区域打开 | 2–4 步，玩家要调整顺序 |
| 主体债 | A 车 20–40% | B 在路径上 | 2–4 步把 A 还到 ≥60% |
| 保底 | 冰 27–28（39 步关） | 第二框车/第二门 | 只给安全路线留一口气 |

### 0.9.7 障碍

- 冰只给真正挡像素/挡门的车；链只锁“一次吃不完”的组；问号只藏颜色；禁止免费链。
- 门车不加冰；保底冰放在“第二框车”上，不放主门。

### 0.9.8 验收（按顺序）

1. 配方重建：`BuildFromRecipe_v1` → 与原关 deep equal；守恒/无空格。
2. `StagePlanCheck_v805`：60/70 两档。

5. 人工试玩：重点感受“被迫/可选/保底”是否可归因。

### 0.9.10 造新图前的设计检查表（逐条问）

> 一次从新图“目标驱动”生成过关是做不到的——00085 这条线调了十几版。
> 新图先按下面 12 条问一遍，缺一条就会在验收里以“玩家死/中段爆/阶段不过”的形式还回来。

1. **图**：四主体 `SubjectDetect` 100%？每主体 ≥150px？每个主体有独占框色？共享色 4–8 个？背景色占多少 px？
2. **顺序**：首手（左下角最近可达像素）落在哪个主体？四个主体的 D 顺序是什么？阶段顺序要跟 D 顺序，不要硬排。
3. **门**：每个门放在哪？到门的必经路径几辆（≤3）？门容量 ≤ 门出现时的可达像素？
4. **下一框车**：当前主体 ≥60–70% 才进池？未来框色在门槛前不进池？
5. **早期 5–8 格**：是不是“一拿即满”的钥匙/背景色？容量 ≤ 当时可达？
6. **共享大车**：2–4 辆、容量错开、放在中晚段？第二辆会不会被饿成 0？
7. **每笔债**：入口进度、还款车、还款步（≤3–4 步）写清楚？没有还款车的不是债，是锁。
8. **链**：只锁“一次吃不完”的组？链伙伴近期能还？会锁死某一成员吗（1 色在书段只有 2/29 那种就是坏链）？
9. **保底**：冰门 27–28 放在第二框车/第二门？只救安全路线，不替代主路线？
10. **摆盘**：没有整排黑墙？20 框不在最后一格？口袋有“即时钥匙 + 限时保底”？
11. **验收顺序**：配方重建 deep equal → StagePlan 60/70 → ArlCheck → PlayerSim（0/2 复活）→ 人工试玩。
12. **迭代**：一次只改一件事；负结果也记日志；不按旧关比例缩放容量。

### 0.9.11 指标口径（避免再看错数）

- **中段 at3（玩家中段 45–80%）**：取 PlayerSim（合理玩家、2 复活）每次取车的当前暂存车数；从中段（取车序列 10%–80%）里数 **暂存 ≥3 车的步数占比**。96% = 几乎每一手中段都背着 3–4 辆没吃完的车，整段没有呼吸；目标 45–80%。
- **峰值**：最小暂存路线的最大暂存车数；目标 4（4=卡点，5=死亡）。
- **2 复活 5/5**：合理玩家最多用 2 次复活能通关 5/5；0 复活是加分项，不是底线。
- **决策度**：按用户口径“能吃到一半以上”算有选；没得选 ≤ 总步数一半。

## 5. 建模与摆障碍（我 + 脚本）

### 5.1 解锁表（关键）

对每辆车算「解锁步」＝该色第几步才够它的容量。
- 解锁晚的 = 天然“锁芯”；
- 全程度不足的 = 永远还不掉的债（不能拿来当锁芯，会锁死）。

工具：`unlockTable`（在 `OverlapBuild_v719.js` / 临时脚本里）。

### 5.2 摆法（按句型）

| 句型 | 手段 |
|---|---|
| 教学句 | 开局 2–3 辆能吃完的车（别放冰） |
| 债务句 | 链(便宜车, 晚解锁车) |
| 释放句 | 让晚解锁车的颜色到位（不动） |
| 过渡句 | 链两辆 unlock 差 5–8 的车 |
| 收尾句 | 冰把最后一辆拖到最后（param=目标球数） |

### 5.3 自动构建（脚本）

`OverlapBuild_v719.js`：以“空窗最小 → at4 最大 → run4 最大”爬山，
移动类型：

- `memberswap`：链组成员与异色车交换「颜色+容量」→ 改释放节奏（最有效）；
- `posswap`：两辆非链车换位置 → 改出场顺序；
- `capmove/capswap`：同色容量转移/互换 → 改每辆要多少；
- `chain`：相邻两辆成链；
- `ice`：加数字冰（param=全局球数）。

| `buffer` | 暂存区里“还没收满”的条目数 | 4 = 卡点；5 = 死亡边界 |
| `at4` | 全知路线里 buffer≥4 的采样步数 | 越大越有压力（006 v62=28/47） |
| `run4` | 最长的连续 buffer≥4 | 平台长度（006 v62=16） |
| `空窗` | 两次 buffer≥4 之间 buffer<3 的连续步数 | 0 = 压力不断档 |
| `免费步` | 收满、不欠债的取车步数 | 越少越“每一步都要想” |
| `免费前缀` | 全零债动作能走的最长前缀（beam） | 开局自由度 |
| `解锁步` | 某色第几步才够这辆车的容量 | 越晚越能当“锁芯” |
