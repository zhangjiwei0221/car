## 0. 一句话说清

**做什么**：给 iOS 游戏 ParkPassenger（车接小人 / Bus Jam 类）生成「可玩、有压力、不劝退」的关卡。

**定位**：用户是游戏关卡策划，本工程是**长期关卡策划工作台**，不是一次性关卡生成器；不同分组 = 不同版本，会持续测试/生成。目标是让游戏更好玩，不是单纯让 19 项全过。

**编号**：`v3/v4` 是产线版本号；`分组3/分组4` 是上线组号。当前 **v1 现役**、**v3 是“更清楚造关”的实验层（冻结）**、**v4 已停止**、**v1.5 已停止（2026-11-11）**。

**怎么做**：不是靠生成器一键出关，而是「**AI 定剧本与验收 + 脚本做切块与搜索**」的半自动流程：

| 环节 | 谁做 |
|---|---|
| 选图 / 定任务顺序 / 判定好不好 | AI（人看手感） |
| 切车 / 构建 / 障碍 / 验收 | 脚本（`03_工具/正式版/`） |

**当前主线**：**主线产线 v1.0**（见 `关卡流程 §0`），验收 `ArlCheck_v793`（19 项）。
现役造关入口是 **CLI**（`JointSearch_v799`），不是网页批量生产；网页批量生成属于「搜关卡」时代，已长期不用（历史说明见 §5.2）。
**v2.0 是实验、尚未通过**（`关卡流程 §0.11`）：人定骨架 + 工具算容量 + 试玩校准，只到候选阶段，没有出货。

## 1. 这个工程是做什么的

给手机游戏「车接小人」（蚂蚁拿块玩法）**批量生产可玩关卡**。

- 输入：一张像素图（TXT 像素矩阵，一格一个颜色号）
- 输出：一关 `toprow / blocks / maprow / mapcol / spools` 结构的 JSON，可直接放进游戏客户端的 `bin/` 目录
- 中间：切球 → 选盘 → 摆障碍 → 放车 → 求解 → 评估 → 择优/兜底

核心矛盾（整个工程都在围绕它调）：

```
车太碎 → 车多盘大、开局全是免费车 → 没有压力
车太大 → 车少盘小、每辆都能一口吃下 → 也没有压力
压力 = 中段（30~80% 进度）手里"攒着几张吃不完的票"持续得够久
```

## 3. 技术架构

### 3.1 代码组成（`02_工程/游戏主bin/bin/js/`）

| 文件 | 职责 |
|---|---|
| `generator.js` | 生成主逻辑：切球、选盘、铺盘、卡点树、验收编排（最大，1.3 万行） |
| `app.js` | 界面与批次调度：参数装配、线程池、日志、结果条、落盘 |
| `solver.js` | 求解器：6 遍（贪心×2 / 三步树×2 / 噪声×2），产出取盒序列与压力采样 |
| `solver-strategy.js` | 选步策略：贪心打分、三步前瞻树 |
| `playersim.js` | 玩家模拟：不同"手痒程度"的 10 局，含死因埋点 |
| `simulator.js` | 规则内核：棋盘可达/激活、消除 flood-fill、锁链/冰判定 |
| `analysis.js` | 审核：卡点审计、难度分 |
| `utils.js` | 关卡解析、游戏格式转换 `toGameFormat` |
| `release-route-constructor.js` | v535只读路线构造模块：验证参考路线，或从接近中段的高压父状态构造完整`pickOrder`并独立回放；尚未参与默认生成 |

### 3.2 两条产线

| 流程 | 入口 | 特点 |
|---|---|---|
| **生产用（v495 起）** | `generatorFlow:'new_fixed'` → `produceFixed()` | 按"结构/层"铺盒 + 候选优选 + 卡点变体；容量上限已在 v495 夹紧 |
| 旧流程（仅复现/对照） | `generatorFlow:'old'` → `produce()` | 切球定车数、棋盘按盒数反推、结构组合轮换 |

> **v495 变更**：UI 批量从 `old` 切到 `new_fixed`（`app.js` `genApplyFixed`）。本次只改算法，
> 参数块仍沿用原生产口径；`old` 保留可随时回退（`generatorFlow:'old'` 或全局 `AntSolver.Generator.FLOW='old'`）。

> 红线：**一个会话只能走一条产线**。任何"重产一次"的分支（纠偏 `bandFixOnce`、兜底）都必须走 `runFlowOnce()`，
> 否则会出现"你设 30~60，结果满盘 8~25"的事故（v314）。

> **v536实验开关**：仅当 `config.instantReleaseRoute=true` 且瞬时模式、候选结构与容量已合格时，
> 才会附加完整释放路线证据；默认关闭，不改变普通生产、目标模式门或障碍配方。


### 3.4 三种玩法模式与消除顺序（2026-10-26 补，此前文档缺失）

`entryMode` / `config.instantChain` / `config.bottomOnly` 决定消除规则；**顺序规则不同，可解性会不同**。

| 模式 | 键 | 连通/进入 | 消除顺序（关键） |
|---|---|---|---|
| 四方向（默认生产） | `entryMode:'fourSide'` | 四边皆入口，4-邻接 flood fill | **不看小车/暂存位置**：入口源分层「底→左→右→顶」+ 依赖波深度 |
| 底部单入口 | `bottomOnly:true` | 只从底边进入 | 同上，但上/左/右不开 |
| 四方向瞬时连锁 | `instantChain:true` | 四边入口 | **按离该订单暂存起点的曼哈顿距离**近优先；平手先最底、再最左；且按"快照批次"整批消，不是逐格暴露 |

- 瞬时连锁的"起点"= 车进入暂存后所在槽位映射到目标图底行：`col = floor(槽号/5 × 图宽)`、`r = 图高 − 1`（`simulator.js` `slotStartCoord`）。
- 名字解释：**四方向**指连通规则，**瞬时连锁**指"一整批一起消"；曼哈顿距离只是这个模式的**排序细节**，名字里没有体现。
- 代码入口：默认 `floodFillEliminate`；瞬时连锁 `instantChainEliminate` + `Solver.solveInstantChain`。
- **待确认（2026-10-26）**：用户在客户端观察到"按小车与小人的曼哈顿距离"，疑似真机是瞬时连锁；若确认，生产验证需切到该模式并重跑基准（当前默认生产的求解/评价走的是四方向）。
- **客户端侧（2026-11-03）**：`~/Desktop/游戏版本/ParkPassenger_corner` 现在只改了一处 ——
  排序键 `TargetBoard::_getCandidateScore` → `D = r_int + c`（内部行 0 = 底行，等于文档的 `|r_disp-(R-1)|+c`），
  平手"行升序→列升序"由原比较器自带。**候选集合（阻挡关系）保留**，仍只取"能通到边缘"的同色格。
  ⚠ 两处试过都回退了：① 13:38 把候选钉成"全图同色格" → 用户否决（忽略阻挡）；
  ② 14:05 把取用改成"逐个取、取到就置已消" → **进关卡车接人时 SIGSEGV 闪退**（动画回调重入时对象已失效）。
  现役 sha256 `4c844ac5…`。工具/崩溃证据见 `02_工程/补丁/客户端补丁_corner曼哈顿/`（§9）。
  **仍未实现**：文档 §一.2 的"逐个确定、被解锁的立即参与"；同色多车争用次序（§一.3）也未验。

## 4. 产物与数据格式

### 4.1 关卡 JSON（客户端可直接用）

```json
{ "toprow": 40, "blocks": [[色号…]], "maprow": 5, "mapcol": 7, "spools": [[…]] }
```

- `blocks`：目标图像素矩阵（色号，0 = 空）
- `maprow/mapcol`：车场行列
- `spools`：每格一辆车 `{id, count, type:[…], param:[…]}`；`type` 里 5=锁链、6=问号、7=数字冰，11~14=管道

### 4.2 批次产物目录

```
输出文件/<批次名>/

│   ├─ 逐关记录.jsonl             ← 每关一行（结果/棋盘/难度/性能）
```

### 7.1 旧六条（goodV3，已降级为“旧判据”）

| 指标 | 定义 |

| **覆盖率** `band3Pct` | 进度 30~80% 区间里，暂存 ≥3 的采样点占比 |

| **玩家通关率** `playerPassPct` | 5 种手痒度 × 2 种子 = 10 局，不给复活 |

> **v364 起旧六条不再决定合格**；v366 起只作为报告里的「旧判据（仅供参考）」和搜索早停的辅助。

- **问号（type 6）**：隐藏颜色，控制“信息”。

## 19.2 最终目标

批量生成可解、守恒、可理解、有真实卡点且能释放的关卡，而不是只追求：

- 首通率低；
- 峰值高；
- 免费连数字小；
- 障碍数量多；
- 搜索时间长。

核心质量仍是：**卡点数量合理、玩家能看懂、能通过思考释放、路线基本公平。**

历史目标中的006/1001、008/014、PlayerSim、多图和真人校准仍是总验收的一部分；
v613~v615新增的是生产工具和需求约束，不等于总Goal已经完成。

## 19.3 已确认的用户偏好

### 2.1 棋盘与车

- 棋盘可以自动推荐，但必须允许用户指定范围和具体尺寸。
- 用户已明确：**不强制行列必须为7以上**。历史偏好仍可优先较大棋盘，但7不是硬门；
  棋盘大小应服从容量硬输入、每色可拆车数、故事角色和必要障碍。
- 6×6、6×7、7×6可以参与正式版可行性搜索，不能被无条件排除。
- 容量不要求统一，允许40px锚点车与6~18px小车混合。
- 47、49这种大容量偏大；当前优化方向是更多中小容量车。
- `boxSizeMin/Max`、`capNormMin/Max`是用户硬输入，不得缩放、对半拆或偷改。
- 目标车数应由“棋盘格数 − 允许黑块 − 管道占格”推导，不能永久写死“车数=格数”。
- **同色车连续摆放不是缺陷本身**。判断标准是它是否服务于目标区域消除、
  债务形成或预期卡点；不得为追求颜色分散而破坏故事和压力。
- 多种排列只有在满足故事与目标区消除后才比较观感；不能把“颜色规律”
  当作独立于玩法的否决项。
- 当前关卡的核心体验指标是计划卡点处的暂存区3/4压力。至少应有两个
  可解释的压力窗口，并能在不依赖复活的情况下明显释放。

### 2.2 黑块

- 不要黑墙和大量补位黑块。
- 当前零黑块实验有效，00199和00028都已生成7×7/49车/0黑。
- `0黑`是当前实验的优先目标，但不应成为所有地图不可回退的唯一方案。
- 建议策略：优先0黑；确实无法满足容量与棋盘合同时，允许最多≤5%黑块作为回退，禁止形成墙。

### 2.3 数字冰

- 约40辆车的关卡允许10~20个数字冰。
- 冰即使不增加新的卡点，也可以用于增加障碍厚度。
- 当前v615默认目标为12个冰，已验证可实际落下12个。
- 冰不能把开局完全锁死；当前实验从第2行开始放冰。
- 多冰只算厚度，不能自动等同于“体验目标通过”。

### 2.4 锁链

- 锁链数量要更多；当前实验目标为6组，实际能落5~6组。
- 锁链优先连接小容量车；当前阈值是至少一头≤18px。
- 不应只按颜色需求差配对，还要考虑容量、路线段和是否真的形成可释放债务。
- 不是所有生成seed都能补到6组，必须记录实际组数，不能把计划数冒充落地数。

### 2.5 问号

- 用户目前没有给问号设定独立数量上限。
- 保留现有生成与统计口径，不把“问号≤2”等未经确认的临时判断写成产品需求。
- 若后续用户明确反馈问号过多，再作为独立实验变量处理；问号不能替代有效卡点设计。

### 2.6 管道

- 不认为“必须0管道”。
- 管道必须可配置：0条、自动、至少1条、固定1~2条。
- **管道与黑块一样是永久占格的硬阻挡**，会阻断棋盘通行和可达性；
- 管道比黑块多出队列语义：可暂存并分阶段释放车辆，出口被拿取后成为新的可达源；
- 黑块是纯空间塑形；管道同时承担硬阻挡与“延迟供给/局部开启”，两者不可混记为同一种障碍；
- 管道不能用来掩盖容量错误或不可解问题。
- 当前v614/v615为了“格数=车数/0黑块”暂时写死0管道，这是实现限制，不是产品规则。

### 2.7 债务与选车

- 玩家只会合理选择当前场上存在、且能实际消除一部分目标的颜色；
- 当前可消颜色不足时，玩家选择该车会自然留下债务；这种“收不满”是选择后的
  延迟成本，不是设计者强行制造的惩罚；
- 锁链组必须正交相邻，且组内至少有一辆在进入时具有当前实际消除量；
- 锁链可以包含已完成车和未完成车，让完成车等待组内其他成员，但必须能说明
  当前需要的颜色和目标区；
- 不强制每条路线都承担债务，也不强制重债路线收益最高；
- 优先保证至少一条债务路线有可见收益，并记录安全/轻债/重债的真实成本。

### 2.8 障碍厚度与选择后果

- “不能硬加障碍”不等于“障碍越少越好”；障碍同时承担故事语义、
  难度厚度和游戏观感；
- 数字冰和锁链不能因为已有一条压力路线就被默认移除，
  应保留足够的视觉与决策厚度；
- 锁链可以存在多组。每组必须正交相邻，且至少一辆在进入时具有当前实际消除量；
- 锁链组可以有主职责，也可以作为厚度层；不要求每个厚度障碍单独改变主路线，
  但组级移除必须改变选项数量、buffer曲线、等待时间或路线分布中的至少一项；
- 数字冰可以主要承担节奏与厚度，但必须避开初始路口，且不能封死所有替代选择；
- 第一行的同色或近同色入口必须做“首取后果矩阵”：
  记录直接收益、债务、后续可达区、峰值和成败分布，禁止入口差异只是随机惩罚；
- 当前 v17 的`2黑 + 3连锁 + 1管道 + 0冰`不足，作为“逻辑成立但厚度不足”的节点保留。

## 19.5 正式版的结构分层

正式版必须停止把棋盘、黑块、管道和容量绑在同一个“混合容量”开关里。四类策略仍有独立配置价值，但都必须服从同一份体验剧本：

1. **棋盘策略**：自动、手填范围、指定7×7/7×8/8×8等。
2. **黑块策略**：0优先、最多5%、最多15%。
3. **管道策略**：0、自动、至少1、固定1~2。
4. **容量策略**：最小/最大、40锚点比例、小车阈值、小车占比。

剧情节拍至少包括：

- 教学；
- 预期债务；
- 可理解的释放；
- 第二次变奏；
- 收尾。

冰、链、管道、黑块和问号的数量是剧本编译结果，不先设配额再找用途。

## 19.6 生成与验收规则

1. 每色容量和必须等于该色像素数；包含管道queue。
2. 最终棋盘必须重新审计容量、逐色守恒、黑块、管道、障碍落位和可解。
3. 计划障碍数与实际落位数必须分别记录。
4. 多个候选按完整剧本、旁路、恢复与交付结果比较，不能只看单一峰值。
5. 体验目标通过不等于qPass通过；qPass未过仍标“可玩·没支路/一学就会”等。
6. 结果必须能回放；不能把unknown写成无解或0。
7. 实验失败必须保留负结果和回退路径。

## 19.9 程序端关卡 JSON 格式（交付契约，2026-11-11）

> 交付给程序/上线的关卡一律按这个格式写；实现出处 `02_工程/游戏主bin/bin/js/utils.js` 的 `toGameFormat/fromGameFormat`。
> **程序侧 2026-11-11 新规则：`type` 是数组时，`param` 必须是同序、同长度的数组。**

### 5 个键

| 键 | 含义 |
|---|---|
| `toprow` | 目标图行数（= `blocks.length`），不是棋盘行数 |
| `blocks` | 目标像素图 `[toprow][宽]`，`0`=空位，色号实际用 1–34 |
| `maprow` / `mapcol` | 车盘（棋盘）行数 / 列数 |
| `spools` | 车盘 `maprow × mapcol`，每格一个 `{id,type,param,count}` |

### 每格字段

| 字段 | 含义 |
|---|---|
| `id` | `>0` 车色；`0` 空格 / 管道格；`-1` 黑块 |
| `count` | 盒容量（像素数）；空格 / 黑块 / 管道格为 0 |
| `type` | `0` 普通、`4` 老冰（已废，导入按数字冰 3）、`5` 锁链、`6` 问号、`7` 数字冰、`11–14` 管道（上/右/下/左） |
| `param` | 功能参数，与 `type` 对位 |

### type / param 写法（硬规则）

1. **单功能**：`type` 标量，`param` 标量。例：`{"id":13,"type":5,"param":2,"count":50}`（链组 2）。
2. **多功能**：`type` 数组，`param` 必须同序、同长数组，`param[i]` 属于 `type[i]`。
3. 无参数的功能（`0/4/6`）在对应位置写 `0`；`5` 写链组号；`7` 写剩余球数。
4. **管道**：`type` 标量 `11–14`，`param` 整个是队列 `[{id,count}]`，不套同序规则；`id=0`、`count=0`。
5. **纯问号车**统一写 `type:6, param:0`；不要把 `0` 写进 `type` 数组（禁止 `[0,6]`）。
6. **不写 `q` 字段**：历史残留，引擎不读；问号只认 `type` 里的 `6`。

### 示例

```json
// 普通车
{"id":28,"type":0,"param":0,"count":82}
// 锁链
{"id":13,"type":5,"param":2,"count":50}
// 数字冰
{"id":30,"type":7,"param":30,"count":76}
// 锁链 + 数字冰：链组 2，冰 42 球
{"id":13,"type":[5,7],"param":[2,42],"count":50}
// 老冰 + 锁链：老冰无参→0，链组 90
{"id":32,"type":[4,5],"param":[0,90],"count":75}
// 老冰 + 问号
{"id":26,"type":[4,6],"param":[0,0],"count":69}
// 纯问号
{"id":6,"type":6,"param":0,"count":38}
// 黑块
{"id":-1,"type":0,"param":0,"count":0}
// 管道（出口向上，队列先出 15:21）
{"id":0,"type":11,"param":[{"id":15,"count":21},{"id":31,"count":40}],"count":0}
```

### 交付前校验

1. 逐色守恒：`sum(count)`（**含管道队列里的车**）== `blocks` 里该色像素数；
2. `type` 数组 ⇒ `param` 同长数组；
3. 纯问号 `type:6`，没有 `[0,6]`、没有 `q`；
4. `fromGameFormat` 解析出的棋盘与设计一致；
5. 参考修正件：`归档_三组格式对齐/`（原 `程序发的关卡_修正_20261111/`，2026-11-11 修正后移到归档；G1/G2/G3 共 723 关；`修改报告.md` 有逐项校验）。

> **已知缺口（2026-11-11 实测）**：`toGameFormat` 对「链+问号」仍输出标量 param（`{"type":[5,6],"param":2}`），违反第 2 条；其他组合合规（`[5,7]→[2,42]`、`[5,6,7]→[2,0,42]`、纯问号 `6,0`）。修工具前，导出后必须检查并改成 `[2,0]`。


### 8. 分阶段允许颜色与框车时机（2026-11-04 用户补充）

这是当前关卡设计的新硬需求：

- 每个主体阶段必须显式定义“当前允许出现的颜色”。
- 当前阶段只允许当前主体的框车进入可选池；其他主体的框车不得提前进入可选池。
- 框车本身不得用数字冰遮色；需要延迟时，用其他车冰柱或黑块封闭道路。
- 每个允许出现的颜色必须回答：
  - 这个颜色是否真的需要？
  - 它是否能形成债务？
  - 它的债务由哪个颜色、哪个主体、哪个阶段释放？
- 主体内要安排债车的暴露顺序，不能只靠容量或随机位置让玩家碰运气。

示例目标：

```text
第三象限香肠开始
→ 红色框车 35px 消去
→ 暴露白色/黑色/蓝色等非框车
→ 第二手白车吃一半
→ 第三手蓝车吃一半，同时打开白车的释放路径
→ 白车还债
→ 某个 4px 颜色与香蕉内部颜色绑定，留到香蕉阶段
→ 香肠基本完成
→ 才允许第二象限香蕉框车出现
```

反例：

- 当前 v3b 第 16 步香肠 54%、香蕉 6%、奶茶 2%、猕猴桃 7%，四个主体同时进行，不合格。
- 未来若其他框车在阶段完成前进入可选池，直接判定阶段结构不成立。

验收必须同时报告：

- 当前阶段允许颜色；
- 当前可选框车；
- 每个债车的进入步、释放步和释放颜色；
- 主体进度是否按任务顺序推进；
- 容量与逐色守恒；
- 最小暂存路线峰值。
