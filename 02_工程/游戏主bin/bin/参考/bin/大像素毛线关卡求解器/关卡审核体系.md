# 关卡审核体系（含可切换审核基准档）

> 配套：`难度评分体系.md`（难度值/曲线判定的细节）、`三档玩家求解逻辑说明.md`（求解器档位）。
> 入口：`run.js`（生产批量审核）→ `Validator.analyzePlayerSolution(..., auditTier)` + `Validator.computeDifficultyScore(result, { omniResult, auditTier })`。

## 1. 审核做的四件事 + 一道结构检验

每个候选关卡（每轮 5 个候选、最多 10 轮）用审核档求解器**跑 3 遍**（降随机误触扰动），再依次过：

| # | 闸门 | 来源 | 说明 |
|---|---|---|---|
| ① | 难度强度 ∈ [MIN, MAX] | **最好那遍**的 `difficultyStrength` | 量级，0-100 |
| ② | 曲线合规 `compliant` | **3 遍按球平均曲线** `computeDifficultyScore(curveMode:'avg').compliant` | 符合预期 / 趋势符合 视为合格 |
| ③ | 全知版通关 | `analyzeOptimalSolution` | 保证关卡至少“有解” |
| ④ | 审核基准档通关 | `analyzePlayerSolution(..., auditTier)`（3 遍至少半数通关） | 该档能打通 |
| 结构 | 不卡死 | 卡死检验工具 | 仅对合格候选再检验 |

> **判定看平均、展示看最好**：合格(②)用 **3 遍按球平均曲线**判（稳，不让单遍随机决定过不过）；而**客观难度①、曲线质量/卡点、路线、压力曲线**都用 **3 遍里"最好的一遍"**自洽地算与导出（见 §8）。

全部通过 → 合格输出；否则保留“最接近合格”的失败候选并写明卡在哪条标准。

> 兜底（前期压不住）：跑满轮次后，若最佳候选**唯一卡在 `前期峰值前移`**（①难度区间 ②全知通关 ③该档通关 ④不卡死 都满足，仅曲线因前期超限不符合），则**选该最接近候选并入合格+排序**，JSON 内嵌 `_analysis.earlyOverLimit/note` 标注，报告记 `合格·前期偏高(已标注)`。其余失败类型仍为“不合格/需美术返图”。详见 `动态难度平衡策略.md` §3.1。

## 2. 审核基准档 `AUDIT_TIER`（互斥切换）

审核以哪一档玩家的求解表现为基准，由环境变量切换；**一次只跑一档**，报告即该档的：

| 取值 | 含义 | 难度下限默认 | 前期约束（前期5%窗口平均暂存上限） | 状态 |
|---|---|---|---|---|
| `strong`（默认） | 高手 | 30 | **≤4.2**（>4.2 判前移，见 §4） | 现网口径 |
| `novice` | 菜鸟 | 20 | **<3.5**（≥3.5 判前移，见 §4） | 本次新增 |
| `mid` | 中级 | 30 | 暂沿用高手 ≤4.2 | 占位，专属阈值待填 |

用法：

```
AUDIT_TIER=novice node run.js          # 用菜鸟基准审核
AUDIT_TIER=novice DIFFICULTY_MIN=25 node run.js   # 覆盖难度下限
node run.js                             # 默认高手，等价旧行为
```

闸门④与曲线判定都改用所选档：`tierPass = playerResult.tiers[AUDIT_TIER].completed`；曲线用 `result.tiers[auditTier]` 的按球暂存曲线。全知线（闸门③）所有档都跑、都必须通关。

## 3. 难度值口径（所有档统一）

- 融合：`难度 = 0.8 × 基准档强度 + 0.2 × 全知强度`（原 0.6/0.4 已调整）。
- 三因子：`强度 = (0.45·f2平均暂存占比 + 0.20·f3平均滞留 + 0.35·f4高压加权) × 100`。
  原 f1（线轴数，权重 0.05）已移除，权重并入 f2。
- 归一化分母 `_RATIO_CAP=50 / _RES_CAP=4.5 / _HP_CAP=1.0`：按 64-90 难批·**高手档**标定，不变。
  - 换菜鸟基准后，菜鸟在卡点区暂存更高、滞留更长，f2/f4 更易触顶 → 难度分整体偏高（属预期：菜鸟看着更难）。如出现过多“极难”，手动调 `DIFFICULTY_MIN` 或后续单独标定菜鸟 caps。
- 难度档边界不变：简单 0-25 / 普通 25-50 / 困难 50-70 / 极难 70-100。

## 4. 曲线判定：高手线 vs 菜鸟线（核心差异）

进度轴=已结算订单球数；目标区=50-90% 进度，前期=0-50% 进度，收尾 90-100% 不参与卡点。

| 维度 | 高手线（strong，默认） | 菜鸟线（novice） |
|---|---|---|
| 曲线来源 | 高手档按球暂存曲线 | 菜鸟档按球暂存曲线 |
| 中后期卡点 | 目标区最高 **10%** 窗口平均暂存 **≥4** | 同左（**不变**） |
| 前期窗口宽 | **5% 球数** | **5% 球数** |
| 前期上限（绝对） | 前期最高 5% 窗口平均暂存 **≤4.2**（>4.2 判前期峰值前移） | 前期最高 5% 窗口平均暂存 **<3.5**（≥3.5 判前期峰值前移） |
| 设计意图 | 高手略能扛一点前期压力，但仍禁止前期跳升 | 真实低水平玩家前期暂存到 3-4 就大量失败，故更严格 <3.5（前期必须明显低难度） |

> 变更说明：高手档原"相对规则"（前期反超目标区才算前移）已**废弃**，改为与菜鸟同形态的"前期 5% 窗口绝对上限"规则，只是阈值更宽（≤4.2 vs <3.5）。目的：**全部关卡生产时前期压力都不出现跳升**。中级(mid)暂沿用高手口径(≤4.2)，待细化。

判定逻辑（统一）：

- 有效卡点 `capPointValid = zoneAvgBuf ≥ 4`（所有档一致，10% 窗口）
- 前期峰值前移 `earlyViolation`：前期最高 **5%** 窗口平均暂存超过该档上限即为真
  - 菜鸟：`earlyAvgBuf ≥ 3.5`（前期必须明显低难度）
  - 高手 / 中级：`earlyAvgBuf > 4.2`
- `compliant = capPointValid 且 !earlyViolation`
- 趋势符合（兜底合格）= `!capPointValid 且 !earlyViolation 且 zoneAvgBuf > earlyAvgBuf`

> 为什么前期用 5% 窄窗口取"平均"而不是"整段峰值"：窄窗口的平均对短促前期小高峰高度敏感，等价地把短峰也卡掉，又避免单点噪声误杀。已验证：前期一个 2 球的暂存=4 小高峰，10% 窗口被稀释（均 2.5），5% 窗口能抓出（均 4.0）。

## 5. 不变项（明确边界）

- 求解器档位参数 `PLAYER_TIERS`（前瞻/误触/均匀管道/重玩上限/权重）不变——拟合真实玩家靠“评估口径”，不动求解策略。
- 暂存死亡阈值 `BUFFER_LIMIT=7` 不变（它只是求解规则）。
- 全知最优版逻辑、卡死检验逻辑不变。
- `server.js`、单关网页分析调用 `analyzePlayerSolution` 不传档位 → 默认 `strong`，行为不变（向后兼容）。

## 6. 与真实玩家数据的对应（菜鸟线的依据）

来自 108-160 关真实表现 + 求解器批量分析的拟合结论：

- 真实玩家在求解器暂存 **2-3** 时，该进度段的条件失败率就已从 ~16% 跳到 35-41%；而高手基准的死亡阈值是 7，二者差约 3-4 个暂存单位。
- 玩家死亡峰值普遍比高手暂存峰值**早 5-7 个进度段**，集中在前 30%。
- 被现网判为“简单/全部通关”的关（如线上 112、117，难度 60 档）真实失败率高达 76-78%、平均重开 10-22 次。用菜鸟线复跑：这两关因“前期最高 5% 窗口平均暂存 ≥3.5”被判**前期峰值前移/不合格**，而旧高手线放行——菜鸟线成功拦下真实卡玩家的关。

## 8. 三遍求解 · 平均判定 · 最好遍导出（消除网页扰动）

为什么三遍：审核档（尤其菜鸟）带 8% 误触，单遍曲线有随机扰动；跑 3 遍既降噪、又让菜鸟误触表现更充分。

- **判合格**：把 3 遍的**逐球暂存曲线按球位平均**（`runPlayerTierAvg` 产出 `ballCurveAvg`），在这条平均曲线上判卡点/前期（`computeDifficultyScore(..., {curveMode:'avg'})`）。平均达标才算合格——稳定，不被单遍运气左右。
- **导出/展示**：从 3 遍里挑**"最好的一遍"**（`_selectBestRun`）——通关、且个体也符合（前期<阈值 且 目标区卡点≥4）的几遍中**前期 5% 窗均值最低**的一遍；无个体完全符合者则取通关里前期最低。客观难度、曲线质量、卡点、路线、压力曲线全部用这一遍自洽计算（`computeDifficultyScore(bestRun, ...)`），保证展示自洽且前期是三遍里最干净的（其前期必 ≤ 平均，因而过审关展示的前期一定达标）。

### 审核求解数据.json（网页直接复用，零重算）
合格（含"前期偏高挽救"）时，把该关"最好那遍"的解法与自洽结论写进 **`合格关卡/审核求解数据.json`**（单独文件，不污染上线关卡）：

```
{ "<合格关卡文件名，如 066_56.json>": {
    "auditTier": "novice",
    "solve":  { pickOrder, stepBufferHistory, stepElimHistory, stepResidenceHistory, 及各项指标 },
    "score":  <computeDifficultyScore 的完整输出：难度/曲线质量/卡点/compositeCurve 等>
} , ... }
```

- key = **合格关卡文件名**（排序关卡后续重做，暂不依赖）。
- 网页（求解器 `app.js`）导入这个 json + 对应合格关卡后，点"模拟玩家"会**直接用导出的那遍解法渲染路线/暂存曲线/卡点/难度，不再临时求解**（彻底消除"网页重新求解→随机误触→和审核不一致"的问题），并标 `📋来自生产审核(未重算)`。点击其它档仍按需现算。无该 json 的旧关卡回退临时求解（向后兼容）。
