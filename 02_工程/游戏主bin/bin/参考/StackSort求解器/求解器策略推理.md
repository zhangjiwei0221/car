# StackSort 求解器 — 策略推理（活文档）

> 与设计者逐步对齐的求解策略原则。求解器目标：用"玩家最优策略"求解关卡、估计理论最少步数、评估难度。
> 当前实现状态见末尾「实现进度」。本文件随推理持续更新。

---

## 核心架构原则

### 原则 A — 状态分发 + 策略方法库（★刚性分发，不是打分）
不要把所有逻辑揉进一个打分函数（旧做法，已证明错误：调权重会此消彼长、互相打架）。
正确做法：
1. 把每个策略做成**独立可调用的方法**（直接扒拉有用色 / 中转周转 / 中转列扩展 / 万能牌容错 …）。
2. 求解器**先检索障碍类型 → 障碍分发**，识别当前局面状态，再**分发**到对应策略。
3. **混合障碍关：必须优先执行障碍分发，刚性执行对应策略，绝不用"打分加权"去凑。**
   打分会被各种权重互相污染（实测：给石墙相邻列 +30/−8，纯策略只 +1 关却让平均步数变差，
   且解不了 L89）。所以障碍状态下是**确定性流程**，不是 score 加减。
4. 这样能逐步搭出一套**策略体系**，让求解器走向"万能求解"。

> 反面教材（已回退）：曾在 chooseRoutingMove/chooseTransit 里加 `unlocksRock` 的 +30/−8 加权。
> 结论：打分微调是错的工具，障碍必须走分发 + 刚性策略。

### 原则 B — 预期列锁定（commit）要分状态，不能一上来就锁死
**名词解释**：`commit[列]=某色` = 求解器给某列打的"我打算把这列做成这个颜色"的标记；
打了之后手里抓到该色就往这列送。**硬锁** = 一旦打标记就永不改（旧做法，挖坑）。

**分状态规则（设计者细化）**：

1. **全局无障碍 / 只有低难度障碍 → 无脑锁预期列**（最初逻辑：哪列某色占比多就定哪色）。
   - 低难度障碍 = **问号(?)、捆绑(Linked)**：不锁颜色供给，等同无障碍。

2. **有高难度障碍（冰块/石墙/限定色等，会锁住颜色供给）→ 此阶段不锁列**：
   - 首要：**解锁障碍 + 挤压有效色、完成有效步**；
   - 同色连续只能**顺手放**——仅当这一手**同时还能挤出有效色**时才顺带连一段；
   - **绝不能因为"顶部连了一段同色"就把这列锁成那色**。否则障碍未解时该列有效色可能已用完，
     提前锁列会一直往这列灌"此刻是无用色"的同色 → **死循环**（L16/49/89 的坑根源）；
   - 硬判据：**若某列已没有有效色可挤，哪怕它顶部有连续同色，也要把手牌放到别的列去挤目标有效色**，
     不留恋这列。

> 一句话：锁预期列只在"无障碍/低难度障碍"时无脑做；高难度障碍阶段**不锁列**，
> 改成"哪能挤出有效色就往哪放，同色连续只是顺带"。等障碍清完回到无障碍态，再无脑锁列收尾。

### （旧 B 的描述，保留参考）不锁死目标列（commit 软化）
当前代码把列 `commit` 永久锁定为某色，这是给自己挖坑（后续复杂障碍上尤甚）。
目标列应是**可改判的软提示**，不是硬锁：
- 列进度低（只摆了 1-2 张某色）时，若更优的有用色更该占这列，可**改判**该列目标色；
- 行数少时改一列主导色成本低，更应允许随时替换；
- 列已摆很多同色、接近完成时才趋于稳定。
（具体改判触发条件结合后续障碍继续推理。）

## 状态分发：已定义的状态

### 状态①：无障碍状态 → 贪心解法
**判定**：场上**所有障碍已清除**（或本就无障碍）。
**注意**：**问号(Surprise) 关也算无障碍状态**——问号只是视觉遮挡，不限制可点动作、不锁颜色；全知版直接读真实色，所以等价于无障碍。
**策略**：直接贪心，快速锁定颜色列——靠近顶部、该色占比多的列定为该色目标列。
但"放哪一列"必须按下面的「有效步评估」来选，不是简单按"该色总数最多"。

### 状态②：含锁色类障碍（冰块 / 限定列 / 后续 石墙·锁定列·保护列）
颜色被锁 → 出现"事实杂色"（可达数 < 行高、当前凑不满一列）。
**策略**：盯住"有用颜色"（可达数 ≥ 行高），优先完成它们去解锁障碍；事实杂色走中转。

### 状态③：大量杂色 / 无用色的难关
**策略**：启用完整中转逻辑（见「中转分级」）。

## 障碍决策状态 + 障碍优先级权重

检索到场上障碍类型后，进入**障碍决策状态**：按"解锁价值"给列排优先级，先做最该做的解锁。

### 优先级权重（已定，持续补充）
1. **石墙的相邻列 = 最高优先权重**。因为石墙靠"左右任一相邻列完成"解锁，
   完成它的相邻列是打开局面的钥匙。
2. **相邻列若是限定颜色列 → 更优先完成它**：限定列目标色是确定的（强制只收该色），
   填它最可预测、最容易凑成完成，从而解锁石墙。

### 典型组合：石墙 + 相邻限定颜色列（如 L89）— 刚性流程（不是加分）
**检测**：扫描障碍 → 发现"石墙 + 相邻限定颜色列"组合 → 进入该组合的专用策略。

**对限定颜色列的本质认识（设计者 B）**：
> 限定颜色列 = 一个"目标色已知、其它所有色都是该列无用色、且本身无锁"的普通列。
> 不需要单独加权——同时去推进两个限定列的完成都是有效进度。
> （所以求解器把限定列当作"已锁定目标色的普通列"对待即可，不必特殊打分。）

**先做哪个限定列的判据（设计者 A，软优先）**：
- 扫描两个限定色在**全场所有坐标的 y 平均值**；
- 坐标以顶部为 (0,0) 起算时，**y 平均值越大 = 越靠近底部 = 越容易被挤出 = 越好完成**；
- 优先专注完成"目标色更靠底部"的那个限定列（但只是软优先，两个一起推进也行）。

**执行**：路上手里遇到某限定色就放进它的列；**杂色用来挤压**（把目标色顶上去、同色连续）；
完成限定列 → 解锁相邻石墙 → 转无障碍贪心收尾。

## 关键修正：列选择按「有效步」评估，而非"该色最多"

手里是有用色 C 时，选放哪一列，要算**这一手能产生几个有效步**：

**反例**：某列 C 占比多，但分布分散——顶部 1 个、中部 1 个、倒数第二行 1 个。
把 C 放该列顶部，**即时有效的只有"顶部那个 + 刚放入的 C"**；中部/底部那两个 C 被杂色埋着，
还要额外花步数把上面的杂色挤出去才能连上——**它们不是即时有效**。
而若 C 放到**另一列**，可能实现"顶部有效 + 挤出的底牌也是有用色（下一手能用）"= **2 个有效步**。
（"为把某列的同色循环挤出去"这种走法，本身只算 1 个有效步。）

**有效步评估的三要素**：
1. **顶部同色连续段的增长**（即时有效）；
2. **挤出的底牌是否有用色**（有用 → 再赚一个有效步，2-for-1）；
3. **被埋的同色不算即时有效**（要额外清杂步才能连上）。



> 现有 `topConcentration`（顶部聚集加权）方向对，但不够：它没区分"即时有效的顶部连续段" vs
> "被埋的同色"，也没考虑"挤出底牌是否有用"。列选择应重写为完整的「有效步」评估。

## 中转分级（原则A 的一个分支，难关用）

- 中转列：手里是杂色/无用色、暂无好归属时，丢进一个周转列换出底牌。
- **枯竭判定**（设计者核心）：看中转列**底部还能不能吐出有用色**。底部反复吐杂色 =「杂色进杂色出」死循环 = 该中转列枯竭。
- **临时扩展（✅ 已实现为决策模式 `gatedX`）**：中转列枯竭、陷入"杂色→杂色"空转时
  （连续 ≥行高 步无新完成且手牌仍杂色），临时征用一个"埋有较多有用色 / 底牌有用"的列做中转
  （丢杂色进去把有用色顶出来，会打乱该列，但恢复挤压目标色的进度）。见 solver.js 的
  `chooseTransit(expandTransit)` + `solveOnce` 的 `junkStreak` 触发。
- 简单关不启用中转，直接扒拉有用色即可。

---

## 万能牌(Rainbow)相关
- 不参与列完成判定，最终必须挤进暂存区（列里有万能牌即未完成）。
- 自动扶正：列内只剩 1 张非主色卡（异色或万能）且不在底部、且暂存是该列主色时，系统自动把它挪到底部，玩家 1 步收口。
- 多限定列僵局时：优先把万能牌丢进限定列做容错（挤出底部杂色、多一步周转）。

## 决策分发框架（方案2，已实现骨架）

**思路**：求解极快（毫秒级），所以不纠结单一策略——把每种"决策模式"都跑几遍，取能通关且最短的；
按"障碍组合标签"记住该类型的胜出模式，下次同类型优先用。这就是走向"万能求解"的骨架。

**组成（solver.js）**：
- `obstacleTag(state)`：给关卡打标签 = 障碍组合 + 尺寸桶，如 `Ice+Rock@8x7` / `plain@5x5` / `Surprise@6x6`。
- `DECISION_MODES`：**决策模式注册表（可扩展）**。当前五个：
  - `gated`：高难度障碍(冰块/石墙)在场时**全场不锁预期列**（省步、容错，治 L16 类）；
  - `always`：一律锁列（个别关更短，治 L89 类）；
  - `dual`：双色块优先(不锁列)——把底层色灌进"含该双色块的列"尽快触发转换；
  - `dualLk`：双色块优先 + 锁列；
  - `gatedX`：gated + **中转列临时扩展**（杂色空转时征用埋有有用色的新列破局，治空转难关）。
  - **★ 后续新障碍若引入共用决策逻辑，在此注册新模式即可，框架不改。**
- `solveTagged(state)`：打标签 → 跑所有模式取最优 → 记忆胜出模式（`decisionMemory[tag]=mode`）→ 下次优先。
- `bench.js` 已接 solveTagged，输出"标签→胜出模式"统计，便于看规律与 A/B。

**当前规律（跑分产出）**：plain/Surprise/Link 多为 `gated` 胜出；Rock 小盘偏 `always`；大盘混合。

> 持续对齐原则：后续所有障碍，凡与已有决策共用的部分（锁列与否 / 有效步 / 中转 / 障碍优先级），
> 一律接入这套 `DECISION_MODES` + 标签框架，不另起炉灶；新障碍专属决策注册为新模式 + 新标签。

## 障碍：双色块（Intertwined / DualColor，高权重，第55关解锁）

**机制**：一个块含两种颜色——**底层**(待完成的目标色) + **顶层**(随机杂色遮盖)。
只有**先完成底层颜色**，底层才被消除，届时**顶层颜色自动替换成该列的牌**。
相当于一个**悬浮功能**：在最大列数基础上多了"悬浮的 1 列"（顶层是延后才生效的另一套牌）。

**策略（高优先级）— 已实现为决策模式 `dual`/`dualLk`**：
1. 遇到双色块 → **优先把底层色灌进"含该双色块的列"**，尽快完成→触发转换（`dualBottomCount` 加成）。
2. 挤压**顺序**讲效率：理想还应算"当前双色块放某位置是否利于解锁后顶层排序"——**这一步(转换后顶层规划)尚未做实**，是 L79 仍超步数的原因。
3. 解锁后顶层并入该列 → 局面回常规态，按有效步/分发继续。

**实测**：6 个双色块关解出 5 个（L55/56/59/72/99）；**L79(Dual+Ice) 仍超步数上限**
（138 步 vs 100，需"转换后顶层规划"深度策略，待做）。

## 障碍：锁定列（Key + Lock，第65关解锁）

**大白话机制**（设计者确认）：
- **锁(Lock)**：挂在某张卡上。**只要某列里有一张带 Lock 的卡，整列就被锁住**——不可点、不参与完成判定。
  与冰块/石墙不同：**锁定列的颜色是可见的**（不隐藏），只是不能操作。
- **钥匙(Key)**：挂在某张卡上。**当这张钥匙卡被转到它所在列的底部时，钥匙消失，并把"从左到右第一个仍被锁的列"解锁**（剥离那列的 Lock，恢复成普通列）。
- 多把钥匙/多个锁：每把到底的钥匙解锁一个（最左的那个锁）。比双色块宽松——只要 key 到底即解锁。

**数据格式**：Key / Lock 都是**卡片级特性**（`cell.features` 含字符串 `'Key'` / `'Lock'`），
parser 已自动捕获，grid/列级特性为空。出现在 L65/66/67/72/73/77/78。

**引擎实现模型**（`js/engine.js`）：
- `keyLockedCol(state,c)`：列里有任意一张带 'Lock' 的卡 → 该列锁定。
- `isBlocked(state,c) = isLocked(冰块/石墙) || keyLockedCol`：统一"不可点/不完成/不扶正"判定。
  注意与 `isLocked` 区分——`isLocked` 仅指**需隐藏渲染**的障碍(冰块/石墙)；Key-Lock 不隐藏，单独走 `keyLockedCol`。
- `resolveKeyUnlock(state)`：每步结算扫描各列，若**底部卡带 'Key'** → 剥离该 Key + 找最左被锁列剥离其 Lock。
  解锁/钥匙消失 = **剥离特性、卡变普通色卡，不删卡**（保持 K×H 守恒）。在 `move()` 的 `revealSurprises` 之后调用。

**求解策略**：
- Key-Lock **锁住颜色供给**（锁定列里的色暂时取不到）→ 归为**高难度障碍**：
  `hasHiddenObstacle` 计入 keyLocked → 触发 `gated` 模式（障碍期全场不锁列，容错优先）。
- `analyzeColors` 把锁定列的卡当作**不可达**（计入 frozenHidden，不计 reachable），与冻结列一致——
  避免把锁定列里的色误判为"有用色"。
- 钥匙列本身是普通可点列，求解器正常点击它即可把钥匙逐步压向底部触发解锁，无需额外刚性流程。
- `obstacleTag` 加 `KeyLock` 标签，沿用 4 个决策模式取最优 + 记忆。

**实测**：7 个 Key-Lock 关（L65/66/67/72/73/77/78）**全部通关**，均在步数上限内
（如 L65 21/35、L73 68/70、L77 66/85），含与 Surprise/Rock/Ice/Dual 的混合关。

## 障碍：保护列（CoveredColor，第80关解锁）

**大白话机制**（设计者确认）：保护列被盖住（不显色、不可点、不参与完成判定），
**必须先完成一列指定颜色（requiredColor）的消除，才能解锁该列**。类似冰块，只是
冰块按"完成列数"解锁，保护列按"完成指定颜色"解锁。难度不高，走常规障碍优先策略即可。

**数据格式**：列级特性 `columnFeatures` 里的 `{type:'CoveredColor', requiredColor:{colorId,shadeIndex}}`。
出现在 L80/81/82/84/86/88/90/92/97。

**引擎实现**（`js/engine.js`）：
- `coverReq[c]` = 该列要求先完成的颜色 key；`state.completedColors` = 已被完成过的颜色集合
  （在 `registerCompletionEvent` 里登记完成列的统一色，双色块按底层色）。
- `isCovered(state,c)` = 有 coverReq 且该色尚未完成过 → 计入 `isLocked`（隐藏渲染）→ 自动进 `isBlocked`
  （不可点/不完成/不扶正）。某列完成其 requiredColor 后该保护列即解锁，变普通列。
- **★哨兵值处理**：L82/L84 的某保护列 requiredColor = `16_4`，而 colorId 16 **全库从不作为真实色块出现**
  → 判定为"通用保护列"哨兵，按最低门槛解锁（完成任意 1 列即解锁，记作 `'__any__'`）。
  createState 时检测 requiredColor 是否在棋盘存在，不存在即转哨兵。

**求解策略**：保护列锁住颜色供给 → 归为高难度障碍（`hasHiddenObstacle`/`analyzeColors` 计入，
锁定列的色当不可达）→ 触发 gated 不锁列。求解器正常完成有用色即会完成 requiredColor 列、
顺势解锁保护列，无需额外刚性流程（设计者："正常跑障碍优先策略即可"）。`obstacleTag` 加 `Covered`。

**实测**：9 个保护列关（L80/81/82/84/86/88/90/92/97）**全部通关**，均在步数上限内
（含与 Ice/Fixed/Surprise 的混合关，及 L82/L84 的哨兵通用保护列）。

## 障碍：炸弹（Bomb，第100关解锁）

**大白话机制**（设计者确认）：炸弹附在某个颜色块上，**每走一步倒计时 -1**，必须在
倒计时归零前完成该颜色订单（完成一列该色）→ 拆弹；否则关卡失败。只增加时间压力，
无特殊机制，正常优先策略即可。

**数据格式**：卡片级特性 `{type:'Bomb', endCondition:{type:'StepCount', stepCount:N}}`，N=倒计时。
出现在 L100。注意：parser 把 `tile.features` 映射成类型字符串会丢失 N，需单独保留 `cell.bomb=N`。

**引擎实现**（`js/engine.js`）：
- `state.bombs = [{color, remaining, defused}]`，createState 扫描带 `cell.bomb` 的卡，按其颜色建表。
- `tickBombs`：每次 `move` 倒计时 -1（仅未拆除的）。
- `syncBombs`：完成判定后，若 `completedColors` 含该炸弹色 → `defused=true`（永久拆除）。
- `bombFailed`：存在未拆除且 remaining≤0 的炸弹 → 真。并入 `isLose`。
- 按颜色追踪（与炸弹卡后续移动/被挤出无关）——完成该色订单即拆弹。

**求解策略**：`solveOnce` 循环中检测 `bombFailed` 即终止该路径（不算通关）；`solved` 也要求未爆炸。
炸弹色本是有用色，求解器走最短解自然会在倒计时内完成，无需额外刚性流程。`obstacleTag` 加 `Bomb`。

**实测**：L100（Bomb@4x4，倒计时 20/上限 30）通关，11 步，炸弹在剩余 11 时拆除。

## 玩家版求解器（模拟真实玩家表现，`js/player-solver.js`）

> 目的：全知版读得到问号真色，抓不住"问号对人类的认知难度"。玩家版在**不完全信息**下模拟熟练玩家，
> 产出"一次过率 / 平均步数"，用来反推问号(及后续捆绑等软障碍)的难度权重。

### 核心模型（与设计者确认）
玩家版 = **复用全知版全部策略**，唯一区别是决策时**未揭示的问号(Surprise)色被屏蔽**（玩家看不见）。
实现上给 `Solver.solveOnce` 注入两个钩子（全知版默认不传 → 零影响）：
- `observe = maskSurprise`：每步把真实棋盘克隆成"玩家可见视图"，未揭示问号的 colorKey 置空（不归属任何色）。
  `move()` 仍在真实棋盘执行，卡被挤到列底/暂存揭示后玩家自然"看见"（引擎自动剥离 Surprise）。
- 策略开关（由决策模式携带）：`relaxUseful / squeezeUnknown / pseudoWild / antiJunkLoop`。

**铁律**：问号是"软障碍"，**永不改变策略**；硬障碍（冰块/石墙/保护列/锁定列）才是目标。
玩家不记牌、不推断隐藏色、不试错回溯；多轮 `multiSolve` 仅用于统计，每轮内部都是单程推理。

### 四条玩家策略（设计者定，写入决策树，跑全量取最优）
1. **纯问号关 = 无障碍关 → 无脑贪心锁列**（`relaxUseful`）：放宽"有用色"判据——手牌任意可见色都是
   合法锁列目标，往一个未锁列顶部一放就占用为该色目标区。（全知版"可达≥行高"判据是因为它能看见所有副本；
   玩家看不见被问号挡住的副本，故放宽。）
2. **问号 + 硬障碍 → 障碍优先 + 无块时降级挤压问号**（`squeezeUnknown`）：先用场上可见的"有用块"
   推进硬障碍（完成可达色去解冻/解锁）；当**没有任何≥行高可完成色**时，才降级去挤压问号揭示信息。
3. **顺手连色防杂色循环**（`antiJunkLoop`）：可顺手做连色铺垫，但若该连色列已是"杂色循环"
   （手牌无用 + 底牌无用 + 无被埋有用色），延长连色只会让下一张底牌仍无用 → 空转，故不再连色。
4. **伪万能中转块**（`pseudoWild`，全局顶级策略）：中转列耗尽（`expandTransit` 触发）且手牌为杂色时，
   把这张杂色**停进一个"已锁列、顶部纯连色、连段≥H/2、连段以下全为非目标色"的列**。代价是顶部插了 1 张异色，
   但挤出的底牌(可能有用)是进度，且该列变成"仅 1 张异色"——后续喂主色时引擎的**自动扶正**会把这张异色
   瞬移到底部、下一颗主色把它挤出，**免费清除**。净省 1 步中转容错。
   - **只准进 1 张杂色**：停入后该列顶部已非目标色 → 不再满足条件，天然杜绝第 2 张（≥2 张会破坏自动扶正、锁列失效）。

### 决策模式（`playerModes(state)`，multiSolve 全量跑取最优）
- 非问号关 → 原 5 个全知模式，与全知版零偏差。
- 纯问号关 → `greedyG / greedyA`（贪心 + gated/always 锁列；公共开 pseudoWild+antiJunkLoop+expandTransit）。
- 问号+硬障碍 → `obstG / obstA`（障碍优先）+ `greedyG / greedyA`（贪心兜底）+ `dualG`，取最优。
- **实测最优普遍是 `greedyA`（贪心 + always 锁列 + ③④）**；`greedyG`（gated）在有硬障碍时不锁列 → 贪心失效，常 0%。
