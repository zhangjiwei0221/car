# StackSort 关卡难度评分体系（活文档）

> 配合 `analyze.js` 批量分析使用。难度 = 关卡内在复杂度 + 步数外力施压，两者综合。
> 评分透明、参数集中，便于持续调参。

---

## 一、输出字段（analyze.js → 关卡分析结果.csv）

| 字段 | 含义 |
|------|------|
| 关卡 / 尺寸 / 颜色种类 | 基础信息 |
| 障碍组合 / 障碍分级 | 出现的障碍类型 + 分级（简单/中等/困难 · 单一/组合） |
| **最优步数** | 多模式多轮求解的最少步数 |
| **平均步数** | 所有成功求解轮次的平均步数（反映稳定性/分支多寡） |
| 成功率 | 成功轮次 / 总轮次（越低=越难稳定解，侧面反映难度） |
| **步数上限** | 关卡给定的 StepCount |
| 容错 / 容错率 | 上限−最优 / (上限−最优)/最优 |
| **难度分 / 难度等级** | 0~100 综合分 + 等级 |
| 难度构成 | 行/障碍/压力/颜色 四项的分项得分 |

---

## 二、难度模型

总分 = 各分项归一到 0~100，按权重合成。**权重：障碍 > 步数压力 > 求解表现 > 行数 > 颜色**。

```
难度分 = 障碍×0.30 + 步数压力×0.25 + 求解表现×0.18 + 行数×0.17 + 颜色×0.10
```
（无求解数据时按旧四项归一：障碍0.35/压力0.28/行0.25/色0.12）

> **为什么加"求解表现"**：障碍的**数量/参数**（冰块解锁列数、炸弹步数、石墙数量、障碍叠加）
> 对难度的真实影响，单看"障碍类型组合"抓不住——但会体现在求解器表现上（障碍越多/越狠
> → 成功率越低、平均步数越离散）。所以引入这一项，让障碍数量/参数自动计入难度。
> 局限：全知求解器读得到问号/隐藏列真值，**抓不住问号/遮挡列对人类的认知难度**（待后续）。

### 1. 行数项（权重 0.35，最高）
- **行数大 = 容错低**：犯错要花更多步把卡重新挤到顶部，所以行高是核心难度来源。
- 计算：`(H-3)/5 × 90 + (K-3)/5 × 20`（列数小幅并入，影响小，符合"列数难度影响不大"）。

### 2. 障碍项（权重 0.30）
- **分级**：
  - 简单（推理/时间压力，不锁颜色供给）：问号=密度权重(见第八节)、捆绑 5、炸弹 6
  - 中等：限定色 6、双色块 14
  - 困难（遮挡列，需前置条件）：冰块 12、石墙 13、保护列 12、锁定列 13
- **组合加成**：障碍种类 >1 时，每多一种 +8（组合障碍更难）。
- 累加后 ×2.4 截断到 0~100。

### 3. 步数压力项（权重 0.22）—— 核心外力施压
- 容错越小越难。**绝对容错**与**容错率**双指标，取更施压的一项：
  - 绝对容错 margin = 上限−最优：≤2 步=极限(100)，每多 1 步 −7，≥15 步≈无压(0)
  - 容错率 ratio = margin/最优：≤5%=极限(100)，≥60%≈无压(0)
- 这样既体现"极限关只给 2-5 步"，也体现"简单关给极低绝对容错也会拉高难度"。

### 4. 颜色项（权重 0.10）
- **颜色种类 / 列数** 比值：
  - =1（每色恰好一列）→ 最复杂(100)
  - <1（某色占多列，目标颜色复杂度降低）→ 越低越简单
- 符合"一色多列降低难度"。

### 5. 求解表现项（权重 0.18）—— 反映障碍数量/参数
- 由求解器多轮表现得出（与最终步数上限无关）：
  - 失败率 = 1 − 成功率（越高越难）
  - 步数离散 = (平均步数 − 最优步数) / 最优步数（越散越易走错）
- `求解表现 = clamp(失败率×65 + 离散×90, 0, 100)`
- 障碍越多/越狠 → 求解越易失败、步数越散 → 此项越高。这样障碍**数量与参数**自动计入难度。

### 生成器：用步数余量对齐目标难度
- 棋盘+障碍固定后，**内在难度（障碍/求解表现/行/色）已定，只有步数压力可调**。
- 生成器据此扫描步数上限 ∈ [最优+1, 最优×4]，找让难度落入目标区间、且最接近区间中点的步数。
- 若该棋盘任何步数都进不了区间（内在难度地板过高/天花板过低）→ 换棋盘重试。
- 效果：在可达范围内**精准把难度调到设定阈值**；简单阈值需配简单参数（小盘/少色/无硬障碍）。

### 等级阈值（可调）
`简单 0-30 | 普通 31-60 | 困难 61-80 | 极难 81-100`

## 六、障碍内部权重标定（A/B 实验）

工具 `calibrate.js`：固定基底（取实验关卡 100 关的行列中位数 = **7×7 / 7 色 / 乱序**），
遍历某障碍的"数量×参数"组合，每组合生成 N 个可解关、每关多轮求解，统计求解器表现反推难度。

### 冰块(Ice) 标定结果（7×7 基线：最优 43.5 步 / 成功率 100% / 离散 1.6）

> ★关键：早期"高冰块全无解"是**生成器脏数据**——随机撒冰块把某色副本锁进冻结列，可达区
> 凑不满该色→永远完不成足够订单解锁。修复：生成时**保证 `durability` 种"钥匙颜色"完整可达**
> （解锁前必有 ≥durability 个可完成列），其余颜色照常混合（保留难度）。修复后全组合 100% 可解。

| 冰块×步数 | 最优Δ | 成功率Δ | 离散Δ |
|----------|-------|---------|-------|
| 1×1 | +9.6 | −8% | +6.6 |
| 1×2 | +11.6 | **−20%** | +9.3 |
| 1×3 | +11.8 | −19% | +11.6 |
| 1×4 | +9.9 | −21% | +12.8 |
| 2×1 | +9.9 | −9% | +7.4 |
| 2×2 | +12.2 | −20% | +10.1 |
| 2×3 | +11.2 | −27% | +9.1 |

**结论**：
- **步数(durability) 是主导**：1 步仅 −8% 成功率，2 步起骤降到 −20%（解锁前要凑更多订单、容错更低）。
- **数量(count) 影响小得多**：1→2 个冰块成功率仅再降 ~1-2%。
- ★**波动组合**：冰块数量太多时，为保证可解必须留出足够可达完整色 → 可达区变小、推理反而变简单
  （7×7 放 4 冰已饱和回落）。所以冰块**数量取 1-3、步数取 1-4 随机组合**最合理。

### 生成规则（已写入 `generator.js`）
- 冰块关用**区域感知** `buildIceLevel`：正常混合棋盘 + **保证 `durability` 种"钥匙颜色"完整可达**
  （解锁前必有 ≥durability 个可完成列），其余颜色照常混合。
- 生成器 `generateOne`：combo 含冰块 → 数量随机 **1-3**、步数随机 **1-4**（可被显式指定覆盖），
  durability 自动钳到 ≤ 可达列数。实测 10/10 可解。

### 已落地的冰块内部权重（`analysis.js` 障碍项）
- 每个冰块列 = **4 + (解锁步数−1)×6**（步数权重 > 数量权重，与"步数主导"标定一致）。
  - 例：1冰1步=4、1冰2步=10、1冰4步=22、2冰1步=8、2冰2步=20。
  - 校验排序：1×2(10) > 2×1(8) ✓ 与数据"1×2 比 2×1 难"一致。
- 配合"求解表现"分项（成功率/离散）共同反映冰块数量与步数的真实施压。

> ★生成器同样改为区域感知（`buildIceLevel`：保证钥匙色可达），避免脏数据无解。

> 后续同法标定其余障碍（石墙数量、限定色数量、保护列、双色块、炸弹步数等），逐一替换 `OBS_W` 为内部权重函数。

### 各障碍标定汇总（7×7/7色基线，相对基线Δ；已落地为内部权重）

| 障碍 | 范围 | 标定要点（成功率Δ） | 内部权重（obsRaw） |
|------|------|---------------------|-------------------|
| 冰块 Ice | 数量1-3 / 步数1-4 | 步数主导：1步−8%、2步−20% | 每列 `4 + (步数-1)×6` |
| 保护列 Covered | 1-4 | 1个−10%、2个−18%；3+饱和 | 每列 `7` |
| 石墙 Rock | 1-3 | **最难**：1个−44%、2个−50%；3个饱和 | `14 + (数量-1)×4` |
| 锁定列 KeyLock | 1-3 | 随量升：1个−9%、2个−22%、3个−21% | 每锁列 `7` |
| 限定色 Fixed | 1-3 | **几乎不加难**（成功率±0，全知求解器易处理） | 每列 `2`（极低） |
| 炸弹 Bomb | 数量1-3 / 倒计时0.4~0.9×步数上限 | 紧迫度 + 数量双驱动（回测2026-06，200关）：紧迫度↑成功率↓(urg0→0.44, 0.45→0.06)；数量↑成功率↓(1个0.54/2个0.38/3个0.24) | 每弹 `紧迫度×12` + `数量×5`（紧迫度=(最优−倒计时)/最优） |
| 双色块 Dual | 1-2 底色 | 求解器测≈0(顶层可见)；隐藏依赖=认知难度，求解器盲区 | 每种底色 `12`；**链式 +10** |

**共性"波动"**：遮挡类障碍（冰块/保护列/石墙）数量过多时，为保证可解需留出更多完整可达色 →
可达区变小、推理反而变简单（饱和回落）。所以这类障碍**数量取 1-3 最有效**；饱和由"求解表现"项自动修正。

### 嵌套依赖（避免区域感知导致过简单）
区域感知把"钥匙色"全放自由区会让关卡偏简单。**嵌套依赖**反过来把"可解部分嵌进下一个障碍内"，形成
"必须先解 A 才能解 B"的依赖链，在保证可解的前提下提升难度：
- **保护列链（已实现 `buildNestedCoveredLevel`）**：cover_i 的需求色 = cover_{i-1} 列持有的色 →
  完成 R_1(自由)→解锁持 R_2 的保护列→R_2 可完成→解锁持 R_3 的…无环链，**100% 可解**。
  难度模型检测"某保护列需求色=另一保护列持有色"→ 判定链式，**+10** 认知加成。generateOne 在 ≥2 保护列时随机启用。
- **冰块/石墙同理（设计，可扩展）**：冰块按解锁所需"完成列数"分层（低步数冰块的内部含解锁高步数冰块
  所需的色）；石墙按相邻完成顺序分层。**限制**：每个被锁列仅 1 列容量 ≈ 1 种色，故依赖跳跃受列预算约束
  （如"1步冰块直接含4步冰块全部前置色"需该列容纳 3 列色，不可行）→ 依赖链宜按相邻档位逐级嵌套。

**生成规则**：各障碍均做**区域感知/可解性保证**生成（`generator.js`：buildIceLevel / buildCoveredLevel /
buildBombLevel / buildRockLevel / buildFixedLevel / buildKeyLockLevel / **buildDualLevel**），并接入 `generateOne`（按 combo 触发，
数量/参数按上表范围随机）。实测全部障碍生成 8/8 可解。

**双色块机制（设计者确认）**：底色 X 占满 1 列份量(H个)的双色块、散布盘面；每个双色块顶层借用一个
在场色 Y。完成 X 列 → 转换 → 那 H 格变 Y、Y 补足为整列（X 腾出 1 列、Y 多 1 列，总列数守恒）。
本质走底色逻辑可解。生成 `buildDualLevel`：选占 1 列的色作底色、顶层=另一在场色，配平可解（100% 可解）。

**链式双色块（局部难度增强）**：≥2 个双色块时，让一个双色块的**顶层 = 另一个双色块的底色** →
完成前者才释放更多后者，形成"必须先消一个才能解另一个"的依赖纠缠。仍 100% 可解（平衡守恒）。
求解器(全知)感受不到该依赖，故按认知难度在难度模型里 **+10**。生成器 2 底色时随机启用链式。

## 七、调参建议

- 觉得"困难"占比过高 → 调高等级阈值，或降低行数项权重/斜率。
- 想强化"步数施压"主导 → 提高 pressure 权重（如 0.22→0.30），相应降行数。
- 障碍权重表 `OBS_W` 可按实测体感单独微调（如双色块更难可调高）。
- 各分项与权重集中在 `analyze.js` 顶部 `WEIGHTS` / `OBS_W`，便于 A/B。

## 八、问号(Surprise)难度标定 —— 玩家版 A/B（认知难度）

> 全知求解器读得到问号真色 → 测不出问号难度（best 不变）。问号是"软障碍"：不改变棋盘可解性，
> 只屏蔽玩家可见颜色。所以问号难度必须用**玩家版求解器**（`js/player-solver.js`）在**同一批棋盘**上
> 相对全知版的退化来标定。工具：`calibrate-surprise.js`。

### 标定方法
- 基底 7×7 / 7 色 / 乱序（与其它障碍同基线）。
- 纵向变化"问号密度"= 问号格数 / 总格数（0% → 70%），每档生成 N 个可解棋盘。
- 全知版求理论最优步 best；玩家版在**真实紧余量**预算（上限 = best × 1.12）下求解。
- 指标取**最优模式一次过率**（熟练玩家选定最佳策略 greedyA 后的单次成功率），而非全模式平均。

### 标定结果（N=40/档，runsPerMode=6，紧余量 +12%）

| 问号密度 | 最优模式一次过率 | 相对0%下降 | 步数膨胀 |
|---------|------------------|-----------|----------|
| 0%  | 98% | —    | 1.06× |
| 10% | 93% | −6   | 1.06× |
| 20% | 86% | −12  | 1.07× |
| 30% | 79% | −20  | 1.08× |
| 40% | 72% | −26  | 1.07× |
| 50% | 71% | −27  | 1.08× |
| 60% | 73% | −25  | 1.08× |
| 70% | 63% | −35  | 1.09× |

**结论**：
- 一次过率随密度**近似线性下降 ≈ 0.5 × 密度**（40% 后略饱和）。
- **步数膨胀极小**（1.06→1.09×）→ 问号难度的本质是"**紧余量下的成功率波动/失手**"，
  不是"需要更多步"。步数充裕(无限)时玩家几乎 100% 能解，因为无障碍贪心锁列只需看手牌(永远可见)与列顶。

### 已接线的问号内部权重（替换固定 `OBS_W.Surprise=3`，见 `analysis.js` difficulty 的 Surprise 分支）
> ★已改为【按数量分档加分】（见第 12 条），不再用密度内部回测。下方密度公式作废，仅留作历史。
```
密度 = 问号格数 / 总格数（非空格）
含硬障碍(冰块/石墙/保护列/锁定列) → 问号 obsRaw = round(密度 × 34)   // 混合关：全权重
纯问号关                          → 问号 obsRaw = round(密度 × 18)   // 较低（贪心易解、步数通常宽）
```
- 设计者定调：**问号难度主要体现在"混合障碍关"**（既要解硬障碍又被蒙眼的双重压力）；纯问号关
  贪心锁列即可、步数也给得宽，故系数较低。系数由"成功率下降 ≈ 0.5×密度"标定 + 混合区分。
- 实测落点：纯问号 L8(20%)→障10、L14(43%)→障19、L74(75%)→障34；混合 L39/L73/L90→障 72~84（叠加障碍+组合奖励）。

> 同法可继续用玩家版标定**捆绑(Linked)**等"软/认知"障碍（全知版同样测不出）。

## 九、混合障碍关：玩家版通关率"混合附加分"

> 单一障碍的难度已逐一标定（第六节 + 第八节问号）。但**混合障碍关**的难度无法纯解析加权——
> 障碍组合爆炸、相互作用各异，逐组合标定要海量测试。设计者方案：**在基础难度分之上追加一档分**，
> 由【玩家版在该关真实步数上限下的最优模式通关率】决定，最贴近真实体感。

### 公式（已落地 `analysis.js` difficulty）
```
仅当 障碍种类 > 1（混合关）且提供 playerSucc 时：
  混合附加分 = round(clamp((1 − 玩家最优模式通关率) × 20, 0, 20))
  难度分 = clamp(基础难度分 + 混合附加分, 0, 100)
```
- `玩家最优模式通关率` = `PlayerSolver.multiSolve(st, RUNS).bestModeSucc`，st 用该关**真实 StepCount** 作预算
  → 反映"既要解硬障碍又被问号蒙眼/紧余量"的真实失手率。通关率越低 → 加得越多（最高 +20）。
- 单一/无障碍关不加（已由各自标定权重覆盖）。`analyze.js` 仅对混合关跑玩家版（省时）。
- CSV/控制台"难度构成"末尾以 `+混N` 展示。

### 实测（runsPerMode=15）
- L39 问号+冰块 +混17→84(极限)、L49 冰块+限定色+石墙 +混15→100、L73 锁定列+问号 +混16→100、

### 生成器对齐（已落地）
- `generator.js` 的 `generateOne`：混合关(障碍种类>1)在扫步数前**跑一次玩家版(宽步数)**，
  用 `PlayerSolver.bestModeSuccAt(profile, sc)` 对每个候选步数 sc 查通关率 → 传入 `difficulty` 算混合附加分。
  原理：玩家决策不依赖剩余步数，故一次跑可查任意上限的通关率，**与审核端 analyze.js 完全一致**、且不必每步重跑。

### 步数余量 + 异常检测（已落地，设计者定）
- **去掉锁死容错**：不再用 marginRatio 百分比。
- **步数余量 0~maxMargin【绝对步数】(默认 20)，以最优解为基线**：扫描 `[最优, 最优+20]` 找命中阈值的步数；
  够不着就换棋盘重试（不再用 best×4 的大余量）。难度随步数增大单调下降（压力+混合附加同向）。
- **异常检测**：含问号/混合关跑玩家版，`|玩家最优步 − 全知最优步| > maxSolverGap(默认20)` 或玩家无解 → 判异常、弃用重生成；
  难度基线取两者更小值；分配步数上限须 ≥ 玩家最优（保证玩家能通关）。
- 网页 `index.html` 引入 `player-solver.js`；`app.js` 批量/单关分析与生成传参(`maxMargin`/`maxSolverGap`)同步。

### 多重障碍：可达性依赖生成（已落地 `buildMixedLevel`）
> 设计者方案 B：不另写组合生成器，而是在现有障碍生成逻辑上，**遇多重障碍即生成"可达性依赖"**，
> 复用 `buildLockedLevel` 区域感知底座（可达区 + 锁定区 + 完整 key 色），保证可解。

- 棋盘 = 自由可达区（含足够"完整 key 色"可立即完成）+ n 个锁定列（每列 1 个硬障碍），解锁依赖接到可达性：
  - 冰块(D)：完成 D 列即解冻（D ≤ key 色数）；
  - 石墙：锁定列均匀铺开、紧邻可达列，邻列完成即解锁；
  - 保护列：requiredColor = 某可达 key 色，完成它即解锁；
  - 锁定列：Lock 在锁定列、Key 在可达列（正常玩钥匙到底解锁）。
- 全部解锁后 = 满平衡棋盘 → 必然可解。**问号(软)按密度叠加，不碰 Key/Lock 卡**；限定色可加在可达列。
- `generateOne`：combo 障碍种类>1 且不含 Dual/Bomb/Linked → 走 `buildMixedLevel`（硬障碍链+问号/限定叠加）；
  单一障碍仍走各自区域感知生成器。
- **实测**：buildMixedLevel 冰2+石墙 / 保护+冰2 / 锁定+石墙 各 10/10 可解；generateOne 产出
  "问号+冰块+石墙 8x7"等真混合关，难度带混合附加分、玩家/全知最优步偏离<20、步余量≤20。
- **限制/待办**：Dual/Bomb/Linked 与硬障碍的混合暂未进依赖布局（罕见组合），需要时再扩展 `buildMixedLevel`。

## 十、平均步数脏数据清洗 + 余量自动调节 + 结构权重观察

### 1. 平均步数剔除脏数据（对标余量步数，逻辑清洗）
> 问题：全量跑决策树时，某些障碍组合下个别决策模式**完全失配**，求解步数远超最优（如最优 48、该轮 72/80/90）。
> 这类失效解被算进均值会严重拉高 avg（出现"最优 48、均值 72"），污染"求解表现"分项。

- **清洗规则**（`analysis.js` `cleanAvg(steps, best, maxMargin)`）：以最优步 `best` 为基线、步数余量上限 `maxMargin`
  为标尺，**任何一轮解步数 `> best + maxMargin` 即判为脏数据剔除**，再对剩余解求均值。
  - 逻辑依据：`best + maxMargin` 是该关能给到的最大步数预算；连这个预算都解不进的策略 = 失配，不代表真实难度。
  - 例：best=48、maxMargin=20 → 阈值 68，则 72/80/90 步全部剔除。
  - **非比例清洗**（早期用 `best×2` 是比例近似，已废弃）——改为余量步数的"逻辑边界"。
- 接线：`Analysis.multiSolve(state, runs, maxMargin)` 与 `PlayerSolver.multiSolve(state, runs, maxMargin)` 都按此清洗；
  返回新增 `dirtyRemoved`（剔除轮数）。生成器传 `params.maxMargin`（默认 20），批量分析用默认 20。
- `best`/`successRate` 不受影响（best=最优、成功率按全部轮次算），仅"平均步数"剔除失配噪声。

### 2. 未达目标关：余量自动调节（point 2，已落地 `generateOne`）
- 配置余量区间 `[minMargin, maxMargin]` 内未命中目标阈值时，自动在**硬上限 [0,20]** 内再扫：
  - **超出难度阈值（太难）→ 加余量步数**（更多步、降压力、降难度）；
  - **未达阈值（太易）→ 减余量步数**（更少步、升压力、升难度）。
- 仍命中不了 → 返回最接近(ok=false)由 UI 标红警告（此时多为结构权重过高，见下）。

### 3. ★待优化方向：按障碍组合记忆命中策略（决策树调用优化）
> 当前对**所有障碍组合复用同一组决策模式**，全量跑取最优。某些特殊组合上多数模式失配 → 产生大量脏数据
> （上面用统计端剔除兜底）。**更优方案**：记忆"障碍组合 → 命中策略"映射（类似 `solver.js` 的 `decisionMemory`
> 已对 obstacleTag 做的雏形），按组合直接调用对应策略，从源头避免失配解。
> 当前内存/速度充裕、剔除脏数据已够用，故暂缓；**后续要做策略调用优化时回到这里**。

### 4. ★结构权重观察（L69：best 低却超阈值）
> 现象：L69 限定色×4+冰块(步1/步2)，7×7×7，**best=48、玩家 100% 通关**（明显易解），但即便给到最大余量
> +20（上限 68），难度仍 = 57[困难]。分项：障=72 压=33 为=12 **行=88 色=100** 混=0。

- 根因：**结构性分项接近饱和**——`rowScore` 对 H=7 给 88、`colorScore` 对"满色平衡盘"(色数=列数)恒给 100。
  二者合计 `88×0.17 + 100×0.10 = 25` 的高"地板分"，而真正反映"好不好解"的**求解表现项(为=12)权重仅 0.18**，压不下去。
- 即：**易解的大盘/满色盘有难度地板，求解表现无权把它拉回简单档**。这不是某条权重写错，而是模型对静态结构
  （行高、满色）赋权偏高、对实测可解性赋权偏低的取向问题。
- **候选修正（待设计者确认，未改动）**：
  - (a) `colorScore` 重标尺：平衡盘(色≈列)应为**基准**而非最高分（现恒 100），按"多色挤一盘"的超额部分给分；
  - (b) 让**高可解性反向松动结构地板**：玩家一次过率高 + 余量充裕时，按比例下调 row/color 贡献（最贴合"易解=不难"）；
  - (c) 提高"求解表现"权重 / 降低行数项斜率。
  - 三者都会移动全量分布与等级阈值，属**评分体系级改动**，需先确认再动（遵循"不靠打分乱调权重"）。

### 5. ★已落地：移除颜色项权重（2025 设计者拍板）
- **决定**：直接**移除颜色项**——绝大多数关是满色平衡盘（色数=列数）→ colorScore 恒 100 = 无意义"地板分"；
  少数"一色多列"降难度的情形影响有限、占比小，不值得保留该项。
- **权重再分配**（颜色 0.10 分给 障碍/步数/求解表现，行数不变）：
  - 含求解表现：`障碍 0.34 · 步数压力 0.28 · 求解表现 0.21 · 行数 0.17`（原 0.30/0.25/0.18/0.17/颜色0.10）。
  - 无求解表现：`障碍 0.41 · 步数压力 0.34 · 行数 0.25`（原 0.35/0.28/0.25/颜色0.12）。
  - `parts.color` 仍计算并展示（信息用），但**不计入总分**。
- **效果（L69 验证）**：余量+20 时难度由 57[困难] → **49[普通]**（+0=68极限 / +10=60困难 / +20=49普通），
  步数余量终于能把易解关从极限调回普通；地板由"行(15)+障(24.5)"构成，压力项在 49↔68 间可调，范围合理。


### 6. ★求解表现项重定义（2025 设计者拍板）：全知+玩家"最优解表现"均值
> 旧法用"全模式池化成功率 + 池化均值离散"，会被失配模式（决策树脏数据）污染。新法只看**最优模式**、
> 并融合全知与玩家两个视角，最贴近真实难度。

- **公式**（`analysis.js` difficulty 第 5 项）：
  ```
  每方表现 perf = clamp(失败率×65 + 步数离散×90, 0,100)
    失败率 = 1 − 有效成功率;  步数离散 = clamp((最优模式清洗均值 − best)/best, 0,1)
    有效成功率 = 最优模式成功率×(1−α) + 可行模式平均成功率×α   (α=0.3，"略差"插值)
  求解表现 = ( perf_全知 + perf_玩家 ) / 2     （玩家未跑→玩家=全知）
  ```
- **最优模式**：成功率最高的决策模式（并列取均值步数更优）。`Analysis.multiSolve` / `PlayerSolver.multiSolve`
  均新增返回 `bestModeSucc / bestModeName / bestModeAvg / meanModeSucc`（`byMode` 分模式统计）。
- **"略差"插值 α=0.3**：成功率从"只用最优策略"向"可行模式平均"靠 30%，体现真实玩家不总选最优策略、会失误；
  全知版各模式都强→插值影响小，玩家版模式更分散→插值带来更多"人因"难度，符合实际。
- **基线统一 best**：两方离散都以全局最优步 best 为分母，确保"都是最优解的基线"。
- **脏数据**：离散用最优模式的**清洗均值**（>best+maxMargin 的失配解已剔除，见本节 1）。
- **实测**：L69(限定色+冰块,best48,全知/玩家最优模式均100%) → 为=5（正确反映易解），余量+20 难度=50[普通]；
  L73(锁定列+问号,20%/10%)→为56/难度91、L79(双色块+冰块,10%/10%)→为59/难度100。"为"项在 5-59 间按真实表现区分。
- 接线：`generator.js`(传 playerProf)、`app.js`(批量/逐关/导入，含问号或障碍即跑玩家版)、`analyze.js` 同步。

### 7. ★求解预算与"可玩步数上限"解耦（修复"全知版误报不可解 + 难度不对齐"）
> 现象：生成的 L99(问号+双色块)、L73(问号+锁定列)，难度名标 98，但批量分析只给 86 且"全知版不可解"。
> 排查：剥掉问号后对全知版就是纯双色块/纯锁定列关——用关卡 `stepCount` 当求解预算时全知版 0%，
> 但用**宽预算(999)**全知版能解（L99 best≈78、L73 best≈66，成功率 55-83%）。

- **根因**：批量分析/逐关/导入/analyze 把求解的**移动预算**设成了关卡的 `stepCount`。而全知版在
  双色块/锁定列等关上路由**不如玩家贪心(relaxUseful)高效**（全知 best 常略大于玩家 best、甚至 ≥ 关卡上限），
  于是预算耗尽→误报不可解→`best=null`→无"求解表现"项→难度走无behavior公式而偏低。**生成器本就用 999 预算**，
  所以"生成时对齐、批量分析不对齐"。
- **修复**：求解一律用**宽预算 999**（求解器找最优应与"可玩步数上限"解耦）；难度的步数压力项仍用真实
  `stepLimit`。真最优 `optBest = min(全知best, 玩家best)`（玩家贪心常更高效）。
  已改：`app.js` 批量分析 / 逐关求解(runEditStats) / 导入对齐(importLibraryToGen)、`analyze.js`。
  生成器无需改（早已用 999）。`bench-player.js` 保持 stepCount 预算（其目的就是验证"玩家在可玩上限内能否通关"）。
- **注**：这类硬关难度对求解成功率敏感、低轮数下不稳；审核建议用与生产一致或更高的 runsPerMode。
- **不需要**给全知版加任何问号/逃生策略——全知版看穿问号，这两关对它就是纯单障碍关，只是之前被预算卡死。

### 难度等级改名
- "极限" → **"极难"**（gradeOf 返回值、批量/曲线着色、CSS `.grade-极难`、字段说明同步）。

### 8. ★难度 + 容错率【双限制】合格判定（容错按难度等级对齐）
- 生成器在对齐难度阈值的同时，要求**步数余量(容错)落进该难度等级的目标区间**：
  - 简单(0-30)：**13-20 步** · 普通(31-60)：**9-12 步** · 困难(61-80)：**5-8 步** · 极难(81-100)：**1-4 步**（以最优解 optBest 为基线）。
- **合格(ok=true) = 难度∈[lo,hi] 且 容错∈对应等级区间**，二者缺一不可。
- 实现(`generator.js` generateOne)：在 [0,20] 余量内扫步数，`gradeMargin(score)` 给出等级容错区间，
  取"难度命中 + 容错命中"且最接近 mid 的步数。不合格则换棋盘重试（`maxAttempts` 重随机障碍分布；
  combo 为"默认(true)"时数量也随机）。多轮仍不合格 → ok=false，UI 红行标注原因（难度未达 / 容错N步应X-Z），建议改参数。
- **手动步数余量 [minMargin,maxMargin] 重新生效为【搜索范围】**：调大它会强制抬高步数上限(=optBest+margin)。
  等级容错与手动范围取交集判定合格；交集为空(手动余量超出等级区间)时手动余量优先(只判难度)。
  - 实测：默认 0-20 → 余量按等级(普通 9-12)；minMargin=12 → 余量被强制抬到 12、步数上限随之增大、仍合格。
- 实测：简单/普通/困难各档合格且容错精确对齐；极难需足够强的配置(如 8×8 冰+石墙+保护列)才能在
  容错 1-4 内达 ≥68——弱配置(6×6 单冰块)达不到 → 正确标注不合格、提示改参数。

### 模拟游玩：宽预算求解，避免误报无解
- `runSolve`(模拟界面求解)改用**宽步数预算 999**求解：
  - 解出且步数≤可用上限 → 正常"已求解"。
  - 解出但步数 > 可用上限 → "⚠ 合法可解，但最优 N 步 > 可用 M 步（步数上限偏紧）"——**不再误报无解**。
  - 宽预算下仍无解 → 才判定真·无解/求解器未命中。

### 9. ★一键重生成（不合格自动调参）+ 余量默认按目标等级容错
- **步数余量默认自动对齐**：`genParamForLevel` 中余量默认 = `gradeMargin(目标难度中值)`（简单13-20/普通9-12/
  困难5-8/极难1-4）。优先级：逐关 override → 分组 override → 全局UI(改离 0-20 默认时) → 目标等级容错(自动默认)。
- **一键重生成**（结果表上方按钮 + 模式下拉）：
  - "仅不合格关"：只重生成 `!hit` 的关，先自动调参再生成。
  - "全量重生成"：重生成所有关（不合格关同样先自动调参，合格关重 random 棋盘）。
- **不合格自动调参 `autoFixUnqualified`**：
  - 难度 < 目标 → `nudgeHarder`(硬障碍+1/加新硬障碍/加问号)；难度 > 目标 → `nudgeEasier`(从最难障碍-1/删)。
  - 难度合格但容错不符：余量太紧(撑不住高余量难度)→加障碍；余量太松→减障碍。
  - 并把逐关余量 override 对齐到目标等级容错 `gradeMargin`。
- 单关行内"🔄重生成"仍保留（手调后单关重试）。
- 实测：弱配置(纯问号6)目标困难 → 初难度43不合格 → 自动加冰块 → 难度58-65[困难]容错5-8，全部合格。

### 10. 一键重生成/对齐的细化（2025）
- **一键重生成只改障碍【数量值】，不改障碍组合**：`nudgeHarder` 给数量最少的已有障碍 +1(问号+4)；
  `nudgeEasier` 给数量最多的已有障碍 -1(问号-4)，最少保留 1(问号 2)，**不增删障碍类型**。无障碍则不动。
- **初次调取/导入对齐：自动对齐一次容错**：`autoAlignMargins()` 把每个分组/逐关的步数余量写成其
  目标难度等级的容错(gradeMargin)，在【调取方案 loadSelectedScheme / 导入对齐 importLibraryToGen】时调用一次；
  `defaultGroup` 新建分组时也按目标难度初始化容错。之后手动改难度/参数**不再自动跟随对齐**（余量已是显式值）。
- **难度阈值放宽 ±4**：生成器合格判定 `inBand = score ∈ [lo-4, hi+4]`；结果表"难度未达"警告、
  自动调参方向判定均用同一 ±4 容差。对齐不必太严格。

### 11. 刷新步数余量按钮 + 难度命中【非对称】容差
- **🔄 刷新步数余量** 按钮（生成器顶部）：按当前各组/逐关难度区间，重新调用 `autoAlignMargins()` 把容错
  对齐到对应难度等级。配合"调取/导入时对齐一次、之后不自动跟随"——改完难度区间手动点一次刷新即可。
- **难度命中容差改为非对称**（原则：可以难一点被命中）：合格难度区间 = `[lo, hi+4]`。
  - 向下严格：`< lo`(不够难)不命中 → 收紧、逼生成器用更紧步数把难度顶上去。
  - 向上 +4：`(hi, hi+4]`(难一点)仍判命中。
  - 生成器 inBand、结果表"难度未达"警告、自动调参方向(太易`<lo`加障碍 / 太难`>hi+4`减障碍) 全部一致。
  - 实测：目标 55-65 → 合格难度落 [55,69]，无偏易项。

### 12. 问号难度改为【按数量分档加分】(替代密度回测)
> 起因：密度法下"高难需 70% 密度"在 8×8 即 44 个问号，正常关根本生不出来；且密度权重依赖求解器对玩家的
> 拟合精度（当前算法在混合关甚至不如高手玩家，拟合不足）。故先放宽：按问号【数量】直接分档加分。

- 公式（`analysis.js` difficulty，问号不再进 obsRaw，单独算 `surpriseBonus` 加到总分）：
  ```
  base = clamp(问号数量, 2, 18)        // 纯问号：2-8 低 / 10-14 中 / 14-18 高（上限18）
  纯问号关：  surpriseBonus = base
  混合障碍关：surpriseBonus = clamp(base + round(base×0.6), 2, 30)   // ★额外【加分】(+60%)，非加问号数量
  total = clamp(total + surpriseBonus, 0, 100)
  ```
- **混合关是加难度分、不是加问号格数**（问号数量由生成参数决定，评分只是给更多分）。
- **问号必须偶数生成**：所有放置点(`surprisePattern` / `buildMixedLevel` / `placeObstacles` / `overlayExtras`)都经
  `surprisePattern`，内部 `if(count%2) count--` 强制偶数。
- 实测：纯问号 4/8/12/16→bonus 4/8/12/16、22→封顶18；混合 4/8/12/16→bonus 6/13/19/26(封顶30)，全偶数。
- 待优化（搁置）：求解器对玩家(尤其混合关)的拟合精度——高手不失误时混合关表现可优于全知版最优解，
  算法需更精细；优化难度大，暂以数量分档兜底。

### 13. 稳定性修复：批量生成中断 + 方案存储无限累积
> 起因：导入 40 关后"只有第一关正常 + 下载 ZIP 也坏"、且生成器面板逐渐"打不开"。
> Node 全流程复现（导入 40/40、分组 4 组、生成 40/40、ZIP 40 个唯一文件名）均正常，
> 说明逻辑无误，问题在两处运行时健壮性缺口。

- **批量生成链中断（→ 只剩第 1 关 + ZIP 只 1 关）**：`runGen` / `batchRegen` / `regenerateLevel`
  在 `setTimeout` 链里调用 `SS.Generator.generateOne(params)` **没有 try/catch**。某关（随机障碍分布偶发）
  抛异常 → 整条 setTimeout 链当场断掉，后续关永不生成 → `gen.results` 只剩异常前的关（即第 1 关），
  结果表与 ZIP 都只有第 1 关。**修复**：三处生成调用各包 try/catch，单关异常仅跳过该关、`idx++` 继续。
- **方案存储无限累积（→ 生成器面板卡死/"打不开"）**：每次生成结束 `saveScheme(true)` 自动存档(产)，
  方案数组**无上限**写入 localStorage；积累上百条后，打开生成器时 `renderSchemeSelect` 解析超大 JSON +
  渲染上百 `<option>` 拖垮面板。**修复**：`MAX_SCHEMES=40` 上限，`pruneSchemes` 优先保留手动存档、
  超出按时间丢弃最旧的自动存档；`saveSchemesArr` 配额超限时渐进丢最旧重试；`renderSchemeSelect`
  对历史超限存档**自愈裁剪并写回**（旧版无上限累积的数据下次打开即被瘦身）。
- 经验：所有"逐关 setTimeout 链"必须把单关重活包 try/catch，避免一关坏掉拖垮整批；
  任何"每次操作都写 localStorage"的持久化必须设上限，否则长期使用必然撑爆。

### 14. 方案记忆改为【仅主动保存】+ 删除/清空
- **去掉自动存档**：`runGen` 结束不再 `saveScheme(true)`。方案记忆只保留用户点"保存当前"主动存的方案，
  从根上杜绝"每次生成都写一条"的无限累积（这是之前撑爆 localStorage / 页面卡死的源头）。
- **删除单条**：`deleteSelectedScheme` 加确认弹窗 + 进度反馈（删除后提示剩余条数）。
- **清空全部**：新增"清空全部"按钮(`genSchemeClearAll` → `clearAllSchemes`)，带确认弹窗，一键清空方案记忆。
- 保留 `MAX_SCHEMES=40` 上限与加载即自愈作为安全网（手动存档极少超 40，几乎不会触发裁剪）。

## 待优化需求：隐藏列炸弹（数据已保留，暂不投产）

> 背景：2026-06 给炸弹做了"数量参数 + 倒计时按步数上限挂钩 + 隐藏列两种计时方案"的实现与 200 关回测
> （脚本 `calibrate-bomb.js`，数据 `炸弹回测数据.csv`）。**当前需求端只用"明牌(可达列)炸弹"**，
> 隐藏列炸弹（把炸弹放进被冰块/石墙/保护列/锁定列遮挡的列）**功能底层已实现并保留作储备，但 UI 不暴露、生成不启用**。

**两种隐藏列计时方案（已实现，待投产时再标定权重）：**
1. **独立计时**（`timing: afterReveal`）：炸弹所在隐藏列被揭示/解锁后才开始倒数。引擎 `armBombs` 已支持。
   回测：倒计时取 `0.4~0.6×步数上限`，紧迫度≈0.375、成功率≈0.17。
2. **全局共享步数**（`timing: global`）：开局即随全局步数倒数。倒计时取 `0.8~0.9×步数上限`。
   回测：紧迫度≈0（倒计时＞最优步）但**实测成功率仅≈0.19（很难）**——难度来自"先解锁再拆"的依赖，
   不是紧迫度。

**待优化点（投产隐藏列炸弹时需补）：**
- 现行炸弹权重 = `紧迫度×12 + 数量×5`，**只适配明牌炸弹**。
- **隐藏列·全局炸弹被现行公式严重低估**（紧迫度=0 → 加分≈0，但实测很难）。投产时需新增一项
  **"隐藏列基础分"**（不依赖紧迫度，建议 +8~10/弹），体现解锁依赖带来的难度。
- 隐藏列·独立计时的紧迫度信号有效，沿用紧迫度项即可，可能需再叠加少量解锁依赖分。
