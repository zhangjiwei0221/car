# 数字冰全套逻辑与生产体系说明

> 版本口径：工作区当前代码（2026-09-15）。本文整理正在生效的主链路，并标出退役、实验和历史归档逻辑。代码摘录均来自当前工作区；行号用于回查，后续改动后可能变化。

## 1. 一句话定义

数字冰是叠加在毛线关卡上的按球数倒计时障碍：覆盖线轴后，玩家每拿走一个球，数字冰的 `param` 递减；递减到 0 时 type 7 破碎，线轴恢复可取。

正式版本不是随机撒冰，而是：

1. 先生成无数字冰关卡。
2. 用无冰解法得到 `pickOrder` 和路线进度。
3. 把冰锚定到阶段、关键色和几何咽喉。
4. 用全知/玩家求解器验证，必要时挪冰、摘冰、校正 param。
5. 用关卡级压力曲线决定合格、减压、加压或换球。

目标是同时保证：冰有真实封锁感、管道和开局不被永久堵死、玩家档可通关、难度曲线可控。

## 4. 关卡数据契约

正式落盘的游戏字段只有五个：

~~~json
{
  "toprow": 9,
  "blocks": [[0, 0, 0]],
  "maprow": 10,
  "mapcol": 10,
  "spools": [[{"id": 3, "type": 7, "param": 42, "count": 60}]]
}
~~~

- `id`：颜色/线轴 ID；`id <= 0` 通常为空格、黑块或非球位。
- `count`：线轴容量。
- `type`：单类型或多类型叠加后的打包编码。
- `param`：与 type 对齐的参数；多层时使用求解器的 `typesOfCell / paramsOfCell / packTypeParam`。

| 类型 | 含义 |
|---:|---|
| 0 | 普通颜色球 |
| 4 | 普通冰块 |
| 5 | 锁链 |
| 6 | 问号 |
| 7 | 数字冰 |
| 11-14 | 四个方向的管道 |

数字冰可与问号、锁链叠加，但受 `STACK_MAX_TYPES` 和 `STACK_DEEP_MAX_CELLS` 限制；数字冰与普通冰块互斥，管道格不放数字冰。

数字冰的 `param` 按球数倒计时，不按点击次数倒计时。锁链一步可能拿两个球，所以进度映射也按球数累计：

~~~js
// bin/lib/numice-v4.js:332-347
for (const p of r.pickOrder) {
  balls += (p.chain || p.chainPartner) ? 2 : 1;
  if (p.source === 'pipe') continue;
  const k = p.row + ',' + p.col;
  if (m[k] == null) m[k] = balls;
}
~~~

type 7 的统一增删改实现：

~~~js
// bin/lib/numice-common.js:17-56
function addIce(cell, param, Y) {
  const ts = Y.typesOfCell(cell.type);
  if (ts.indexOf(7) !== -1) return false;
  const ps = Y.paramsOfCell(cell.type, cell.param);
  ts.push(7); ps.push(param);
  const packed = Y.packTypeParam(ts, ps);
  cell.type = packed.type; cell.param = packed.param;
  return true;
}

function removeIce(cell, Y) {
  const ts = Y.typesOfCell(cell.type);
  const i = ts.indexOf(7);
  if (i === -1) return false;
  const ps = Y.paramsOfCell(cell.type, cell.param);
  ts.splice(i, 1); ps.splice(i, 1);
  const packed = Y.packTypeParam(ts, ps);
  cell.type = packed.type; cell.param = packed.param;
  return true;
}
~~~

## 5. 为什么必须先求解、再放冰

旧生成器路径是随机选格，再随机/区间赋 param。大量冰在自然拿到该球之前就破碎，成为无感装饰；param 过大的冰又会变成永久墙。

当前路径是：

~~~text
无冰盘面 -> pickOrder -> natural[格] = 该格被拿走时的累计球数
          -> 目标进度点 P
          -> 仅在 natural 明显早于 P 的格子盖冰
          -> 锁定跨度 = P - natural
~~~

`NUMICE_LOCK_FRAC`、`NUMICE_PARAM_CAP_FRAC`、`NUMICE_RESERVE` 分别控制最小封锁跨度、总球数安全上限和开局保留球。生成器侧随机撒冰开关 `NUMICE_GENERATOR_PLACER` 默认必须为 0，正式分支使用 `NUMICE_PLACER=path`。

## 6. 路线进度与管道安全区

### 6.1 稳定进度图

`numice-zone.js` 的 `stableProgressMap` 对玩家档运行多轮带噪声求解：

1. 每轮要求通关并取得 `pickOrder`。
2. 按累计球数记录每个格子的到达进度。
3. 只保留至少在半数成功轮次中出现的格子。
4. 对同一格取中位数，形成 0-1 进度图。

它用于窗口/关键色策略，不等于最终带冰后的真实路线。

### 6.2 管道安全区

`last` 闸门下，出口初始球和队列必须全部取完才激活四邻；出口四邻或出口外通路被冰封，会形成“闸门 + 冰环”双重锁。因此候选排除管道格、出口格和出口环。

~~~js
// bin/lib/numice-zone.js:222-272（核心语义）
const exitRing = opts.exitRing || 'quad';
for (const p of pipes) {
  bad.add(p.r + ',' + p.c);
  bad.add(p.er + ',' + p.ec);
  if (exitRing === 'quad') {
    for (const [dr, dc] of [[-1, 0], [1, 0], [0, -1], [0, 1]]) {
      bad.add((p.er + dr) + ',' + (p.ec + dc));
    }
  } else if (exitRing === 'dir') {
    bad.add((p.er + p.dr) + ',' + (p.ec + p.dc));
  }
}
~~~

~~~dotenv

PIPE_EXIT_CHAIN_ALLOW=1
~~~

主 BIN 默认仍是 `PIPE_GATE_MODE=first`、数字冰默认关闭，不要为了分支实验直接修改主默认值。

## 7. 数字冰放置策略谱系

入口在 `numice-placer.js:91`。策略是不同封锁形态：

| 策略 | 实现 | 形态 |
|---|---|---|
| progress | `numice-placer.js` | 按进度点择格，基础且稳 |
| detour | `numice-strategies.js` | 半墙绕路 |
| cut | `numice-strategies.js` | 单条割线 |
| stagecut | `numice-strategies.js` | 多段割线 |
| zone | `numice-zone.js` | 稳定路线窗口 + 连通簇 |
| keyzone | `numice-keyzone.js` | 关键色 + 区域窗口，成熟形态 |
| keyband | `numice-keyzone.js` | 拓宽窗口成带，墙值/开口值梯度 |
| keymesh | `numice-keyzone.js` | 反抱团网格和散点 |
| keyhybrid | `numice-keyzone.js` | 带状、网格和装饰组合 |

### 7.1 v5 `numice-v4` 主路径

默认三条核心带：

- 20%-30%：早期第一道阶段封锁；
- 50%-60%：中段第二道阶段封锁；
- 80%-100%：不直接覆盖后区球，使用 `enclose` 包围后区入口。

后区直接盖冰常因末行、安全区、边缘禁放而无候选，包围入口更符合“切断去后区的路”。

~~~js
// bin/lib/numice-v4.js:35-53, 59-77
const STRATEGIES = ['band', 'lock', 'lockOpen'];
const DEFAULT_BANDS = [
  { lo: 0.20, hi: 0.30, margin: 5 },
  { lo: 0.50, hi: 0.60, margin: 10 },
  { lo: 0.80, hi: 1.00, margin: 16, strategy: 'enclose', encLo: 0.80 },
];

function pickBand(cands, want, adjCount, stillOk, maxAdj) {
  const picked = [], taken = new Set();
  for (let lim = maxAdj; lim <= 4 && picked.length < want; lim++) {
    for (const g of cands) {
      if (picked.length >= want || taken.has(g.k) || !stillOk(g.r, g.c)) continue;
      if (adjCount(g.r, g.c) > lim) continue;
      picked.push(g); taken.add(g.k);
    }
  }
  return { picked, shape: 'mesh' };
}
~~~

`lock` 允许连续直线或一次 L 转折，但禁止 2x2 实心块；`lockOpen` 在连续封锁中插入更早破碎的开口。主策略不贴左右边缘、不放末行，辅助策略可以适度放宽。

### 7.2 辅助 A/B/C/D

- A：窄路/割点附近，挡绕路最少的点；
- B：后区入口、封闭区或咽喉包围；
- C：前区少量引导，受 `openFreeSteps` 保护，避免开局前几步被锁；
- D：空旷区/网格补量，填充封锁纹理和隐形开口。

所有来源共享 `usedCell/icedSet`，并受叠加上限、管道安全区、末行和边缘规则约束。

### 7.3 关键色 `keyzone`

关键色策略的流程：

1. 多轮求解生成稳定进度图。
2. 取窗口内路线格和可放冰邻域。
3. 统计进度不早于窗口下界的颜色容量，取前 `topK`。
4. 从窗口外找捐献格，与封锁格交换 `id/count`，保持颜色总量守恒。
5. 关键格加 type 7；非关键区可加入网格散点、低 param 装饰和开口。
6. 输出关键色锁定比、回退数、挪冰数和验证结果。

`keyband` 拓宽一层形成带状封锁；`keymesh` 强调反抱团网格；`keyhybrid` 混用带和网格。

## 8. param、阶段分布与隐形开口

`NUMICE_PARAM_MODE`：

| 模式 | 语义 |
|---|---|
| random | 区间内随机 |
| same | 全部同值，单一解锁点 |
| seq | 连续递增，像拉链 |
| even | 进度带内等间隔 |
| stage | 切成 K 段，每段一批同值，默认 |

默认窗口：`NUMICE_ZONES=0.40-0.50,0.70-0.80`。窗口通常用下界生成墙值，开口格使用提前 `openGap` 的 param，让同一区域分批解锁，而不是整块同时开。

`param >= 总球数` 的冰永远不会破碎，`NUMICE_PARAM_CAP_FRAC` 默认 0.85。几何割线还要求墙外至少保留 `NUMICE_MIN_ABOVE` 个可达球，并按 `NUMICE_ABOVE_PAD` 留余量。

冰很多时 v4 进入 dense 模式：放宽反抱团保持总冰量，但把主封锁冰的 param 向下取整；装饰冰本来就是低 param，不参与削减。

## 9. 可放置约束与叠加规则

~~~js
// bin/lib/numice-common.js:102-126
return function canIce(r, c) {
  if (r < 0 || r >= maprow || c < 0 || c >= mapcol) return false;
  const k = r + ',' + c;
  if (usedCell.has(k) || safe.has(k)) return false;
  if (!ctx.allowLastRow && r === maprow - 1) return false;
  if (!ctx.allowEdge && (c < edgeCols || c >= mapcol - edgeCols)) return false;
  const cell = spools[r] && spools[r][c];
  if (!cell || cell.id <= 0 || isPipe(cell, Y)) return false;
  const ts = typesOf(cell, Y);
  if (ts.indexOf(7) !== -1 || ts.indexOf(4) !== -1) return false;
  if (ts.length + 1 > maxTypes) return false;
  if (ts.length === 2 && ctx.deepCellsRef && ctx.deepCellsRef.n >= deepMaxCells) return false;
  return true;
};
~~~

默认规则：单格最多 3 层类型；三层叠加格默认最多 3 格；数字冰不盖管道、普通冰、末行和主策略边缘列；不同策略共享已用格集合；关键色捐献格不应被错误地永久禁止放冰。

## 10. 验证、漂移保护与增减压

### 10.1 数字冰内部验证

放冰完成后，先用全知解保证路线存在，再用指定玩家档验证真实压力。失败时：

1. 先移除低价值散点/装饰冰；
2. 尝试把问题冰挪到相邻可用格；
3. 仍不可解则摘掉；
4. 直到通过或冰全部回退。

结果记录 `dropped/nudged/verified`，所以目标放置数和最终保留数是两个指标。

### 10.2 v4 后置校正

`arriveMapReal` 用放冰后真正通关的一轮 `pickOrder` 重算实际到达球数。它不同于放冰前的稳定进度图：前者用于校正 param，后者用于找窗口。

### 10.3 关卡级难度闭环

最终候选至少检查：

- 全知通关；
- 基准玩家档通关；
- 难度分在目标区间；
- 平均曲线合规；
- 前期峰值未前移；
- 目标窗口存在真卡点；
- 管道、结构和卡死验证通过。

失败分类为 `early`（前期过压）、`tooSimple`（无真卡点/难度低）和 `other`。对“只差真卡点”的候选，优先换中后期球颜色再审，升级出真卡点才接受。

## 12. v5 生产驱动

### 12.1 传统结构表模式

`跑生产.js` 按棋盘档枚举容量/线轴候选，worker 执行生成、放冰、求解和修复。物理上限：

~~~text
线轴 = 棋盘格数 + 管道数 × (管道深度 - 1)
~~~

默认使用 K(容量) 曲线反推容量，避免高线轴档用旧常数后实际线轴偏低。

### 12.2 AUTO 一图一关

`--auto` 时图池每张图对应一个全局关号，生成器自动选盘，worker 根据实际棋盘现算数字冰数量/大小档：

~~~bash
cd /Users/wzy/Desktop/kiro/关卡生产自动审核产出包/数字冰分支/生产_v5_100关并行包
node 跑生产.js --auto --imgFrom=1 --imgTo=285 --resume --cand=10 --rep=5 --jobs=9 --budget=600
~~~

多机切图时 `--imgFrom/--imgTo` 是图池 1-based 闭区间，关号用全局序号：

~~~bash
# 本地前半
node 跑生产.js --auto --imgTo=285 ...

# 虚拟机后半
node 跑生产.js --auto --imgFrom=286 ...
~~~

前半产出 001-285，后半 286-570，合并 `关卡JSON` 目录不会产生相对关号冲突。

## 14. 产出诊断字段

`产出清单.csv` 中与数字冰最相关：

| 字段 | 含义 |
|---|---|
| 冰总数 | 最终保留数字冰数量 |
| 核心/A/B/C/D | v4 各来源最终数量 |
| 带1/2/3策略、带1/2/3冰 | 三核心带形态和数量 |
| param最小/最大 | 最终参数范围 |
| 开口 | 提前破碎的隐形开口数 |
| 贴边冰、抱团率 | 几何形态风险 |
| 回退、异常摘 | 可解性保护摘掉的冰 |
| param校正 | 放冰后按真实路线修正的冰数 |
| 减压级/减压削/减压摘 | 过压修复量 |
| 加压级/加压提 | 过简单修复量 |
| 前20%暂存、峰值、前5窗 | 玩家压力曲线 |

排查“玩家容错低、路线少”时，先看管道、可用空间、开口、回退、前20%暂存、前5窗和峰值，再结合具体冰位置和出口环。

## 15. 常见误区

1. 不要重新启用生成器侧随机撒冰；它只用于旧沙盒复现。
2. `NUMICE_COUNT_MAX=0` 是关闭按个数放置，不等于所有窗口策略都不放冰。
3. 不要用一次求解逐格顺序当稳定路线；正式窗口策略使用多轮中位数。
4. param 是球数，不是点击数；锁链一步可能消耗两个球。
5. `last` 闸门下不要把出口四邻当普通候选。
6. 不要为了增加冰数取消末行、边缘和开局保护。
7. 不要把分支基线直接写回主 BIN 默认。
8. 不要只看放置数，要同时看最终保留数、跨度、回退、验证和压力曲线。

## 17. 结论：正确心智模型

~~~text
路线观测 -> 阶段/关键色建模 -> 几何封锁 -> param 倒计时
        -> 管道/开局/叠加约束 -> 求解验证
        -> 挪冰/摘冰/参数校正
        -> 难度曲线验收 -> 反向决定下一轮加压或减压
~~~

任何新方案都应回答：

1. 改变的是候选格、param、管道安全区，还是关卡级增减压？
2. 会不会把无冰进度映射与带冰后的真实路线拉开？
3. 是否保留全知可解、玩家档通关和前期压力闸门？
4. 会在 `产出清单.csv` 中体现为哪些指标？

能在代码和产出数据中闭环，才是有效的游戏性调整，而不是单纯增加视觉数量。
