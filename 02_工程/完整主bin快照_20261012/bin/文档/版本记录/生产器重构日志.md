## P4d · 求解器架构问题定论（前瞻 vs 贪心+噪声重试，实测）
用户质疑：(1) 玩家"暂存空却卡死"是否与"全知可解"相悖？(2) 全知求解为何是贪心而非前瞻？贪心是否纯浪费？
**Q1 结论（非 bug，不相悖）**：0001 卡死快照 —— 暂存空、棋盘剩 2 盒：盒(7,9)色31链组2、盒(7,10)色33链组2+**冰3未化**，两盒同属一条**锁链**且其一带冰。锁链须整组解冻才可取；冰靠"取其它盒推进步数"解冻。玩家贪心/乐观把这条**带冰锁链留到最后**→ 已无其它盒可取以推进解冻 → 锁链永久锁死 → 空暂存死锁。全知按更优顺序在中途取走该冰链故可解。**属顺序诱发锁**（合法关卡、有难度），复活清棋盘残留盒正好救此局。
**Q2 实测（8 个已确认可解候选，solver.js 加 opts.lookahead/maxRetries/timeBudgetMs 覆盖）**：
| 策略 | 解出 | 均耗时/关 |
|---|---|---|
| LOOKAHEAD=1 仅round1 | 5/8 | 230ms |
| LOOKAHEAD=2 仅round1 | 5/8 | 1757ms(7.6×) |
| LOOKAHEAD=3 仅round1 | 5/8 | 9853ms(43×) |
| 默认(贪心LA1+8轮噪声重试) | **8/8** | **435ms** |
| LA2+3轮重试 | 7/8 | 3896ms |
| 贪心LA1+时间预算2000ms | **8/8** | **381ms** |
**定论**：
- 加深前瞻**不提升可解检出**（LA1/2/3 同为 5/8），却贵 7.6×/43×——**前瞻才是浪费**，当前 55×55 用 LA1(贪心)是对的。
- round1 解不出的 3 关靠**噪声重试(随机重启)**救回（轮1/2/3），确定性搜索任何深度都救不了 → **噪声重试是必要机制，不能砍**。
- 真正的浪费 = ① 每轮 listMoves 冗余 floodFill(**已修**) + ② 硬/不可解变体把 8 轮重试跑满(4-9s)。
- **推荐修法：每次 solve 加时间预算封顶(2000~3000ms)** —— 实测 8/8 不降、均 381ms（更快），只截断极贵的 round5-8 与不可解全败。**不改贪心、不动噪声重试、不引入前瞻。**
- solver.js 已加 `opts.timeBudgetMs`/`maxRetries`/`lookahead`(默认保持现状)，待用户拍板预算值后接入 produce/generateFromBlocks 的 solve 调用。

## P17 · 三档优先级排序漏洞修复 + 并行分支澄清 + 《生成器逻辑体系.md》产出（v84 发布）

### 排查结论
- **难度分与合格标准确认已是独立分支**：`evaluateGeneration()` 的 `pass`/`tier` 只读 `chokepointAudit`(压力曲线)；`computeDifficulty()` 是独立调用，不反向影响 `pass`/`tier`。此条无需改代码，只需在文档里显式写清楚（已写入 `生产审核评分体系.md` §4b 开头 + `生成器逻辑体系.md` §6）。

## P24 · 修复后台线程回退双触发导致整批被自动停掉（v91 发布）
承用户反馈："1、批量生产的后台线程无效；2、后台线程无响应就自动停止批量生产了。"

### 根因
- **#2 自动停止（真 bug）**：`genRunViaWorker` 的 `onerror` 回调调用 `genWorkerFallback` 时**没有** `clearTimeout(readyTimer)`。于是 worker 异步创建失败(如 file://)时：onerror → `genWorkerFallback`(结果数=0) → `genRunSync()` 主线程开跑；但那个 4s 的 `readyTimer` 仍在 → 4s 后再次 `genWorkerFallback`，此时主线程已产出若干关 → 命中 `genBatchResults.length` 分支 → `genFinalizeBatch(...)` 把整批**收尾停掉**。表现即"刚生产没几关就自己停了"。
- **#1 后台线程无效（环境）**：核对 worker 依赖的 7 个模块(utils/simulator/solver-strategy/solver/playersim/analysis/generator)顶层均**未**引用 `window/document/localStorage/navigator`(grep 命中的 `opts.window` 是属性名，非全局)，worker 代码本身正确；http:// 下可正常工作。"无效"基本是 file:// 方式打开时浏览器禁用 Worker 所致——Chrome 下 `new Worker()` 直接抛(被 try/catch → 走 else 分支主线程)，Safari 等可能是先创建成功再异步 onerror → 命中上面的双触发 bug。

### 已改（app.js，已发布 v91）
- 重写 `genRunViaWorker`：引入一次性哨兵 `settled` + 就绪标志 `workerReady`，新增内部 `fallbackToSync(reason)`——**只在启动探测阶段回退一次**，回退时 `clearTimeout(readyTimer)` + `terminate` 半死 worker，然后 `genRunSync()` 用主线程把整批**跑完**(不再收尾停批)。`ready/loadfail/onerror/超时` 四条路径都经由 `settled` 收敛，杜绝重复触发。
- `onerror` 分家：未就绪 → 回退主线程；已就绪后才崩溃(极少见) → 用已产出关卡 `genFinalizeBatch` 收尾，避免整批卡死等不到消息(这才是"用已产出收尾"的正当场景)。
- 删除旧的独立 `genWorkerFallback`(其"有结果就收尾"分支正是被 4s 残留定时器误触发的元凶)。
- 回退日志按 `location.protocol==='file:'` 区分文案：file:// 明确提示"浏览器禁用后台线程，请用 http:// 打开以获得后台线程+即时停止"。
- 就绪等待 `4s → 8s`，避免慢速虚拟机首次加载脚本误判超时。

### 验证

- worker 依赖模块顶层无浏览器专有全局(grep 核对)，确认 http:// 下 worker 可用。

### 修前的真实问题

v95 那次修正（见上文「棋盘尺寸」条）把选择改成（行,列）组合整体枚举，并按
`ov = 盒数 − (行×列 − 黑块目标)` 分三档：`withPipe`(ov≥3) → `fit`(ov≥0) → `all`(全组合兜底)。

漏掉的情形是 **`ov < 0`，即所有候选棋盘都比盒数需要的容量大**。此时 `withPipe` 与 `fit` 都为空，
落到 `all` 分支**随机挑一个**，多出来的空格随后被 `fillSurplusWithBlack` 全部补成黑块。

**机制指纹**：水平同色对占比（水平相邻 = 铺盒 `_seq` 连续，是「同色盒连续铺入」的直接产物）

### 实现：`baseFillBoxesBottomParallel`

用户口径：底边最中心起向左右和上方扩散；维持 P 个活跃槽位，每槽绑一个颜色和一个正在装的盒；

新参数 `boxParallelCount`：`null` = 取 `bufferLimit`（默认 5，语义「手上同时能攒几种颜色」）、
`0` = 关闭回退老路径、`>=1` = 指定路数。

**模拟器内核无误**：`applyPick` 取锁链组时 `steps++` 只加一次、整组一起离场；
`processChainGroup` 给组内 N 盒打同一 `link`/同一 `enterStep`，且**整组入场后才判 `overflow`**
（一步 N 盒占 N 位、瞬时超限判死）。玩家版 `doPick` 同样正确（用 `mv.groupSize` 在**移除棋盘盒之前**
判空位，N 盒各自入槽同 `link`/同 `enterTick`）。

**缺陷只在记录**：`solver.js` 每步只 push 一条 `pickOrder`（用触发盒坐标与球数），
组内另外 1~2 个成员**零记录**，该步 `count` 也只记触发盒球数。
玩家版 `tickPickInfo` 有 `groupSize` 但 `color`/`need` 同样只是触发盒的。

实测 `输出文件/v110底部49关-08-27`（46 关）：127 个锁链组（2连×86、3连×41）中
**126 组只有 1 个成员有步号**；缺口 `totalBoxes − pickOrder.length` 与「锁链成员数 − 组数」
**46/46 关完全吻合**，合计缺 **168 条**；样例 3 连组实际 139 球只记 47（少记 92 球）。

**连带损坏**：`app.js` 的「`pickOrder.length === totalBoxes`」门槛对含锁链关卡恒为假 →
消除序号视图**静默退回机械左→右序**，46/46 关中招。

### 记录口径（用户裁决「方案 A」+ 两项补充）

`pickOrder` 逐盒展开、同一 pick 共享 `step`，新增 `chain`/`chainSize`/`chainIndex`（0 = 触发盒）；
新增 `stepStats`（每 pick 一条）：`{step, boxes, bufBefore, bufEnter, bufAfter, isChain}`。

`bufEnter` 是唯一真正新增的信息 —— **整组入场后、结算前**的占用，正是内核判 `overflow` 所用的值，
以前判完即被 `autoReleaseBuffer` 抹掉。实测有关卡结算后峰值 4、**入场瞬时峰 5**（等于上限）。

**两类入场语义不同（不是缺陷，是玩法）**：锁链 `processChainGroup` **无条件**推入全部 N 个成员
（某成员当步消完也要留着等伙伴）→ `bufEnter === bufBefore + boxes` 严格成立；
单盒 `processAntBox` 当步消完则直接完成、不入暂存 → `bufEnter` 为 `bufBefore` 或 `+1`。

### 消费方必须知道的两点

1. **回放要跳过同 `step` 的后续条目**（整组已在触发盒那次离场）。修图工具 `core.js` 原先对不可取格子
   是**硬失败**（`回放中断; break`），不跳过会直接断掉；其步号原用数组下标 `i+1`，跳过后会跳号，
   已改为真实 pick 计数。旧格式每步仅 1 条，两处改动逐值等价。
2. **判定「某坐标是否锁链成员」要取该坐标的首条记录**。同一坐标可能被取多次 ——
   管道释放会把新盒放到出口格，而该格可能正是先前某锁链成员的位置（实测 **28/46 关**存在）。

### 验证

`_验v112.js` 25 项 0 失败（46 关全量重新求解、全部通关）；`_验v113.js` 24 项 0 失败
（玩家版 46 关：锁链 tick 123 个全部满足逐盒齐全/触发盒在前/`bufEnter = bufBefore + N`；
单盒 tick 2716 个全部满足 `+0/+1`；工具新回放循环不中断且旧格式行为不变）。
六套历史回归全部 0 失败。

**验证脚本自身修正两处**（非代码问题）：原断言 `bufEnter === bufBefore + boxes` 对单盒不成立；
原「坐标→条目」映射用后者覆盖，而同一坐标会被取多次。

## 2026-08-27 · 填盘层局部交错：聚集与趋势解耦（v114 发布，任务 `ANT-GEN-FILL-INTERLEAVE-20260827`）

> 承接同日 v110 条目的「后续方向」—— 那条写的是「并行度随进度递增」，**已被本轮实测否掉**，
> 见该条目末尾的更正小节。本轮找到的才是对症的那一层。

### 推理链（每一步都有实测支撑）

1. **旧路径的聚集与趋势忠实是同一个事实的两面**。`eliminationOrder` 每轮消完一个颜色的全部可达像素，
   旧路径按此出盒 → 盒序 = 像素消除序（趋势最忠实，裸盘当步即消 82.5%、溢出 12.5%）；
   而同一事实造成「某色 300 像素 ÷ 盒容 50 = 连续 6 个同色盒」。
2. **调并行度 P 无效**：`boxParallelCount` 1~∞，抗聚集（簇 2.00~2.23）与趋势忠实
   （通关率 57.5%~72.5% 无单调趋势）**双双持平**。P 是开关（并行 on/off），不是旋钮。
3. **交错出盒有真代价**：像素流改交错后严格按序回放溢出率 12.5% → 35%。
   根因是**盒粒度固有限制** —— 盒是 40~65 个单色球、整批消耗，像素级交错无法打包进盒级投放：
   攒球时 A/B 交错消掉，投放时 A 的盒整个来 50 球，此时盘面 A 的可达像素可能只有 20 个，
   剩下 30 球占着暂存等。这是结构性的，改不掉。
4. **但聚集根本不是队列的属性，是棋盘相邻性的属性**。逐行左→右填盘才是把「同色连续盒」
   变成「一行同色格」的那一步。把打散放到填盘层，两个目标就不再抢同一个自由度。

### 实现

新参数 `fillInterleaveWindow`（默认 6，`0` = 关闭）。每个可放格从队列头部宽 W 的前瞻窗口里挑
「颜色既不同于左邻、也不同于上邻」的盒，命中后移到队首位置再前进（只局部换位、不改整体顺序）；
窗口内全冲突退回队首（不卡住、不丢盒）。W 即位移上限（裸盘平均位移 1.13、最大位移中位 4）。
管道入队不参与交错（管道队列不构成表面相邻）。

### ⚠ 两处填盒点，只改一处等于没改

| 函数 | 服务对象 |
|---|---|
| `fillStructureFixed`（~2096） | **v95 起正式流程**（`produceFixed` 纠偏版） |
| `buildBoard` 内基础填球段 | 旧流程 `generateFromBlocks` |

第一版只改 `buildBoard`，真实棋盘前 3 行最大同色簇 5.0 → **5.5**（几乎无变化），
因为受测 12 关全部走 `produceFixed`。**裸盘实验查不出这个漏洞**——裸盘脚本自实现填盘、
不经过这两个函数。故在验证脚本里专设「真实棋盘上 W=6 的同色相邻对必须少于 W=0」一项钉住它。
这是本轮最值得记住的一条：**新增生成参数后必须在真实棋盘验一次「它到底有没有被正式流程走到」**。

### 实测

裸盘 40 张（用户指定验收判据）：W=0 簇 6.00 / 同色对 18.0 / 最长横排 5.0 / 通关 80.0% / 溢出 20.0%；
**W=6 簇 1.00 / 同色对 0.0 / 最长横排 1.0 / 通关 77.5% / 溢出 22.5%**。
W=3 不够（簇 3.00），W=6/9/12 等效 → 取 6。逐色守恒。

真实棋盘（P=0，8 关）：前 3 行同色相邻对中位 **11.0 → 1.5**。

真实棋盘四组合（12 关，正式入口）：**`P=5 W=6` 前 3 行簇 1.0、同色对 0.0，四组合最低**。
裸盘上占优的 `P=0 W=6` 在真实棋盘上不成立（簇只回到 2.0、合格 0/12、难度中位 66、全知均暂 0.46）。
真实棋盘上黑块/墙/管道天然打断相邻，是裸盘与真实结论分歧的来源。
故 `boxParallelCount` 默认未改。

### 用户裁决的验收口径

「只要裸盘能完成需求就可以。后续通过换球策略+障碍策略即可。不要扩大范围。」
因此合格率影响（12 关下 2 vs 1，属噪声）不再扩大样本测量，留给换球与障碍策略调节。

### 遗留

- 交错对合格率的影响未测出（样本不足，按裁决不扩量）。
- 工具 bin 副本落后 v113（`generator.js`/`app.js` 不一致），同步需批准。
- 卡点形不成（`hasChoke` 17.4%）本参数不解决 —— 方向是给卡点线独立参数，
  现行 `highThreshold` 被三条判据共用，v110 下调、v111 回滚已证明动它会连带出问题。

## 2026-08-27 · 参数区间化 + 卡点类型改概率机制（v115 发布，任务 `ANT-GEN-PARAM-RANGE-CHOKE-PROB-20260827`）

**目标**（用户三问）：
① 障碍设置参数改为可填上下限，生产器**在候选时随机组合**区间内的参数；
② 「瞬时连锁专用」那组参数转为通用参数，同样支持上下限；
③ 卡点类型数改为「出现检查次数 × 概率」，并算出最终出现类型数的**数学期望**。

**批准范围**：`bin/js/generator.js`、`bin/js/app.js`、`bin/index.html`、`网页启动器/生产服务.js`
+ 四份文档。禁止范围：求解器/玩家模拟/难度与合格门/盒切分与填盘交错/后段削减系数/关卡图修改工具/已产出批次。

### 改了什么

**q1+q2 区间化**：新增 `sampleRangedConfig(config)`（已导出），七项参数各加 `Min`/`Max`：
冰% / 黑% / 锁链组数 / 问号% / 管道数下限 / 队列深度 / 可用空间目标。
默认全 `null` → 逐字段退回单值 → 与 v114 逐值一致。`min>max` 自动交换，`min===max` 不掷随机。

**采样粒度＝每候选一次**，挂在 `produceFixed` 的 `for (k<K)` 循环内。
用户原话：「不同的候选都可以随机选取参数限制范围内。因为当前批次关卡都是同样的参数，输出的关卡结构会同质化」。
每关一次不够 —— 那只让关与关不同，同一关的 K 个候选仍同质。

**保持单值三项**：`pipeMinFill` / `pipeFloorCount` / `pipeFloorDepth`（阶梯硬地板，给地板加区间语义含混）。
同轮去掉 `index.html` 上「瞬时连锁专用 ↓」分组标签 —— **该标签自 v99 起即失准**：
引擎里这些参数从无 `instantChain` 门控、`app.js` 无条件透传，`输出文件/底部消除` 那批就是
底部入口模式下靠 `minPipes=4` / `usableSpaceTarget=0.74` 跑出来的。

**q3 概率机制**：`pickChokeTypes` 重写。掷 `chokeTypeRollsNormal`/`Boss` 次，每次以 `chokeTypeProb` 判定是否出现，
出现则从已勾选且未抽中的池里加权无放回取一个；池耗尽后剩余次数不再产生新类型
（用户口径「预算是指检查次数预算耗尽」）。旧 `chokeTypeCountNormal/Boss` **停用**，
仅在 `rolls` 未设时兼容读取（P 视为 1，`legacyMode:true`）。

### 期望不能写成 `rolls × P`

池会截断：命中数 `X ~ B(rolls,P)`，实际类型数 `min(X, poolSize)`。
池 2 / 检查 6 / P=0.9 时 `rolls×P = 5.4`，**真实期望 1.9999**。
实现按 `E = Σ k·P(X=k) + min(poolSize,rolls)·P(X≥poolSize)` 精确枚举（对数阶乘避溢出）。
实测对照：池 4/检查 4/P=0.5 → 理论 **2**、实测均值 **2.0069**，分布 `0种6.1% 1种24.9% 2种37.5% 3种25.2% 4种6.3%`；
截断场景理论 **1.9999**、实测 **1.9999**。

### ⚠ 参数一波动，落库就成了必需项，而变体差点又漏一次

区间化之后同一批各关参数不再相同，「这关为什么障碍这么少」必须能从产物回答。
落库补三处：`逐关记录.jsonl` 加 `采样参数`/`卡点计划` 两个对象；`分析报告.csv` **表尾加 12 列**（39→51）；
`debugData` 同样保留两者。

**关键点**：`makeChokeVariantFixed` 必须透传 `sampledConfig` —— 变体只 clone 父棋盘后改盒的 `color`/`count`，
用的还是父候选那组参数。**这与 v103 漏传 `chokePlan` 是同一类问题**，本轮 6 关实测
**4 关最终候选来自变体**（chokeRound=1 或 2），不透传则近 2/3 的关采样值为 `null`。
验证脚本因此专设一项「produce 出口每关都带 `sampledConfig`（含变体胜出的关）」并打印各关候选层。

**缺值写空串不写 0** —— 0 在这些列里是有意义取值（`采样管道数=0` 表示不铺管道、
`卡点检查次数=0` 表示不启用类型化），写 0 会让「旧批次没这列」和「本关确实取 0」无法区分。

### 后段削减保留（用户裁决）

**已知后果：棋盘实际障碍量可能低于设定下限。** `采样参数` 记的是削减**前**的值。

## 2026-08-27 · 区间上下限改双端滑块 + 补上一条从不采样的候选路径（v116 发布，同任务 `ANT-GEN-PARAM-RANGE-CHOKE-PROB-20260827`）

**用户追加裁决**：「把上下限做成左右端可拖动的，而不是左端可拖动，右端变成填入」→「继续」。
追加批准 `bin/css/style.css`（双端滑块必须自带样式，无法只靠内联样式实现）。
**不改 generator 的采样/概率口径、不改落库格式、不改任何算法。**

### 改了什么

七项区间参数（冰/黑/锁链/问号/管道数/队列深度/可用空间）从「左侧原控件＝下限 + 右侧数字框＝上限，
上限留空＝不启用」改为**一条轨道两个滑钮**。实现要点：

- 两个原生 `<input type=range>` 绝对叠放，容器 `pointer-events:none`、只有 `::thumb` 恢复 `auto`
  → 保留浏览器原生键盘操作（←/→、Home/End）与无障碍语义，不自造 div 滑钮。
- **两钮重合 = 不启用区间**，`readRange` 返回双 `null` → generator 退回单值，逐值等价 v114。
- **推挤**而非夹住：夹住时两钮贴死后再也拉不开（尤其轨道两端），推挤任何位置都能拖。
- 下限到最右端时容器加 `.at-max` **反转层级**，否则下限被上限钮压住拖不回来。
- 读数重合显单值、张开显两端并高亮，直接标示「哪些参数在波动」。

**轨道域统一放宽**（两钮须共用取值域，取两者更宽的）：冰 0~30→0~40、黑 0~20→0~25、
锁链 0~10→0~12、问号 0~50→0~60、管道数 0~12→0~16、队列深度 1~20→1~24、可用空间 0~0.95 不变。
副作用：单值也能设得更高，属预期放宽。

### ⚠ 一个只有旧方案才会暴露的坑

v115 的方案里 `gen-*-max` 存的是空串。把空串赋给 range 控件时**浏览器落到区间中点**
（冰 0~40 → 20），于是「原本不启用区间」被静默变成「18~20 启用区间」——
方案与实际批次参数不符，且页面上看不出异常。
故 `applyScheme` 对双端滑块上限专门处理：**空值 → 上限 = 下限**。
颠倒的上下限由 `refreshDualRanges` 按「上限=下限」收敛，不静默放大区间。

### 顺带修掉一条从不采样区间的候选路径（真缺陷，非 UI 问题）

`makeChokeVariantFixed` 内 `round ≥ 2` 且 30% 概率的**压力调整重生成**分支是从头重建棋盘，
原先直接把 `pa.cfg` 交下去 → ①区间在该路径被完全忽略（建盘读单值，用户设的上下限不生效）；
②无 `sampledConfig`，落库为 `null`。命中率不低（6 关样本常有 1~2 关来自它）。
v116 起先 `sampleRangedConfig(pa.cfg)` 再建盘，并带 `regenerated: true`
（它没有 `chokeRound`，不标会在结果里被误认成基础候选）。

**这条是验证断言抓出来的**，不是读码发现的：`_验v115.js` 的「produce 出口每关都带 `sampledConfig`」
打出 `chokeRound=0:MISSING`。与 v114「两处填盒点只改一处等于没改」是同一类教训 ——
**新增生成参数后要确认所有产出路径都真的走到了它**，路径清单要穷举，不能只看主循环。

## 2026-08-28 · 手点模拟改时间驱动并发结算 + 暂存满时取盒判定修复（v122 发布，任务 `ANT-SIM-LIVE-CONCURRENT-20260828`）

**背景**：用户实测反馈两件事 ——「快速点几个盒，视觉上还是等前一个动画演示完才开始下一个，
多余的盒只排进队列而不真的同步结算」；「暂存满了没空位时没立即判死，而是再放一个盒变 6/5 才死，
6/5 状态结算还把暂存释放了，属于 bug 作弊」。并给出真机规则：
**每个盒都要出蚂蚁，约 1 秒出 5~8 只（= 消 5~8 像素），在这个周期内玩家会继续放盒。**

**备份**：本轮为纯新增 + 一次等价抽取，未新建备份目录（回退：`?v=` 回 121 + 还原 4 个文件）。

**改动**：`bin/js/simulator.js`、`bin/js/app.js`、`bin/index.html`（`?v=` 121→**122**）、`bin/css/style.css`。
**未动**：`solver.js`/`solver-strategy.js`/`playersim.js`/`analysis.js`/`generator.js` 一行未改。

### 读码 + 实测定位到的三件事

1. **动画速率**：`animPxPerTick=2` / `animFrameMs=45` → **44.4 像素/秒每盒**，是真机 5~8 的 **5.5~8.9 倍**。
   用户「动画播放太快」的判断准确。
2. **不并行**：`animTickCore` 首段 `if (animActiveEats.length) { …推进…; return; }` 提前返回，
   连点时新到的 ops 进了 `animQueue` 却进不了 `animActiveEats`。
3. **逻辑层比"排队"更远**：`pickBox → applyPick → autoReleaseBuffer(while changed)` 是
   **一次点击结算到底**。落库 `stepStats` 实测 271 关 16295 步，**69.7% 的步 `bufAfter == 0`**
   —— 近七成的盒在自己那一步内就被吃干抹净、从不跨步占暂存。
   **所以「在出蚂蚁周期内继续放盒」在原逻辑里根本不存在**，只放慢动画是障眼法。

### 为什么必须让逻辑也按时间走（而不是只改动画）

暂存压力是这个游戏唯一的失败源，也是难度分 f1（65%）的来源。逻辑瞬时 → 暂存几乎总是空的
→ 连点造成的真实压力测不出来。故本轮把手点路径改成「逻辑按时间推进 + 动画直接渲染逻辑态」，
**取消原来的双轨**（逻辑瞬时 + 动画补播）。那套双轨也是「棋盘立刻更新、目标图慢慢补播」错位的根源。

### 实现要点（三个纯新增函数）

`pickCapacityOf` / `pickBoxLive` / `settleStep`。四个容易踩的点都处理了：

- **小数累计**：6.5 像素/秒在 40ms 帧上是 **0.26 像素/帧**，不累计就永远取整为 0、一个像素都消不动。
- **真实时间戳**：`dt` 用 `performance.now()` 差值，不假设帧间隔（`setInterval` 漂移、后台标签页被节流到 1s）；
  `dt` 上限夹 1000ms，否则切后台回来会一次补一大段、瞬间消掉一片。
- **一次只吃 1 像素再轮到下一盒**：若一次吃满预算，先手盒会把争用像素全抢走，与真机并行不同序。
- **消除内核一行未改**：吃像素就是 `elimDispatch(s, color, 1, …)`；争抢次序沿用 `autoReleaseBuffer`
  的既有口径（瞬时连锁先进先得 / 其余距离优先）。

### `releaseCompletedBuffer` 的抽取

`settleStep` **不能**调 `autoReleaseBuffer` —— 后者 `while(changed)` 会把进度一路推到完成，
**正好抵消掉「每秒只出 5~8 只蚂蚁」的速率限制**。但两者的离场规则（普通盒各自完成、锁链整组同步）
必须完全一致，所以把那一段抽出来共用，**而不是复制第二份** ——
这个工程已经在「第二份算法副本」上栽过几次（碎色包装层、工具 bin 副本）。
纯搬移、判据与副作用逐行未改；等价性由十五套历史回归 + 「重跑全知求解与落库逐字段一致」背书。

### 6/5 作弊：表层 + 深层

**表层**：`isPickable`（`:322`）不判暂存容量，`listMoves`（`:966`）却算了 `blocked`
—— **两套口径不一致**，求解器避开、手点点得下去。于是第 6 个盒被塞进暂存、置 `overflow`、
**仍执行 `autoReleaseBuffer` 释放暂存**、才判死。UI 上这些盒还带 `.pickable`，毫无提示。

**深层（真正的作弊）**：`processAntBox` 的 `if (result.completed)` 让**能一次消完的盒根本不进暂存**
→ 5/5 满暂存下可**无限次**取这类盒。时间驱动改造直接消灭它（入场即占槽、容量门无 `canConsume` 豁免）。

**修后**：点放不下的盒 → 拒绝（棋盘一格不动、不入暂存、不结算、不置 `overflow`、不判死）；
真正的死亡交给已有的死锁检测。UI 加 `.noslot`（灰显 + ✋ + `not-allowed`）并去掉 `.pickable`。

**顺带量出的一个数据，供后续求解器调整参考**：这条免槽豁免在全知求解器里只用了
**18 步 / 16295（0.11%）**、涉及 **4/271 关（1.5%）**，且**这 4 关全部不合格**。
即把求解器也改成「每盒必占槽」不会影响任何已合格关卡。**本轮未改求解器。**

## 2026-08-28 · 修高频重绘吃掉棋盘点击 + 修逐关无损数据的导入分类（v123 发布，任务 `ANT-IMPORT-PERLEVEL-DATA-20260828`）

### bug1：v122 第一版自己引入的回归

`renderLive` 每帧（40ms）调 `renderQueues`，而后者是 `container.innerHTML = html`
—— 整块棋盘拆了重建 25 次/秒。`click` 只在 mousedown 与 mouseup 的**共同祖先**上派发，
节点被换掉后共同祖先退到容器，**而监听器是逐格绑的 → click 根本不触发**。
这就是「动画播放中点不动其他盒」。锁链更明显：占多槽 → 结算更久 → 重绘窗口更长 → 几乎点不中。

**教训**：把「逻辑瞬时 + 动画补播」改成「每帧渲染逻辑态」时，
`renderQueues` 这种**重建整块 DOM** 的函数不能跟着进每帧循环。v122 那一版只想着「直接渲染逻辑态最简单」，
没意识到它同时是**交互层**。判断标准很简单：**凡是会重建带事件绑定的 DOM 的渲染函数，都不能进高频循环。**

两条修法：①点击改**事件委托**（绑容器一次，子节点被换也收得到，且按当前逻辑态重判、不信 DOM class）；
②棋盘只在签名 `steps|buffer.length|completedBoxes|gameOver` 变化时重建（实测状态不变时 25 帧只重建 1 次）。
签名在 `enterSimulation`/`doReset`/`doUndo`/`exitSimulation` 处置 `null` 作废
—— 撤销会让 `steps` 回退到与之前相同的值，不作废就漏绘。

**同轮核实「锁链后点不动」不是逻辑问题**：3 连入场（占 3 槽、剩 2 空位）后 6/6 个可取盒
`pickCapacityOf` 全 `ok`，并成功再取一个。容量门无误判。

### bug2：逐关无损数据被当成普通关卡本体

用户操作：从 `输出文件/v119底部消除298-08-28` 同时导入「合格关卡」+「生产文档」。
实况：合格 133 / 不合格 84 / 逐关无损数据 217。结果 218 关、85 含玩法标记、还带进了不合格关卡。

`生产文档/关卡数据/<名>.json` 顶层**直接是一个关卡对象**，原有三个判据都不匹配
（`isDataPack` 要 `type` 或 `levels[0].board`；`isSolveData` 要顶层 `pickOrder`+`meta`；
`isOldAudit` 要**没有** `blocks`）→ 掉进 `levelFiles`。三条后果：与 `合格关卡/` **平级竞争同一个键**
且 `add(entry,true)` 是先到先得（FileReader 异步、顺序不定 → 那个随机的 85）；
`parseLibrary` 不读 `solve`/`audit`（求解数据全丢，`paired=0`）；
它自带完整关卡内容 → 217 关全变条目（含 84 不合格 = 用户说的「非法关卡」）。

四条修法：①新增 `isPerLevelData`；②**「有本体则只补不建」**（无对应本体的跳过并计数，
完全无本体时才回落建条目）；③配对键用**文件名**不用 `j.name`（后者是源图名、带 `.txt`、
重名关会被生产侧改名 —— 实测该批恰有 1 关不一致，正是那个多出来的第 218 条）；
④`normKey` 再剥 `__遍历兜底`/`__超时兜底`/`__兜底`（该批 84 关带此后缀，不剥会把同一关拆两条）。

**效果**：合格关卡+生产文档 → **133 / 133 含玩法 / 133 含求解 / 0 不合格 / 0 幽灵**，
并提示「跳过 84 关未选中的无损数据」。另三个场景（只导生产文档 217、只导合格关卡 133 无附加数据、
不合格+生产文档 84）全部符合预期。

**教训**：这个工程的落库产物里，「关卡本体」「无损数据」「求解数据」三类文件**都可能带完整关卡内容**，
但语义完全不同。导入侧靠「有没有某个字段」做分类已经出过三次问题（v121 的 `.solve`、
本轮的逐关无损数据、以及历史上的「幽灵关卡数据」）。
**根子是落库侧没有统一的文件类型标记** —— `关卡数据.json` 有 `type:'ant-level-data'`、
`求解数据/*.solve.json` 有 `type:'ant-solve-data'`，唯独逐关无损数据**没有 `type`**。
建议后续在生产服务落库时给它补一个 `type`，导入侧就不必再靠字段形状猜。**本轮未改落库侧**（范围外）。
