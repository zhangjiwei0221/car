## 2. 建棋盘（`generateFromBlocks` / `buildBoard`）

> **⚠ v115 起本节引用的障碍参数是「每候选采样后的值」**：`blackPercent`/`icePercent`/`chainCount`/
> `questionPercent` 以及 `minPipes`/`pipeMaxDepth`/`usableSpaceTarget` 七项都可填上下限，
> 由 `sampleRangedConfig` 在 `produceFixed` 的候选循环内**逐候选采样一次**再交给本节流程（见 §8e.1）。
> 不填区间时逐字段退回单值，本节口径与 v114 完全一致。
> 后段自动削减（黑 ×0.85 / 冰 ×0.9 / 链 ×0.85）仍作用在采样值之上，故**实际障碍量可能低于设定下限**（§8e.4）。

1. **尺寸按盒数与黑块目标选择**（`chooseBoardDimsFixed`，2026-07-31 重写；此前为「范围内随机选组合」）：

   **形态硬约束**：棋盘必须 `列数 > 行数` 且 `列数 − 行数 ∈ {1,2}`。不允许行列相等、行多于列、或列比行多 3 格及以上。

   **选择依据**：令 `可放盒容量 = 行×列 − 黑块目标`，`ov = 盒数 − 可放盒容量`。
   - `ov ≥ 0`：盒能填满棋盘，多出来的盒进管道，**不产生余格黑块**，最终黑块 ≈ `blackPercent`；
   - `ov < 0`：棋盘偏大，`|ov|` 个余格会被 `fillSurplusWithBlack` 补成黑块，**最终黑块超过 `blackPercent`**。

   因此按以下顺序取候选（同档内取 `ov` 更小者）：
   1. 形态合法且 `ov ∈ [0, pipeRoom]`——正好填满或小幅溢出进管道（`pipeRoom = max(3, 盒数×25%)`，用途只是避免把几十个盒全推进管道撞 `pipeCapacity`，真正的管道容量仍由后续检查把关）；
   2. 形态合法且 `ov > pipeRoom`——溢出偏多；
   3. 形态合法但 `ov < 0`——会产生余格黑块，取超标最少者；
   4. 若「方案给定行列范围内」最好的结果仍落在第 3 档，才允许**向下缩小到范围外**继续找（缩小候选的列只取 `行+1` / `行+2`，天然满足形态约束）；
   5. 完全没有合法形态可用时退回「范围内随机」，并置 `boardPick.shapeRelaxed = true` 如实上报，不静默假装合规。

   返回值新增 `boardPick` 诊断字段：`tier`（命中哪一档）、`cap`、`boxCount`、`blackTarget`、`surplusToBlack`、`finalBlack`、`finalBlackPct`、`shrinkUsed`、`shapeRelaxed`、`shapeDiff`、`rangeGiven`，供生产报告如实展示「目标黑块 / 实际黑块 / 实际比例 / 是否缩小过棋盘」。

   **只改「选哪个棋盘」**：不改障碍参数、不改盒容量、不在事后删黑块或裁棋盘。棋盘缩小只改行列，`blackPercent`/`icePercent`/`chainCount`/`questionPercent`/`narrowPath*` 一律按缩小后的实际棋盘正常计算，不得静默降低。

   **默认行列范围**（2026-07-31 起，取自 `方案文件夹/方案_v95四方向消除统一默认参数.json`）：6-9 行 × 7-10 列（原 8-9 行 × 11-16 列）。该范围内满足形态约束的合法组合共 7 个：6×7、6×8、7×8、7×9、8×9、8×10、9×10。

   装不下的盒仍由管道吸收（见步 3）。
2. **黑块/墙 + 窄路**：按 `blackPercent` 铺黑块；`narrowPath` 开启时用不规律锯齿墙+缺口制造唯一可达通道（需推理才能通过）。墙体形态有硬约束：不得组成 2×2 墙块，任意直线最多 3 面墙相连（边缘也视作墙）。
3. **占位管道（守恒反推）**：`管道数 = ⌈(盒总量 − 有效空位) / 每管容量⌉`，即"装不下棋盘的盒必须由管道吸收"反推出管道数量。管道同时充当墙体占格参与窄路制造。
4. **基础填球（消除顺序，第一遍单扫 + 第二遍均匀）**：盒序列按目标图**由底部+左右两侧向中心**的消除趋势切分，对应棋盘**首行→尾行、左→右**顺序填入；管道本体格第一遍只填 1 个（必不满），第二遍按管道位置 round-robin 均匀填满剩余（每管容量 `pipeMinFill`~`pipeMaxDepth`，**v105 起可调，默认 4-6 = 原写死值**；超过深度上限会触发容量兜底：重随机尺寸或增大盒容量降低溢出。管道数不足另有兜底，见 §12.5b）。
5. **首批障碍（两批语义）**：问号/冰块**全部**在建棋盘阶段填入；**锁链只填 50%**，剩余一半留给卡点阶段按依赖关系定向补链（`chainInitialRatio` 可调）。

**目标图入口模式（`bottomOnly`，v96 新增，见 §11）**：基础填球的盒切分在四边入口(默认)下用 `baseFillBoxes`（几何趋势流）；仅底部入口下改用 `baseFillBoxesBottom`，由 `pickBoxSplit(blocks, config)` 统一分发。棋盘取盒方向、障碍/管道规则不受此参数影响。
**v110 起底部分支内部再分两路**：`boxParallelCount > 0`（默认，取 `bufferLimit`=5）走**多色并行吐球** `baseFillBoxesBottomParallel`；`=0` 回退到原**单色批量依赖流**。详见 §2b。

## 3. 合法性门（不做求解，只做结构检查）

`structuralDeadlockCheck`：结构性可达检查（锁链组可激活/盒可达）+ 无管道共用同一出口的 bug 检查。只有通过这一步，候选才进入求解阶段——这一步**不跑求解器**，纯结构校验，成本低。

## 4. 求解：全知版 vs 玩家版

| | 全知求解器 `solver.js`+`solver-strategy.js` | 玩家模拟器 `playersim.js` |
|---|---|---|
| 信息 | 已知问号色/管道序，理论最优 | 只知当前半消画面，**乐观估计、会误判** |
| 推进 | 串行按步取盒 | 并发按 tick 逐像素消除 |
| 目的 | 判可解性、给参考解、当审核压力基准 | 拟合真人难度（含犯错）、当难度分主要依据 |
| 失败处理 | 严格判死（不可解即淘汰） | 死锁触发**复活道具**（§5） |

### 4.1 六遍求解编排（`solve()`）
贪心×2(noise 0/0.6) → 三步前瞻树×2(noise 0/0.8) → 噪声贪心×2(noise 1.0/1.5)，任一遍通关立即停。三类策略互补：贪心快、树能解贪心+噪声解不出的关、噪声能救树差一点的关。基础棋盘的首解用全六遍；卡点变体的重解也是全六遍（早期版本曾用 `greedyOnly` 跳过树，已改为全量）。

### 4.2 三步前瞻树（`treePick`）
宽 3 × 深 3（≤27 条三步路径），每候选克隆状态真实执行一次，用真实差值评分。分阶段主目标：前期 <20% 拓展棋盘、中期 20-50% 拓展目标图可达、后期 ≥50% 生存。
（**注意别与审核窗口混淆**：这里的 20%/50% 是**求解器选盒策略**的阶段目标，在 `solver-strategy.js` 里；
审核的卡点窗口是另一套，v117 起为 卡点区 30~80% / 中期 20~30%，见 §6.1。两者互不影响，本轮只改了审核那套。）暂存压力分级：轻/中/高三档，高压时候选必须能释放已有暂存盒或有实际消除。

**锁链滞留周期奖励（v83 新增）**：对暂存区里"滞留超过一步的锁链组"（2/3 连），滞留步数越长、占位越多（3连>2连）、当前暂存压力越大，促进其推进/整组释放的分数越高；三步窗口内越早整组释放评价越高。滞留步数只按**真实决策步骤**滚动计算，前瞻假设步骤不提前算数——每次真实执行一步后，从新真实状态重新建立三步窗口。详见 `求解器算法逻辑.md` §5.5。

### 4.3 提速（行为等价）
`listMoves`/`canConsume` 的判定从"整图拷贝+完整 floodFill"改为"外部连通空腔缓存(`computeExteriorOpen`) + 同色可达计数(`canConsumeReach`，达 count 即止)"，等价性经 2589 个真实状态逐一验证。单轮 solve 提速约 40%，`listMoves` 提速 13-15×。玩家模拟器同法提速约 3.1×。

## 5. 玩家复活道具

玩家卡死（连续多 tick 无推进）时自动触发：优先消除暂存区剩余订单最大的 2 个盒；暂存不足 2 个则从棋盘残留盒补足；无视依赖封锁按最近距离直取像素释放。每关最多 2 次，≤2 次通关即算玩家版合格。评分偏好复活次数更少（0 次 +40 / 1 次 +30 / 2 次 +20）。

**演示动画接入（v83）**：复活事件独立捕获（`curFrame.revive`），演示界面常驻显示"复活: 已用/上限"，触发时选中目标高亮，消除结果严格复用模拟器算好的数据（动画层不重新选择/计算），结束提示补充复活次数/是否用尽/是否因复活耗尽而失败。

## 6. 审核（合格标准）与难度评分：两条并行分支

> 这是最容易被混淆的一点，单独强调：**审核决定"这关能不能用"，难度分决定"这关有多难"，两者互不决定。**

### 6.1 审核（`chokepointAudit`）——依据全知求解器的压力曲线

**当前真实行为（v118）**，完整阶段表与实测见 `生产审核评分体系.md` §1b：

- **三段划分**（**中期已移除**）：前期 `[0,30%]` / 中后期 `[30%,80%]` / 后期 `[80%,100%]`，
  窗口宽**全阶段 5%**、起点步长 1%。**卡点线 = `L−1.8`**（L=5 时 3.2），中压线仍 `L−2.5`。
- **合格**（`curveOK`）= `hasChoke && earlyOK && safeEdge`：
  中后期 `[30,80%]` 至少 1 个 5% 窗口 ≥ 卡点线；**前期 `[0,30%]` 不出现卡点**（只比卡点线，不再比中压线）；
  全程暂存峰值 < 上限（不触死亡边界）。后期 `[80,100%]` **只记录不判定**。
- **简单关·趋势过平**（`flatTrend`）：放宽第①条 —— 不要求真实卡点，只要求前期不出卡点
  且 `bump = max(中后期峰, 后期峰)` 达中压且高于前期峰。**仍可用**，占「简单关名额」。
- **不合格**：以上两档都不满足。
- `tier = curveOK ? '合格' : (flatTrend ? '简单关·趋势过平' : '不合格')`；
  `usable = curveOK || flatTrend` 是「能不能用」的单一判据。

> **历史沿革与订正**（2026-08-27 核对代码后整理）：
> ① 档次字样自 **v104** 起就已从「困难合格 / 简单合格」改为「合格 / 简单关·趋势过平」
> （任务 `ANT-GEN-AUDIT-RESET-20260824`），本节当时未同步，已补。
> ② 窗口区间 **v117** 改为 卡点区 30~80% / 中期 20~30%（原 50~100% / 20~50%）。
> ③ **v118**（任务 `ANT-GEN-AUDIT-STAGE-RESHAPE-20260827`，用户直接下达）：卡点线 `L−1.5 → L−1.8`、
> 窗宽全阶段 5%、**中期整段与 `midOK` 判据移除**、前期扩到 30% 且判据改为「不出现卡点」。
> `midMax` 与 `midOK` 字段保留但恒为 `0`/`true`（删字段会让 `auditScoreOf` 变 `NaN`）。
> 旧口径峰窗由 `lateMaxLegacy`/`midMaxLegacy`/`highLegacy`/`hasChokeLegacy` 记录（按旧阈值旧窗宽算），只作对照。
> ④ **难度分自 v118 起与卡点线解耦**：`DIFF_CAP.f1` 仍 3.5，卡点线已是 3.2，两者不再相等。

### 6.2 生产输出三档优先级（`produce()` 的 `candTier`/`candBetter`，v84 修复）
```
档3 困难合格 > 档2 简单合格 > 档1 安全兜底(双方可通关,未触死亡边界) > 档0 其余(不可解/打不通/触死亡)
```
候选选择**先比档次，同档才比评分**——不允许"不合格但分数凑巧高"的候选压过"合格但分数凑巧低"的候选。这是 v84 发现并修复的一处真实排序漏洞：旧逻辑用混合分数比较，档次之间可能被分数"倒挂"。一关合格（档 2/3）即停搜索；全程无合格则按档次从高到低兜底，绝不会把"打不通"的坏关交出去。

**兜底标记**（v86）：档 1/0 的兜底交付会在输出对象上标 `fallback=true`（档 3/2 正常输出为 `false`），`fallbackTier`(0或1) 区分"安全兜底(可通关但未形成卡点)"与"最接近标准(仍不合格)"，`fallbackType`(`'timeout'`超时中止 / `'exhausted'`穷尽仍无合格) 说明是怎么走到兜底的，`fallbackReason` 给一句人读说明。判定用的是候选原始档次，不是事后看 `audit.tier` 字面值——即使 `audit.tier` 显示"简单合格"，只要玩家版实际没通关，仍会被正确标记为兜底，不会被曲线形状的表面合格蒙过去。批量生产的完成提示、CSV、`关卡数据.json`、生产报告都能看到这些字段。

### 6.3 难度评分 v3（`computeDifficulty`→`Analysis.difficulty`）——依据玩家版求解器表现
```
难度分 = clamp(f1×0.45 + f2×0.25 + f3×0.10 + f4×0.20 + 复活次数×8, 0, 100)
f1 = 玩家平均暂存 ÷ 2.5     f2 = 全知平均滞留 ÷ 7
f3 = 基础障碍强度 ÷ 200      f4 = (玩家平均暂存−全知平均暂存) ÷ 1.5
```
f1 改用**玩家版**（而非全知版）平均暂存，因为全知版为确保可解会刻意压低暂存，用它算难度会把分数系统性压低、封顶在普通档。`computeDifficulty()` 只在候选**已经通过审核判定后**才被调用计算展示分数，其输出从不反馈进 `candTier`/`candPass`/`evaluation.pass` 这些"能不能用"的判定——改难度分权重只影响分数展示，不影响哪些关卡被选中输出。

## 7. 卡点制造（生产核心手段）

历史上曾拆分四类（换球/容量、锁链带无用球、关键色分散/藏管道、冰块）逐一验证有效性，v80 按实测结果精简收敛为 **2 种**（冰块手段用户决定不采纳）。**基础阶段(建棋盘+首次求解)不做任何换球/换位扰动**（v86，此前残留的两处基础阶段换球已删除）——换球只在候选未合格、进入以下卡点分支后才执行：

1. **换球/搬盒 `chokeSwap`**：
   - **锁链定向换球**（`chokeChainColorSwap`，v86 新增，优先执行）：把前期段锁链组（2/3连）的一个代表成员，换成目标图里【当前埋得最深】的颜色（`interiorColorRank` 计算——某色像素当前靠外部连通区域的暴露比例越低，越深埋，要等其他颜色先消开才摸得到）。换后该锁链组的依赖满足时机被推迟，组内其他成员消完也无法单独释放，形成结构性的长期滞留（配合 §4.2 的锁链滞留奖励，求解器会优先设法处理它）。默认一次处理 4 组。
   - **网关色搬运**：定向到目标图的【网关色】（消掉该色能解锁最多其他颜色像素的关键色，`gatewayColorRank` 计算；v81 修复了维度 bug——此前误用棋盘维度只扫到目标图左上角一小块，导致识别到的网关色极少甚至为 0）。把网关色关键盒搬到离原位最远处（后期棋盘格或管道最深层），跨度=曼哈顿距离（藏管道按队列深度折算）。一次最多搬 12 处（实测的甜点值；试过提到16/20次，合格率反而下降，说明换太多是过度打乱）。
2. **增容 `chokeInflate`**：把某种颜色的暂存容量集中灌进一个后期盒，抬到盒容量上限的 1.5-2 倍，让它长期占用暂存位；同色donor盒降到最小容量，颜色总量守恒。

两种手段按 60%/40% 概率分派（`applyOneChoke`）。第 2 轮起额外有 30% 概率走"增减压重生成"（据审核诊断调障碍基础参数，±3 级、每级 5%）。

## 8. 生产主入口 `produce()` 完整流程（v96 起前置一道底部入口可达检查，见 §11）

```
K 个候选，每候选：
  1. 初生成(建棋盘+首批障碍) → 合法性门 → 六遍求解
  2. 达档2/3(简单/困难合格) → 立即输出并停
  3. 未合格且可解 → 展开 B 个卡点制造分支(换球/增容) → 重解+审核
  4. 分支合格 → 立即输出并停；否则进入下一轮(共 N 轮)
  5. 单关时间预算封顶(默认5分钟)，到点立即停止搜索
全程无合格/超时 → 按三档优先级(§6.2)兜底输出最优候选
```
默认参数：`K=6 B=3 N=2`，单张源图未早停时最多评估 `6×(1+3+9)=78` 个生产状态。

批量生产额外支持**简单关比例**参数（默认 30%）：按比例把部分关卡名额定为"简单关"（趋势符合即过，`requireHardPass=false`），其余为"困难关"（必须真实卡点，`requireHardPass=true`），名额均匀分布在整批里。

### 8b. 批量生产的并发线程池（v101 新增，任务 `ANT-GEN-PARALLEL-WORKERPOOL-20260820`）

> 本节记录该改动后的真实行为、输入输出、参数阈值、失败回退、与上一版差异、对应实现函数、验证结论与已知限制。
> **生成、求解、审核、难度四条逻辑一行未改**——本节只涉及"谁在什么时候被派去算哪一关"。

#### 为什么改

v88~v100 是**单个 Worker 串行**：`produce` 一关 → 落库确认 → 才派下一关，同一时刻只有 1 关在算。
实测依据（`输出文件/unnamed-08-20` 批次前 32 关）：各关 `produce` 耗时**求和等于墙上时间**
（17.4 分钟），说明落库写盘开销 ≈ 0，**瓶颈就是串行本身**。单关中位 21.8s、均值 32.6s、p90 98.6s，
按此推算 200 张需约 1 小时 49 分。

#### 真实行为

`genPool` 是 N 个槽位，每槽一个独立 Worker，**每槽同一时刻只处理一关**；槽空闲即领下一个待处理下标。
因此慢关不再堵住后面的关（旧结构里一关磨满 5 分钟预算会把整批一起拖住）。

| 项 | 实现 | 说明 |
| --- | --- | --- |
| 建池 | `genSpawnPool(size)` | 逐槽 `genSpawnSlot` + `genBindSlot` 握手；返回 false 表示一个都建不出来 |
| 领关 | `genSlotDispatch(slot)` | 先取 `retryQueue`（线程死亡退回的下标），否则 `nextIdx++`；无可领则置空闲并试收尾 |
| 结算 | `genSlotSettle(slot, idx, fn)` | 落库确认后才释放槽位并领下一关（落库门保留，只是由「全局串行」变「按关独立」） |
| 收尾判据 | `genMaybeFinalize()` | 全部派完 + 无人在飞 + `retryQueue` 空 + 无待重试落库 → 收尾。**不能再看单游标** |
| 进度 | `genPoolProgressText()` | 并发下同时列出各槽在算的关；进度按 `genBatch.doneCount` 计 |

#### 参数与阈值

- **并发线程数**：UI `#gen-pool-size`，默认 **6**。在 `batchProduce` 里被 `Math.min(值, navigator.hardwareConcurrency)` 收窄。
  设 **1 则与 v100 的串行行为完全等价**（用于对照与回退）。
- **为什么不允许超订**：单关预算 `timeBudgetMs` 是**墙上时间**，不是 CPU 时间。并发数超过物理核数时，
  各关在同样的 5 分钟墙上时间内实际算得更少 → `budget_timeout` 与兜底关变多，是**质量回退**。
- **单关预算不因并发缩短**：`timeBudgetMs` 由 `produceFixed` 内部各自 `t0`/`_deadlineAt` 计时，
  每个 Worker 跑自己的 `produce`，各关都拿满完整预算。本次改动未触碰该逻辑。
- **单关看门狗**：仍是 `预算 + 2 分钟`，但**下沉到每槽**（`slot.watchdog`）。超时只重启那一个槽，其余照跑。

#### 失败与回退

| 情况 | 行为 |
| --- | --- |
| 一个槽握手失败/崩溃，但**已有其他槽就绪** | 只丢这一个槽（`genSlotDead`），在飞那一关退回 `retryQueue` 由别的槽重跑，**不丢关、不记失败** |
| **所有槽都没就绪**（如 `file://` 禁用 Worker） | 整批回退主线程 `genRunSync()`（仍是串行，主线程跑 produce 本就阻塞页面，多开无意义），只回退一次 |
| 全部槽都停用 | 直接收尾，已落库关卡全部保留 |
| 落库失败 | 该关挂入 `genPersist.pendingPayloads[idx]`，**该槽停住不再领新关**（避免服务已写不进去还继续空转产出）；「重试落库」按钮一次重发全部待重试关 |

#### 顺带修掉的两个并发下才暴露的缺陷

这两处在串行下表现正确，池化后必错，属本次改动的必需修正：

1. **单关耗时全错**：原先用全局 `genBatch.itemT0`，会被后派发的关覆写。改为 `genInFlightT0[idx]` 按关记派发时刻。
2. **落库回调错行**：原先按「从尾部找第一个 `_full` 记录」定位本关，并发下多关同时挂着 `_full`，
   会把本关的输出路径写到**另一关**的记录上，且本关完整数据永不释放（内存不降）。改为按 `rec._idx` 精确匹配。

同时 `genPersist.pendingPayload` 由单槽改为按下标的 `pendingPayloads` 字典——并发下多关同时落库失败，
单槽会互相覆盖、把先失败那关永久丢掉。

#### 对应实现

`bin/js/app.js`：`genPool`/`genPoolSize`/`genPoolReadyCount`/`genInFlightT0` 状态，
`genSpawnPool`/`genSpawnSlot`/`genBindSlot`/`genSlotDispatch`/`genSlotSettle`/`genSlotDead`/
`genOnLevelStuck`/`genMaybeFinalize`/`genPoolProgressText`，以及 `batchProduce`/`genFinalizeBatch`/
`stopBatchProduce`/`genPersistOne`/`genRetryPersist`/`genRunSync` 的配套调整。
`bin/index.html`：`#gen-pool-size` 控件 + `?v=` 提到 101。
**`bin/js/gen-worker.js` 未改动**——其协议本就是每消息无状态、每 Worker 一份独立全局（`GENPERF`/
`Solver.resetPerf`/`PlayerSim.resetPerf` 各自一份），池化天然安全。

#### 服务端：批次续跑 `/api/production/resume`

`网页启动器/生产服务.js` 新增。原先 `batches` 只在内存、`batchToken` 每次启动随机、
`createBatchDir` 遇同名目录直接跳号，因此**服务一重启或页面一刷新，原批次目录就再也写不进去**，
已跑完的关卡只能作废重跑。`resumeBatch(dirName)` 从盘上重建内存态并签发新令牌：

- 计数与 `doneIndexes` 一律以**`逐关记录.jsonl` 的实际行**为准（那是每关落库时真实追加的），
  **不信任 `生产状态.json` 的汇总数字**（那是快照，可能停在崩溃前的旧值）；
- 分类计数用与 `persistResult` 相同的 `classify` 口径重算，保证恢复前后报告口径一致；
- 同一 `输入序号` 只算一次（容忍历史重复行）；缺失子目录自动补齐。

并发写盘安全性：`persistResult` 与其调用的 `atomicWrite`/`appendLine` **全同步**，
Node 单线程事件循环天然把并发 POST 序列化，因此 CSV/JSONL 追加、计数器、`doneIndexes`、
`uniqueName` 的 existsSync-then-write 均无竞态。**服务端因此无需为并发做任何改造**。

#### 验证结论

- **语法**：`app.js`、`生产服务.js` 均通过 `node --check`。
- **调度状态机**（`_kiro临时/08.20-多线程生产/_验线程池调度.js`，从 `app.js` 切出真实源码在 stub 环境驱动）：
  见该脚本输出，覆盖并发派发、慢关不堵快关、槽死退回队列、看门狗只杀一槽、收尾判据、
  耗时按关计、落库回调按 `_idx` 匹配。
- **真实生产**：`输出文件/unnamed-08-20` 批次以 6 线程续跑剩余 140 关（前 60 关为 v100 串行产出，
  同一目录、同一批次配置、同一参数）。产出记录与串行段**顶层字段集、`性能` 字段集完全一致**，
  关键字段非空，`开始时间`/`fallback*` 的 null 分布与串行段相同（属既有行为，非本次引入）。
  实测吞吐见 §10 v101 条目。
- **未验证**：浏览器内的池化实机行为（进度行显示、停止按钮即时性、多线程下的界面响应）
  需在浏览器实机确认，本轮由用户手动验收。

#### 已知限制

- 主线程回退模式（`genRunSync`）**不并发**，只在 Worker 完全不可用时兜底。
- 并发下 `生产状态.json` 的 `当前输入索引`/`当前关名` 语义变为「最后一个落库的关」而非「正在处理的关」
  （服务端 `persistResult` 每次落库都会覆写这两个字段）。这两个字段本就只作提示、不参与任何判定。
- 网页端目前**没有**「续跑」入口按钮：`/api/production/resume` 已具备能力，但 UI 未接入，
  刷新页面后仍会开新批次。命令行续跑可用（见 `_kiro临时/08.20-多线程生产/续跑-多线程.js`）。

### 8c. 生产前置碎色闸门（v102 新增，任务 `ANT-GEN-FRAGMENT-GATE-20260824`）

> 记录该闸门的真实行为、输入输出、参数阈值、失败回退、与上一版差异、对应实现函数、验证结论与已知限制。
> **求解器、玩家模拟、难度评分、卡点合格门四者未改**——本闸门是**生产前置过滤**，不参与审核档次、不进难度分。

#### 是什么

「碎色」= 目标图上**自己不够大、附近同色也凑不够**的色块。它迫使一个 35~80 容量的盒跨越许多互不相连的
小片才能吃饱，从而拉长订单在暂存区的滞留。闸门在**生成候选之前**判定源图碎色率，超限即跳过该图。

#### 真实行为与调用时机

`checkFragmentGate(blocks, config)` 在 `produceFixed` 内、紧跟 `checkBottomEntryFeasibility` 之后调用，
位置与模式完全对齐既有的底部入口前门：

```
produceFixed
  → instantChain/bottomOnly 互斥修正
  → [仅底部入口] checkBottomEntryFeasibility  → 不可达则返回 bottomEntryInfeasible
  → [本闸门]    checkFragmentGate            → 超限则返回 fragmentGateBlocked
  → resetGenPerf / 预算计时开始 / K 候选循环 …
```

**超限时返回**：`{ level:null, valid:false, lastFailReason:'fragmentGateBlocked',
structural:{ok:false, reason:'fragmentGateBlocked：…'}, fragmentGate:{ok:false, rate, limit, frag, detail} }`。
**不消耗时间预算**（实测 <1.5s vs 20s 预算）、**不产出任何关卡结构**（绝不造假关）。

#### 碎色率算法（`computeFragmentation`）

| 步骤 | 口径 | 依据 |
| --- | --- | --- |
| ① 分块 | 同色 **4-连通** | 与游戏消除一致（`simulator.js` `floodFillEliminate` 亦为四方向） |
| ② 分档 | 孤立 ≤1px / 小色块 ≤10px / 正常 >10px | 08-24 扫描最优 |
| ③ 隔断 | 0-1 BFS 求两同色块间**异色像素数** `px` 与**颜色种类数** `kinds` | 目标图完全填满（实测 344/345 关无背景），故 `px` ≈ 曼哈顿距离−1 |
| ④ 并簇门 | **AND**：`kinds>1` 且 `px>3` 才算隔开 | 用户原式；08-24 扫描显示 AND(0.6198) 优于 OR(0.6170) |
| ⑤ 长期隔断 | 隔断色不先于本色被消 → 不并簇 | 轮次取自 `AntSolver.eliminationOrder` |
| ⑥ 救回 | 簇总像素 >10 → 整簇改判正常 | 用户规则4 |
| ⑦ 输出 | **碎色率 = 碎色像素 ÷ 彩色像素总数** | 用户指标① |

另同时输出 `isoRate`/`smallRate`/`maxColorRate`（最碎单色）/`avgFragDepth`（碎色平均消除轮次）作诊断。

#### 参数与阈值

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `fragmentMaxRate` | **0 = 关闭** | 碎色率上限。0 时整段跳过，行为与引入前完全一致 |
| `fragmentIsoMax` / `fragmentSmallMax` | 1 / **7** | 孤立块与小色块上限。**2026-08-25：smallMax 由 10 改为 7**（用户「把小色块要求放宽给到小于 8」，即 ≤7），回到用户 08-24 的原始定义 |
| `fragmentBarrierPx` / `fragmentBarrierKinds` | 3 / 1 | 隔断像素数与种类上限，取 AND |
| `fragmentDetail` | `false` | **只影响返回值，不影响任何计算**。传 `true` 时额外返回块级明细，见下 |

**UI 默认阈值沿革**：15.16%（v102 标定）→ **18%**（2026-08-25 用户裁决）→ **22%**（2026-08-26 用户裁决，v110 当前值）。
`DEFAULT_CONFIG.fragmentMaxRate` 始终是 **0 = 闸门关闭**，阈值由 UI 传入，算法与口径参数一律未随之改动。
⚠ **两端已不同源**：修图工具的达标提示仍用 18%。方向是安全的——工具更严，
所以「工具里判达标的图，生产时一定不会被碎色闸门卡掉」这条保证仍然成立；
反向不成立（工具判不达标的图，生产端 22% 可能仍放过），只让工具偏保守，不会误导美术弃用可用的图。

**方案持久化（v109 起）**：UI 的碎色阈值控件 `gen-frag-max` 已进方案白名单 `SCHEME_INPUTS`
（任务 `ANT-GEN-SCHEME-CHOKE-TYPES-20260826` 同轮追加，用户裁决「碎色门阈值当然补进参数」）。
在此之前该阈值**存了方案也存不住**、加载后回落 `index.html` 默认值 18%。
由于它决定哪些源图在生产前被直接跳过（`fragmentGateBlocked`），属批次可复现性的关键参数。
加载 v109 之前保存的旧方案时该控件保持当前值，不被清零。

#### 可选块级明细（`fragmentDetail`，2026-08-25 新增）

`computeFragmentation` 原先只返回汇总指标。传 `cfg.fragmentDetail = true` 时**额外**返回：

| 字段 | 内容 | 恒等关系 |
| --- | --- | --- |
| `fragCells` | `[{r,c,color,size,iso}]` 碎色像素坐标 | `length === fragPixels` |
| `fragBlockList` | `[{color,size,iso,cells}]` 碎色块 | `length === fragBlocks` |
| `perColorDetail` | `[{color,total,frag,rate}]` 分色明细，按碎色率降序 | `Σfrag === fragPixels` |

**不传时这三个字段不存在**（`undefined`，不是空数组），返回体仍是原来那 10 个汇总字段。

**为什么加**：修图工具要把「哪些像素被判为碎色」高亮给美术看。此前工具只能自己按
「块自身大小 ≤ smallMax」近似判定，拿不到本函数内部的**并簇救回**结果，于是把
**视觉上连续的条带**也标成了碎色。用户实机反馈：「高亮的孤立色统计了一些视觉上并不孤立的像素，
例如连续的边缘带、间隔一个条带的同色条带」。6 张真实图实测误标 **608 块**，
其中与最近同色块只隔 1 像素的占 **559 块（92%）**、条带形状占 **427 块**。
在工具侧复刻并簇逻辑会再造一份算法，故改为由本函数把内部已知的判定结果输出出去。

**零计算改动**：明细完全来自结算循环中**已有**的 `compCells[i]` 与既有的两个 `continue` 判据
（`compSize[i] > smallMax`、`clusterPx[find(i)] > smallMax`），未新增任何判断、未改任何阈值比较。
已用 25 张真实图验证：**传与不传时 10 个汇总字段逐字段完全相同**。

UI `#gen-frag-max` 填**百分比**，`getGenConfig()` 转成 0~1。
**默认值 2026-08-25 起为 18**（此前为 15.16），用户裁决：「给到 18% 作为碎色率上限」。
`DEFAULT_CONFIG.fragmentMaxRate` 本身仍是 **0（关闭）**——阈值一律由 UI/调用方给，
不在默认配置里硬开闸门，否则脚本直接调 `produce` 会被意外过滤。

#### 阈值标定（两套口径，别混用）

**旧口径（smallMax = 10，2026-08-24 标定，已停用，保留供回溯）**
上线 345 关四等分：Q1 上界 0.1516 好关率 38.5%（最高）、Q2 0.1879/32.1%、Q3 0.2253/23.1%、Q4 0.3336/24.7%。
该口径下 0.1516 很严格：上线批仅 24.8% 可过，200 新图 4.0%，347 修复批 15.3%。

**现行口径（smallMax = 7，2026-08-25 重标定）**

#### ⚠ 窄路概率 与 窄路两个卡点类型的关系（用户 2026-08-27 提问「是否会重叠？」）

**不会重复建墙，但那两个卡点类型在默认配置下是空转的。** 三层关系：

| 层 | 参数 | 决定什么 |
| --- | --- | --- |
| ① 结构 | `narrowPath`（开关）+ `narrowPathProb`（概率，默认 1）+ `narrowPathGapsMin/Max` | **本关是否建窄路墙、留几个活口**。唯一决定窄路结构存在性的地方（`narrowPathHits` → `reserveNarrowWalls`） |
| ② 装饰 | `narrowPathIce` / `narrowPathChain`（**内部默认 `true`，UI 无控件**） | 要不要在活口格上叠冰 / 叠锁链 |
| ③ 类型门控 | 卡点类型 `narrowGapIce` / `narrowGapChain` + `chokeGateNarrowByType`（**默认 `false`**） | 只有 `chokeGateNarrowByType=true` 时，②才额外要求「本关抽中该类型」 |

代码里的条件是
`config.narrowPath && config.narrowPathIce !== false && (!gateNarrowByType || CK.narrowGapIce) && narrowGaps.length`。
`gateNarrowByType` 为 `false` 时 `(!false || …)` 恒真 → **叠冰/叠链无条件发生**。

于是默认配置下：

- 勾选 `narrowGapIce` **不会**让它更容易出现（本来就恒开）；
- 不勾选 **也照样**出现；
- **但它仍在抽签池里**：会被抽中、占掉一个「卡点类型数」名额、计入 `chokeCount`、写进报告 ——
  却对棋盘毫无影响。v115 把数量改成「检查次数 × 概率」的随机量之后，这种浪费更隐蔽。

`方案文件夹/方案_v110底部消除.json` 正是这种配置（两类型权重 1、`chokeGateNarrowByType: false`），
所以那批只要抽中这两种就是空占名额。

- 卡点类型只进生产侧记录，不入关卡本体。
- ~~**卡点类型参数存不进方案**~~ —— **该限制已在 v109 解除**（任务 `ANT-GEN-SCHEME-CHOKE-TYPES-20260826`）。
  v103 引入本体系时，16 个 UI 控件一个都没进 `app.js` 的 `SCHEME_INPUTS` 白名单，
  导致「勾好类型 → 存方案 → 重新加载」后勾选全部回落 HTML 默认值、卡点数量归零，
  任务 W 的「每关各类型卡点数量可配」在方案层面不成立（实证：`方案文件夹/方案_v104.json`
  的 `inputs` 24 个键、零个卡点键）。v109 补入 17 个卡点相关 ID：11 个类型勾选 + 卡点数量 2 个 +
  门控 1 个 + 超大盒倍率 2 个 + `gen-boss-interval` 1 个；**同轮另按用户追加裁决补入
  `gen-frag-max`**（碎色闸门阈值，见 §8c），白名单合计 30 → **48** 个 ID。
  `captureScheme`/`applyScheme` 未改（本就按 `el.type` 处理勾选框）；历史方案不回填、不清零。

#### 方案持久化（v109）

卡点类型的全部配置、以及碎色闸门阈值 `gen-frag-max`，随方案保存与加载。
落盘格式见 `方案文件夹/*.json` 的 `inputs` 段，键名即控件 ID。
**加载旧方案（缺这些键）时相应控件保持当前值**，不会被清零——
因此从旧方案切换过来时，卡点配置与碎色阈值是「上一次手动设置的值」而非方案里的值，
需要复现某批产出时应使用 v109 之后保存的方案。

### 8e. 参数区间化 + 卡点类型改概率机制（v115 新增，任务 `ANT-GEN-PARAM-RANGE-CHOKE-PROB-20260827`）

> **求解器、玩家模拟、难度评分、合格门、盒切分、填盘交错 六者未改。**
> 本节只涉及「候选拿到的参数从哪来」与「卡点类型数量怎么定」。

#### 为什么改（用户口径）

- 区间化：「当前批次关卡都是同样的参数，输出的关卡结构会同质化」——同一批 N 张图共用一组固定参数，
  冰/黑/链/问号比例逐关一致，结构自然趋同。
- 卡点类型改概率：「旧的机制无法用稳定的期望算出会出多少这样卡点类型，同时也无法制造波动」——
  v103 的 `chokeTypeCountNormal/Boss` 是固定 N，产出恒定 N 种，既不波动也谈不上期望。

#### 8e.1 区间采样（`sampleRangedConfig`）

**七项参数**支持上下限，每项新增 `XxxMin` / `XxxMax`：

| 新参数 | 关联单值 | 取整 | 影响 |
| --- | --- | --- | --- |
| `icePercentMin/Max` | `icePercent` | 是 | 冰块比例 |
| `blackPercentMin/Max` | `blackPercent` | 是 | 黑块比例 |
| `chainCountMin/Max` | `chainCount` | 是 | 锁链组数 |
| `questionPercentMin/Max` | `questionPercent` | 是 | 问号比例 |
| `minPipesMin/Max` | `minPipes` | 是 | 管道数下限（§12.5b） |
| `pipeMaxDepthMin/Max` | `pipeMaxDepth` | 是 | 每管队列深度 |
| `usableSpaceTargetMin/Max` | `usableSpaceTarget` | **否**（比例） | 可用棋盘空间目标（§12.5） |

**默认全部为 `null`** → 逐字段退回读同名单值 → **默认行为与 v114 逐值一致**（旧批次可复现）。
只给单值 = 视为 `min=max`，故 `方案文件夹/*.json` 旧方案不失效。

**采样粒度＝每候选一次**（用户裁决「不同的候选都可以随机选取参数限制范围内」）：
挂在 `produceFixed` 的 `for (k < K)` 候选循环内，同一关的 K 个候选各拿一组不同参数。
**不是每关一次** —— 每关一次只能让「关与关之间」不同，同一关的 K 个候选仍同质。

- 输入：`config`（含 Min/Max 或单值）
- 输出：叠加采样值后的**新** config（不改入参），并把这一组值写进 `_sampled`
- 调用时机：候选循环每轮开始、`generateFromBlocksFixed` 之前

**三条候选产出路径都必须采样**（v116 补齐第③条）：

| 路径 | 何时走 | 采样位置 |
| --- | --- | --- |
| ① 基础候选 | `produceFixed` 的 `for (k<K)` 每轮 | 循环内 `sampleRangedConfig(config)` |
| ② 卡点变体 | `makeChokeVariantFixed` 改盒分支 | 不重建棋盘，**透传**父候选的 `sampledConfig` |
| ③ 压力调整重生成 | `makeChokeVariantFixed` 内 `round ≥ 2` 且 30% 概率 | **从头重建棋盘**，故 v116 起在此单独 `sampleRangedConfig(pa.cfg)` |

③ 原先直接把 `pa.cfg` 交给 `generateFromBlocksFixed`，后果两条：
**区间在这条路径上被完全忽略**（`buildStructureCandidateFixed` 读的是单值 `icePercent` 等，
用户设的上下限对这些关不生效）；返回值没有 `sampledConfig`，落库时该关采样值为 `null`。
实测该路径命中率不低（6 关样本里常有 1~2 关最终候选来自它），因此这不是边角情况。
该候选另带 `regenerated: true` 标记 —— 它没有 `chokeRound`，不标出来会在结果里被误认成基础候选。

#### UI 口径（v116 起：双端滑块）

七项区间在页面上是**一条轨道两个滑钮**：左钮＝下限（也是不启用区间时的单值），右钮＝上限，
**两钮重合 = 不启用区间**（`app.js` 的 `readRange` 此时返回双 `null`）。拖动为**推挤**语义
（下限越过上限就顶着上限一起走，反之亦然），任何位置都拖得动、不会互相锁死；
下限拖到轨道最右端时容器加 `.at-max` 反转两钮层级，否则下限被上限钮压住拖不回来。
读数在重合时显示单值（`18%`）、张开时显示两端（`18~26%`）并高亮，一眼看出哪些参数在波动。

> **历史（v115 第一版，已停用）**：当时是「左侧原控件＝下限 + 右侧新增数字框＝上限，
> **上限留空**＝不启用区间」。用户裁决「把上下限做成左右端可拖动的，而不是左端可拖动，右端变成填入」，
> v116 改为双端滑块。两种表示在引擎侧**逐值等价**（都归结为 Min/Max 是否为 `null`），
> 换的只是 UI 与「不启用」的表达方式。
>
> **旧方案兼容（必须留意）**：v115 保存的方案里 `gen-*-max` 存的是空串。若直接把空串赋给 range 控件，
> 浏览器会落到**区间中点**（冰 0~40 → 20），把「原本不启用区间」静默变成「18~20 启用区间」。
> 故 `applyScheme` 对双端滑块的上限做了专门处理：**空值 → 上限 = 下限**，保持不启用。
>
> **轨道域被统一放宽**：双端滑块两钮必须共用同一取值域，故取原「下限控件」与「上限框」两者中更宽的那个：
> 冰 0~30→**0~40**、黑 0~20→**0~25**、锁链 0~10→**0~12**、问号 0~50→**0~60**、
> 管道数 0~12→**0~16**、队列深度 1~20→**1~24**、可用空间 0~0.95（不变）。
> 副作用：这些参数的**单值**现在也能设到比 v115 更高，属预期放宽。

**转通用但保持单值的三项**：`pipeMinFill`（每管最少装几盒）、`pipeFloorCount`（管道绝对下限）、
`pipeFloorDepth`（绝对深度下限）。它们是**阶梯硬地板**，给地板加区间会使「地板」判定语义含混。
同轮去掉了 `index.html` 上「瞬时连锁专用 ↓」的分组标签 —— 该标签**自 v99 起即失准**：
引擎里这些参数从无 `instantChain` 门控、`app.js` 无条件透传，`输出文件/底部消除` 那批就是
底部入口模式下靠 `minPipes=4` / `usableSpaceTarget=0.74` 跑出来的。

**边界**：`min > max` 自动交换；`min === max` 直接返回该值不掷随机。

#### 8e.2 卡点类型数量：检查次数 × 概率（`pickChokeTypes` 重写）

| 新参数 | 含义 | 默认 |
| --- | --- | --- |
| `chokeTypeRollsNormal` | 普通关的**出现检查次数** | 0 |
| `chokeTypeRollsBoss` | BOSS 关的出现检查次数 | 0 |
| `chokeTypeProb` | 每次检查的出现概率 P | 0.5 |

流程：掷 `rolls` 次；每次以 P 判定是否出现；出现则从**已勾选且未被抽中**的池里**加权无放回**取一个
（沿用 v103 的「同关内类型不重合」）。池耗尽后剩余检查次数不再产生新类型
（用户口径：「预算是指检查次数预算耗尽」，与时间预算无关）。

**替代关系**：`chokeTypeCountNormal` / `chokeTypeCountBoss` **停用**，不再决定数量。
仅在 `rolls` 未设时作兼容读取（此时 `P` 视为 1，复现「固定抽 N 种」旧行为，返回 `legacyMode:true`）。

**数学期望**（`chokePlan.expected`）用精确式而非 `rolls × P`：命中次数 `X ~ B(rolls, P)`，
实际类型数 `= min(X, poolSize)`，故

```
E = Σ_{k=0}^{min(poolSize,rolls)-1} k·P(X=k) + min(poolSize, rolls)·P(X ≥ poolSize)
```

**池会截断** —— 池 2 / 检查 6 / P=0.9 时 `rolls×P = 5.4`，真实期望只有 **1.9999**。
`rolls` 很小，实现里直接按上式枚举（对数阶乘避溢出）。

**返回新增可观测字段**：`rolls` / `prob` / `hits`（本关实际命中次数）/ `expected` / `pool` / `legacyMode`。
`generateFromBlocksFixed` 的重试重建 `attemptPlan` 时同样补带这六项，否则重试过的关这些字段会丢。

**抽取时机不变**：仍是**每关一次**，经 `config._chokePlan` 透传（v103 口径）。
每次候选重试**不重新掷** —— 重掷会让同一关跨重试累计用到远超预算的类型。

#### 8e.3 产物记录（追溯口径）

参数一旦波动，「这关为什么障碍这么少」就必须能从产物回答，否则批次不可分析。

- `逐关记录.jsonl` 新增两个对象：
  - `采样参数`：本关**最终采用的那个候选**实际采到的七项值（保留原精度）
  - `卡点计划`：`rolls` / `prob` / `hits` / `expected` / `pool` / `legacyMode`
- `分析报告.csv` **表尾追加 12 列**（39 → 51 列）：
  `采样冰%` `采样黑%` `采样锁链` `采样问号%` `采样管道数` `采样队列深度` `采样可用空间`
  + `卡点检查次数` `卡点概率` `卡点命中` `卡点期望` `卡点池`。
  **一律加在表尾**，旧列位次不变（按位取值的旧解析脚本不受影响）。
  缺值写**空串而非 0** —— 0 在这些列里是有意义的取值（`采样管道数=0` 表示不铺管道、
  `卡点检查次数=0` 表示不启用类型化），写 0 会让「旧批次没这列」和「本关确实取 0」无法区分。
- `生产文档/关卡数据/<名>.json` 的 `debugData` 同样保留两者，供单关级复查。

**变体必须透传采样值**：`makeChokeVariantFixed` 新增 `sampledConfig: parent.sampledConfig`。
卡点变体只 clone 父棋盘后改盒的 `color`/`count`，用的还是父候选那组参数；
不透传则**近半数关卡查不到自己那组参数**（与 v103 漏传 `chokePlan` 是同一类问题，实测本轮
6 关中 **4 关最终候选来自变体**，漏传时这 4 关的采样值会是 `null`）。
**压力调整重生成分支另需自己采样**（v116 补，见 §8e.1 三条路径表）—— 它不是改盒而是重建盘，
透传父值不成立，必须新采一组；漏了则该路径的关既忽略区间又落库为 `null`。

#### 8e.4 后段自动削减仍作用在采样值之上（已知后果）

用户裁决「保留，如果加了参数范围，我写入参数时会包含部分兜底的小参数障碍」。
故 `buildStructureCandidateFixed` 的后段削减（黑 ×0.85 / 冰 ×0.9 / 链 ×0.85）**不动**，
作用在采样值之上。**已知后果：棋盘实际障碍量可能低于设定下限** —— 这是预期行为，
`采样参数` 记的是削减**前**的采样值，与棋盘实测值对不上时应先想到这一层。

#### 8e.5 行为变更声明

- 区间默认 `min=max` → 行为不变；**一旦设成区间，同一关的不同候选参数不同 → 旧批次不可复现**。
- `chokeTypeRolls* > 0` 后，卡点类型数量**由固定 N 变为随机**（期望见 8e.2）→ 产出结构随之波动，
  这是用户明确要的「制造波动」。
- 中途 `resume` 一个 v114 期开的批次时，CSV 表头是旧的 39 列、新行是 51 列 → **表尾 12 列无表头名**。
  数据不错位（新列在尾部），但读表时需自行补列名。

### 8f. 棋盘结构指标落库（v117 新增，任务 `ANT-GEN-USABLE-REPORT-CHOKE-WINDOW-20260827`）

> 用户 2026-08-27：「**当前报告内没有可用空间的指标。** 我测试手感发现是否管道+墙的参数
> 突破了我要求的可用空间参数」。
> **本节只做「把实际值记下来」，没有改任何生成/落位逻辑。**机制层面的问题见 8f.3，待用户裁决。

#### 8f.1 落了什么

`app.js` 新增 `boardStructStat(level, parsed, target)`：**现场从最终 `board.cells` 重数**，
口径与 generator 出口闸门一致 —— `可用空间 = (总格 − 墙 − 管道格) / 总格`。

**为什么不直接抄 `spaceQuota.realUsable`**：那是**结构候选阶段**算的，最终 board 可能来自
卡点变体或压力调整重生成（§8e.1）。现场数才是这关真正交付出去的样子。
配额层记录的 `quotaUsable`/`quotaBlackTarget`/`quotaBreachLevel`/`quotaRealUsable` 一并带出 ——
两者不一致本身就是信号（例如「余格补黑」会让实际墙数超过配额目标）。

- `逐关记录.jsonl` 新增 `棋盘结构` 对象：`rows`/`cols`/`cells`/`black`/`blackPct`/`pipeCells`/
  `boardBoxes`/`usable`/`usableTarget`/`usableDevPp`/`pipeWant`/`pipePlaced`/`pipeTier`/

#### 8f.3 三条根因（已读码确认，机制**本轮未改**，待用户裁决）

1. **`blackPercent` 被可用空间配额覆盖**：开启 `usableSpaceTarget` 后墙数由 `B = K − P` 反推
   （§12.5），`blackPercent` 只作**容差中心**参与判定，且容差还带 2 次 ×5pp 突破预算

2. **`minPipes` 在这组参数下必然落空**：`pipeMinFill` 被夹到 ≤ `pipeMaxDepth`（方案设 3），

3. **撤管道后不再复核可用空间**：`trySolveNoPipe` 自己会查一次容差，但**结构候选出口**那道
   `devPp > uTolPp` 闸门在 P=0 分支被 `intentionalZero` 放行 → 撤除抬高的可用空间没人拦，
   即那 2 关超上限的来源。

**待裁决三项**（见 `codex助理/01_当前任务.md` 任务 AH）：
① 出口是否补一道**黑块容差复核**（现在只复核可用空间）／或把余格补黑计入配额不再额外加墙；
② `noPipe` 分支后是否按 `usableSpaceTolPp` 再判一次（会淘汰那 2 关）；
③ `pipeMaxDepth < pipeMinFill` 时区间必空，是否改为以深度上限为准并在报告里显式告警。

### 8g. 窄路进池 + 卡点类型逐类参数化 + 卡点进度位置（v120 新增，任务 `ANT-GEN-CHOKE-TYPE-PARAMS-20260827`）

> 用户 q1：「将窄路不作为默认开启的单独参数，正常接入卡点类型里面，同时窄路缺口这样的参数也接入。
> 至于出现概率就同其他卡点类型一样用期望概率抽取。**所以我的卡点类型池就是为了设置期望和概率，
> 随机从池子内输入对应卡点类型组合，从而让关卡棋盘结构出现丰富的变化**」
> 用户 q2：逐类参数化十一项 + 「同时增加参数：卡点组合出现的进度位置（默认为 15-80% 位置）」

#### 8g.1 窄路进池

`CHOKE_TYPE_LIST` 新增 **`narrowPath`（窄路墙缺口）**，池大小 11 → **12**。
决定权改由 `narrowNeeded(config, chokePlan)` 统一给出：

| 情形 | 窄路是否出现 | `narrowStat.source` |
| --- | --- | --- |
| 启用类型化 且 抽中 `narrowPath` | 是 | `chokeType:narrowPath` |
| 启用类型化 且 抽中 `narrowGapIce`/`narrowGapChain`（但没抽中 `narrowPath`） | **是（自动补建）** | `implied:narrowGapIce` / `implied:narrowGapChain` |
| 启用类型化 但三项都没抽中 | 否 | `chokeType:notDrawn` |
| **未**启用类型化 | 回落旧口径：`narrowPath` 开关 + `narrowPathProb` 概率 | `legacy:*` |

「启用类型化」的判据（`chokeTypingActive`）：池里至少一个权重 > 0，**且** 检查次数或旧的固定数量 > 0。
未启用时逐值走旧行为 → 旧方案与旧批次可复现。

**为什么抽中叠加类要自动补建窄路**：否则那两个名额会空转 ——
这正是 v103~v119 的老毛病（`chokeGateNarrowByType` 默认 `false` 使门控条件恒真，
勾选与不勾选毫无差别，但类型仍被抽中、占名额、计入 `chokeCount`、写进报告）。
不能换个形式重犯。`chokeGateNarrowByType` 随之**退役**，仅保留读取以兼容旧方案。

#### 8g.3 卡点组合出现的进度位置

新参数 `chokePosMin` / `chokePosMax`（默认 **0.15 / 0.80**）。
口径：`nullCells` 本就是**行主序**收集的未来盒格，而填盘正是按这个顺序灌入目标图消除序的盒队列，
所以「在 `nullCells` 里的下标 ÷ 总数」就是这一格的消除进度。`clipByProgress` 按此裁剪候选池。
v114 的填盘局部交错最多让盒位移 W(默认 6) 位，对 15%~80% 这样的宽带影响可忽略。
带内无候选时**退回全池**，不因此产不出关。

**只约束卡点类型手段，不约束基础障碍** —— 基础障碍（按比例铺的冰/问号/锁链）要铺满全盘，
一起收窄会连带改变整体障碍分布，那是另一件事。

> ⚠ 与合格门的卡点判定区（`[30%,100%]`，见 `生产审核评分体系.md` §1b）是**两件事**：
> 这里是「卡点造在哪」，那里是「压力峰出现在哪」。障碍造在 15% 处，其压力后果可能到 40% 才显现。
> 本轮 `analysis.js` 一行未动。

#### 8g.4 ⚠ 修掉一个自 v103 起就让 `chainCluster` 完全无效的缺陷

`fillStructureFixed` 的绑定阶段有一道「组间不得相邻」的检查 `chainGroupConflict`，
它**无条件执行**、完全没看本关是否抽中 `chainCluster`。而规划期的 `plannedConflict` 是按
`CK.chainCluster` 放开了 8-邻接的 —— 于是簇被规划出来、到绑定期又被一律否掉 → 整个候选淘汰
→ v103 的聚集类风险回退把 `chainCluster` 摘掉。

**实测：单开 `chainCluster` 时 5/5 全被摘**（`chokeFallback.dropped=["chainCluster"]`），
即**这个卡点类型从 v103 引入起就从未真正生效过**。
修法：绑定期与规划期用同一口径（抽中 `chainCluster` 时放行组间相邻）。
修后同配置下 6 次里 3 次成簇，簇内 BFS 平均距离 1.67~2.22（紧贴）。

另加一道 `plannedChainActivatableStrict`：规划期把**所有已规划的锁链格**（不只本组）视作障碍来判可激活性，
不过就换锚点重试。原 `plannedChainActivatable` 只把本组当障碍，组分散时够用，
但簇是故意让多组紧贴的，近似会失真。

**剩余已知限制**：风险回退是在**任何**结构失败后按风险序摘类型，不只在与该类型相关的失败时摘。
于是像 `方案_v110底部消除.json` 那种 `usableSpaceTarget=0.8` + `pipeMaxDepth=3` 的紧配置下，
`usableSpaceDeviation` 频发 → `chainCluster` 仍会被连带摘掉（实测该配置下仍近 100%）。
要根治需让回退只在失败与该类型相关时才摘 —— 不在本轮范围。

### 为什么要有 `求解数据/`（与修图工具的对齐口径）

`关卡图修改工具` 按**文件名**配对导入（`baseKey` 去掉 `.solve.json`/`.json`/`.txt`，
`*.solve.json`→求解数据、其余 `.json`→关卡、`.txt`→TXT图），**不看目录名**。
以前导出包缺 `求解数据/`，工具只能**现场求解**；而现场求解走 `core.js` 的 `solveStandard`，
是按 `DEFAULT_BUDGET_MS = 180000` 的**时间预算**跑九遍梯队——不同机器/负载可能停在不同遍，
`pickOrder` 会漂且**原理上不可复现**（梯队种子本身写死，所以漂移不是随机种子造成的）。
带上本目录即彻底消除该项不确定性。

**契约**：`pickOrder` 是唯一权威；**不输出** `replay`/`defaultInterval`——工具本来就自己按真机口径
毫秒级重放，多写一份反而多一处会漂的数据。**只有真拿到 pickOrder 才写该文件**：工具 `detectKind`
判 `'solve'` 的条件是 `meta && summary && (replay || pickOrder)`，写出 `summary:null` 的空壳会被判成
`'unknown'` 落进「读不出来」计数。无 pickOrder 的关不写，`索引.csv` 里如实标注。

单关导出（`exportLevel()`）同样产出 `求解数据/`，避免"批量有、单关没有"的不一致。

对应实现：`bin/js/app.js` 批量导出段与 `exportLevel()`。

## 11. 目标图消除入口模式（`bottomOnly`，v96 新增）

> 任务：`ANT-GEN-BOTTOM-ONLY-20260729`。本节记录该开关引入后的真实行为、输入输出、失败与回退口径、对应实现文件函数、验证结论与已知限制。

### 11.1 是什么、影响什么

`config.bottomOnly`（布尔，默认 `false`）决定目标图的外部消除入口：

- `false`（默认）：四边入口——上/左/右/下四条边均可作为外部消除入口，与本参数引入前的 v95 行为完全一致。
- `true`：仅底部入口——上/左/右三边视为封闭，目标图只能从底边开始向内消除。

**只改变目标图消除入口，不改变棋盘取盒方向**：棋盘仍按原有暴露/障碍/管道/冰/锁链规则取盒。默认关闭时不影响任何现有生产结果与产物格式。

### 11.1b 底部盒切分：多色并行吐球（§2b，v110 新增）

> 任务 `ANT-GEN-BOTTOM-PARALLEL-V3-20260826`，用户裁决「落地 v3 底部生产器」。
> 实现：`generator.js` → `baseFillBoxesBottomParallel`。只作用于 `bottomOnly` 分支，四方向分支一行未改。

#### 当前真实行为

`baseFillBoxesBottom` 现在是一个分发壳：读 `boxParallelCount`（`null` → 取 `bufferLimit`，默认 5），
`>0` 转 `baseFillBoxesBottomParallel`，`=0` 走原单色批量依赖流（下方 11.1 描述的老路径，逐值保留）。

并行路径逐步：

| 步 | 行为 |
|---|---|
| ① 起点 | 底边最中心 `(rows−1, ⌊(cols−1)/2⌋)`。每色内部按**曼哈顿距离**取最近可达像素；同距离时更靠底优先，再取离中心列更近者 → 「向左右和上方扩散」 |
| ② 前沿 | 与 `simulator.js` 的 `reachable()` **同口径**：`bottomOnly` 下**底行恒可达**，其余靠「四邻中有已消除格」。每色一个小顶堆 |
| ③ 槽位 | 维持 **P 个活跃槽**，每槽绑一个颜色 + 一个正在装的盒（容量由 `makeCapPicker` 独立采样，与另两处铺盒同一采样器）。同色不允许两槽同时装 |
| ④ tick | 每轮询各槽各吃 **1 个像素**；消除即揭露四邻，供所有颜色后续取用 |
| ⑤ 挤出 | 某槽 `count >= cap` → **立刻挤出成队列里一个完整盒** → 该槽补新颜色，维持 P 路在扫 |
| ⑥ 挂起 | 某色可达像素暂时耗尽（被别的颜色挡住）→ **挂起保留进度**，另补一路；其颜色重新可达时优先复活回轮询 |
| ⑦ 收尾 | 活跃槽 + 挂起槽的余量挤出；同色尾盒不足 `boxSizeMin` → 与前一同色盒**合并平分**（沿用老路径同一规则） |
| ⑧ 排序 | 挤出顺序即消除趋势顺序，`elimSeq` = 挤出下标。**无需再排序**（老路径靠 `trendStart` 排） |

填棋盘规则（逐行左→右单扫）与障碍、管道、卡点、换球等后续逻辑**均不变**。

#### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `boxParallelCount` | `null` | `null` = 取 `bufferLimit`（语义：手上同时能攒几种颜色）；`0` = 关闭并回退老路径；`>=1` = 指定路数 |

UI 控件 `#gen-box-parallel`（默认 5），已进方案白名单 `SCHEME_INPUTS`。

#### ⚠ 实测更正：并行度 P 不是抗聚集的成因（2026-08-27）

专项测量 40 张图（`_kiro临时/08.27-锁链步数与暂存结算/_测并行度影响.js`）：

| P | 队列同色 run 最长 | 前 3 行最大同色簇 | 前 3 行同色对数 | 前 3 行色数 | 盒总数 |
|---|---|---|---|---|---|
| **0（老路径）** | **5.85** | **6.50** | **17.93** | **6.28** | 63.9 |
| 1 | 1.98 | 2.10 | 2.48 | 9.57 | 63.6 |
| 2 | 2.05 | 2.00 | 2.38 | 9.55 | 63.6 |
| 3 | 2.08 | 2.15 | 2.30 | 9.63 | 63.8 |
| 5 | 1.88 | 2.13 | 2.52 | 9.55 | 63.4 |
| 8 | 1.98 | 2.23 | 2.70 | 9.63 | 63.9 |

**P 在 1~8 之间对以上各项均无可测影响**（run 1.88~2.08、簇 2.00~2.23、色数 9.55~9.63）。
抗聚集的增益**全部来自另两项机制**：① 像素流由「按色批量」改为「底部中心逐像素扩散」；
② 出盒时机由「盒的第一个像素」改为「盒被装满」。

**这条对调参有直接价值**：既然降低 P 不损失抗聚集效果，那么为压住前期压力
（见下「已实测的代价」）而在前期使用较小的 P 不损失抗聚集效果。

**⚠ 但「并行度随进度递增」这个方向已于 2026-08-27 被实测否掉**，本行原写它是「可行的前提」，那是过度推论：
P 对**趋势忠实度**同样无影响（严格按序回放通关率 P=1~∞ 均在 57.5%~72.5% 无单调趋势），
所以分进度调 P 不会产生任何效果。**`boxParallelCount` 实质是开关（并行 on/off），不是旋钮。**
真正解决「前区聚集」的是 **v114 填盘层局部交错**（`fillInterleaveWindow`，见 §11.1c），
它与出盒顺序解耦，才是对症的那一层。

**尚未隔离测量**：P 是否影响实际游玩的暂存压力（前期峰、`trendOK`）。
前期压力上升是「并行 vs 老路径」的对照结果，未按 P 分档单独测过。

#### 为什么要换（问题与证据）

老路径像素流来自 `AntSolver.eliminationOrder(…, true)`，那是**按轮次批量**消除：每轮挑「当前可达像素最多」
的**一个**颜色，一次 flood fill 消掉它全部可达像素。于是 order 是一段段单色长串（一段可达数百像素），
装箱时同色连续累积成多个盒，且盒按**首个像素 seq** 排序 → 同段产出的盒在队列里连续 → 铺进棋盘就是一整排同色。

### 11.1c 填盘层局部交错（§2b 之二，v114 新增）

> 任务 `ANT-GEN-FILL-INTERLEAVE-20260827`，用户裁决「落地」。

#### 为什么必须改在填盘层，而不是出盒层

聚集是**棋盘相邻性**的属性，与队列顺序无关。旧路径盒序 = 像素消除序（趋势最忠实，
裸盘当步即消 82.5%），但逐行左→右填盘把「同一颜色的连续盒」直接变成「一行同色格」。

改出盒顺序解决不了，有两条实测证据：

1. **调并行度 P 无效**：`boxParallelCount` 从 1 到 ∞，抗聚集与趋势忠实**双双持平**
   （簇 2.00~2.23、通关率 57.5%~72.5% 无单调趋势）。P 是开关，不是旋钮。
2. **交错出盒有代价**：把像素流从「按色批量」改为交错后，严格按序回放的溢出率
   从 12.5% 升到 35%。根因是**盒粒度的固有限制** —— 盒是 40~65 个单色球、整批消耗，
   像素级交错无法打包进盒级投放（攒球时 A/B 交错消掉，投放时 A 的盒整个来 50 球，
   此时盘面 A 的可达像素可能只有 20 个，剩下 30 球占着暂存等）。

#### 当前真实行为

| 参数 | 默认 | 说明 |
|---|---|---|
| `fillInterleaveWindow` | **6** | 前瞻窗口宽度 = 位移上限。`0` = 关闭，逐行左→右原行为 |

每个**可放格**从盒队列头部宽 W 的窗口里，挑第一个「颜色既不同于左邻、也不同于上邻」的盒；
命中后把它移到队首位置再正常前进（**只做局部换位，不改变整体顺序**）。
窗口内全冲突则退回队首 —— **不卡住、不丢盒**。W 即位移上限，取盒顺序最多偏离 W 位
（裸盘实测平均位移 1.13、最大位移中位 4）。

**管道入队不参与交错**：管道队列不构成棋盘表面相邻，那一支仍按队列顺序 `queue.push`。

#### ⚠ 两处填盒点必须同时改（实测教训）

| 函数 | 服务对象 |
|---|---|
| `fillStructureFixed`（`generator.js` ~2096） | **v95 起的正式流程**（`produceFixed` 纠偏版） |
| `buildBoard` 内基础填球段 | 旧流程（`generateFromBlocks`） |

第一版只改了 `buildBoard`，真实棋盘几乎无变化（前 3 行最大同色簇 5.0 → 5.5）——
因为受测的 12 关全部走 `produceFixed`，压根没经过那段代码。
**裸盘实验无法暴露这个漏洞**（裸盘脚本自实现填盘、不经过这两个函数），
故验证脚本里专设一项「真实棋盘上 W=6 的同色相邻对必须少于 W=0」来钉住它。

### 11.2 全链路同一口径

开启后，以下环节全部读取同一个 `bottomOnly` 值，不存在"候选按四边判可解、最终按底部审核"的口径分裂：

1. 盒切分：`pickBoxSplit` → `baseFillBoxesBottom`（v110 起默认再转 `baseFillBoxesBottomParallel`，见 §2b）
2. 候选筛选「1 遍基础 + 最多 3 遍噪声」：`screenCandidateFixed(parsed, timing, bottomOnly)` → `Solver.runSolver(..., bottomOnly, ...)`
3. 卡点分支重求解：`makeChokeVariantFixed` 与旧流程 `makeChokeVariant` 的 `Solver.solve(parsed, { bottomOnly })`
4. 三步前瞻可达、暂存自动释放、锁链滞留、管道推出后消除：均由 `Simulator.createState(level, { bottomOnly })` 起一路透传（`simulator.js`/`solver-strategy.js` 既有能力，本次未改）
5. 最终全知求解：`Solver.solve(parsed, { bottomOnly })`
6. 玩家模拟（审核用与难度分析兜底用两处）：`PlayerSim.run(parsed, { bottomOnly })`；`playersim.js` 内自维护的可达判定 `isReach()` 同步按 `bottomOnly` 分支（默认分支与引入前完全一致）
7. 网关色/内部深度启发（`gatewayColorRank`/`interiorColorRank`，供卡点换球挑目标用）：`outsideReachSeed`/`floodFillEliminate` 传参 + 内部 `edgeOpen()` 按模式分支；两个 WeakMap 缓存按模式分离，避免混用时串味

### 11.3 生产前可达性检查（输入/输出/调用时机）

`checkBottomEntryFeasibility(blocks)`（`generator.js`）：

- **调用时机**：`bottomOnly=true` 时，在 `produceFixed`/`produce` 的候选循环**最前面**执行一次，不通过则立即返回、不进入任何候选生成。
- **算法**：从 `outsideReachSeed(blocks, rows, cols, true)`（只播种与底边连通的空格）起，反复对每种剩余颜色执行 `floodFillEliminate(..., Infinity, ..., true)`，直到某轮 0 消除；此时仍未消除的彩色像素即该模式下永久不可达。复用现有可达逻辑，未引入新算法。
- **输出**：`{ ok, total, left, byColor, positions(≤50个坐标), rows, cols, detail }`。`ok=false` 时结果对象上带 `entryMode:'bottomOnly'`、`bottomEntryFeasibility`、`lastFailReason:'bottomEntryInfeasible'`，`structural.reason` 写明不可达原因，不消耗时间预算。
- **机理**：`floodFillEliminate` 的 `reachable()` 只从底边与已消除格扩散；空白格仅在 `outsideReachSeed` 初始播种时被标记已消除。底部模式只播"与底边连通"的空白，被顶/左/右背景连通空腔包围的色块永久摸不到——四边模式下这些空腔一开始就被播种，所以这是底部模式独有的风险。
- **实测**：348 张现有输入图（`txt图/348关txt图-7.28/`）全部通过检查，0 张不适配。

### 11.4 生产侧标记（不入关卡本体）

关卡 JSON 协议**不变**（`AntSolver.toGameFormat` 未改，本体仍为 `toprow/blocks/maprow/mapcol/spools`）。入口模式只记录在生产侧：

- `produceDispatch` 唯一出口处打 `out.entryMode = 'bottomOnly' | 'fourSide'`
- 网页批量：`app.js` 的 `genBuildRec`/`genLightSummary`/`genPersistPayload.debugData`、CSV 表头与行（新增「目标图入口模式」列）、`关卡数据.json` 每关记录、生产报告标注行
- 单关导出：`currentEntryMode` 变量，随 `produce`/`generate`/主线程批量循环三处生成入口设置，`loadLevel` 时重置为默认
- 传递给程序端的方式：**批次分组**（整批目录即一种入口模式），不新增关卡本体字段——游戏端解包产物（`bin/extracted_game/`）与官方协议文档均无可复用的入口/边界字段，故不自造字段（用户决定 D1）

#### 11.4b 导入侧回读入口模式（v121 新增，任务 `ANT-SIM-FRONTEND-SYNC-20260828`）

> 入口模式一直**只写不读**：生产侧记了三处，导入侧一处不读。
> `loadLevel` 无条件 `currentEntryMode = 'fourSide'`，于是导入一批底部消除关卡后，
> 页面上的求解、玩家模拟、压力图、难度分**全部按四边入口跑**，且界面上看不出任何异常。
> v121 把这条链路补上。

**数据其实早就在**（本轮只是去读它）：

| 来源 | 字段 | 谁写的 |
|---|---|---|
| `关卡数据.json` / 逐关 `关卡数据/<名>.json` | `levels[].entryMode` / 顶层 `entryMode` | v110 起由生产侧写入 |
| `求解数据/<名>.solve.json` | `meta.entryMode` | v100 导出对齐时写入 |
| 部分批次的诊断对象 | `generationEval.entryMode` | 生成期 |

**改前失效的三个原因**（都在 `bin/js/app.js`）：

1. `parseLibrary` **不读** `entryMode`（关卡数据侧的记录被整份忽略）；
2. `finishPackImport` 的 `normKey` 只剥 `.txt|.json`、**不剥 `.solve`** →
   求解数据的键是 `001_x.solve`、关卡本体是 `001_x`，**配对失败**；
3. 求解数据（`type:'ant-solve-data'`，`pickOrder` 在顶层）既不满足 `isDataPack`
   也不满足 `isOldAudit`（该格式**没有** `j.solve` 这个键），于是掉进 `levelFiles` →
   `parseLibrary` 认不出 → **静默丢弃整份求解数据**。

**改后口径**：

- `normKey(n) = n.replace(/\.(txt|json)$/i,'').replace(/\.solve$/i,'')`
- 新增 `isSolveData` 分类（`type==='ant-solve-data'` 或「有 `pickOrder` 且有 `meta` 且无 `blocks/spools`」），
  把 `summary` 搬进 `entry.solve`（免重算）、`meta.entryMode` 读进 `entry.entryMode`
- `parseLibrary` 读 `item.entryMode` / `data.entryMode` / `generationEval.entryMode`
- **优先级**：关卡数据侧 > 求解数据侧。两侧不一致时**以关卡数据为准并记 `entryModeConflict`**，
  面板显示黄字提示，不静默取一个
- `selectLevel` 在 `loadLevel` **之后**写 `currentEntryMode`（`loadLevel` 会把它复位），
  并 `syncElimModeSelect(elimModeOfEntry(...))` 同步手点消除模式下拉 ——
  不同步则进入模拟后手点消除仍按四边入口走
- **识别不到时如实回落 `fourSide` 并在面板标注「未知玩法（按四边入口加载）」**，
  **不靠棋盘结构去猜**：猜错会让整关按错规则跑而界面无任何异常

**三套命名的显式转换**（集中在 `entryModeOf` 附近，避免各处各写一遍三元表达式）：

| 概念 | 取值 |
|---|---|
| `entryMode`（落库/导出/generator） | `fourSide` / `bottomOnly` / `fourSideInstantChain` |
| 手点消除模式下拉 `#sim-elim-mode` | `fourSide` / `bottomOnly` / `instantChain` |
| 生成页入口下拉 `#gen-bottom-only` | `0`(缺省) / `1` / `2` |

工具函数：`normEntryMode(v)`（认不出返回 **`null`**，不猜）、`elimModeOfEntry(em)`、
`entryModeLabel(em)`（未知返回「未知玩法」）、`solveByEntryMode(level, em)`、`playerOptsOfEntry(em)`。

**顺带修的一处口径分裂**：`renderPressureCharts` 里全知压力曲线原先写死
`runSolver(currentLevel, 0, 1, true, false, ...)`（`bottomOnly=false` 且不传 `instantChain`），
而同一页的玩家曲线早就按 `playerModeOpts()` 走对了 → 底部/瞬时连锁关卡的**两幅图口径不一致**。
已改为按本关 entryMode。

#### 11.4c 逐关无损数据的分类与「只补不建」（v123，任务 `ANT-IMPORT-PERLEVEL-DATA-20260828`）

> v121 只修了**求解数据**（`求解数据/*.solve.json`）的配对。用户随后用
> `输出文件/v119底部消除298-08-28` 同时导入「合格关卡」+「生产文档」，暴露出第二条：
> **`生产文档/关卡数据/<名>.json` 这份逐关无损数据也没被正确分类。**

**用户实测现象**：导入后 218 关、只有 85 关带玩法标记、还把不合格关卡带进来了。
（该批实况：合格 133 / 不合格 84 / 逐关无损数据 217。用户的判断准确 ——
「你应该是记录的关卡数据包含了关卡内容本身，导致他们一起带进去了」。）

**根因**：`生产文档/关卡数据/<名>.json` 的顶层**直接是一个关卡对象**
（`name/valid/difficulty/grade/entryMode/bufferLimit/blocks/board/audit/generationEval/solve/…`），
而原有三个判据都不匹配 —— `isDataPack` 要求 `type==='ant-level-data'` 或 `levels[0].board`；
`isSolveData` 要求顶层 `pickOrder`+`meta`；`isOldAudit` 要求**没有** `blocks`。
于是它掉进 `levelFiles`、被当成**普通关卡本体**，后果三条：

| # | 后果 | 实测 |
|---|---|---|
| ① | 与 `合格关卡/<名>.json` **平级竞争同一个键**。`add(entry, true)` 是「本体不覆盖已有」→ **先到先得**；而文件走 `FileReader` 异步读、完成顺序不定 | 218 关里只有 **85** 关拿到玩法标记，且每次导入数字都可能不同 |
| ② | `parseLibrary` **不读 `solve`/`audit`** | 求解数据与审核结论**全丢**（`paired = 0`） |
| ③ | 它自带 `blocks`+`board` = 完整关卡内容 → 该目录下**全部** 217 关（含 84 不合格）都变成条目 | 用户看到的「非法关卡」 |

**修法一：新增分类判据**

```
isPerLevelData = !j.type && !j.levels && !Array.isArray(j) && j.blocks && j.board &&
                 ('solve' in j || 'audit' in j || 'entryMode' in j || 'generationEval' in j)
```

**修法二：「有本体则只补不建」**（这是本轮的核心口径）

- 同批**存在关卡本体**（`合格关卡/`、`关卡/` 等）→ 逐关无损数据只给**已有条目**补数据
  （覆盖 `level`、补 `solve`/`audit`/`generationEval`/难度/`entryMode`/`valid`），
  没有对应本体的（例如不合格那批的无损数据）**跳过并计数**，**不新建条目**；
- 同批**完全没有本体**（只导入了 `生产文档`）→ 才用无损数据建条目，
  保证「只导入生产文档也能用」这条既有能力不丢。

`level` 用无损的**覆盖**本体：本体是官方格式经 `fromGameFormat` 还原，冰耐久等字段按默认值补（有损）；
无损数据的 `board` 是生成期原样，优先级更高。

**修法三：配对键用文件名，不用 `j.name`**

`j.name` 是**源图名**（带 `.txt`，且重名关会被生产侧改名，实测该批有 1 关不一致 → 产生 1 个幽灵条目），
而 `合格关卡/`、`txt图/`、`求解数据/` 三处都按**文件名同名**约定落库（任务 O 定的三件套同名规则）。

**修法四：`normKey` 再剥落库分类后缀**

`不合格关卡/` 下的兜底关文件名是 `<名>__遍历兜底.json`，而 `生产文档/关卡数据/` 里同一关叫 `<名>.json`。
不剥就配不上，同一关会被拆成两个条目。该批实测有 **84 关**带该后缀（后缀由 `生产服务.js` 落库时加）。
现剥 `__遍历兜底` / `__超时兜底` / `__兜底`。

**修复效果（同一批数据实测）**

| 场景 | 改前 | 改后 |
|---|---|---|
| 合格关卡 + 生产文档 | 218 关 / 85 含玩法 / 0 含求解 / 含 84 不合格 + 1 幽灵 | **133 关 / 133 含玩法 / 133 含求解 / 0 不合格 / 0 幽灵**，并提示「跳过 84 关未选中的无损数据」 |
| 只导入生产文档 | 217 关 | 217 关（回落生效，行为不变） |
| 只导入合格关卡 | 133 关、无附加数据 | 133 关、无附加数据（如实反映「没给数据就是没有」，不伪造） |
| 不合格关卡 + 生产文档 | 168 关（同一关被后缀拆成两条） | **84 关** |

**导入提示同步改为分项如实显示**：`(133，133/133 含求解数据，133/133 含玩法标记，跳过 84 关未选中的无损数据)`。
改前只显示总数与两个可选项，看不出「有多少关被补全、有多少关被跳过」——而这两个数正是判断导入是否符合预期的关键。

验证：`_kiro临时/08.28-导入分类修复/_验v123.js` 第四节（四个场景全部真跑真实批次文件）；
复现脚本 `_复现导入.js` 先精确复现了 218/85/0 三个数再动手。

### 12.5 可用棋盘空间一致性（`usableSpaceTarget`）

**定义**：可用空间 U = (总棋盘格 C − 墙 B − 管道占位 P) / C。
**目的**：同一批像素图产出不同大小的棋盘，而密度保持一致（用户 2026-08-04 需求）。

**求解（`solveSpaceQuota`，全部是守恒、不靠试错）**：

```
占用配额 K = round(C × (1 − U))          ← 由目标可用空间直接确定
上盘盒格 = C − K，溢出盒 D = n − (C − K) = n − C + K
每条管道容量 pipeMinFill ~ pipeMaxDepth 个盒
  ⇒ P ∈ [max(minPipes, ⌈D/pipeMaxDepth⌉), ⌊D/pipeMinFill⌋]
黑块 B = K − P，须落在障碍参数容差内
```

> v105 起深度与单管最少装盒数改为参数（原写死 6 与 4）。默认 `pipeMaxDepth=6`/`pipeMinFill=4` 时
> 区间即原来的 `[max(minPipes, ⌈D/6⌉), ⌊D/4⌋]`，已验证与参数化前逐组等价（486 组）。

**降级顺序**：保持障碍参数 → 突破黑块比例（预算 2 次 × 5 个百分点，最大 10pp，用于保护小棋盘）
→ 两次预算用尽仍无解则该尺寸无解、直接排除（不在函数内偷偷改盒数）。硬上限 25% 始终生效。

**接入三处**：①`chooseBoardDimsFixed` 的尺寸取舍标准改为「该尺寸能否解出满足目标的组合」，
并在有解尺寸中择取（**v125 起不再是「所有有解尺寸随机取一个」**，改为「保管道 + 不突破墙上限」优先 + 逐行缩小，见 12.5c）；
②`buildStructureCandidateFixed` 的黑块数与管道数改取配额解；
③结构候选出口新增闸门，按**实际落位结果**复核。

**为什么必须有第 ③ 道闸门**：配额算得准，但落位会偏离——窄路墙黑块数不受配额控制会挤占黑块份额，
管道也可能因走廊保护与落位规则放不满。补闸门前实测 20 关中 3 关管道 <4、最大偏差 5.4pp 超容差；
补上后偏差收到 1.0pp、管道全部达标。淘汰理由为 `usablePipeShort` / `usableSpaceDeviation`。

**一个算出来的硬结论**：大棋盘 + 管道≥4 + 盒数约 57 三者互斥。
7×8(56格) 只溢出 15~16 个盒，而 4 条管道每条至少装 4 盒 = 至少 16 个；7×9(63格) 溢出仅剩 10~11 个，
连 3 条管道都填不满。要覆盖更大棋盘只能增加盒数（切分容量），这是守恒结论、不可绕过。

**实测取值**（65%~78% 扫描后）：目标 **74%**、容差 5 个百分点。该档是唯一同时满足
偏差 ≤5pp、管道 ≥4、尺寸多样、出关率不低的档；78% 出关率虽 100% 但管道均值跌破 4、偏差 6.6pp 超容差。

### 12.5b 管道容量口径参数化 + 管道不足兜底（v105，任务 `ANT-GEN-PIPE-DEPTH-FALLBACK-20260825`）

**当前真实行为**：管道容量不再有写死数字，全部由三组参数决定，取值统一经
`pipeDepthOf(config)` / `pipeMinFillOf(config)` 读取（缺省或非法回落原写死值，`pipeMinFill` 夹到 ≤ `pipeMaxDepth`）。

| 参数 | 默认 | 进入哪些判据 |
| --- | --- | --- |
| `pipeMaxDepth` | 6 | `pipeCapacity` 容量校验、溢出盒入队上限、`pipeDepth` 深度合法性、`pipeStat.capacityPerPipe`、`solveSpaceQuota` 的 `P` 下界、旧路径 `generateFromBlocks` 的重铺判据 |
| `pipeMinFill` | 4 | `solveSpaceQuota` 的 `P` 上界 `⌊D/pipeMinFill⌋`、`pipeCountByConservation` 的区间上界 |
| 两者共同 | — | `pipeCountByConservation` 区间 `[⌈D/(maxDepth−1)⌉, ⌊D/(minFill−1)⌋]`（首扫每管已占 1 格）；`chooseBoardDimsFixed` 的 `minOv = minPipes × ⌈(minFill+maxDepth)/2⌉`（原写死 `×5`） |

**为什么深度可调不触及求解器**：官方格式 `spools[].param` 是不限长的队列数组，`simulator` 也不校验
队列长度（读码确认）。深度只是生成期的容量口径。

#### 参数矛盾：这是 v105 之前一次全批 0 产出的直接成因

`minPipes` 条管道要求 **溢出盒 `D ≥ minPipes × pipeMinFill`**。这条约束原先没有任何提示。

2026-08-25 实测：`方案_v104.json`（`minPipes=4`、盒容量 40-70、棋盘 8-9×8-10、可用空间 74%）
对「55像素图纸修复后汇总 8.20」生产，53 张过碎色闸门的源图 **0 产出**，0.1 秒返回 `noCandidate`。
两条失败路径：

- `0 < D < 16` 的组合：配额层**全部无解**（46/46，本轮验证脚本已复现）；
- `D ≤ 0` 的组合：配额层直接给 `P = minPipes` 看似有解，但棋盘多出空格（`structSurplus`）
  或 4 条管道在走廊保护/出口唯一/可达性约束下**放不满**（实测 `want 4 → placed 0~3`）。

该批源图实际盒数 52~65，而结构层可行窗口实测 `n ≥ 68` → 0/53 落在窗口内。

#### 兜底：两个触发点

用户 2026-08-25 两次裁决：①「如果其他参数影响导致管道不够，则保底 2 个管道，深度 3」；
②「突破下限管道数，最低为 2 个管道 2 层深度。如果低于这个下限就直接去除管道」。

| 级 | 判据 | 参数 | 默认 |
| --- | --- | --- | --- |
| ① 主轮 | `minPipes` 条 / 每管 ≥ `pipeMinFill` | — | 4 条 / ≥4 |
| ② 兜底 | `pipeFallbackCount` 条 / 每管 ≥ `pipeFallbackDepth` | `pipeFallbackCount`、`pipeFallbackDepth` | 2 条 / ≥3 |
| ③ 绝对下限 | `pipeFloorCount` 条 / 每管 ≥ `pipeFloorDepth` | `pipeFloorCount`、`pipeFloorDepth` | **2 条 / ≥2** |
| ④ 去除管道 | 连 ③ 都到不了 → `P = 0`，管道格全让给盒 | — | 不可单独关（见回退开关） |

每级都是**硬下限**，没有「放行更浅管道」的松弛（该松弛是本轮早先的口径，已被用户第二次裁决取代）。
口径统一为 `D ≥ P × 每管最少`（保守读法：实际填球时首扫每管还先得 1 个盒，故实际深度只会 ≥ 要求）。

**两个触发点**：

1. **配额层** `solveSpaceQuota`：按 ① 求不出可行 `(P,B)` 就依次试 ②③，都不行走 ④。
   命中 ②③ 返回 `pipeFallback` + `pipeFallbackTier`（`'fallback'`/`'floor'`）+ `pipeFallbackFrom/To`；
   命中 ④ 返回 `pipeWant:0` + `pipeDropped` + `pipeDroppedDevPp` + `pipeDroppedBoxCells/BoxNeed`。
2. **结构层** `buildStructureCandidateFixed`：按**实际落位**复核同一阶梯。落位达不到 ③ 时
   **撤除已落位的全部管道**、格子退回普通盒格，标 `pipeStat.pipeDropped` + `pipeDroppedInfo`；
   撤除后仍有盒无处安放才淘汰。落在 ②③ 档则标 `pipeStat.fallback` + `fallbackTier`。
   `P=0` 且属有意为之（配额层判无需管道 / 已整体撤除 / 溢出为 0）时标 `noPipeAccepted`，
   不再拿 `minPipes` 卡它。

**边界与失败回退**：

- **④「去除管道」的守恒推导**：`P=0` 时上盘盒格 = `C − B`，装下全部 `n` 个盒需 `B ≤ C − n`。
  取 `B = min(K − D, C − n, bMax)` —— 既尽量贴近占用配额 `K`（可用空间偏差最小），又不越过
  「盒必须全部上盘」与「黑块比例容差 + 25% 硬上限」两条上界，按既有降级顺序在最早可行的突破级别命中。
  **不能把 `B` 固定成 `K − D`**：`D ≤ 0` 时 `K` 本身可能超过黑块 25% 硬上限（原先那 P 条管道占的是
  "非墙"的占位额度），固定住会让所有 `D ≤ 0` 的尺寸全判无解（实施中实测到该缺陷并已修）。
  代价是墙变少、可用空间高于目标，偏差记在 `pipeDroppedDevPp`，超 `usableSpaceTolPp` 则该尺寸判无解。
- **结构层撤管道的守恒前提**：撤掉 P 条管道使普通格 `+P`、溢出 `−P`，只有 `overflowReal − placed ≤ 0`
  才允许撤（否则撤了就丢盒）；不满足则保留管道，由 `pipeCapacity` / `usablePipeShort` 如实淘汰。
  撤管道只移除障碍，不可能破坏「空格顶部可达」与墙体形态约束（2×2 / 直线 3 连），故无需重查。
- **`D ≤ 0` 直接走 ④**：棋盘本来就装得下所有盒时，硬塞管道只会得到装不满 2 层的空管道，
  而那些空管道正是落位失败（`usablePipeShort`）的主要来源。**这改变了 v104 的行为**
  （v104 会给 `minPipes` 条空管道）。
- **守恒硬约束贯穿全阶梯**：`D ≤ P × pipeMaxDepth`，且 `P=0` 时必须 `D=0`。
  已用「溢出 40 > 2×6」构造样例验证不放行。
- **完整回退开关**：`pipeFallbackCount = 0` **且** `pipeFloorCount = 0` → 连 ④ 也不做，

#### 与上一版差异及变更原因

| 项 | v104 及以前 | v105 | 原因 |
| --- | --- | --- | --- |
| 管道深度 | 常量 `MAX_PIPE_DEPTH = 6` | 参数 `pipeMaxDepth`，默认 6 | 用户要求可调 |
| 单管最少装盒 | 写死在 `⌊D/4⌋` 里 | 参数 `pipeMinFill`，默认 4 | 只放开深度等于只调一半；这个 4 才是 0 产出的成因 |
| 管道不足 | 直接淘汰候选（`usablePipeShort`） | 四级阶梯降级，最后一级去除管道；仍不行才淘汰 | 用户要求保底 2条/≥3，绝对下限 2条/≥2，低于则去除 |
| `D ≤ 0` 时 | 给 `minPipes` 条**空管道** | `P = 0`（无管道） | 空管道不构成卡点、又是落位失败主因 |
| 变体关的 `pipeStat` | 丢失 | 透传 | 阶梯降级是行为变更，必须可追溯 |

**⚠ 行为变更**：阶梯默认开启 → 原本被淘汰的候选可能通过、`D ≤ 0` 的关从「空管道」变「无管道」
→ **旧批次不再逐字节可复现**。复现旧批次须 `pipeFallbackCount = 0` **且** `pipeFloorCount = 0`
（两个都要设，只设一个不够）。深度与 `pipeMinFill` 的参数化本身在默认值下已验证等价。

### 12.5c 墙过多缩棋盘（v125，任务 `ANT-GEN-WALL-SHRINK-20260831`）

> 用户 2026-08-31：「墙过多超限制就应该通过缩小……棋盘的方法处理……棋盘小肯定盒多，
> 这样管道就可以正常生产了，也不会执行墙超限兜底」；追问「q1 统一」（采用推荐方案）。

**要解决的现象**：`usableSpaceTarget>0` 时，若方案的行列范围内合法形态（列−行∈{1,2}）都比像素图切出的盒数大，
`solveSpaceQuota` 会在这些大盘上溢出盒 `D≤0` → **去掉管道**（`pipeWant=0`/`pipeDropped`），把
`(1−usableSpaceTarget)` 的占用配额几乎全塞给墙。实测 `方案_v119四方向`（范围 8-9×8-10，合法形态仅 8×9/8×10/9×10）
墙占比均值 13.9%、最高 20%（目标 5%），25 关里 14 关 0 管道。

**当前真实行为**（`chooseBoardDimsFixed` 的 usableSpace 支路，替代原「所有有解尺寸随机取一个」）：
1. 收集**方案范围内 + 逐行向下缩小**的全部可行尺寸。缩小：`rr` 从 `rMin−1` 到 `max(6, rMin−3)`，每级只取
   `cols=rr+1` 与 `cols=rr+2`（天然满足 `boardShapeOk`，绕开「单维交替减 1」会撞的列−行=3 非法态）。每尺寸带 `shrinkDist=rMin−rr`。
2. **优先「干净」尺寸** = 保住管道（`pipeWant>0` 且未 `pipeDropped`）**且 `breachLevel==0`**（墙未突破基础容差），
   取 `shrinkDist` 最小的一级、同级内随机 → **只缩到刚好不再突破墙上限**；不同盒数的图缩到不同大小，保留尺寸多样性。
3. 无 `breachLevel==0` 的 → 退取「保管道里 `breachLevel` 最低、其次 `shrinkDist` 最小」者。
4. 连缩到下限都保不住管道 → 回落范围内可行尺寸随机（原行为），`boardPick.pipeDroppedPick=true` 如实标记。

**只改「选哪个尺寸」**：`solveSpaceQuota` 的配额联立、`buildStructureCandidateFixed` 的落位、管道阶梯一律未动。

**实测对照**（348 源图前 30 张，改前→改后）：墙占比均值 13.9%→**6.4%**、最高 20%→**11.1%**、墙数均值 10.6→**3.9**、
管道均值 1.20→**5.63**、去管道 14/25→**0/30**、全知可解 30/30。底部消除方案（usable 0.8 / 0.74）抽检正常、可解、无崩溃。

**权衡（8f.3 三根因里「墙被配额顶高」这条的实际处置）**：要在 `usableSpaceTarget=0.78`（占用配额 22%）下把墙压到
`blackPercentMax=5%`，管道需占约 17%，这要求大量溢出 → **必须把盘缩到比方案行数下限更小**（实测多落 7×8/7×9）。
即本改动会**系统性无视方案行数下限、把盘缩小**。若要保住较大棋盘又不超墙，应**调低 `usableSpaceTarget`** 或**加深 `pipeMaxDepth`**，属参数层决策。
（另：`方案_v119四方向.json` 同轮把 `pipeMinFill` 4→3 修正了 `pipeMinFill>pipeMaxDepth` 导致主轮管道恒空的自相矛盾。）

### 12.8 已知限制

- **窄路在本模式下稀少**：`narrowPathProb=0.5` 时实际落地率远低于 50%。已排除概率逻辑出错
  （p=1、p=0 端点均正常）与可用空间闸门（放宽容差 5→8pp 无改善，出关率反而下降）。
  怀疑是多候选筛选的评分偏置（窄路增加难度 ⇒ 带窄路候选更易不合格 ⇒ 择优被挤掉），
  **该根因未经验证**。用户裁决接受现状，`narrowPathProb` 仅作开关保留。
- 约 36%~50% 的关卡因最终 board 来自卡点变体（会重建 board）拿不到 `narrowStat`，窄路状态不可观测。
- 本模式暂存压力天然低于原四方向（实测 6 关峰值均值 2.83 对 4.83），**困难合格占比偏低**
  （50 关中困难合格 5~9 关），绝大多数为简单合格。
- 开启管道下限与可用空间一致性后审核淘汰率约 30%~42%。
- 网页端未接入（无模式选择入口、无分段动画播放），属后续需求。
