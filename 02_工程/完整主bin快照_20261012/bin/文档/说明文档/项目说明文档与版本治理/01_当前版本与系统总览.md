## 三、游戏目标与胜负条件（E2，机制见 simulator.js/solver.js）

- 目标：从棋盘按规则取「蚂蚁盒」，消除目标图像的全部像素即通关。
- 取盒 → 消该盒颜色的像素（数量=盒 `count`）；当场消不完的盒进入**暂存区**。
- **胜**：`已消像素 ≥ 总像素`（E2 solver.js）。
- **负（死亡）**：暂存**瞬时超上限**（含锁链整组入场即超）——严格判死、道具不可救；或超上限自动释放后仍超（E2 solver.js）。
- 暂存上限 `bufferLimit` 生产基线 = 5（E2）。

## 四、目标图 / 盒 / 暂存 / 障碍 / 复活的当前规则

- **目标图**：像素图（TXT 或生成），按「由底部+左右两侧向中心」为默认消除趋势切分成盒（E1/E2）。
- **盒**：单色，含 `count` 个同色像素；棋盘取盒始终要求顶部/首行可达（E2）。
- **暂存区**：取下未当场消完的盒暂存，容量 `bufferLimit`（E2）。
- **黑块/墙**：占格制造窄路；墙体硬约束（不组成 2×2、直线≤3 面相连，边缘算墙）（E1，建棋盘）。
- **冰块**：冰锁盒需「已激活且解冻步数≥耐久」才可取；靠取其它盒推进步数解冻（E2 simulator）。
- **锁链**：2/3 连整组同时取、整组释放；组内任一成员未激活/冰未解则整组锁定（E2 simulator）。
- **问号**：未知色像素，揭示后参与消除；全知求解器已知其真实色（E1/E2）。
- **管道**：既作墙体占格制造窄路，又作盒容器（每管容量 4–6）；出口须盘内合法、不共用出口（E1/E2）。
- **玩家复活道具**：玩家卡死时自动触发，优先消暂存区剩余订单最大的 2 盒（暂存不足则从棋盘残留补），无视依赖封锁按最近距离直取；每关 ≤2 次，≤2 次通关=玩家版合格（E2 playersim）。

## 五、生产闭环：TXT → 关卡包（E2，详见 `02` 调用链）

```
TXT 目标图 → 解析目标图 → 建棋盘(尺寸随机/黑墙窄路/守恒反推管道/顺序填球) → 首批障碍(问号冰全填,锁链50%)
→ 合法性门(结构可达+无共用出口,不求解) → 六遍求解(贪心×2→三步树×2→噪声×2)
→ 玩家模拟 → 审核(chokepointAudit)+难度(computeDifficulty)
→ 未合格则卡点分支(换球/增容,B×N 轮) → 三档优先级选候选(合格即停,否则兜底)
→ 批量结果 → 关卡/*.json + txt图/*.txt + 关卡数据.json + 分析报告.csv + 生产报告.md
```

## 六、全知求解 / 玩家模拟 / 审核 / 难度 / 兜底 的关系

- **全知求解器**（solver*）：已知问号色/管道序，判**可解性**（合法性硬门）+ 给参考解 + 出**压力样本**（审核基准）。（E2）
- **玩家模拟器**（playersim）：只知半消画面、会误判、并发按 tick 消除、死锁触发复活；判**真人可通关** + 供**难度主依据**。（E2）
- **审核**（analysis.chokepointAudit）：依据全知压力曲线判「困难合格 / 简单合格 / 不合格」——回答「能不能用」。（E2）
- **难度**（analysis.difficulty / computeDifficulty）：依据玩家版表现打 0–100 分——回答「有多难」。（E2）
- **两条并行分支**：难度分只在候选**已合格后**计算，从不反馈进「能不能用」判定（E2/E1）。
- **兜底**：全程无合格则按三档优先级（困难合格>简单合格>安全兜底>其余）输出最高档候选，并标 `fallback` 系列字段（E2）。详见 `bin/文档/说明文档/生产审核评分体系.md`。

## 七、生产器页面与批量能力（v87–v94，E2 app.js/gen-worker.js）

- **独立生成器页面**（v87）：顶部切换模拟器/生成器；导入 TXT、文件列表排序/分组/筛选/删除；参数手风琴；进度可视化（进度条/统计芯片/实时日志）。
- **批量生产用后台线程**（v88）：Web Worker 跑 `produce()`，主线程不卡、停止即时；`file://` 下浏览器禁用 Worker，自动回退主线程（生产时页面短暂冻结）（v91 明确文案）。
- **手动下载**（v89/v90）：生产完成不自动下载，出现「下载关卡包」按钮点击才下载；大 ZIP 延后 revoke 修复「点了没反应」（v90）。
- **单关看门狗**（v92）：某关超过「单关限时+2 分钟」无返回则判卡死、跳过并重启线程续跑（仅 Worker 模式）。
- **导入修复**（v93）：导入关卡包不再逐关求解（改惰性，打开某关才算难度），整包 `关卡数据.json` 与 `关卡/*.json` 按去扩展名去重、不再翻倍。
- **逐关自动落库**（v94，**当前正式生产路径**，E2/E3）：由 `网页启动器/生产服务.js`（零依赖 Node，只绑 127.0.0.1、只写 `输出文件/`）与页面配合——每产出一关即 POST 落库，**服务原子写盘确认后才派发下一关**；写盘失败立即暂停并可「重试落库」（按 `batchId+inputIndex` 幂等）。批次目录 `输出文件/<批次名>-月-日[-2/-3]/`，分 `合格关卡/`、`不合格关卡/`(名带失败分类)、`txt图/`、`不合格txt图/`、`生产文档/`(批次配置/生产状态/逐关记录.jsonl/分析报告.csv/生产报告.md/关卡数据/)。落库确认后浏览器只留轻量摘要，**不再构建整批 ZIP**（旧 ZIP 下载仅在未连服务的兜底模式保留）。看门狗超时同样落库后才重启线程。
- **生产性能埋点**（v94，E2）：每关记录建盘/管道重铺/基础候选/卡点变体/重生成/评价次数、`solve` 调用与贪心遍/树遍数、玩家模拟次数、各阶段耗时与停止原因，写入逐关记录与 CSV。**仅测量，未改动任何生成/求解策略**（算法提速属阶段6，待单独批准）。
