## 1. 压力阈值（随暂存上限动态）

设暂存上限为 `L`（生产基线 `L=5`）。

| 名称 | 计算 | L=5 | L=7 | 含义 |
|---|---|---|---|---|
| **卡点阈值**（旧称高压阈值） | **`L − 1.8`**（v118 起） | **3.2** | **5.2** | 卡点线。沿革：`L−1.5`(v104~v117) → v110 曾试 `L−2.5` 当日回滚 → v118 用户改 `L−1.8` |
| **中压阈值** | `L − 2.5` | 2.5 | 4.5 | 中压线 `L−2`，额外 `−0.5` 滑点。**自始未改** |

> **v118（用户 2026-08-27「将卡点阈值改为 N-1.8」）**：卡点线由 `L−1.5` 下调为 `L−1.8`。
> 这是**放宽**，与同轮的「窗口宽 10%→5%」同向，用于缓解卡点形成率过低（见 §1b 实测）。
> 与 v110 那次下调不同：本次 3.2 仍**严格高于**中压线 2.5，不会出现两线重合、层次消失的问题；
> 且 v118 已把「中期」整段移除、前期改用卡点线判定，不存在 v110 那种「一个常量同时改三条判据」的耦合。
>
> **与难度分已解耦**：`DIFF_CAP.f1` 仍为 **3.5**（= 旧 `L−1.5`），本轮**未改难度分**。
> 两者从此不再相等 —— f1 是难度标定（「平均暂存摸到 3.5 即满分」），卡点线是合格门判据。
> 把两者当成同一个数是 v110 踩过的坑，此处显式分开记录。
> 代码中对应 `CHOKE_OFFSET = 1.8`；旧偏移 `CHOKE_OFFSET_LEGACY = 1.5` 保留，仅供旧口径对照字段使用。

#### 一次已回滚的阈值下调（v110 → v111，2026-08-26，留档以免重复踩）

v110 曾按用户裁决把高压阈值下调为 `L − 2.5`，**同日 v111 按用户裁决「恢复 N-1.5」回滚**。
当时的起因与数据都成立，日后若再动这条阈值应先读本节。

**起因**：底部消除参数下实测**后期 10% 窗口均值中位仅 2.25~2.33**，高压线 3.5 很难摸到。
隔离变量实测（同一批压力曲线只换阈值、不重跑生产）：

| 盒切分 | `high=3.5` | `high=2.5` |
|---|---|---|
| 单色批量（12 关样本） | 有卡点 0/12，合格 0 | 有卡点 **7/12**，合格 **7** |
| 多色并行（12 关样本） | 有卡点 1/12，合格 1 | 有卡点 6/12，合格 5 |
| 单色批量（8 关样本，v111 复核） | 有卡点 2/8，合格 2 | 有卡点 4/8，合格 3 |
| 多色并行（8 关样本，v111 复核） | 有卡点 3/8，合格 2 | 有卡点 4/8，合格 2 |

⚠ 注意两次样本结论不同：3.5 线下的卡点形成率**不是恒为 0**，而是**很低且噪声大**
（12 关样本 0/12，8 关样本 2~3/8）。无种子控制，小样本不足以定标。

**下调带来的三处副作用**（很可能正是回滚的原因）：

1. **高压线 == 中压线**。中压阈值本就是 `L−2.5`，下调后两者相等，合格门退化为**单一压力线 2.5**，
   三档层次（前期中压线 / 中期高压线 / 后期卡点线）消失。
2. **`midOK` 被动收紧**。该条判据是「中期峰 < 高压阈值」，故中期上限由 3.5 变 2.5（实测 `midOK` 10/10 → 7/10）。
3. **「简单关·趋势过平」这一档几乎消失**。该档定义是 `trendOK && !hasChoke`；
   阈值重合后后期只要到 2.5 就算卡点，够不到就多半连 `trendOK` 也不过。
   12 关样本在 2.5 下是「不合格×5 / 合格×7」**零个简单关**；v111 恢复 3.5 后重新出现（8 关样本得 2~3 个）。
   这一档承担「简单关名额」，消失等于失去难易配比的一个来源。

**结论**：卡点难形成是**真问题**，但下调 `highThreshold` 不是干净解法——它同时改了三条判据。
若要再解决，方向是**给「卡点线」独立参数、与「中期爆压线」解耦**，而不是动这条共用阈值。

**临时对照口径**：调用方可传 `opts.high` 覆盖，不必改代码
（`chokepointAudit(samples, totalBoxes, bufferLimit, { high: 2.5 })` 已实测可用）。

- 「窗口均值」= 该进度窗口内所有压力样本的暂存均值。
- 窗口为**滑动窗口**，起点步长 **1%（未改）**。
  **窗口宽自 v118 起全阶段统一 5%**（v117 及以前：前段 5%、卡点区 10%）。
  用户原话「同时卡点窗口滑动改为 5%」。窗口变窄 → 短促峰值被平均得少 → 峰窗值抬高，
  与阈值下调同向，都是放宽卡点判定。实测该批中后期峰窗中位 **2.5 → 3.0**（44/47 关抬高）。

`Math.max(0, a.midMax - high)` 变 `NaN` → 候选评分全废（静默污染，比报错难查得多）；

### 为什么中期必须同步收缩到 20%~30%

中期判据是「峰 < 高压」，卡点判据是「峰 ≥ 高压」。卡点区一旦下移到 30%，
`30%~50%` 就被**同时**要求两件相反的事 —— 逻辑矛盾。不收缩会让落在 30~50% 的卡点关
「明明有卡点却仍判不合格」，改动等于打了折扣。故中期收缩为 `[20%, 30%]`，这是唯一自洽读法。
（`输出文件/110底部-08-27` 实测：两种取法结果相同、冲突关数 0，故该批结论不受此选择影响。）

## 2. 合格标准（v103 及以前的两档口径，已被 §2-0 取代，保留供回溯）

进度轴 = 已完成盒数 / 总盒数（0~100%）。审核不再是单一及格线，而是**两档标准**（`chokepointAudit()` 同时算出两者，取更优的一档）：

### 2.1 困难合格 `pass`（四条件全部满足）

| # | 阶段 | 条件 | 目的 |
|---|---|---|---|
| ① | 后期 50-100% | **至少 1 个** 10% 窗口均值 **≥ 高压阈值**（= 真实卡点） | 中后期必须存在高压卡点 |
| ② | 前期 0-20% | **不存在** 5% 窗口均值 **≥ 中压阈值** | 前期必须低压（不早爆） |
| ③ | 中期 20-50% | **不存在** 5% 窗口均值 **≥ 高压阈值** | 中期可到中压，但不可高压（避免卡点前移） |
| ④ | 全程 | 暂存**峰值 < 上限**（留 ≥1 空位余量，不触达 L） | 全知被迫塞满暂存(峰值=上限)=死亡边界=真人必死的非法卡点，判不合格 |

```
high = L − 1.5 ;  mid = L − 2.5
earlyMax = 前期[0,20%]内 5%  滑窗均值的最大值
midMax   = 中期[20%,50%]内 5%  滑窗均值的最大值
lateMax  = 后期[50%,100%]内 10% 滑窗均值的最大值
peakBuf  = 全程暂存峰值
pass = (lateMax ≥ high)   // ① 有卡点
     且 (earlyMax < mid)  // ② 前期不超中压
     且 (midMax  < high)  // ③ 中期不超高压
     且 (peakBuf < L)     // ④ 暂存峰值低于上限(留余量，非死亡边界)
```

### 2.2 简单合格 `easyPass`（趋势符合，v82 新增）

四条件里的①放宽：**不要求真实卡点，只要求压力趋势朝正确方向走**——前中期不越压力阈值，且中后期压力确实比前期高。**不要求"升高后必须回落"**，也不要求真的形成结构性卡点，允许把"造不出真实卡点、但走势健康"的关卡也留用（比如目标图本身依赖链条较少、天然做不出高压点）。

```
bump = max(中期峰窗, 后期峰窗)
easyPass = (earlyMax < mid) 且 (midMax < high) 且 (peakBuf < L)   // 前中期不越界 + 未触死亡边界(与困难合格②③④相同)
         且 (bump ≥ mid) 且 (bump > earlyMax)                      // 中后期压力≥中压，且高于前期(趋势提升)
```

### 2.3 分档结论 `tier`

```
tier = pass ? '困难合格' : (easyPass ? '简单合格' : '不合格')
```

- 窗口按「完全落在该阶段区间内」统计（前期起点 0~15%、中期 20~45%，均为 5% 窗；后期起点 50~90%，10% 窗）。
- `pass` 和 `easyPass` 都不满足 → **不合格**，报告给出原因（`reasons`）。

## 2b. 生产输出的三档优先级（`generator.js produce()`）

生产选出哪个候选作为最终输出，遵循**严格的三档优先级**（`candTier()`/`candBetter()`），档次之间**不允许用分数互相压过**，同档才比 `candScore`（审核评分+封锁曲线+玩家表现细分）排出更好的那个：

| 档 | 名称 | 条件 |
|---|---|---|
| **3** | 困难合格 | 审核 `tier='困难合格'` **且** 全知/玩家均可通关 **且** 全知暂存峰值 < 上限 |
| **2** | 简单合格 | 审核 `tier='简单合格'`（趋势符合） **且** 同上可通关条件 |
| **1** | 安全兜底 | 全知/玩家均可通关、未触死亡边界，但压力曲线未达标（不算合格，但至少是能正常玩通的关，不是坏关） |
| **0** | 其余 | 不可解 / 玩家打不通 / 触死亡边界 |

- **一关合格即停**：只要候选拿到档 3 或档 2，立刻输出，不再继续搜索（`candPass`）。批量生产可用 `requireHardPass` 参数强制只认档 3 早停（简单合格不算数，继续搜索直到拿到困难合格或超时），供"按比例分配简单/困难关卡"的批次配比使用。
- **全程无合格 → 兜底**：搜索预算（候选数×分支×轮次，或超时）用完仍没拿到档 2/3，输出树内已评估过的**档次最高**的那个候选（同档再比 `candScore`）；即"最优先出合格关，其次趋势符合关，最差也要挑一个安全能玩的简单关垫底"，绝不会因为凑巧分数高就把一个"玩家打不通"或"触死亡边界"的坏关当作兜底结果交出去。
- 最终输出对象上：`audit.tier` 始终准确反映困难/简单/不合格（`chokepointAudit()` 定的，不会被覆写）；`audit.pass` 在 `produce()` 收尾后表示"整体合格"（档 3 或档 2 都算 true），如需区分具体是哪一档，认 `audit.tier`。

### 2b.1 兜底标记（v86 新增）

档 3/2（正常合格）与档 1/0（兜底交付）在输出对象上有明确区分，不需要靠"没看到合格原因"去猜是不是兜底：

| 字段 | 含义 |
|---|---|
| `fallback` | `true`=这关是兜底交付的（档1或档0），不是正常合格输出；`false`=正常合格（档3或档2） |
| `fallbackTier` | 仅 `fallback=true` 时有值：`1`=安全兜底(至少双方可通关，但压力曲线未达标)；`0`=最接近标准的候选(仍不合格，含"玩家打不通"等更严重的问题) |
| `fallbackType` | 仅 `fallback=true` 时有值：`'timeout'`=单关生产时间预算到点被迫中止搜索；`'exhausted'`=候选数×分支×轮次已经穷尽仍无合格候选 |
| `fallbackReason` | 供人读的一句话说明，按 `fallbackTier × fallbackType` 组合给出对应文案，同时会追加进 `audit.reasons` |

判定用的是候选的**原始档次**（`candTier`，在 `audit.pass` 被改写为"整体合格"语义之前算好），不是事后看 `audit.tier` 的字面值——例如某关 `audit.tier` 显示"简单合格"（压力曲线形状达标），但玩家版实际未通关，`fallback` 仍会正确判定为 `true`（因为"能否真交付"要求全知和玩家都必须能通关），不会被曲线形状的表面合格蒙过去。
批量生产的完成提示、CSV 报表（"是否兜底"/"兜底类型"两列）、`关卡数据.json`、`生产报告.md`（独立的"兜底关卡"章节，与"不合格明细"分开列）都会带上这四个字段。

## 4. 生产主流程（P3 候选审核树，取代老版两轮爬山）

> **本节描述的是当前 `produce()` 的实际流程**。老版"候选筛选 + 第二轮爬山强化"（`strengthenBudget` 驱动的单路径微调）已在 v79 被 §2.b 描述的**候选审核树**取代退役；`strengthenLevel` 函数及其5个扰动子函数已在 v85 确认无调用者后删除。

批量生产按【候选数 K × 卡点分支 B × 轮数 N】的树状搜索进行（默认 `K=6 B=3 N=2`，详见 `生产器重构需求.md` §2）：

1. **K 个候选初生成**：各过【结构无卡死 + 六遍求解可解】的合法性门。
2. **任一候选初生成即达档 2/3（简单/困难合格）→ 立即输出并停**。
3. **未合格的候选** → 展开 **B 个卡点制造分支**（换球/增容，见 `生产器重构日志.md` P8/P10/P16）→ 各自重解 + 审核；任一变体合格即停。
4. **不合格变体** → 进入下一轮（共 N 轮），第 2 轮起附带增减压修复（据审核诊断调障碍参数）。
5. **单关时间预算封顶**（`timeBudgetMs`，默认 5 分钟）：到点仍未合格立即停止搜索。
6. **全程无合格 → 兜底**：按 §2b 的三档优先级（`candTier`/`candBetter`）选出树内已评估过的**最高档**候选输出，同档再比 `candScore`（下方评分函数）。

`candScore`/评分函数（同档候选排序判据）：`min(后期峰窗, 高压) − max(0,前期峰窗−中压)×3 − max(0,中期峰窗−高压)×3 (+合格100) + 全知/玩家封锁曲线加分 + 玩家复活越少越优`。
可解性由"每步重求解"保证；颜色守恒由"换球只换色+量、增容守恒同色总量"保证。

## 4-0. 难度评分体系 v5（现行）：f1 重标定 + f2 改无量纲占比

> 2026-08-05 起生效，取代下方 §4a 的 v4。任务 `ANT-DIFF-V5-SCALEFREE-20260805`。
> 实现：`analysis.js` 的 `DIFF_CAP` 与 `difficulty()`。**公式与权重不变**，只改两个因子的上限/量纲。

```text
难度主分 = f1×65% + f2×25% + f3×10%
难度总分 = clamp(主分 + 复活次数×8, 0, 100)
```

| 因子 | v4 | **v5** | 变更理由 |
|---|---|---|---|
| f1 玩家平均暂存 | cap **2.5** | cap **3.5** | 当初取 3.5 的理由是「3.5 = 当时的高压阈值 `L−1.5`，含义是平均暂存摸到高压线即满分」；v4 的 2.5 只等于暂存上限的一半，把**正常运行区间当成了天花板**。**⚠ 该等式自 v118 起不再成立**：卡点线已改为 `L−1.8`（L=5 → 3.2），而 f1 cap **仍是 3.5 且本轮未动** —— 两者**已解耦**，见 §1。沿革：v110 下调阈值时等式曾短暂失效 → v111 回滚后重新一致 → **v118 再次分离，此后按「f1 是难度标定、卡点线是合格门判据」两条线各自维护，不得因改一个而顺手改另一个**（v110 就是这么踩坑的）。f1 cap 自 v5 起从未改动 |
| f2 玩家平均滞留 | **原始步数**，cap 7 | **无量纲占比** `平均滞留 ÷ 有效操作步`，cap **0.06** | 「操作 tick」在不同玩法下不是同一量级，原始步数不可跨模式比较（见下） |
| f3 基础障碍 | cap 200 | **不变** | 用户裁定 f3 表现正常：同批障碍参数一致时 f3 近似常数是**预期结果**，不是缺陷 |

等级边界、复活 +8、权重 65/25/10 **均未改动**。

### 为什么 f2 必须无量纲化（实测证据）

「操作 tick」的物理含义随玩法变化：

| 玩法 | 一个 tick 是什么 | 有效操作步（实测中位） | 平均滞留（实测中位） |
|---|---|---:|---:|
| 四方向消除 | 各球各吃 **1 像素**的一轮 | **1743** | **80.3** |
| 四方向瞬时连锁 | 取盒 + **完整瞬时结算** | 26~87 | **1.27** |

两者原始滞留相差 **63 倍**，单一 cap 不可能同时服务：v4 的 cap=7 在瞬时连锁上零封顶、
在四方向上**封顶 63/63**，f2 退化成恒等于 25 分的常数、完全丧失分辨力
（这是 `试验关卡/四方向消除63关` 难度中位 100、平均 97.16 的直接原因）。

改成占比后，分子分母同为「操作 tick」、单位相消：

| 口径 | 四方向 vs 瞬时连锁 中位之比 | 结论 |
|---|---:|---|
| 原始滞留步数（v4） | **63.00** | 不可比 |
| **÷ 有效操作步（v5 采用）** | **2.03** | ✅ 口径统一 |
| ÷ 盒数 | 63.81 | ❌ 排除——分母是盒数、分子仍是 tick，单位没消掉 |

残留的约 2 倍差异是**真实玩法差异**（四方向盒子逐像素慢吃、相对滞留确实更久），不再是量纲问题。

**cap = 0.06 的标定依据**：两批合并 411 关的占比分布 p99 = 0.0592，取 0.06 ≈ p99；
封顶合计 **5/411 = 1.2%**（四方向 0/63、瞬时连锁 5/348）。

## 4c. 难度重标定（v121 新增，任务 `ANT-SIM-FRONTEND-SYNC-20260828`）

> **一句话**：v5 公式**一行未动**。重标定改的是**喂给公式的那条玩家路线** ——
> 从「单跑一次」改成「多轮里挑最有代表性的一条」。
> 实现：`analysis.js` `recalibrateDifficulty(level, opts)`；入口：生成页「🎯 批量难度重标定」按钮。

### 为什么需要

难度分的 f1（65%）+ f2（25%）= **90% 的权重来自玩家模拟的单次结果**，而生产审核与页面分析
都只跑**一遍**玩家模拟。同一关换一种玩家风格，`revives`（每次 +8 分）、`bufferPeak`、
`avgResidence` 都会变，分数随之抖动。**实测 110底部-08-27 全 47 关：单轮之间的分数极差平均 17.9 分，
最大 20 分的关卡靠一次抽样定档。** 更严重的是 **16/47 关会出现「部分轮通关、部分轮不通关」**——
即 `rankable`（能否进正式难度排序）本身也是抽样结果。

### 口径

| 步骤 | 做法 |
|---|---|
| 全知 | **只跑一遍**（同一关同一模式下 `solve` 是确定性入口，且 f1/f2 都不取全知值）。允许调用方传入复用 |
| 多轮玩家 | 跑 `runs` 轮（默认 5），逐轮换 `pickThreshold`（见下） |
| 逐轮算分 | 每轮都调**现行 `difficulty()`**，不另写公式 |
| 选代表 | ① 只在**通关轮**里挑 → ② **复活次数最少** → ③ **峰值暂存最低** → ④ **难度分最接近多轮中位数** |
| 全轮未通关 | **不伪造代表**：取「进度最远」的一轮作诊断代表，`rankable = false`，`note` 写明 |
| 输出离散度 | 通关率、分数 min/中位/max/极差、峰值 min/max/极差、复活 min/max、**不同路线条数** |

判据顺序的理由：复活是 +8 分的**硬加成**，一轮多复活就能把分数整体抬高，故先排除；
峰值暂存是唯一的失败源，低峰值代表这条路线走得稳；最后用「接近中位」排掉分数离群的轮次。
**拒绝「取最高分」**——那等于专挑离群轮。

### ⚠ 多轮的扰动轴是 `pickThreshold`，不是随机种子

`PlayerSim.run` 的 `opts.seed` **当前完全无效**（`rng()` 有定义、零调用，详见
`求解器算法逻辑.md` §8.3）。若按种子跑 N 轮，会得到 N 条**完全相同**的路线，
「取最稳一条」恒等于单轮 —— 功能跑通但恒等空转。

故改用**已有的 `pickThreshold`**（前一个球消到该比例才继续取下一个 = 玩家的激进程度）：
这只是**换调用方传入的参数**，不触碰玩家模拟的决策与消除逻辑。
默认在 **`[0.50, 0.70]` 窄带**内均匀取 `runs` 个点（`runs=1` 时退回 PlayerSim 默认 0.6）。

**窄带取值的实验依据**（`_kiro临时/08.28-前端模拟同步/_实验-默认轮次标定.js`，110底部-08-27 全 47 关）：

| 阈值带 | 平均不同路线 | 退化为单路线的关 | 平均分数极差 | 代表轮 vs 单轮(0.6) 分差 |
| --- | --- | --- | --- | --- |
| **0.50~0.70（采用）** | 4.36/5 | 0 | 17.9 | 中位 **0** / 均值 3.0 / 最大 20 |
| 0.40~0.90（未采用） | 4.98/5 | 0 | 34.3 | 中位 0 / 均值 7.1 / 最大 33 |

宽带的 34.3 分极差已不是「同一玩家的运气波动」而是「不同玩家风格」，按它取代表等于在**挑风格**；
窄带则多数关与单轮一致（分差中位 0）、只纠正离群关（最大 20 分），符合「避免审核扰动」的原意。
**轮数增大只把同一窄带取得更密，不外扩。**

`seed` 仍逐轮传入并记录在 `samples[].seed` 与 CSV 的「采用种子(当前无效)」列：
一旦 `rng()` 被接进选盒（需另行批准），无需改结构即可获得第二个扰动轴。

### 返回字段

```
{ ok, runs, rankable, difficulty,               // difficulty 就是代表轮那一份，不是第三次计算
  chosen: { index, seed, pickThreshold, score, grade, revives, peak, won },
  omniCompleted, samples: [每轮明细], stability, gateVersion:'recalibrate-v121', note }
```
`stability` 里两个字段专门用来判断**这次多轮有没有意义**：

| 字段 | 含义 |
|---|---|
| `distinctRoutes` | 多轮实际产出了几条**不同**的取盒路线（用取盒坐标序列做指纹） |
| `degenerate` | `distinctRoutes ≤ 1 且 runs > 1` → **N 轮等于 1 轮**，重标定分与单轮同值 |

`degenerate` 为真时 `note` 会写「多轮退化为单一路线」，页面表格里该关的「路线数」列标 ⚠，
CSV 的「多轮退化」列写「是」。**这一列存在的意义**：不让用户因为「跑了 5 轮」就以为结果更可信。

### 与合格门的关系

**无关。** `chokepointAudit`（合格门）本轮一行未动，仍是 `audit-gate-v119`（见 §1b）。
重标定只影响**难度分这一个数**，不影响任何关卡的合格判定。

### 对应实现与验证

| 项 | 位置 |
|---|---|
| 函数 | `bin/js/analysis.js` `recalibrateDifficulty` |
| 批量入口 | `bin/js/app.js` `batchAnalyze({recalibrate:true})`、按钮 `#btn-recalibrate`、轮数 `#gen-analyze-rounds` |
| 报告导出 | `bin/js/app.js` `exportAnalysisCSV`（重标定时表头追加 **16 列**） |
| 单关显示 | `selectLevel` 面板的「🎯 重标定」一行（轮数 / 不同路线数 / 通关率 / 分数区间 / 采用阈值） |

验证：`_kiro临时/08.28-前端模拟同步/_验v121.js` 第二节 —— 真实关卡上真跑 5 轮，
逐条钉住四级判据、离散度自洽、`degenerate` 不误报（`runs=1` 不算退化、人为把 5 轮阈值设成同一个才算），
并交叉验证「重标定内部用的就是现行 `difficulty()`」（同输入 → 同分数与同 f1/f2/f3）。

**已知限制（v121 当时）**：①重标定结果只进页面与导出 CSV，**未回写**落库的 `逐关记录.jsonl` / `分析报告.csv`

重标定是**事后**工具，不改变已产出批次的分数；③耗时随轮数线性增长（每轮一遍玩家模拟）。
> **②已在 v126 解决 —— 见下方 §4d。** ①的落库口径也随 §4d 补入生产侧 `debugData`（关卡数据.json）。

## 4d. 多轮难度标定接入生产（v126，任务 `ANT-DIFF-MULTIROUND-PROD-20260901`）

> 用户 2026-09-01：「把多轮玩家求解标定难度接入生成器。确保求解的稳定性和准确性。多轮次多少和消耗多少预算可以测试一下」。

**做了什么**：把 §4c 的 `recalibrateDifficulty`（多轮取最稳路线）从「页面事后工具」接进**生产流程**——
生产出的关卡的难度分不再是单轮 seed7，而是多轮标定后的稳定值。**难度公式（v5）一行未动**，改的只是「喂给公式的路线」从 1 条变成「N 轮里最稳的一条」。

**接入点（只在唯一出口，避免候选爆炸）**：
- 候选筛选、卡点变体阶段仍用**单轮** `computeDifficulty`（快，不动）——否则 candidateCount×卡点变体×N 轮会爆。
- 只在 `generator.js` `finalizeProduce` 出口，对**最终选中的这一关**调 `recalibrateDifficulty(runs=difficultyRounds, omni=solveResult, bottomOnly/instantChain)`：
  - 复用已求得的 `solveResult` 作 `omni`，**不重解**；只多跑 N 次玩家模拟（solve 是确定性入口）。
  - 用其结果覆盖 `cand.difficulty`，并挂 `cand.difficulty.calibration`（rounds/rankable/scoreMedian/scoreRange/winRate/distinctRoutes/degenerate/chosenPickThreshold/singleScore）；单轮值保留在 `cand.difficultySingle`。
  - 与合格门**无关**：`audit.pass` 不受影响（难度不决定合格）。

**参数**：`DEFAULT_CONFIG.difficultyRounds`，默认 **7**（缺省即生效，方案不写也走 7）；UI 控件 `#gen-difficulty-rounds`（1~25）；`app.js buildConfig` 读入；`=1` 逐值回到旧单轮口径。

**轮次/预算实测**（20 关跨难度，以 R=25 为参考，脚本 `_kiro临时/09.01-345整理/_轮次预算*`）：

| R | 代表分偏差(均/最大) | 中位分偏差(均/最大) | 耗时/关 | 相对单轮 |
|---|---|---|---|---|
| 1 | 3.5/24 | 1.9/8 | 2.0s | ×1.0 |
| 5 | 2.6/20 | 0.7/4 | 2.5s | ×1.2 |
| **7（采用）** | **1.1/13** | **0.2/1** | **2.8s** | **×1.4** |
| 13 | 1.1/13 | 0.1/1 | 4.3s | ×2.1 |

R=7 是收敛拐点；rankable 在全 R 内 0 翻转。

### ⚠ 这个结论的边界：是「内部收敛」，不是「对真人更准」

2026-09-01 按 Codex 审查 P1-2 降级表述。上表**只能**支持：

- 相对**同一算法**跑到 R=25，R7 的代表分平均绝对偏差 1.1；
- R7 约 2.78s/关，为 R1 的 1.38 倍；
- 该 20 关样本内 rankable 相对 R25 无翻转。

**不能**支持「准确性已确保」，理由三条：

1. **R25 不是真人难度真值** —— 它只是同一选择规则跑了更多次抽样，两者收敛只说明算法自身稳定。
2. **代表轮判据本身有方向性偏差** —— 「复活最少 → 峰值最低 → 最后才接近中位」天然偏向**更轻松的成功路线**，
   不是纯中位去噪，因此多轮值系统性地偏「顺利那一侧」。
3. **最大偏差仍达 13 分** —— 样本序号 250：R7=81、R25=94。

**并且 `degenerate` 识别不了多路线双稳态。** 它只判「多轮里只有一条不同路线」；
序号 250 实测 `routes=6`、`scoreRange=25`、`degenerate=false` —— 双稳态**只能从 `scoreRange` 看见**，
而当前**没有任何阻断或告警阈值**，这类关会照常进排序。

**要声称准确，需补**：拿线上/实机标签做相关性、排序一致性或分档命中验证。**该验证未做。**
**待决**：`scoreRange` 超阈值时是否不自动排序、标人工复核或自动加轮。

**落库**：`app.js` 生产记录新增 `difficultyCalibration` / `difficultySingle`，写进生产侧 `debugData`（关卡数据.json）；难度分数列（CSV/JSONL）本身即多轮值，**列约定未变**（未加新列，避免破坏既有解析）。

### 同源性：救援成功后必须重解析最终关卡（2026-09-01 加固，Codex 审查 P0-1）

的**混合口径难度分**，且完全静默。

返回的候选对象逐字段列举、**不含 `parsed`**（`res.parsed` 只在函数内部供 `evaluateGeneration`/

**已去掉短路**，行为逐值不变（原本就恒走重解析），同源性改由本行自身保证。

### 口径定义（实现细节）

**有效操作 tick**（f1 的分母）：取了盒、或有消除推进、或发生复活的 tick。
纯空转的停滞检测 tick 被排除，避免同一暂存状态被反复加权。

**滞留计入范围**（f2）：
- 普通盒：完成离场时按当前操作 tick 计
- 锁链盒：组内每盒各记自己的 `enterTick`，**整组完成才离场**，先完成的成员在等待伙伴期间继续累计
- 复活**从暂存**释放的盒：按 `复活tick − enterTick` 计入
- 复活**从棋盘残留区**直接移除、从未进暂存的盒：**不计入**
- 未通关时仍滞留暂存中的盒：**不伪造离场**，不计入

**失败局**：`playerWon:false` 且 `rankable:false`。分数仍会算出以供诊断，
但按需求 §4.5 **不得用于正式难度排序分组**。

### 两条压力轨迹并存（重要，勿混用）

| 数组 | 横轴 | 用途 | 是否可改语义 |
|---|---|---|---|
| `pressureSamples` | **完成事件轴**（每有盒离场记一次，字段 `done`/`buf`） | 前中后期**卡点审核 / 合格门**（§1、§2） | **不可改**——改它会让 348 关合格判定整体漂移 |
| `tickTrajectory` | **玩家操作 tick 轴** | f1、f2、压力图、复活前后回溯 | v4 新增 |

`generationEval.player` 上同时保留两套：`avgBuffer`（完成事件轴，与 `pressureOffset`、卡点审核同源）
与 `avgBufferTick`（操作 tick 轴，v4 的 f1 源）。`computeDifficulty()` 优先取后者，
缺失时退回前者并在 `playerStats.statsAxis` 标出实际用的是哪条轴，避免两种口径混着比。

### 复活轨迹记录（需求 §5）

`tickTrajectory` 每条至少含：`tick`、`done`、`progress`、`pick`、`bufferAfter`、
`normalDone`、`reviveDone`、`releasedSlots`、`effective`/`idle`，
以及复活步的 `revive`、`reviveIndex`、`bufferBeforeRevive`、`bufferAfterRevive`。
复活步的 `bufferAfter` 取**复活后**的真实值（记录点在复活处理之后），
因此压力图能在该操作步表现真实下降并从下降后的值续接。
另有 `reviveEvents` 列表单独汇总每次复活（前后暂存、释放槽位、来自暂存/棋盘的数量）。

#### `pick` 子对象的字段（v113 起补齐锁链信息）

| 字段 | 含义 |
|---|---|
| `r` / `c` | 触发盒坐标（玩家点的那一格） |
| `color` / `need` | **触发盒**的颜色与球数（注意：不是整组合计） |
| `groupSize` | 该次取盒的锁链组大小（1/2/3） |
| `wasQuestion` | 取的是否是未揭示的问号盒 |
| **`boxes`**（v113） | 这一步实际入场几个盒。与 `groupSize` 同值，语义上对齐 solver 侧 `stepStats.boxes` |
| **`picked[]`**（v113） | 逐盒明细 `[{r,c,color,count}]`，**`[0]` 是触发盒**。改前只有触发盒的 `color`/`need`，另外 1~2 个成员无从得知 |
| **`bufBefore`**（v113） | 取盒前的槽占用 |
| **`bufEnter`**（v113） | **整组入场后、消除阶段之前**的槽占用 |

`bufEnter` 与 solver 侧 `stepStats.bufEnter` 同口径，两类语义不同（不是缺陷，是玩法）：

- **锁链**：整组 N 个成员**无条件**入槽（某成员当步消完也要留着等伙伴，组未全完成不能离场）
  → `bufEnter === bufBefore + boxes` 严格成立。
- **单盒**：当步消完则直接完成、不入槽 → `bufEnter` 为 `bufBefore` 或 `bufBefore + 1`。

**玩家版的决策逻辑自始正确**（`doPick` 在**移除棋盘盒之前**用 `groupSize` 判空位，不足则不取、走死锁复活），
v113 只补记录、未改任何决策。实测 46 关：锁链 tick 123 个、单盒 tick 2716 个，上述两条口径全部成立。
难度分 f1/f2 仍取 `bufferAfter` 轴（口径未变），`bufEnter` 目前只作观测，不参与评分。

> **实现注意（既有 off-by-one）**：`playersim.js` 的 `ticks++` 位于停滞检测**之前**，
> 而复活发生在停滞检测**之内**。若直接用 `ticks` 记复活步会整体偏大 1。
> v4 起统一使用每 tick 开头固定取值的 `curOpTick`，入场/离场/复活/轨迹全部以它为准。

### 已知限制（如实记录）

1. **操作 tick 在三种玩法下不是同一单位**，跨模式的 f1/f2 不可直接比较：
   瞬时连锁一个 tick = 「取盒 + 完整瞬时结算」；四方向/仅底部一个 tick = 「各球各吃一像素的一轮」。
   实测同一关：瞬时连锁 51 ticks、玩家滞留 0.37；四方向 1746 ticks、滞留 71.59；仅底部 692 ticks、滞留 66.16。
2. 因上一条，**cap 的旧标定值（f1≤2.5、f2≤7）是按 55×55 批的旧口径定的**，
   套在 v99 瞬时连锁上 f2 会接近零、f1 也偏低，难度分整体压缩。本轮按需求要求不调 cap，
   只在 348 关重评分报告中给出封顶比例与接近零比例，供用户决定是否重标定。
3. 难度分与合格门仍**互不决定**（见 §4b 顶部说明，v4 未改变这一点）。

## 4b. 难度评分体系 v3（已被 v4 取代，保留供回溯）

> **本节为历史记录。** v3 自 2026-08-05 起停用，现行体系见上方 §4a。
> 停用原因：f4（全知-玩家偏移）把全知数据掺进难度分、稀释玩家信号；f2 用全知滞留而非玩家滞留。
> 回退定位：v3 权重仍以 `DIFF_W_V3` 常量保留在 `analysis.js`（仅供对照，不参与计算）。

> **难度分与合格标准是两条并行、不互相决定的分支**：
> - **合格标准**（本文档 §2/§2b）回答"这关能不能用"——依据全知求解器的**压力曲线**（是否形成结构性卡点/趋势是否健康），决定 `tier`（困难合格/简单合格/不合格）与是否被 `produce()` 选中输出。
> - **难度分**（本节）回答"这关有多难"——依据求解器（主要是**玩家版**）的**表现数据**（平均暂存、平均滞留、复活次数等）打一个 0-100 的量化分数，供分级展示/筛选用。
> - 两者**互不决定**：`computeDifficulty()` 只在候选**已经通过合格判定后**才被调用计算展示分数，它的输出**从不反馈**进 `candTier`/`candBetter`/`candPass`/`evaluateGeneration.pass` 这些"能不能用"的判定里；反过来，难度分数再高或再低，也不会让一个"审核不合格"的候选变成合格。改难度分的权重/上限只影响分数展示，不会改变哪些关卡被选中输出。

难度分体现的是**求解器表现为主**的情况（v3 起以【玩家版】表现为主要依据，因为全知版为保证可解会刻意压低暂存，不能反映真实难度）。旧版难度分对"障碍多的大图"无分辨力（obs、scale 都顶满100 → 全挤极难）。v2/v3 改为围绕**实际压力动态 + 全知-玩家差距**，障碍只作低权重标定：

| 因子 | 定义 | 归一化上限 | 权重 |
|---|---|---|---|
| **f1 玩家平均暂存** | **玩家版**求解全程平均暂存占用（v3 改用玩家版，不再是全知版） | ÷2.5 | **0.45** |
| **f2 全知平均滞留** | 每球从"入场暂存"到"被消除"停留的步数，取平均（仍用全知版） | ÷7 | **0.25** |
| **f3 基础障碍** | 冰/黑/锁链/管道 按基础权重累加的障碍强度 | ÷200 | **0.10** |
| **f4 全知-玩家偏移** | (玩家平均暂存 − 全知平均暂存)，偏移越大越难 | ÷1.5 | **0.20** |
| **复活加成** | 玩家每用一次复活道具 **+8 分**（≤2 次 → 最多 +16），叠加到主分后再截断到 100 | — | 加成项，非权重因子 |

- 难度分 = `clamp(f1×0.45 + f2×0.25 + f3×0.10 + f4×0.20 + 复活次数×8, 0, 100)`。
- 归一化上限按 55×55 批实测标定（f1 玩家avgBuf≤2.5、f2 滞留≤7、f3 障碍≤200、f4 偏移≤1.5），可在 `analysis.js` 的 `DIFF_CAP` 调。
- **改用玩家版的原因**：全知版为确保可解会刻意压低暂存（避免自己也被逼到高压），若用全知版平均暂存算难度，难度分会被系统性压低、封顶在普通档；玩家真实占用更能反映真实难度。
- **难度分本身不设合格门槛**——"玩家版必须通关"是**合格标准**（§2b）的判定条件，不是难度分的一部分；难度分只在候选已合格后才计算展示。
- 实测（v83批）：合格关难度分从改用玩家版前的 45~60(普通) 提升到 67~91(困难/极难)，评分终于能反映真实难度梯度。
