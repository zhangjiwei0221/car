## 1. 求解器要回答的问题

给定一个关卡（棋盘上排布的蚂蚁盒 + 目标图像 + 障碍：黑块/墙、冰、锁链、问号、管道），求解器要判断并给出：

- **是否可解**（`completed`）——这是生产环节的**合法性硬门**：不可解的候选关卡直接淘汰。
- **一条可行的取盒顺序**（`pickOrder`）——供后续按进度划分区域、制造卡点、评难度。
- **过程压力指标**（`pressureSamples`、`maxBuffer`、`avgResidence` 等）——供审核与难度评分。

“全知”指：求解器**已知**问号真实颜色、管道内部队列顺序，按理论最优信息求解；它不模拟真人的误判。

## 2. 两层架构

```
solve(level, opts)                      ← 入口：多轮重试 + 时间预算编排
  └─ runSolver(level, noise, seed, …)   ← 单轮：核心模拟循环（建状态→逐步取盒→判胜负→汇总）
        每一步：
          moves = Simulator.listMoves(state)                 ← 机制：枚举可取盒
          move  = SolverStrategy.pickBestMove(state, moves)  ← 策略：选这一步取哪个盒
          Simulator.applyPick(state, move.r, move.c)          ← 机制：执行取盒+消除+解冻+管道释放
```

- **核心循环（`solver.js`）**：只管“流程骨架”——推进步骤、判胜负 / 暂存溢出 / 道具救场、记录结果。不含任何“怎么选盒”的智能。
- **搜索策略（`solver-strategy.js`）**：只管“这一步选哪个盒”——前瞻深度、前瞻树、评分启发式。**可整体替换**，不影响核心循环。
- **游戏机制（`simulator.js`）**：所有真实规则——消除的像素级依赖波、盒可取判定、冰/锁链/管道/激活。求解器与玩家共用同一套机制，保证 `valid=可解` 等于真机规则下可解。

> 拆分意义：策略与流程/机制解耦，可单独重写策略。当前有两种策略模式：**贪心(greedy·快)** 与 **三步前瞻树(tree·强·较慢)**，由 `solve()` 编排。

## 3. 求解主流程 `solve()`（贪心 → 多重策略 → 噪声）

```
求解编排（共 6 遍，任一遍通关即停；与 solver.js solve() 一致，2026-07-27 据源码校正）：
  贪心×2 → 3步前瞻树×2 → 噪声(贪心)×2
  ① runSolver(mode=greedy, noise=0,   seed=1)   → 通关即返回 retryRound=0
  ② runSolver(mode=greedy, noise=0.6, seed=53)  → 通关即返回 retryRound='g2'
  ③ runSolver(mode=tree,   noise=0,   seed=1)   → 3步前瞻树(强·确定性)；通关即返回 retryRound='tree'    〔greedyOnly 跳过 ③④〕
  ④ runSolver(mode=tree,   noise=0.8, seed=29)  → 3步前瞻树(扰动)；通关即返回 retryRound='tree2'       〔greedyOnly 跳过〕
  ⑤ runSolver(mode=greedy, noise=1.0, seed=211) → 噪声随机重启；通关即返回 retryRound='n1'
  ⑥ runSolver(mode=greedy, noise=1.5, seed=401) → 噪声随机重启；通关即返回 retryRound='n2'
每遍执行前检查 timeBudgetMs（超时跳过剩余遍）；全部失败 → 返回“最接近通关”的一轮(eliminatedPixels 最大者)。
```

**设计动机**（实测支撑，见 §9）：
- 贪心对**可解棋盘**已近 100% 命中且极快（~0.2–0.4s）；绝大多数关卡在阶段1 解出。
- 只有贪心 2 次都失败的**硬关卡**，才动用较贵的 3 步前瞻树（强的确定性搜索）+ 噪声随机重启来**确保可解**。
- 因此“快”（易关走贪心）与“强/命中”（硬关走多重策略）兼得；`solve()` 命中 ≥ 旧“贪心+噪声”（多一层 tree 兜底）。

**可调旋钮（`opts`，默认不改变现有行为）**：
- `opts.greedyOnly=true`：只跑贪心(2 次)+噪声，**不启用 3 步树**。用于生成器【基础棋盘首解】（无卡点、要快）。
- `opts.timeBudgetMs`：总时间预算封顶（超时放弃剩余，截断个别拖时的硬关/不可解关）。
- `opts.maxRetries`：噪声重试轮数上限。`opts.lookahead`：树深度覆盖。
- `opts.bottomOnly`：仅底部进入（`solveBottom`）。`opts.capturePreviewStats`：逐盒采集锁率压力快照（供审核，较贵）。
  - **v96 起（`ANT-GEN-BOTTOM-ONLY-20260729`）**：`opts.bottomOnly` 不再只是网页端"底部专用演示"（`app.js` `runBottomDemo`）的单点用法，生成器 `generator.js` 的候选筛选、卡点分支重求解、最终全知求解均按同一 `bottomOnly` 值调用本函数，与玩家模拟（`playersim.js`）、目标图闭合（`utils.js` `outsideReachSeed`/`eliminationOrder`）保持同一入口模式口径。详见 `生成器逻辑体系.md` §11。本文档描述的求解算法本身（六遍编排、三步前瞻树、消除模型）不因该参数改变，只是入口边界从"四边开口"变成"仅底边开口"。

## 4. 单轮求解 `runSolver()`（核心循环）

```
建状态 state = Simulator.createState(level, {useSlotStart:true, bottomOnly})
LOOKAHEAD = SolverStrategy.chooseLookahead(level, opts)
maxSteps  = totalBoxes + 50          // 安全上限

while (!gameOver && steps < maxSteps):
    moves = Simulator.listMoves(state)
    if moves 为空:  (道具救场 opt-in) 否则 break        // 无路可走
    bestMove = SolverStrategy.pickBestMove(state, moves, {lookahead, noise, rng})
    if bestMove 为空(全被暂存阻塞):
        兜底取第一个未阻塞盒；仍无 → (道具救场 opt-in) 否则 break
    Simulator.applyPick(state, bestMove.r, bestMove.c)  // 取盒→消除→解冻→管道释放
    记录 pickOrder（v112 起逐盒一条，锁链同 step 多条）/ stepStats / stepBufferHistory
    判胜负：
        eliminatedPixels ≥ totalPixels → 通关
        overflow(瞬时超暂存上限，含锁链整组入场即超) → 死亡（严格，不可救）
        buffer.length > 上限 → autoReleaseBuffer；仍超 → 死亡
```

**暂存（buffer）**：取下但没当场消完的盒进暂存；暂存有容量上限（`bufferLimit`）。瞬时超限 = 死亡，这是最关键的失败判据。

**道具救场（`useItems`，默认关）**：无路 / 全阻塞时可消掉“进度最低的暂存球”腾位。仅演示/特定模式开启；正常求解**不用**道具（保持严格可解性判定）。

### 单轮返回结果字段
| 字段 | 含义 |
|---|---|
| `completed` | 是否通关（可解性结论） |
| `pickOrder` | 取盒顺序。**v112 起「一条 = 一个盒」**：`[{step,r,c,color,count,chain,chainSize,chainIndex}]`，锁链 2/3 连的成员是同一 `step` 的多条记录。详见 §6.5 |
| `stepStats` | **v112 新增**，每 pick 一条：`{step,boxes,bufBefore,bufEnter,bufAfter,isChain}`。详见 §6.5 |
| `steps` / `completedBoxes` / `totalBoxes` | 步数 / 完成盒数 / 总盒数。**注意 `steps ≠ totalBoxes`**：步数是 pick 次数，盒数含锁链连带 → 1 步可 2/3 盒 |
| `eliminatedPixels` / `totalPixels` / `progress` | 已消像素 / 总像素 / 百分比 |
| `maxBuffer` / `avgBuffer` | 暂存峰值 / 平均占用。口径是**每 pick 结算后**（取自 `stepBufferHistory`）；入场瞬时峰见 `stepStats.bufEnter` |
| `avgResidence` | 平均滞留（球入场→消除的步数） |
| `stepBufferHistory` | 每 pick **结算后**的暂存占用，长度 = `steps`。口径自始未变 |
| `pressureSamples` | 逐盒完成时的压力样本（含 lockRatio，需 capturePreviewStats） |
| `retryRound` / `time` | 第几轮解出（0=首轮）/ 总耗时 |

### 6.5 求解路线与锁链：一条记录 = 一个盒（v112）

> 任务 `ANT-SOLVER-CHAIN-PICKORDER-20260827`，用户裁决「方案 A」。

#### 改之前的缺陷

`applyPick` 取锁链组时整组一起离场、`steps` 只加一次，但 `solver.js` 每步只 push **一条** `pickOrder`
（用触发盒的坐标与球数），组内另外 1~2 个成员**零记录**，该步 `count` 也只记触发盒的球数。

实测 `输出文件/v110底部49关-08-27`（46 关）：127 个锁链组（2连×86、3连×41）中 **126 组只有 1 个成员有步号**；
缺口 `totalBoxes − pickOrder.length` 与「锁链成员数 − 组数」**46/46 关完全吻合**，合计缺 **168 条**；
样例 3 连组实际 139 球只记 47（少记 92 球）。
连带损坏：`app.js` 的「`pickOrder.length === totalBoxes`」门槛对含锁链关卡恒为假 →
消除序号视图**静默退回机械左→右序**（46/46 关中招）。

#### 现在的记录口径

`pickOrder` 逐盒展开，同一次 pick 的成员共享 `step`：

| 字段 | 含义 |
|---|---|
| `chain` | 锁链组 ID（`0` = 非锁链） |
| `chainSize` | 该步共取几盒（1/2/3） |
| `chainIndex` | 组内序号，**`0` = 触发盒** |

于此 `pickOrder.length === totalBoxes` 恒成立。

`stepStats` 每 pick 一条，补上此前完全没有记录的两类信息：

| 字段 | 含义 |
|---|---|
| `boxes` | 这一步放进来几个盒（步数是 pick，盒数含锁链） |
| `bufBefore` | pick 之前的暂存占用 |
| `bufEnter` | **整组入场后、结算（`autoReleaseBuffer`）之前**的占用 |
| `bufAfter` | 结算后的占用（= `stepBufferHistory` 同位值） |
| `isChain` | 该步是否为锁链整组 |

`bufEnter` 是本轮唯一真正新增的信息：它就是 `processChainGroup`/`processAntBox` 里判 `overflow` 所用的那个值，
以前判完即被 `autoReleaseBuffer` 抹掉、从未被记录。实例：`step=18　暂存 0 + 3 盒 → 入场 3 → 结算后 3`。
实测有关卡结算后峰值 4、**入场瞬时峰 5**（等于上限），这种瞬时压力只有 `bufEnter` 能看见。

#### 两类入场语义不同（不是缺陷，是玩法）

- **锁链**：`processChainGroup` **无条件**把 N 个成员全部推入暂存 —— 即使某成员的球当步就消完了，
  也必须留在暂存等伙伴（组未全完成不能离场）。故 `bufEnter === bufBefore + boxes` 严格成立。
- **单盒**：`processAntBox` 若当步消完则**直接完成、不入暂存**。故 `bufEnter` 为 `bufBefore` 或 `bufBefore + 1`。

#### 消费方必须知道的两点

1. **回放要跳过同 `step` 的后续条目**。整组在触发盒那一次 `pickBox` 里已全部离场；
   逐条调用会对已空的格子调 `pickBox`（返回 `false`）。旧格式每步仅 1 条，跳过逻辑对其逐值等价。
2. **判定「某坐标是否锁链成员」要取该坐标的首条记录**。同一坐标可能被取多次 ——
   管道释放会把新盒放到出口格，而该格可能正是先前某锁链成员的位置（实测 **28/46 关**存在）。

#### 实现位置

`simulator.js`：`applyPick` 末尾的 `s.lastPick` 只读快照（`picked` 数组，`[0]` 必为触发盒）；
`processChainGroup`/`processAntBox` 里的 `s._enterPeak`。
**取盒机械、入场、`overflow` 判定、`autoReleaseBuffer`、`elimDispatch` 一行未改** —— 本轮只把内核
已经算出来的中间状态暴露出去。
`solver.js`：按 `state.lastPick.picked` 逐盒 push + `stepStats`。
`app.js`：回放跳过同 `step`；`=== totalBoxes` 门槛因此自动恢复；`stepStats` 接入落库与导出包。

#### 验证结论

`_kiro临时/08.27-锁链步数与暂存结算/_验v112.js` **25 项 0 失败**：46 关全部重新求解且全部通关、
`pickOrder.length === totalBoxes` 46/46、`stepStats.length === steps` 46/46、127 组成员全部入账且球数合计一致、
`chainIndex` 连续且触发盒在前、按「同 step 跳过」回放可走完全程（并用反例证明不跳过必然出现不可取条目）、
同输入两次求解结果一致（未引入随机性）。
**未验证**：浏览器实机（回放动画、消除序号视图）→ 待用户实机验收。

## 5. 搜索策略 `SolverStrategy`（可替换·双模式）

`pickBestMove(state, moves, ctx)` 按 `ctx.mode` 分派；两种模式都遵守约定：**返回一个未阻塞 move，或全阻塞返回 `null`**（交回核心循环兜底）。

### 5.1 贪心模式 `greedyPick`（默认·快，毛线口径单步评分）
对每个未阻塞 move 用 `greedyEvaluateMove` 打分（+噪声），取最高：

| # | 规则 | 分值 |
|---|---|---|
| 1 | 能当场消完（不进暂存） | +30；否则按暂存占用扣分（≥4:−20 / ≥3:−10 / ≥2:−5 / 其它:−2） |
| 2 | 本次可消像素数 `potential` | +potential × 2 |
| 3 | 消除后能连锁释放的暂存盒数 | +数 × 15 |
| 4 | 暂存中已有同色球 | +8（命中一次即止） |
| 5 | 进暂存的临界惩罚 | −(暂存占用率)² × 25 |
| 6 | 位置微偏好（越靠上先暴露） | −move.r × 0.05 |

单步、无克隆、极快；`solve()` 阶段1 与噪声重试都走它。

### 5.2 三步前瞻树模式 `treePick`（多重策略·强·较慢）
依据《三步前瞻选盒策略需求》：**宽 3 × 深 3**（≤27 条三步路径），每候选在**独立克隆态**里真实执行一次，用**执行后真实差值**评分；只执行最佳路径第一步，再基于新真实状态重新建树。

- **分阶段主目标**（盒进度 = 已完全消除盒数 / 总盒数，含管道内部盒）：
  - 前期 <20% → 最大化**棋盘盒拓展**（新可点盒/色）；
  - 中期 20~50% → 最大化**目标图可达/可消色拓展**；
  - 后期 ≥50% → **生存**（压低暂存峰值/叶暂存，避免死亡）。
- **暂存压力**（N=上限）：轻 ≤N-2 允许激进；中 =N-1 转保守；高 =N 优先释放已有暂存盒（放宽后：释放 或 有实际消除即可，纯占位会溢出被排除）。
- **锁链**：整组进入/整组释放；`blocked`(暂存放不下整组) 已在 `listMoves` 排除；当步整组消完给高奖励。
- **路径评价**：先淘汰死亡/溢出路径 → 按阶段加权综合（生存·棋盘拓展·目标图拓展·消除量·障碍推进），通关路径最高。
- **性能**：手写快克隆(不走 JSON)、廉价可点集(`isPickable`)、目标图可达一次 O(area)（仅中期算）、完整 `listMoves` 仅对将展开的 Top-K 节点惰性计算、`prescan` 预筛候选。即便如此，单次树解 ~2.5–3.5s（55×55），故只在贪心失败的硬关卡才用。

### 5.3 `cloneState(state)`
手写深拷贝 `eliminated`/`cells`/`buffer`/`activated`/`removed`/`frozen`，共享静态 `blocks`/`chainGroups`。供分支模拟，不污染真实状态。

### 5.4 替换约定
重写策略只需改 `greedyPick`/`treePick`（及其评分），保持 `pickBestMove` 的入出约定即可与 `solver.js` 无缝对接。

### 5.5 锁链滞留周期奖励（v83 新增）
2 连/3 连锁链整组入暂存后，只有组内所有成员全部消完才整组释放——期间会一直占用 2 或 3 个暂存位置。`treePick` 在此基础上加了一层"专项关注"：

- **滞留基线只认真实步骤**：每次 `treePick()` 被真实调用（即每一次真实决策），都会从**当前真实根状态**里读一次"暂存区里还滞留着哪些锁链组、各滞留了多少真实步数"（`buildDwellBaseline`）。三步窗口内 1/2/3 层的所有假设分支共用同一份基线——**假设步骤不会提前把滞留步数算进去**。等真实执行完一步、真实状态推进后，下一次 `treePick()` 调用会用新的 `state.steps` 重新算，滞留感知天然跟着真实步骤"滚动"（不是把树深度从 3 步改成 5 步，仍是宽 3 × 深 3）。
- **推进量与整组释放**：对比某一步执行前后，暂存里"根态已滞留"的锁链组剩余消除量——变小算"推进"，归零算"整组释放"。只统计决策发生时刻已经在滞留的组，不会跟"本步刚入场的锁链"的既有奖励重复计分。
- **奖励怎么放大**：滞留步数越长、占的暂存位置越多（3 连比 2 连多加 35%）、当前暂存压力越紧张，同一个"推进"或"释放"动作拿到的分就越高；同一个三步窗口里，越早把锁链整组释放掉，分越高（当前步 > 下一步 > 第三步）。
- **决策记录（可选开启）**：把 `ctx.recordChainDecisions` 设为 `true`，每次决策会额外记一份日志——当前还滞留着哪些锁链组、Top3 候选各自对锁链的推进量、这次选的动作有没有推进/整组释放锁链、拿到的锁链专项奖励是多少，便于复盘调参。
- **不改变硬规则**：锁链整组入场瞬时溢出直接淘汰、锁链释放前已死亡的路径直接淘汰、单个成员消完不能提前腾位置——这些都还是原来的判定，锁链滞留奖励只影响"在这些硬规则允许的路径里怎么排优先级"。

## 6. 消除模型 `Simulator.floodFillEliminate()`

取一个盒 = 消该盒颜色的像素，数量为盒的 `count`。消除遵循**像素级动态依赖波**：

- **可达 = 从外界能“流入”**：像素在棋盘边界（`bottomOnly` 时仅底边），或相邻某个**与外界连通的已消除格**，才算可达。
  - 关键：图内被彩色像素**封住的背景空洞**（预消除）**不算开口**——它没通到外界。可达性用 `accessKey`（从边界经已消除格 BFS）严格判定。
- **入口优先级**：底 → 左 → 右 → 顶；同源内按“由外向内”的距离波推进。每消掉一格，其同色邻居继承入口、进入下一波（depth+1）。
- **手动/玩家模式**（传 `start`）额外以“离盒起点的曼哈顿距离”为最高优先级，拟合真人从固定起点就近消除。
- 消到 `count` 个即停（`maxCount` 上限）。

> 一句话：**同色像素能被消掉的总量 = 从当前外部开口出发、沿同色 4 连通可扩展到的连通区大小**；顺序影响“先消哪些”，不影响“能消多少”。

## 6b. 第三种消除模型 `Simulator.instantChainEliminate()`（v99 新增）

> 任务 `ANT-GEN-CHAIN-INSTANT-20260803`。**§6 的 `floodFillEliminate` 未作任何改动**，
> 本节是并列的第二条结算路径，由模式开关分发。

### 6b.1 与 §6 的核心区别：批次边界

| | `floodFillEliminate`（原两种模式） | `instantChainEliminate`（新模式） |
| --- | --- | --- |
| 次序单位 | **逐格增量**：消一格 → 立即刷新可达 → 重新挑距离最近的下一格（有插队效应） |**快照批次**：快照当前可达同色全集 → 排序 → 一次消掉 `min(快照数, 剩余容量)` → 整体刷新 → 再重扫 |
| 排序依据 | 有起点时按离起点曼哈顿距离，平手用入口源分层 + 依赖波深度 | 按离订单起点曼哈顿距离，平手取最底、再最左 |
| 起点要求 | 可选（`start=null` 时纯依赖波） | 必需（`needStart = useSlotStart \|\| instantChain`） |

**实测差异**：5×5 小图三个同色像素、容量=1 时，原实现选底边 A、新规则选左边缘 C，**选中集合不同**；
容量=3 时次序也不同（原 A→C→B，新 C→A→B）。容量小于可达数时集合就分叉，
之后目标图形态与可达性一并分叉。

### 6b.2 签名与统计回填

```
Simulator.instantChainEliminate(elim, blocks, rows, cols, colorId, capacity, trace, start, stat)
  → 返回本次实际消除的像素数
  trace  逐格轨迹（可传 null）
  stat   可选，回填 rounds / batches / snapshotFirst / startFallback，供诊断与验证
Simulator.instantChainCount(tempElim, …)  以 Infinity 容量探测可消数量
  ⚠ 首参名为 tempElim：契约是【必须传副本】，与原 floodFillCount 一致，
    直接传实盘矩阵会把整张图清空（曾在测试中踩到）
```

### 6b.3 统一分发（避免口径分裂）

```
Simulator.elimDispatch(state, colorId, maxCount, trace, start, stat)
    → 作用于 state.eliminated
Simulator.elimOnMatrix(matrix, state, colorId, maxCount, trace, start, stat)
    → 作用于调用方给定的 scratch 矩阵（打分试算、可达预览用）
```

两者共用同一模式判断，因此**真实结算与打分试算永远同口径**。
走分发的调用点：`executeAntBox`、`processAntBox`、`processChainGroup`、`autoReleaseBuffer`、
`previewNextEliminationOrder`、`getNextSlotStart`，以及 `solver-strategy.js` 的两处三步前瞻打分试算。

### 6b.4 全知求解侧的接入

- `solve()` 读 `opts.instantChain` 并透传进 `baseOpts` → `runSolver()` → `createState`。
- 新增导出 `solveInstantChain(level, opts)`：强制 `instantChain=true`、`bottomOnly=false`。
- `solver-strategy.js` 的克隆态带上 `instantChain`，**三步前瞻与真实结算同口径**。
- `createState` 里 `instantChain` 与 `bottomOnly` 互斥（前者强制关闭后者）。
- 暂存自动释放（`autoReleaseBuffer`）在本模式下保持 buffer 原序 = 先进先得，不做距离重排。

**一处必须记录的更正**：早期曾判断「全知侧本来就是瞬时连锁语义」，经实测推翻。
`solver.js` 的 `createState` 本来就是 `useSlotStart: true`，即全知**一直**在用槽位映射起点，
`keyOf` 在有 start 时把离起点距离作为最高优先级。真正只用纯依赖波（`start=null`）的是生成器侧的
辅助函数：`utils.js` 的 `eliminationOrder`、`generator.js` 的 `checkBottomEntryFeasibility`。
因此新旧差异不在「有没有起点」，而在**批次边界与平手口径**。

### 6b.5 验证结论

- 原两种模式在合入前后逐项比对完全相同（全知取盒顺序逐步一致、玩家结果一致），4 张真实目标图。
- 守恒锁到四维：单次结算轨迹条数=返回数、不超订单容量、无像素被消两次、消除颜色=订单颜色；
  4 张真实图各调用 762~865 次结算全部消尽且累计数=矩阵标记数。
- 详见 `bin/文档/说明文档/生成器逻辑体系.md` §12 与 `bin/文档/版本记录/更新记录.md` v99。

## 7. 可取判定与提速

### 7.1 盒是否可取 `isPickable(s, r, c)`
`是盒 && 已激活 && 未被冰锁 && 未被链锁`：
- **激活**：盒从顶部经空格可达（`computeReach` BFS：从第 0 行空格 + 已开口管道出口出发，穿空格扩散；`isExposedAt`=在第 0 行或邻接可达空格）。取盒→腾出空格→暴露更深的盒。
- **冰锁** `isIceLocked`：`!(已激活 && thaw ≥ durability)`；冰靠“取其它盒推进步数”解冻。
  - **耐久统一为 3**（`AntSolver.ICE_DURABILITY_DEFAULT`，2026-08-05 起）：生成侧铺冰与官方格式导入还原
    共用该常量。此前 `fromGameFormat` 写死 2，导致从官方 JSON 导入的关卡少锁一步（任务 `ANT-ICE-THAW3-20260805`）。
  - **首行不再免费激活**（2026-08-05 起，任务 `ANT-ICE-ROW0-NOFREE-20260805`）：
    首行盒天然暴露，原先 `createState` 末尾的 `updateActivation` 会让首行冰块开局即 `activated`，
    配合 `applyPick` 内「先 `advanceIce` 后 `updateActivation`」的顺序，首行只需 3 步解冻、比其它行少一步。
    现已在 `createState` 初始化后把 `frozen[k].activated` 归零，激活只能发生在至少一次取盒之后。
  - 因此统一口径为 **「1 次激活 + 3 次全局」**：准确表述是**激活步与解冻步的差值恒为 3**，
    而非「总步数恒为 4」——盒被埋得越深、暴露（激活）越晚，总步数自然越大。
  - 未改动 `advanceIce` / `isIceLocked` / `updateActivation` 的判定口径本身；
    也未动 `s.activated`（盒是否可取的单调标记），否则首行盒开局将不可取、改变玩法。
- **链锁** `isChainLocked`：锁链组内**任一**其它成员未激活或冰未解 → 整组锁定（锁链必须整组同时取）。

> 这解释了「暂存空却卡死」：若一条**带冰锁链**被留到最后，已无其它盒可取来推进解冻 → 冰永不化 → 链永久锁死。全知按更优顺序在中途取走它故可解——属**顺序诱发锁**，非非法关卡。

### 7.2 枚举可取盒 `listMoves(s)`
遍历棋盘，对每个可取盒产出 `{r,c,antBox,canConsume,groupSize,blocked}`：
- `canConsume`：该盒能否被一次性消完（可达同色像素数 ≥ count）。
- `blocked`：取则必超暂存（普通盒：暂存满且消不完；锁链组：暂存现有 + 组员数 > 上限）→ 严格避免（取则死亡）。

### 7.3 `canConsume` 提速（行为等价，已上线）
`canConsume` 原本对**每个盒**都整图拷贝 + 跑完整 `floodFillEliminate`（含堆/两次整图扫描），只为一个布尔——是热点。现改为：

- `computeExteriorOpen(s)`：**每个 state 只算一次**“外部连通空腔”集合（口径与 floodFill 的 `accessKey` 一致，正确排除封闭背景空洞）。
- `canConsumeReach(s, box, open)`：从“边界/空腔旁”的同色像素起，沿同色 4 连通计数，**达 count 即止**；无整图拷贝、无堆。

等价性经 2589 个真实状态逐盒比对（0 不一致）、以及新旧 `pickOrder` 完全一致验证。`listMoves` 提速约 13–15×，单轮 solve 约 −40%。

## 8. 与玩家模拟器的区别

| | 全知求解器（本文档） | 玩家模拟器 `playersim.js` |
|---|---|---|
| 信息 | 已知问号色 / 管道序，理论最优 | 只知当前半消画面，**乐观估计、会误判** |
| 推进 | 串行、按步取盒 | 并发按 tick 逐像素消除 |
| 消除起点 | 依赖波（可传起点距离优先） | 固定暂存槽映射起点，就近消除 |
| 目的 | 判**可解性**、给参考解、压力指标 | 拟合**真人难度**（含犯错） |
| 失败处理 | 严格判死（不可解即淘汰） | 死锁触发**复活道具**（每关 ≤2 次，消剩余最大 2 盒；≤2 次通关=玩家版合格） |
| 结算时机 | **串行瞬时**：一次取盒就 `autoReleaseBuffer` 推到底 | **时间驱动并发**：每球每 tick 吃 1 像素 |

> **第三套：手点模拟**（网页「模拟游玩」）。v122 起与玩家模拟同族（每盒固定速率 5~8 像素/秒、多盒并行），
> 改前它是独立的第三套模型（一次点击结算到底）。完整口径见 §8.2b。

两者共用同一套 `simulator` 机制，因此“全知可解”与“玩家能过”的差距，本质是**取盒/消除顺序**与**信息**的差距，而非规则差异。

### 8.1 玩家侧滞留与逐 tick 轨迹（2026-08-05 新增，任务 `ANT-DIFF-PLAYER-REVIVE-20260805`）

此前**只有全知侧**有滞留统计（本文档 §6 表中的 `avgResidence`，来自 `solver.js` 的 `resSum/resCount`），
玩家侧完全没有。难度评分 v4 要求 f2 改用玩家滞留，故在 `playersim.js` 新建了一套：

- 每个球入场时记 `enterTick`；离场时按 `离场操作tick − enterTick` 累加，产出 `avgResidence`/`residenceCount`
- 锁链盒**整组**完成才离场，组内各成员按各自 `enterTick` 分别计入（先完成的成员等待期间继续累计）
- 复活**从暂存**释放的盒计入；复活**从棋盘残留区**直接移除、从未进暂存的盒不计入
- 另产出 `tickTrajectory`（逐操作 tick 轨迹）与 `reviveEvents`（复活前后暂存、释放槽位）。
  **v113 起 `tickTrajectory[].pick` 补齐锁链信息**：`boxes`（这步入场几盒）、`picked[]`（逐盒明细，`[0]` 是触发盒）、
  `bufBefore`、`bufEnter`（整组入场后、消除前的槽占用）—— 与 §6.5 solver 侧 `stepStats` 同口径。
  字段清单见 `生产审核评分体系.md`「`pick` 子对象的字段」。

### 8.2 玩家侧 `pickOrder`（v121 新增，任务 `ANT-SIM-FRONTEND-SYNC-20260828`）

**新增什么**：`PlayerSim.run` 的返回值增加 `pickOrder` —— **玩家版的棋盘取盒序列**，
口径与 §6.5 全知侧 `solver.pickOrder` 完全一致：**一条 = 一个盒**，同一 pick 的锁链成员共享同一 `step`。

```
pickOrder: [{ step, tick, r, c, color, count, chain, chainSize, chainIndex }]
```
| 字段 | 含义 |
|---|---|
| `step` | 第几次取盒（1 起算，= `picks` 计数）。锁链整组的 2~3 个成员**共享**同一 step |
| `tick` | 该次取盒发生在第几个操作 tick（= `curOpTick`），可与 `tickTrajectory` / `pressureSamples` 对齐 |
| `r` / `c` | **棋盘坐标**（`board.cells` 的行列） |
| `chain` | 1 = 该步是锁链整组，0 = 单盒 |
| `chainSize` | 这一步共取几盒（1/2/3） |
| `chainIndex` | 组内序号，0 = 触发盒（沿用 `pickBoxRaw` 的排序） |

**为什么必须新开一个字段**（不是「顺手加」）：改前**没有任何**可用于画玩家路线的棋盘坐标 ——
- `frames[i].picks[j]` 的 `sr`/`sc` 是**暂存槽起点坐标**（`slotStart` 映射到目标图的行列），不是棋盘行列；
- 棋盘坐标只存在于函数内部的 `lastPickDetail.picked`，从不出函数。

因此网页端此前只能显示全知路线。本字段把**已有信息**汇总出去，**不新增任何计算**：
数据源就是 v113 的 `lastPickDetail.picked`，填充点在 `tickPickInfo` 赋值之后。

**调用时机与去处**：`bin/js/app.js` 的 `buildRouteOverlay` 在路线下拉选「玩家版」或「双路线」时读取，
经 `routeMapOf` 转成 `{'r,c': [盒号...]}` 后由 `applyRouteMark` 注成棋盘角标。

**边界与回退**：旧版 `playersim.js` 没有该字段时，`buildRouteOverlay` 如实提示
「玩家模拟模块未加载或运行失败 / 玩家版没有产出取盒序列」，**不画空路线**。

**只读保证（验证已钉住）**：`pickOrderPS` 在文件中只出现三种用法 —— 声明、`push`、`return`，
不参与任何判断；同种子重跑逐字段一致，证明记录没有干扰决策。
见 `_kiro临时/08.28-前端模拟同步/_验v121.js` 第一节（含「一步多盒的锁链步」「条数与 tickTrajectory 守恒」两项）。

### 8.2b 手点模拟改为时间驱动并发结算（v122，任务 `ANT-SIM-LIVE-CONCURRENT-20260828`）

> **一句话**：手点模拟原本是**第三套结算模型**（一次点击就结算到底），与真机和玩家模拟都不同源。
> v122 把它换成与真机同构的「每盒固定速率、多盒并行」。
> **全知求解器的串行口径一行未改** —— `applyPick`/`autoReleaseBuffer`/`listMoves` 原样，回放与三个演示按钮继续走它。

#### 真机规则（用户 2026-08-28 给出）

> 每个盒都要出蚂蚁，大概 1 秒出 5~8 只（= 消 5~8 像素）；**在这个出蚂蚁的周期内玩家就会接着放盒**。

即**每盒固定速率、多盒并行**。这与 `playersim.js` 的 tick 模型同构（每球每 tick 吃 1 像素、共享像素池抢占）。

#### 改前的两个问题（都已实测）

| 层 | 现象 | 实测 |
|---|---|---|
| 动画 | 太快、且不并行 | `animPxPerTick=2` / `animFrameMs=45` → **44.4 像素/秒每盒**，是真机的 **5.5~8.9 倍**；`animTickCore` 第一段 `if (animActiveEats.length) { …; return; }` 提前返回，连点时新盒进不了当前并发批 |
| 逻辑 | 一次点击结算到底 | `pickBox → applyPick → autoReleaseBuffer(while changed)`。271 关 16295 步中 **69.7% 的步 `bufAfter == 0`** —— 近七成的盒在自己那一步内被吃干抹净、从不跨步占暂存 |

**关键推论**：逻辑瞬时的话，「玩家在出蚂蚁周期内继续放盒」这件事**根本不存在**（盒早消完了）。
只放慢动画只是让画面像并行，暂存压力仍测不出真实值。所以必须让逻辑本身按时间推进、
动画直接渲染逻辑态，**取消原来「逻辑瞬时 + 动画补播」的双轨**（这套双轨也是「棋盘立刻更新、
目标图慢慢补播」错位的根源）。

#### 三个新增函数（`simulator.js`，纯新增）

| 函数 | 作用 |
|---|---|
| `pickCapacityOf(s, r, c)` | 取盒容量门。返回 `{ok, reason:'noSlot'/'noSlotChain'/'locked'/…, need, free}` |
| `pickBoxLive(r, c)` | 手点取盒：**只入场占槽、不做任何消除**。放不下则拒绝（棋盘一格不动） |
| `settleStep(dtMs, ratePerSec)` | 按速率推进一次结算。返回 `{eaten, released, over}` |

`settleStep` 的实现要点：

- **小数累计**：6.5 像素/秒在 40ms 帧上是 0.26 像素/帧，直接取整会永远是 0。故每盒带 `acc`，
  `acc += rate×dt/1000`，取整数部分作本次预算。
- **真实时间戳**：`dt` 由调用方用 `performance.now()` 差值给出，不假设帧间隔
  （`setInterval` 会漂移，后台标签页会被浏览器节流到 1s）。`dt` 上限夹到 1000ms，
  避免卡帧/切后台回来时一次补一大段、瞬间消掉一片。
- **一次只吃 1 像素再轮到下一盒**：若一次吃满预算，先手盒会把争用像素全抢走，
  与真机的并行不同序。
- **争抢次序沿用既有口径**：瞬时连锁 → 先进先得（buffer 原序）；其余 → 距离优先
  （离各自暂存槽起点最近者先消）。与 `autoReleaseBuffer` 完全一致。
- **消除内核一行未改**：吃像素就是 `elimDispatch(s, color, **1**, …)`。

#### `releaseCompletedBuffer` 的抽取（行为等价）

「谁能离场」的规则（普通盒各自完成、锁链整组同步）原先内联在 `autoReleaseBuffer` 第 2 步。
`settleStep` **不能**调 `autoReleaseBuffer` —— 后者 `while(changed)` 会把进度一路推到完成，
正好抵消掉速率限制。但两者的离场规则必须完全一致，故抽成 `releaseCompletedBuffer(s)` 共用，
**而不是复制第二份**（这个工程在「第二份算法副本」上栽过几次）。
纯搬移、判据与副作用逐行未改；等价性由十五套历史回归 + 「重跑全知求解与落库结果逐字段一致」背书。

#### ⚠ 容量门与 `listMoves.blocked` 的口径**有意不同**

| | 判据 | 服务对象 |
|---|---|---|
| `listMoves.blocked`（未改） | 普通盒 `buffer满 && !canConsume`；锁链 `buffer+groupSize > limit` | 全知求解器（**瞬时**结算模型） |
| `pickCapacityOf`（新增） | `空位 < groupSize` 即拒绝，**无 `canConsume` 豁免** | 手点（**时间驱动**模型） |

差异原因：瞬时模型下「能一次消完的盒」不占槽，所以满暂存也允许取；
时间驱动下**每盒都要占一个槽 `count/rate` 秒**，那条豁免在真机口径下不成立。

**这条豁免正是用户报的「6/5 作弊」的根**：`processAntBox` 里 `if (result.completed)` 让能一次消完的盒
根本不进暂存，于是 5/5 满暂存下可以**无限次**取这类盒、一个槽都不占。

**该豁免在全知求解器里的使用量（实测，供后续求解器调整参考）**：
**18 步 / 16295（0.11%）**，涉及 **4/271 关（1.5%）**，且**这 4 关全部不合格**。
即把求解器也改成「每盒必占槽」不会影响任何已合格关卡，风险极低。
诊断脚本 `_kiro临时/08.28-手点并发结算/_诊断-满暂存免槽取盒.js`。**本轮未改求解器。**

#### ⚠ v123 修：高频重绘把点击吃掉了（v122 第一版的回归）

**用户报的现象**：「动画播放过程中，无法正常点击其他盒，同时放入 2连3连锁链后就无法正常点击盒子」。

**根因**：v122 第一版的 `renderLive` **每帧（40ms）都调 `renderQueues`**，而后者是
`container.innerHTML = html` —— 把整块棋盘拆了重建 **25 次/秒**。而 `click` 事件只在
**mousedown 与 mouseup 的共同祖先**上派发；节点在这两者之间被替换后，共同祖先退到容器，
**而监听器是逐格绑的 → click 根本不会触发**。锁链场景更明显：2/3 连占多个槽 → 结算持续更久
→ 重绘窗口更长 → 几乎点不中。

**修法一：棋盘点击改事件委托。** 在 `#board-queues` 容器上绑**一次** `onBoardDelegatedClick`
（幂等标记 `container._antDelegated`）。委托的三个要点：

- 从 `e.target` 向上找最近的 `.board-cell`（点到内部的数字/角标 `<span>` 也能命中）；
- **按当前逻辑态重判**能不能取（`pickCapacityOf`），**不信 DOM 上的 class** ——
  高频重绘时 class 可能还是上一帧的；
- 只有「放不下」才提示，锁着/空格/管道一律静默忽略（点它们本来就没意义）。
  节点被重建导致 `click` 落在容器自身时安全忽略、不抛错、不误取。

委托同时天然解决了原问题：即使子节点被换，`click` 仍会冒泡到容器，处理器照样收到。

**修法二：棋盘 DOM 只在真的变了的时候重建。** 用签名
`steps | buffer.length | completedBoxes | gameOver` 判定 —— 棋盘可见内容只由「取盒」
（`steps`，管道吐球与冰解冻都在这一步）和「盒离场」（影响 `.pickable`/`.noslot`）改变。
目标图与暂存槽仍每帧刷新（canvas / 少量节点，不吃点击）。
实测：状态不变时 25 帧只重建 **1** 次（改前 25 次）。
`enterSimulation`/`doReset`/`doUndo`/`exitSimulation` 都会把签名置 `null` 作废
—— 撤销后 `steps` 会回退到与之前相同的值，不作废就会漏绘。

**同轮真跑核实了「锁链后点不动」不是逻辑问题**：取一个 3 连锁链组入场（占 3 槽、剩 2 空位）后，
棋盘上 6/6 个可取盒的 `pickCapacityOf` 全部为 `ok`，并成功再取一个（暂存变 4）。
即容量门没有误判，那条现象纯粹由上述重绘吃点击造成。

#### 已知限制

1. **手点暂存峰值会明显上升**（更真实），与历史批次口径**不同源**。手点模拟不参与生产审核
   （全知走 `applyPick`、评分走 `PlayerSim`，调用链无交叉），故不影响任何已产出批次。
2. **全知求解器仍是串行模型**，其 `pickOrder` 在时间驱动模型下个别步会放不下（那 0.11%）。
   回放走原串行路径因此不受影响；要让两者同源属后续「求解器调整」范围。
3 三套模型现状：**手点（时间驱动并发）≈ PlayerSim（tick 并发）≠ 全知求解器（串行瞬时）**。
   前两者现在同源，第三者仍是异类。

验证：`_kiro临时/08.28-手点并发结算/_最小样例.js` **44 项 0 失败**（真实关卡上真跑：
速率 6.5/8 各验一次、单帧不被取整吞掉、连点 3 盒同时占槽且各自都有进度、满暂存拒绝且棋盘未动、
`canConsume=true` 的盒同样被拒、锁链整组同步入场与离场、抽取等价、串行路径与门控齐全）。

### 8.3 ⚠ 玩家模拟的 `opts.seed` 当前无效（v121 实测，未修）

`playersim.js` 里 `rngState`（由 `opts.seed || 12345` 初始化）与 `rng()` 都有定义，
但 **`rng()` 在整个文件里零调用** —— 玩家模拟是**完全确定性**的，换种子不改变任何结果。

| 实测 | 结果 |
|---|---|
| 同一关 × 6 个种子（7/131/277/431/613/811），6 关 | **逐字段完全相同**（ticks/picks/peak/revives/won/均暂/取盒序列） |
| `PlayerSim.multiRun(level, 5)` | 5 轮跑同一条路线 → `successRate` 只可能是 0 或 1（也解释了它一直没有调用点） |
| `rng` 在文件中出现次数 | **1 次**（定义那一行本身） |

诊断脚本 `_kiro临时/08.28-前端模拟同步/_诊断-种子无效.js`。

**影响**：任何「按种子跑多轮玩家模拟」的做法都等于重复跑同一条路线。
故 v121 的难度重标定（`生产审核评分体系.md` §4c）改用 `pickThreshold` 作为多轮扰动轴，
`seed` 仍逐轮传入并记录，一旦 `rng()` 被接进选盒即可自动成为第二个扰动轴。
**是否接入属决策逻辑改动，需用户另行批准，本轮未改。**

**⚠ 两侧滞留不可直接比较**：全知的「步」是一次取盒；玩家的「tick」在四方向/仅底部下是
「各球各吃一像素的一轮」、在瞬时连锁下是「取盒 + 完整瞬时结算」。实测同一关全知滞留 1、
玩家瞬时连锁 0.37、玩家四方向 71.59。详见 `生产审核评分体系.md` §4a「已知限制」。

评分公式、权重与 cap 的完整定义在 `生产审核评分体系.md` §4a，本文档不重复。

> 本节记录的是**重写前瞻策略之前**（毛线口径策略）的旧观测，历史存档；重写后的三步前瞻树见 §5.2/5.5，`solve()` 的六遍编排见 §3。

- **策略已解耦**（`solver-strategy.js`）：重写策略不影响核心循环与机制，`pickBestMove` 契约不变即可对接。
