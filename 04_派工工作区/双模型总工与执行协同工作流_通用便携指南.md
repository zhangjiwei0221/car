# 「主脑 Agent + 执行 Agent」双会话并行协同工作流范式

## 一、核心架构与省 Token 底层原理

在复杂工程中，同时开启 **两个独立的 Agent 会话窗口**（各自常驻不同定位的模型，共享同一个本地项目目录）是兼顾**思考质量**与**额度成本**的高效范式：

- **会话窗口 A：主脑 Agent（领导 / 架构角色，常驻高阶旗舰模型，如 Opus / Gemini Pro）**
  - 负责需求拆解、架构设计、疑难根因诊断、制定**方案契约与验收标准**、以及对最终结果做轻量抽检。
- **会话窗口 B：执行 Agent（施工 / 落地角色，常驻高性价比模型，如 DeepSeek / Flash / Haiku / Sonnet）**
  - 负责跨文件阅读与编码、编写样板代码、执行**「改代码 ↔ 跑测试/跑实验/跑批量脚本 ↔ 看日志修 Bug ↔ 汇总数据」的多轮循环**，并将最终结果写回交工区。

### 💡 为什么这套架构能省 80% 额度？（理解 Agent 烧 Token 的真正黑洞）
在 Claude Code 等 Agent 工具中，真正烧光额度的**不是最后产出的那几百行代码**，而是**「带长上下文的多轮工具调用循环（Tool-Use Loop）」**：
- 假设当前会话历史已有 `5 万 Token`；Agent 每执行一次 `读文件 → 改代码 → 跑测试/跑脚本 → 看输出 → 再调 → 再跑`，**每一轮循环都要把那 `5 万 Token` 的历史上下文重新计费读一遍**！一个任务如果来回循环 15 轮，就是 `15 × 5 万 = 75 万 Token`。
- **双 Agent 省额度的核心秘密**：
  1. **把“多轮试错、编译调试与实验跑数循环”彻底剥离到窗口 B（便宜模型）**：让主脑只交互 **1~2 轮** 定好方向与验收门槛，把需要来回折腾 15~30 轮的苦力循环全部扔给窗口 B；
  2. **保持窗口 A（主脑）上下文永远短小干净**：窗口 B 刷出的几万行编译日志、报错堆栈和实验过程数据全留在窗口 B，绝不污染窗口 A，主脑后续每一轮对话的上下文底数都极小。

## 二、两大核心适用场景：按你的工作类型选对「派单粒度」

这套范式在 **「算法/策略/数据实验型项目」** 与 **「常规软件开发（前后端/全栈/重构）」** 中的派单侧重点截然不同，用对方式才能既省钱又不翻车：

### 场景 A：算法调优 / 策略迭代 / 数据实验 / 批量生产型工作（重实验、重跑数）
> **典型特征**：每次改动的核心算法代码可能只有 10~30 行，但改完后需要**反复跑实验脚本、跑模拟/回测、跑大批量生成、看日志调参、对比改前改后指标表格**（极其消耗工具轮次与等待时间）；且便宜模型一旦自己瞎改算法公式，实验数据就会全废。
- **主脑怎么派单（精确公式级派单）**：
  - 主脑直接读懂核心算法文件，在派工单里**把那 10~30 行最关键的算法公式 / 阈值逻辑直接写清楚（精确到行号或替换块，绝不让便宜模型乱发挥算法）**，并写明要跑哪几组对照实验命令、收集哪些指标；
- **执行干什么**：
  - 备份原脚本 → 精确换上主脑给的算法代码 → **承担后面耗时几十分钟的 N 组对照实验跑数、日志监控、异常重试与改前/改后指标汇总填表**；
- **为什么极省 Token**：
  - 主脑只花 1 轮写好核心公式，省掉了后面 **20~40 轮“跑实验 → 等结果 → 解析日志 → 算统计表”** 的巨额循环开销；且在窗口 B 跑实验的半小时里，窗口 A 可以同时复盘数据或设计下一轮实验。

### 场景 B：常规软件开发（前后端功能开发 / 写 UI 页面 / 接口联调 / 模块重构 / 补单元测试）
> **典型特征**：思路并不玄奥，但**涉及文件多（动辄改 5~15 个文件）、样板代码量大（几百上千行 CRUD / 组件 / 测试代码）**，且写完后需要反复跑 `tsc / eslint / npm test / build` 修编译错误和挂掉的测试用例。
- **主脑怎么派单（架构契约级派单 —— 切忌代写完整代码！）**：
  - 主脑**千万不要**自己把 10 个文件全读一遍、更**不要**在派工单里把几百行完整业务代码写出来让执行去复制粘贴（那样最贵的阅读和长输出全让主脑干了，一点不省 Token！）；
  - 主脑只花 1~2 轮写 **「模块设计契约」**：明确要新建/修改哪几个文件、接口入参和返回值格式是什么、状态流转与边界怎么处理、最后跑通哪条测试/构建命令算合格；
- **执行干什么**：
  - 在窗口 B 里自己去翻那十几个关联文件 → 自己写出几百行完整实现与单元测试代码 → 自己循环跑编译和测试 → 遇到报错自己在窗口 B 里改 5~10 轮直到全绿 → 在交工区贴出 `git diff --stat` 和测试通过输出；
- **主脑怎么验货**：
  - 主脑不重读全部 1000 行代码，只看测试通过结果 + `git diff` 抽检核心接口逻辑。

## 三、真省 Token 用法 vs 假省 Token 错误用法（3 组避坑对照）

| 维度 | ❌ 错误用法（反而费双倍 Token！） | ✅ 正确省 Token 用法（省 70%~85% 额度） |
| :--- | :--- | :--- |
| **1. 什么活该派单？**<br>（短活 vs 长活） | **无论大小活全走派工单**：<br>明明只是改 1 个小函数或修 1 行配置（主脑顺手 `Edit` 只要 1 轮），却非要让主脑写一篇 100 行的派工单，再切窗口 B 让执行去读文件改掉，最后主脑再读一遍验收——**1 轮的事变成了 4 轮！** | **1~3 轮短活直做，5 轮以上长活才派单**：<br>- **短活（小改/答疑/单点修 Bug）**：直接在当前窗口用「① 默认直做档」当场改完，零派单；<br>- **长活（多轮实验跑数 / 多文件编码 / 循环跑测试修报错）**：才开派工单交给窗口 B！ |
| **2. 主脑写多细？**<br>（区分实验型与常规开发） | **在常规开发中让主脑代写几百行样板代码**：<br>主脑在窗口 A 把所有业务文件读一遍，在派工单里写出 500 行完整业务代码，把执行 Agent 当成单纯的“复制粘贴打字员”——**最贵的长文本生成全让主脑干了**。 | **按场景二选一**：<br>- **实验/算法调优（场景 A）**：主脑给出最关键的 **10~30 行核心公式**，让执行去跑几十轮实验与汇总表格；<br>- **常规软件开发（场景 B）**：主脑只写 **接口契约 + 边界规则 + 验收命令**，让执行去写那几百行实现代码并调通测试。 |
| **3. 主脑怎么验货？**<br>（轻量抽检 vs 全量重读） | **主脑把执行改过的所有文件从头到尾重读一遍**：<br>执行 Agent 改了 8 个文件共 1000 行，主脑验货时用 `Read` 把 8 个文件全读进窗口 A——**主脑上下文瞬间暴涨**。 | **看客观命令输出 + `git diff` 定向抽检**：<br>- 执行 Agent 必须在交工区贴出**客观验证命令的真实输出**（测试结果、构建状态、实验指标表）；<br>- 主脑验货时先看客观指标与 `git diff --stat`，**只对核心逻辑做定向抽查**；若有 ≤10 行的小尾巴，主脑当场顺手修掉即收官。 |

## 四、目录结构与配置范式

### 1. 共享工作区目录结构（跨 Agent 通信枢纽）
在项目根目录下建立 `04_派工工作区/`，作为 **主脑 Agent** 与 **执行 Agent** 之间唯一的任务交接总线（之所以不把长篇模板塞进 `AGENTS.md`，是因为 `AGENTS.md` 每轮对话都会自动加载，塞太多内容会白白增加每轮对话的基础 Token 开销）：

```text
项目根目录/
├── AGENTS.md (或 CLAUDE.md)         <-- 两个 Agent 共同加载，仅放 15 行“三档口令切档”开关
└── 04_派工工作区/
    ├── README.md                    <-- 存放派单、接单与验收的通用模板规程（触发时才按需读）
    ├── 当前任务单.md                <-- 【跨会话交接活单】上半区由主脑写入，下半区由执行填写
    └── 历史派工归档/                <-- 主脑下达新单前，自动将上一张已完结任务单归档于此
```

---

### 2. 写入 `AGENTS.md`（或 `CLAUDE.md`）的 15 行触发开关

```markdown
## 默认直做 vs 领导派单 / 执行接单（双 Agent 会话按口令自动分流）

- **① 默认直做档（未提“派单 / 出主意 / 执行任务单”时）**：
  - 1~3 轮能解决的日常小改、问答、修小 Bug，当前会话**直接动手完成**，不分角色，不写派工单。
- **② 主脑（领导 Agent 会话，触发词：“你是领导 / 针对XX想主意 / 只出主意 / 派单 / 写任务单 / 验货”）**：
  - **省额度原则**：不在本会话执行多文件样板编码、耗时构建、反复实验跑数或重度循环调试；只做根因诊断与方案设计，按 `04_派工工作区/README.md` 规范操作。
  - **派单规范**：先将上一单归档至 `04_派工工作区/历史派工归档/YYYYMMDD_HHMM_派工单XXX.md`，再在 `04_派工工作区/当前任务单.md` 写入新单（实验型任务给出核心算法锚点与对照实验命令；常规开发任务给出模块接口契约、边界禁区与测试命令，**不代写大段样板代码**），交由执行 Agent 落地。
  - **验货规范**：读取磁盘上的 `04_派工工作区/当前任务单.md` 下半区交工记录，通过测试/实验真实数据与 `git diff` 关键点做轻量抽检（不盲目全量重读所有文件）；微小收尾（≤10 行）直接顺手修平，较大偏差再开单打回。
- **③ 施工（执行 Agent 会话，触发词：“干活 / 接单 / 执行 `04_派工工作区/当前任务单.md`”）**：
  - 读取磁盘上由主脑写好的 `04_派工工作区/当前任务单.md` 上半区，独立完成编码、实验跑数、循环调试与自检，**严禁删改上半区或私自另开派工单**；若中途有口头需求变更，在下半区注明 `HH:MM 口头变更：...`；完成后填妥下半区交工记录并将顶部状态改为 `🟢 待验收`。
```

## 五、双 Agent 并行运转闭环（工作流全景图）

```text
   【会话窗口 A：主脑 Agent（旗舰模型）】               【会话窗口 B：执行 Agent（高性价比模型）】
   (仅交互 2~3 轮，上下文极短、极省额度)                 (承担 15~30 轮翻文件、写代码、跑实验/修报错循环)
                   │                                                     │
  1. 在窗口 A 说： │                                                     │
  “针对XX需求定方案│                                                     │
   确认后写派工单” │                                                     │
                   ▼                                                     │
     主脑用 1~2 轮定位核心问题，归档旧单，                               │
     将【架构契约(常规开发) 或 核心公式+实验命令(实验型)】写入磁盘：     │
     [04_派工工作区/当前任务单.md (上半区)] ──────── 磁盘文件同步 ───────► │ 2. 在窗口 B 说：
                   │                                                     │ “执行 04_派工工作区/当前任务单.md”
                   │                                                     ▼
     (⚡ 窗口 B 循环编码/跑测试/跑实验期间，             执行 Agent 读取《当前任务单.md》，
      窗口 A 完全零消耗，或可并行讨论下一模块！)          承担多文件编码 → 跑测试修报错 / 跑批量实验，
                   │                                     直到自检完成，将 diff 摘要与结果表写回：
                   │                                     [04_派工工作区/当前任务单.md (下半区)]
```
