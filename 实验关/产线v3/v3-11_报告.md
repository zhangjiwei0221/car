# v3-11 报告：ReachPlan_v1——失败关都至少有一种颜色「玩家路线没拿到足够可达量」

> 日期：2026-11-06
> 工具：`03_工具/正式版/ReachPlan_v1.js`
> 输入：v1 十批 110 张 + G2 10 张
> 目的：资源层体检——每种颜色在玩家路线/求解器路线里到底能露出多少像素。

---

## 1. 方法

对每张关，分别沿两条路线统计每种颜色：

- **玩家路线**：`PlayerSim` 0 复活（实际死亡路线）；
- **求解器路线**：`Solver.runMinBuffer`（完整拿起全部车；参考上界）。

指标：

| 指标 | 含义 |
|---|---|
| `total` | 该色总像素 |
| `playerSum` | 玩家路线里，该色各车被拿时的 reach 之和 |
| `playerMax` | 玩家路线里该色出现过的最大 reach |
| `solverSum` | 求解器路线里，该色各车被拿时的 reach 之和 |
| `shortPlayer` | `total - playerSum` |

判定：

- `ok`：`playerSum >= total`；
- `route-short`：玩家不够，但求解器够（路线没走到）；
- `both-short`：两边都 < total（reach 是下界，需进一步看）；
- `unpicked`：玩家路线根本没拿到该色。

## 3. 结论

1. **失败关不是「容量没分好」，是「玩家路线没拿到足够像素」。** 103/103 失败都至少有一种颜色 `playerSum < total`。
2. `route-short`（103 张）说明求解器路线能拿到，但玩家路线走不到——玩家在拿到这些颜色之前就死了。
3. `both-short`（92 张）不等于「绝对不可通」：`reach` 是拿车那一刻的下界，车在吃的过程里还会继续暴露像素；这个状态是「需要进一步看」，不是判死。
4. `unpicked`（102 张）说明玩家路线连这些颜色都没碰过——死亡太早。
5. **ReachPlan 是诊断，不是判死**：通关的关也可能有 short 颜色（G2 8_0024 通关但有 3 个 both-short）。可靠的失败预测仍是 v3-08 的 fatal 时序。

---

## 4. 这对 v3 编译器意味着什么

v3 的「可玩」至少要满足三层：

1. **Reach**：每种颜色在意图路线上有足够可达量（ReachPlan）；
2. **Capacity**：每辆车容量 ≤ 还债前的可达量（CapacityPlan）；
3. **Timing**：玩家引擎能实际走通，债务在爆仓前被追上（PlayerEngineCheck + fatal）。

ReachPlan 是第一层：先找瓶颈颜色，再决定改棋盘/障碍/路线，还是换图。**不要跳过 reach 去调容量**——v3-09/10 已经证明调不动。

---

## 5. 下一步

1. **挑一张 `route-short` 的关**（如 00154 / 00195），看瓶颈颜色为什么玩家拿不到：是死得太早，还是像素被别的颜色埋住。
2. **用决策图谱找「能活到瓶颈颜色」的路线**：如果不存在，改棋盘/障碍/车位置，让主色更早暴露。
3. **把 ReachPlan 接进编译器**：生成时先保证 `playerSum >= total`（意图路线），再分配容量。
4. 然后回到 M2 信息层（可见 reach vs 真实 reach）。
