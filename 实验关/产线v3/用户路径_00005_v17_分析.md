# 用户点击路径分析：00005 v17（2026-11-09）

> 文件：`用户路径/点击路径_2026-11-09T02-58-04.json`（v637 导出）。
> 47 次点击，1600/1600 像素，通关；`bufferAfter` 最大 4，没有超过 5。

## 1. JSON 本身：没有大问题

- 47 条记录，`steps` 1–47 连续，`eliminatedPixels` 单调递增到 1600，最后一击 `gameWon=true`。
- 每条的 `picked`、`buffer`、`bufferAfter`、`progress` 都能对上；链组（n41、n46、n47）展开了全部成员。
- 唯一的小问题：`session.level.name = null`，因为导入的关卡 JSON 没有 `name` 字段；不影响路径分析。
- 没有 `bufferAfter > 5`，说明 v636 的容量门在串行手点路径上生效。

## 2. 体感“前中期免费步多”是对的，但不是 `buffer=0`

| 口径 | 步数 |
|---|---:|
| `bufferAfter = 0`（严格免费） | 2 / 47（只有最后 n46、n47） |
| `bufferAfter ≤ 1`（低压力） | 15 / 47 |
| `bufferAfter = 2` | 21 / 47 |
| `bufferAfter = 3` | 9 / 47 |
| `bufferAfter = 4` | 2 / 47 |

所以严格意义的“免费步”并不多；你感觉多，是因为前中期大量步骤只有 **1–2 辆车**，而且其中一辆往往只差几像素。

## 3. 更关键的发现：后期 buffer 高，但“有效债”是 0

把“有效债”定义为 `剩余 > 10px` 的车（差几像素的车玩家几乎感觉不到压力）：

| 阶段（按进度） | 有效债 0 辆 | 有效债 1 辆 |
|---|---:|---:|
| 前段 <40% | 7 步 | 4 步 |
| 中段 40–80% | 7 步 | **19 步** |
| 后段 >80% | **10 步** | **0 步** |

- 后期 n41–45 虽然 `bufferAfter=3/4`，但 buffer 里是 `30:28/30`、`24:17/20`、`13:89/90` 这类**只差 1–3px** 的车；按 10px 阈值，后期有效债为 **0**。
- 你体感“后期还不错，要思考”，其实是 raw buffer 高；真正需要决策的压力集中在中段。
- 中段 n18–34 的 19 步有效债，主要是同一辆 `28:31/79`（差 48px）从进度 48.7% 一直挂到 70%；另一个位置是 `13:88/90`（差 2px），几乎不算压力。

## 4. 中期是不是顺序问题？

有一部分是。

- n18 你在 48.7% 时点了 `28:79`，当时它只有约 31px 可达，留下 48px 债，一直占到 n34；这是中段唯一的真实债，也是你觉得“前中期免费”里那笔真正要思考的地方。
- 后期 n41 你才点后排链组 `24:20 + 30:30`；到那时 30 只剩 28/30、24 只剩 17/20，链组只是把两辆“快吃完”的车一起收尾，**没有制造有效债**。
- v17 的点击结算贪心路线在 n39 就点这个链组（30:18/30 + 24:4/20），所以它能在最后 8 步压出 2 辆真债；你的路线把链组推迟到 n41，后段就变成 raw buffer 高、有效债低。

所以不是“你点错了导致失败”——你通关了；而是**链组点得晚，后段债被错过了**。中期那辆 28 的债和后期链组的时机，是一个取舍：想后段有真债，链组要更早；想中段轻一点，28 可以更晚拿。

## 5. 结论

- JSON 数据质量没问题，可以用于对账。
- 我们之前的“免费步”统计必须分三层：`buffer=0` / `buffer≤1` / `有效债（剩余>10px）`；只看 `bufferAfter` 会把“快吃完的车”误当压力。
- 00005 v17 目前是**中段债型**：中段有 19 步有效债，后段是 raw buffer 收尾，不是有效压力。
- 下一步如果要“后段也要思考”，不是加大后排容量，而是让后排链组更早被点到（或加冰/改位置，使它不能拖到最后）；如果接受中段债型，就把这版作为难度基准进 M5。
