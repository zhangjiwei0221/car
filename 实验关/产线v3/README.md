# 产线 v3（实验记录）

> **名称**：产线 v3（不叫 v3.0；现役叫产线 v1）。
> **定位**：在 `产线 v1` 的候选关之上，加一层「后果 + 信息」的核算。v1 继续出候选，v3 负责解释、筛选、修复、出证书。
> **状态**：草案 v0（2026-11-06），目标待讨论确认。

---

## 1. 一句话目标

**让每个决策点都能算出「所有走法的后果」和「玩家看得见什么」，再用这两张表去造关、验关、解释关——而不是只看 19 项指标。**

v3 的成功标准不是「又产了多少关」，而是：

1. 给定一张关，能说清**每一步**：有哪些车可拿、拿了会怎样、有没有安全替代；
2. 给定一次死亡，能说清**是哪一步、哪辆车、缺什么信息**导致的；
3. 给定一个障碍，能说清它**改变了什么**（选项数 / 债务时点 / buffer / 路线分布）；
4. 给定一张出货关，附带**路线证书**（意图路线、债务事件、陷阱步、恢复路径）。

---

## 2. 为什么不是 v1 / v2

| | 做法 | 问题 |
|---|---|---|
| **产线 v1** | `JointSearch` 自动搜索候选，19 项验收 | 能出「还不错」的关，但会出「指标关」；不知道玩家会怎么走 |
| **v2（实验）** | 人定骨架 + 可达曲线 + 试玩校准 | 未通过，停在候选阶段；脚本和实测对不上 |
| **产线 v3** | 先建「后果表 + 信息表」，再用手搭/搜索造关 | 第一版不追求产量，追求「能解释」 |

v3 不替代 v1 的工具。v1 继续当候选生成器；v3 是架在它上面的一层尺子和证书。

---

## 3. 七点怎么落地

| 七点 | v3 里的具体东西 | 第一版做到什么 |
|---|---|---|
| ① 三种量化 | 规则表 / 后果表 / 信息表 | 先做**后果表** |
| ② 后果层 | `DecisionAtlas`（决策图谱） | 死亡步反事实 + 3 张关的逐步走法表 |
| ③ 信息层 | `VisibleReach`（可见 reach vs 真实 reach） | 算出每色每步的「误判差」 |
| ④ 障碍可控 | `ObstacleContract` + `Ablation` | 每个障碍移除/移位，测 4 个 Δ |
| ⑤ 设计单元 | `DecisionFingerprint`（决策指纹） | 每关一张指纹：开局可点、第一笔债、最大债、释放步、陷阱、恢复 |
| ⑥ 落地顺序 | M1 → M5 | 先 M1 |
| ⑦ 别做的事 | 见 §5 | 写进每次实验的约束 |

## 4. 里程碑

### M1（先做）：决策图谱能解释已知死亡

- 对 3 张已知关（00085 v25d / 拼接006 / G8_115 手搭）输出逐步走法表；
- 对已知死亡步做反事实：如果改拿 X，会不会活；
- 验收：至少解释 80% 的已知死亡/卡点步；解释不了的，记录「模型缺什么」。

### M2：信息层

- 算「可见 reach vs 真实 reach」，输出每色每步的误判差；
- 用真人试玩对账：玩家实际选择是否更接近「可见 reach」而不是真实 reach；
- 验收：预测路线分布与试玩的一致率，比「真实状态模型」高。

### M3：障碍契约 + 消融

- 每个障碍写契约：gate 什么状态、延迟几步、隐藏什么信息、改变哪个走法集合；
- 移除/移位测 Δ（可选走法数、债务时点、buffer、路线分布）；
- 验收：每个障碍都有非零且有界的 Δ；Δ=0 的标为装饰，Δ 覆盖全关的标为单点故障。

### M4：语法库 + 路线证书 + 一张新关

- 把验证过的门/口袋/走廊/链组/冰闸/管道队列写成语法；
- 每张出货关附路线证书（意图路线、债务进入/释放步、陷阱步、恢复路径、误判风险）；
- 验收：用语法造一张新关，硬门 + 体验契约全过，证书可审计。

### M5：批量

- 在语法上搜索，不在全参数空间搜索；
- 每次批量产出都带决策指纹和证书，按指纹筛选，不按总分筛选。

---

## 5. 不做什么（每次实验都遵守）

1. 不追求「预测某个人」——只预测分布，并给证书；
2. 不用单一求解器路线代表玩家——min / 贪心 / 信息受限策略族分开报；
3. 不把 19 项指标当目标——它们只做护栏；
4. 不把「变化多」当归宿——变化要收敛成语法；
5. 不先做全自动批量——先把一个决策做到可解释；
6. 不复用骨架——黑块/门位不能永远在老地方；
7. 不搬冰参数——换图必须按该关状态重推；
8. 不拿「压力变大」当成「玩家愿意背债」——还要看可读性和可恢复性。

## 6. 第一实验：v3-01 死亡步反事实

**问题**：v25d 的已知死亡步（0 复活自然打法第 10 步 21% 死）上，是否存在安全走法？链组的问号是否让玩家无法预判？

**已确认的事实（2026-11-06）**：

- `合理玩家报告_v804_v25d.json`：5 个 seed（7/19/37/73/101）**全部第 10 步死**，progress 21%，buffer 5/5。
- 死亡暂存：`30:39 / 24:13 / 32:32 / 1:0 / 32:41`。
- 重跑 PlayerSim seed 7，拿到精确选车序列：
  `29:60 → 14:70 → 29:80 → 33:35 → 32:13 → 14:41 → 30:53 → 24:13 → 32:42 → 链组1（1:17 + 32:41）`。
- 第 10 步是**链组 1**：`r1c4 1:17` + `r2c4 32:41`（同组；32 还带问号）。`1:17` 填满（rem 0），`32:41` 填不满（rem 41），整组锁死。
- 也就是说：**死亡不是随机手痒，是「链组 + 问号 + 前 9 步的债」共同造成的确定性结果。**

**输入**：
- `实验关/四象限/00085_7x7_主体债减书债_v25d/关卡_00085_7x7_主体债减书债_v25d.json`
- `合理玩家报告_v804_v25d.json`（5 seed 死亡快照）
- `ArlCheck_v794_soft_v25d.txt`（基线指标）
- 精确选车序列用 `PlayerSim.run(..., { seed: 7, reviveCap: 0 })` 的 `pickOrder` 复现。

**方法**：
1. 把局面重放到死亡步；
2. 枚举该步所有可拿车；
3. 对每个走法，用现有求解器往前跑到终局（或深度 N），记录：能否通关、最大暂存、债务增量、释放步；
4. 给每个走法分类：安全 / 背债 / 陷阱 / 必死；
5. 对比玩家实际走法，给出反事实：「如果改拿 X，会活/会死」。

**验收（可证伪）**：
- 至少给出 1 条「改拿 X 就能活」的路线，并用 `ArlCheck_v793` 或求解器验证；**或**
- 证明该步无安全走法，并定位是哪笔债/哪个障碍造成的。

**产出**：
- `实验关/产线v3/v3-01_报告.md`
- `实验关/产线v3/v3-01_死亡步反事实.json`
- 工作日志新增一节（五段式）

**负结果也有意义**：
- 如果所有走法都死 → 设计问题（不是玩家选错），记下是哪笔债不可释放；
- 如果模型算出的「安全走法」玩家实际拿了也死 → 模型缺信息层，进 M2；
- 如果求解器跑不完 → 记录状态数，缩小深度/抽象，进 M1 的工具迭代。
