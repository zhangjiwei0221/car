## 1. 一句话目标

**让每个决策点都能算出「所有走法的后果」和「玩家看得见什么」，再用这两张表去造关、验关、解释关——而不是只看 19 项指标。**

v3 的成功标准不是「又产了多少关」，而是：

1. 给定一张关，能说清**每一步**：有哪些车可拿、拿了会怎样、有没有安全替代；
2. 给定一次死亡，能说清**是哪一步、哪辆车、缺什么信息**导致的；
3. 给定一个障碍，能说清它**改变了什么**（选项数 / 债务时点 / buffer / 路线分布）；
4. 给定一张出货关，附带**路线证书**（意图路线、债务事件、陷阱步、恢复路径）。

**产品是「一张关 + 三张证书」**（指标 / 体验 / 排版），不是分析报告。
决策图谱、障碍契约、信息模型是产线的**传感器和执行器**，不是交付物。

## 4. 里程碑

### M1（先做）：决策图谱能解释已知死亡

- 对 3 张已知关（00085 v25d / 拼接006 / G8_115 手搭）输出逐步走法表；
- 对已知死亡步做反事实：如果改拿 X，会不会活；
- 验收：至少解释 80% 的已知死亡/卡点步；解释不了的，记录「模型缺什么」。

### M2：信息层

- 算「可见 reach vs 真实 reach」，输出每色每步的误判差；
- 用真人试玩对账：玩家实际选择是否更接近「可见 reach」而不是真实 reach；
- 验收：预测路线分布与试玩的一致率，比「真实状态模型」高。

### M3：障碍契约 + 消融

- 每个障碍写契约：gate 什么状态、延迟几步、隐藏什么信息、改变哪个走法集合；
- 移除/移位测 Δ（可选走法数、债务时点、buffer、路线分布）；
- 验收：每个障碍都有非零且有界的 Δ；Δ=0 的标为装饰，Δ 覆盖全关的标为单点故障。

### M4：语法库 + 路线证书 + 一张新关

- 把验证过的门/口袋/走廊/链组/冰闸/管道队列写成语法；
- 每张出货关附路线证书（意图路线、债务进入/释放步、陷阱步、恢复路径、误判风险）；
- 验收：用语法造一张新关，硬门 + 体验契约全过，证书可审计。

### M5：批量

- 在语法上搜索，不在全参数空间搜索；
- 每次批量产出都带决策指纹和证书，按指纹筛选，不按总分筛选。

## 5. 不做什么（每次实验都遵守）

1. 不追求「预测某个人」——只预测分布，并给证书；
2. 不用单一求解器路线代表玩家——min / 贪心 / 信息受限策略族分开报；
3. 不把 19 项指标当目标——它们只做护栏；
4. 不把「变化多」当归宿——变化要收敛成语法；
5. 不先做全自动批量——先把一个决策做到可解释；
6. 不复用骨架——黑块/门位不能永远在老地方；
7. 不搬冰参数——换图必须按该关状态重推；
8. 不拿「压力变大」当成「玩家愿意背债」——还要看可读性和可恢复性。

## 6. 第一实验（历史，2026-11-06）：v3-01 死亡步反事实（G2_bq_level_9_0023）

> 以下保留第一实验原文；当前候选和规则见 §0、实验索引见 §10。

> 原打算用 v25d，但它是 Mode A「任务阶段计划」关，阶段门会干扰结论；改用桌面 `拟导入的关卡/G2/G2_bq_level_9_0023.json`（通用关）。v25d 保留为对照案例。

**问题**：这关的合理玩家 0 复活 5/5 都在第 11 步死；第 11 步有没有安全走法？如果没有，是哪一步造成的？

**已确认的事实（2026-11-06）**：

- 合理玩家（seed 7/19/37/73/101，0 复活）**全部第 11 步死**，progress 38%，buffer 5/5。
- 死亡暂存：`30:13 / 30:49 / 29:0 / 4:24 / 31:23`。
- 第 11 步拿的是链组 2（`29:24 + 4:24 + 31:23`）：`29` 填满，`4`/`31` 填不满，整组锁死；前 10 步已有两辆 30 在暂存，正好 5/5。
- 选车序列：`链组1(1/14/32) → 1:43 → 13:50 → 26:36 → 13:37 → 33:36 → 22:33 → 19:33 → 30:44 → 30:52 → 链组2`。
- 19 项基线：峰值 4 ✅、容错 11/20 ✅、主体并行 57% ✅、决策 30/36、可通关（最小路线）✅；不通过项：中段 29%、中段最长低压 15、象限 3.61、未动主体 0、开局可点 4、at4=1。

**实验结果（A/B/C）**：

A. **一步偏离扫描（第 1–10 步）**：
- 第 1–10 步各有 2–5 个合法替代；
- **没有任何单步改动能活**（全部仍在第 11 步、progress 38 死）；
- 结论：死亡不是某一手选错，是整条策略收敛到同一个死点。

B. **强制最小路线**：
- `Solver.runMinBuffer` 的路线 36 步、46/46 通关；
- 把这条路线的前 19 步强制给 PlayerSim：**0 处不匹配**（玩家完全能照走），但第 19 步结算后死；
- 求解器同一条路线第 19 步后 buffer=1；玩家 buffer=3（`30:21 / 32:6 / 1:34`），且还空 2 格——不是爆仓，是「无路可走」。

C. **结论**：
- **同样的选车序列，求解器通关、玩家引擎死**；
- 分歧不在选车，在**结算/填充/释放**：同一批像素被分给了不同的同色车，导致玩家侧留下两辆接近满但未完成的 30/32 车；
- 因此「可通关（最小路线）✓」是**求解器口径**，不保证玩家引擎可复现；这是 v3 要补的后果层缺口。

**复现注意**：`forcedPicks` 的键是 **0 起算**（代码里 `forcedPicks[picks]` 在 `picks++` 之前）；用 `step` 当键会整体错一位，我第一次扫描就踩了这个坑。
