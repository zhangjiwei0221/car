# v3-07 报告：容量 vs 暴露步可达——必要风险条件，不是判死规则

> 日期：2026-11-06
> 工具：`03_工具/正式版/CapacityReachCheck_v1.js`
> 输入：v1 十批 110 张 + G2 10 张
> 口径：PlayerSim 默认策略（pickThreshold 0.6，0 复活）；`reachAtPick` 是「该盒被拿那一刻，该颜色在目标图上的可达像素数」。

---

## 1. 方法

在 `PlayerSim` 的 `pickOrder` 里新增只读字段 `reachAtPick`（拷贝消除矩阵后调 `floodFillCount`，不改任何决策）。然后标：

- **singleOver**：单盒车 `count > reachAtPick`；
- **chainSuspect**：链组任一成员 `count > reachAtPick`（成员可能被同组其他车吃出来，只标记，不判死）。

---

## 2. 结果（110 张 v1）

| 项 | 数 |
|---|---:|
| 0 复活通关（默认策略） | 7/110 |
| 0 复活失败 | 103/110 |
| 有 singleOver 的关 | 62 |
| 有 chainSuspect 的关 | 87 |
| **失败且至少一项违规** | **103/103（100%）** |
| 失败且 singleOver | 55/103 |
| 失败且 chainSuspect | 83/103 |
| **通关但也有违规（假阳性）** | **7/7** |

`maxOver` 分布：

| | min | 中位 | max |
|---|---:|---:|---:|
| 失败关 | 0 | 12 | 81 |
| 通关关 | 4 | 17 | **59** |

阈值扫描：`maxOver ≥ 40` 能标出 32/103 失败，但仍会误标 1/7 通关；没有单一阈值能分开。

---

## 3. 结论

1. **「容量 > 暴露步可达」是 0 复活失败的**必要**条件：103/103 失败都有；但不是充分条件——7/7 通关也有，最大 maxOver=59。
2. **原因是时间**：一辆车被拿时可达量不够，不代表它永远不够；其他车清掉阻挡色后，可达量会追上来。通关的关就是「债务在爆仓前被追上」，失败的是「债先爆」。
3. **所以规则不能写成「count ≤ reachAtPick」**，要写成「**count ≤ 债务必须偿还前的可达量**」——即 **容量 + 时间**，不是容量一个数。
4. `CapacityReachCheck` 仍然有用：它是**高召回的风险预筛**（100% 命中失败），不是硬门；可以先用它把可疑车/链组标出来，再用图谱看债务时序。

---

## 4. 对 v3 编译器的要求

1. 车容量按「暴露步可达 + 债务可等待时间」分配，不是按颜色总量平均切。
2. 链组成员要逐个检查「在整组必须释放前，每个成员的可达量是否够」；只看拿的那一刻会误判（链组 1 的 32:56 拿时 reach=0，后来被同组吃出来）。
3. 风险预筛：`CapacityReachCheck` 标出的车/链组，进入图谱做时序检查；不要直接淘汰（会误杀）。
4. 真正的判死仍是 `PlayerEngineCheck` + 决策图谱；容量检查只负责「先看哪里可能出问题」。

---

## 5. 下一步

1. **加「债务时序」**：对每个 singleOver 车，找它同色下一次被拿/可达追上来的步；如果追上来的步晚于爆仓，标 `fatal`。
2. **链组单独处理**：模拟整组入场后、其他成员吃出的可达量，判断是否可填；不要用拿的时刻一刀切。
3. 把「容量 + 时序」写进 v3 编译器；`CapacityReachCheck` 作为预筛保留。
4. 继续 M2 信息层（可见 reach vs 真实 reach）。
