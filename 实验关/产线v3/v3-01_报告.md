## 3. 实验 B：强制最小路线

方法：`Solver.runMinBuffer` 产出 36 步路线（46/46 通关）；把它的前 n 步用 `forcedPicks` 强制给 PlayerSim。

| 强制前 n 步 | 不匹配 | 玩家结果 |
|---:|---:|---|
| 3 | 0 | 第 11 步死（策略继续选了链组 2） |
| 5 | 0 | 第 11 步死 |
| 10 | 0 | 第 11 步死 |
| 15 | 0 | 第 20 步死，progress 63 |
| 16 | 0 | 第 20 步死 |
| 17 | 0 | 第 20 步死 |
| 18 | 0 | 第 19 步死，progress 60 |
| 19 | 0 | 第 19 步死，progress 59 |
| 20+ | 1+（第 20 步起） | 第 19 步已死，后续强制不生效 |

**关键**：前 19 步**全部匹配、玩家完全能照走**；但第 19 步结算后，玩家引擎死。

### 3.1 同一条路线，两边的状态

| | 求解器 | 玩家引擎 |
|---|---|---|
| 第 19 步后的 buffer | **1** | **3**：`30:21 / 32:6 / 1:34` |
| 空槽 | — | 2（不是爆仓） |
| 死因 | — | 无路可走（dead end） |

**结论**：同样的选车序列，求解器通关、玩家引擎死。分歧不在选车，在**结算/填充/释放**——同一批像素被分给了不同的同色车，玩家侧留下两辆接近满但未完成的 30/32 车。

### 3.2 第一处分歧：第 2 步（链组 1 入场）

逐车对比（强制最小路线的前两步：`r0c4 13:50` → 链组 1 `1:101 + 14:127 + 32:56`）：

| | 求解器第 2 步后 | 玩家第 2 步后 |
|---|---|---|
| `13` 车 | **已完成离场**（done=1） | 还在：`13:0/50` |
| `1` | `101/101`（满） | 未满 |
| `14` | `127/127`（满） | 未满 |
| `32` | `25/56` | `0/56` |
| buffer | **3** | **4** |
| done | 1 | 0 |

玩家帧里每个 tick 只吃 2–3 个像素（`frames[1..5].eats` = 2/2/2/3），求解器一次 `applyPick` 就把整组结算完。

**根因（代码级）**：
- 求解器走 `Sim.applyPick`：`processChainGroup` / `processAntBox` → `autoReleaseBuffer`，**一次取车 = 一次完整结算**。
- 玩家走 `Sim.pickBoxRaw` + tick 循环：只做取盒机械，消除按 tick 逐步进行（并发多球）。
- 两套都是既有实现，不是本次引入；差别在**结算模型**，不在选车合法性。

**推论**：`Solver.runMinBuffer` 的「最小路线」只在**完整结算模型**下成立；玩家引擎是**逐步结算模型**。如果真机是后者，那么「可通关（最小路线）」需要改用玩家引擎重跑；如果真机是前者，玩家引擎需要对齐。**这必须先确认真机口径。**

**真机确认（2026-11-06 用户）**：三锁链快吃完时，蓝色已经开始吃了——真机是**并发/逐步结算**，不是求解器的一次性结算。因此以 `PlayerSim` 为准；求解器 min 路线只作规划参考。

## 4. 这意味着什么

1. **「可通关（最小路线）✅」是求解器口径，不保证玩家引擎可复现。** 本关就是反例：求解器 36 步通关，玩家照走前 19 步却死。**真机已确认是并发/逐步结算，所以最终以玩家引擎为准，`ArlCheck` 的「可通关」需要玩家引擎复核。**
2. **死亡不是玩家选错。** 第 1–10 步的所有单步替代都救不了；真正的问题在引擎/口径，不在玩家。
3. **v3 的「后果层」假设成立**：只看 19 项指标会把这关判为「可通关」，但玩家走不通。必须补上「同一局面、每个走法的真实后果」。
4. **并发结算也是设计杠杆**：真机里下一辆车可以在上一辆还没吃完时开始吃，意味着同色像素会在多辆车之间竞争。什么时候点下一辆，会改变哪辆车先填满——这既可能制造债，也可能释放债。这是 v3 信息层/后果层要量化的东西。
