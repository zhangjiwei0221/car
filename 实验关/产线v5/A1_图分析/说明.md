## 1. v2 做了什么

1. **corner 消融序列**（纯图，无车）：
   - 初始“已吃”为空；0 空位视为已经空的格子。
   - 暴露 = 与图四边相邻、或与已吃格/已空 0 格 4 邻接的彩色格。
   - 每步在暴露的未吃彩色格中选 **D = (行数-1-r) + c** 最小的那个吃掉；平手先 r 大（更靠底），再 c 小；重复到吃完。
   - 每个被吃的格子记录 `(进度 = 已吃彩色像素 / 总彩色像素, 颜色)`。
2. **需求曲线** `demandCurve[20]`：进度每 5% 一个窗口，每色在该窗口被吃的像素数。
3. **每色 progress 分位**：`p10 / p50 / p90`，以及 `firstProgress / lastProgress`。
4. **需求峰**：窗口 W 里某色占该窗口像素数 ≥30% 且 ≥40px，记为一个峰 `(color, W)`。
5. **门候补**：某色在 20%–90% 区间有峰、且该色总像素 ≥60，列为门候补。
   **额外要求该色开局不可达**（没有贴边像素、也不能经 0 连通到图边）；否则它从 0% 就能吃，后置的门卡不住。
   这一条是为了让单色图 / 左右两色图不产生门候补（见 §5.1）。
6. **verdict 三档**：
   - ≥2 个不同窗口有门候补 → **图可以**
   - 只有 1 个窗口 → **图一般（最多一个门）**
   - 0 个 → **图不行**
7. **v1 结果保留**在 `diagnostics.blockModel`，只作参考，不参与 verdict。

## 4. 为什么 v1 的 layerDepth 不能用于选图

v1 用“逐格 BFS 必须吃掉的格数 / 总像素”作为 E。图里没有不可吃的格子，最短路只能到最近图边的距离，E 有硬上限：

| 图 | v1 逐格 BFS 实测 `diagnostics.eCell.maxE` | 对应格数 |
|---|---:|---:|
| 40×40 | 0.011875 | 19 / 1600 |
| 45×45 | 0.010864 | 22 / 2025 |
| 48×48 | 0.009983 | 23 / 2304 |

也就是说，“像素被别的颜色挡住”在 40×40 图上最多只能拖到约 1.2% 进度，**数学上永远到不了 30%**。卡点只能靠供给（车/锁链/管道/冰），而供给是我们自己摆的；图能提供的是**需求**（进度到 X% 时正在吃哪些颜色）。v1 的 block-Dijkstra 把“整色块计费”的抽象当成层次，会把大背景图误判成“很多层”（23 的 11 个候选全在同一 30–35% 桶），所以不能用于选图。v1 的结果仍在 `diagnostics.blockModel` 里，方便对照。

### 5.4 人工核对（至少 3 个峰）

用**独立的 O(N²) 逐步扫描脚本**（不是工具本身）重放消融序列，重算 20 个窗口的每色计数：

- 三张真实图的整条需求曲线与工具输出 **diff = 0**（23/18/91 全部）。
- **23 / 色 31 / 50–55%**：独立重放 41px，工具 41px；这些格子的质心 (r19,c20)，落在车身主体，确实是“这一进度在大量吃车身色”。
- **91 / 色 27 / 20–25% 与 25–30%**：45px、55px；质心 (r29,c14)、(r28,c17)，在左下区域。
- **91 / 色 27 / 75–80% 与 80–85%**：40px、51px；质心 (r11,c26)、(r12,c30)，在右上区域。两段在几何上是分开的，所以记为两条需求带（20–30% 和 75–85%）。

结论：峰的数字、位置和“该进度在大量吃这个颜色”一致。

## 7. 局限（用之前必读）

1. **消融顺序是“无车自由吃”的固定顺序**：每步吃全局最小 D 的暴露格。真人会换颜色、换顺序，需求峰可能被绕开；v2 说的是“这条 canonical 顺序下，图在 X% 需要什么”，不是“所有玩法都必然需要”。
2. **峰阈值是暂定值**：占比 ≥30%、窗口 ≥40px、门候补总量 ≥60px。18 只差 2px 就有一个峰，说明结论对阈值敏感；改阈值前先跑三张对照。
3. **门候补额外要求“开局不可达”**（本版新增）：没有贴边像素、也不能经 0 连通到图边。否则单色/左右两色图会被固定扫描顺序误判出门候补。代价是：一个颜色只要有 1 个贴边像素，就整色不算门候补（偏保守）。
4. **“不同窗口”不等于“不同门”**：同一色连续跨多个窗口会算多个窗口；`distinctGateBands` 才是“几条分开的需求带”。34/100/212 就是 1 条带跨 2 个窗口。
5. **91 的两条带是同一颜色在两个空间端**（左下 20–30%、右上 75–85%），可能只是一个门在两端被吃；是否算两个门要 S1 卡片人工判断。
6. **图可以 ≠ 关卡能落地**：v2 只给需求，不含车/锁链/管道/冰。门候补只说明“图上在这个进度需要这个颜色”，能不能造出供给卡口还要 S1 规划、S3 建造、S5 合法性、T5 检查。
7. **进度分母是彩色像素**（v2 口径），与 v1 的 H×W 不同；有 0 空位的图两者会差一点。
8. **只新建/改这两个文件**：未改现有工具、未动 `02_工程/`、未 commit、未改索引文档。

## 8. 对“212 张图里有多少能做供给卡口 / v2 是否让大多数图可做门”的判断

- **不是大多数**：12/212（5.7%）图可以，14/212（6.6%）图一般，186/212（87.7%）图不行。
- 其中真正有 ≥2 条分开需求带的只有 9/212（4.2%）；把“同一条带跨两个窗口”也算上的 12 张是任务书定义的宽松口径。
- 所以 v2 并没有“让大多数图可做门”；它比 v1 更严、更能区分“需求在哪”，但仍然是少数图有 ≥2 个可用需求峰。
- 主要变化：真实图 91 从 v1 的“图不行”变成“图可以”（色 27 两条带）；23 从 v1 的“11 层”降为“图一般（一个门）”；13/134/153 被降级，3/5/34/100/106/165/170/192/212 新入选。建议后续选图用 `图可以 && distinctGateBands≥2`（9 张）作为第一轮候选，再人工看峰的位置和颜色。
