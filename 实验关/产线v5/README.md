## 0. 一页纸总结

**这个游戏的本质**：玩家在一个 5 格暂存区的约束下，决定“先拿哪种颜色的车、什么时候拿”。每辆车进暂存后去目标图上吃同色、且已暴露的像素；吃不满的车留在暂存里，就是“债”。5 格被吃不满的车占满，就死。

**过去冲突的根源**：
- 压力 = 暂存里有吃不满的车；
- 容错（旧定义）= 总有一辆能吃满的“免费车”可以点；
- 玩家只要有免费车就不会欠债 → **安全就平，有压力就脆**；
- 锁链要占空格、而且整组吃完才离场 → **压力越大，锁链越拿不了** → 锁链关容错低。

**v5 的做法**：
1. **用线上数据校准尺子**：只有和线上失败率相关（|ρ|≥0.6）的指标才进验收。目前已证实：**随机玩家通关率**（ρ=−0.86，12 关）、**选择熵**（9 关 ρ=−0.83）。
2. **卡点用“不变量”造，不用“预期路线”造**：卡点 = 进度到 X% 时，下一层需要颜色 Y，而 Y 的供给大部分在“门”（锁链 / 管道 / 冰）后面。所有玩家都必经，不会因为换顺序而消失。
3. **用一群模拟玩家检查，不用一条路线**：卡点覆盖率、通过率、死亡归因距离、死亡进度。
4. **不达标按“症状 → 原因 → 旋钮”修**：摆放 → 同色容量 → 障碍参数 → 增删障碍 → 规则，一次只动一类。
5. **成批上线，用失败率 / 失败流失 / 重玩次数校准**，每批都缩小预测误差。

**策划的五个目标在 v5 里的位置**：合理（合法性 + 无暗死）、有卡点（卡点规划）、卡点有道理（钥匙可见 + 代价可回收）、失败能归因（归因距离短 + 死在卡点上）、可惜想再来（死在后段 + 卡点有多种过法 + 线上失败流失低）。

## 1. 游戏理解：规则（精确到代码）

> 出处：`02_工程/游戏主bin/bin/js/simulator.js`（corner 规则；分组2/3 均为 corner，分组1 不是）。

### 1.1 两块板

| 板 | 是什么 | 数据 |
|---|---|---|
| **目标图** | 像素画，每格一个颜色号，0=空 | `blocks[toprow][宽]`，常见 40×40=1600 像素 |
| **车盘** | `maprow × mapcol`（常见 7×7），每格一辆车或障碍 | `spools`，每格 `{id, type, param, count}` |

- 车：`id`=颜色，`count`=容量（能吃多少像素）。
- **容量守恒**：每种颜色所有车的容量和 = 该颜色像素数（含管道队列里的车）。这是硬约束（AGENTS 红线 1）。

### 1.2 能点哪辆车（车盘侧）

- 可达区域：从车盘**第 0 行**开始，经已经空出来的格子 4 邻接扩散（`computeReach`）。
- 车“暴露” = 在第 0 行，或与可达空格相邻（`isExposedAt`）。暴露过一次就一直算激活（单调）。
- 可点 = 已激活 + 不被数字冰锁 + 不被锁链锁（`isPickable`）。
- 锁链：组内**所有成员都已激活、且都没被冰锁**，整组才可点；点任意一个，整组一起离场（`isChainLocked` / `applyPick`）。
- 管道出口一旦被拿过车，就成为新的可达源（`markPipeOpenedIfExit`）。

### 1.3 车进暂存后发生什么（目标图侧）

- 暂存上限 **5**（`bufferLimit`）。
- 车进暂存后，去目标图上吃**同色、且与外界连通**的像素（外界 = 图边或已消除的、与图边连通的空格）。
- 吃的顺序（corner）：同色可达像素里，按 `D = 行(从底数) + 列` 从小到大，即**从左下角往外**。
- 吃满 `count` 就离场；吃不满就留在暂存里，之后其他颜色被吃掉、露出新像素时，它会**自动继续吃**（`autoReleaseBuffer`）。
- 同色多辆车同时在暂存：**剩余容量少的先吃**（`contendOrder`）。
- **锁链组整组都吃满才一起离场**（`releaseCompletedBuffer`）：一辆已经吃满的锁链成员，会一直占着格子等同伴。

### 1.4 死亡

- 暂存满 5，且暂存里**没有一辆还能吃**（无可达同色像素）→ 死（`isDeadEnd`）。
- 盘上没有任何可点的车，且未通关 → 死。
- 锁链组进场时暂存 + 组员数 > 5 → 这一步不可点（视为阻塞）。

### 1.5 障碍

| 障碍 | type | 规则 |
|---|---|---|
| 锁链 | 5，param=组号 | 同组正交相邻；整组同取；整组吃满才离场 |
| 问号 | 6 | 颜色对玩家隐藏；相邻格被拿走或本格激活后揭示（`isRevealed`） |
| 数字冰 | 7，param=剩余数 | **按全局拿走的车数倒计时**（锁链一次拿 N 辆就扣 N）；归零后变普通车（仍需暴露） |
| 管道 | 11–14（方向） | 永久占格、阻挡通行；出口格空了就吐出队列下一辆；拿过一次出口，出口就是可达源 |
| 黑块 | id=−1 | 永久占格、阻挡通行 |

### 1.6 交付格式

见 `工程说明 §19.9`：`type` 是数组时 `param` 必须同序同长；纯问号写 `type:6, param:0`；不写 `q`。（v5-1 发现安全版原件有 `[0,6]`+`q` 违规。）

## 2. 游戏理解：玩家实际在做什么

### 2.1 每一步的决策

玩家每一步看到：盘上能点的几辆车（颜色、数字）、目标图当前露出的像素、暂存里压着的车。他要决定：**点哪辆**。

每个选项的后果可以分成三类：

| 类型 | 定义 | 玩家感受 |
|---|---|---|
| **免费** | 点了之后暂存里吃不满的车不增加 | 安全、爽 |
| **代价** | 会多压一辆吃不满的车，但之后还有路 | 紧张、在“投资” |
| **致命** | 点了之后不可能通关；分“当步就死”（看得见）和“当步没死、其实已无解”（看不见，**延迟致死**） | 前者是正常的失败；后者是“死得莫名其妙” |

### 2.2 真人不是贪心，也不是最优

- 用户真人路径（ZC_18_safe，`点击路径_2026-11-11T07-11-34.json`）：经常点第 3–11 个“最诱人”的车，长期背着 2–3 辆吃不满的车，buffer≥3 共 17/49 步（日志 §1095）。
- 现役求解器 `runMinBuffer`（depth3）偏弱：同一 corner 规则下，宽度 4–16 的束搜索能解的关，它判“不通”（日志 §1094）。
- “每步吃最多”的贪心玩家（P3=0）和“free-first”玩家都不像真人。
- **“在看得见的死之外随机点”的随机玩家**，其通关率和线上失败率高度相关（§6）。
  → 解读：普通玩家**能看见当步就死的选项并避开**，但**看不见几步之后的后果**。这正是“延迟致死”伤害最大的原因。

### 2.3 玩家理解关卡靠什么

- 目标图上**看得见的颜色**：哪种颜色露出来了、哪种被挡住。
- 盘上**看得见的车**：颜色和数字。
- 吃的顺序（corner：从左下往外）**难以预判**：玩家不容易知道这辆车会吃到哪几格、能不能吃满。这是失败难以归因的来源之一（也是三面墙 / 底边入口想解决的问题，见 §14）。

## 3. 游戏理解：压力、容错、卡点从哪来

### 3.1 压力

- **压力 = 暂存里吃不满的车的数量**（以及剩余格子数）。5 格里压 3–4 辆，就是紧张。
- 压力的来源：可点的车里，“现在吃不满”的占多数；或者玩家为了别的目的（拿钥匙、清路）主动接受了债。
- 压力不是越多越好：长时间 buffer≥3 是“磨”（分组2 L7：中段压力 87%，长磨型高流失）。

### 3.2 容错

- **v5 的定义**：一个“看得见当步死、看不见以后”的普通玩家，有多大概率能通关 → **随机玩家通关率**。
- 次级定义：**没有延迟致死**，尤其是“最诱人的选项是延迟致死”（诱饵陷阱）。

### 3.3 为什么过去压力和容错打架

- 旧的容错 = “总有免费车可点”。有免费车，玩家就不欠债，压力消失（ZC_18_safe：每步都有强免费选项，安全但平）。
- 去掉免费车，剩下的都是债选项，其中只要有一个是陷阱就死（ZC_181：弱免费 + 不可恢复 → 死局）。
- A 方案六种杠杆全部 mid 0–6（日志 §1093）：容量 / 位置只改变“如果拿它会怎样”，不改变“玩家会不会拿它”。

### 3.4 为什么锁链关容错低（机制）

1. 锁链进场要 N 个空格；压力越大空格越少 → **压力和锁链在抢同一样东西：格子**。
2. 锁链**整组吃满才离场** → 已吃满的成员继续占格子，等吃不满的那个。
3. 锁链只在“组员全部暴露、没被冰锁、暂存 ≤5−N”时可点 → **可拿窗口窄**。
4. 如果当下需要的颜色恰好在锁链里，压力又高，就会出现“想拿拿不了、不拿解不开” → 死锁（ZC_18：4 组锁链共 11 车，第 36 步死）。
5. 普通玩家不会“提前清空格子准备拿锁链”，随机玩家更不会 → 窄窗口 = 低容错。

**结论**：锁链不能少放了事（锁链是唯一能“强制”玩家的机制），而要**按节奏放**：在压力释放、格子空出来时拿锁链；锁链里放“钥匙”，用它触发下一次释放。

### 3.5 卡点

- **卡点** = 一段进度窗口里，玩家必须完成某个特定动作（拿到钥匙 / 打开管道 / 等冰化）才能继续，而这段时间暂存压力高。
- **卡点有道理** = 钥匙看得见（已暴露或下一步暴露），为什么需要它从目标图上看得懂（被挡住的颜色就在那），付的代价之后能收回来。
- **卡点会消失** = 卡点建立在“随顺序变化”的东西上，玩家换顺序就绕开了（§5）。

### 3.6 失败、归因与“可惜”

- **能归因的失败**：错误决定和死亡之间只隔 1–3 步，而且错误发生在卡点上。
- **不能归因的失败**：延迟致死；死在非卡点的地方；因为吃像素顺序预判不了而死。
- **可惜想再来**：死在后段（进度 60–90%）、差一点；卡点有不止一种过法，下次换个打法就能过。线上对应**失败流失**（CSV 列，按字面是“失败后离开的比例”，口径待确认）低、**重玩次数**适中。

## 4. 游戏理解：每种机制的作用与风险

| 机制 | 主要作用 | 能制造什么 | 主要风险 | v5 用法 |
|---|---|---|---|---|
| **车的位置** | 决定什么时候能拿到什么颜色 | 日常压力、节奏 | 随顺序变化，单独造不出必经卡点 | 卡点之间调节奏（`PressureBuild_v5`） |
| **车的容量** | 决定吃不吃得满 | 债的大小 | 大车（>60）制造长期债；碎车（≤5）排版否决 | 卡口颜色把容量集中到门后；普通颜色接近均匀（离散度≈0.25） |
| **锁链** | 强制一起拿 | 钥匙 + 代价的卡点 | 抢格子、整组离场、窗口窄 → 死锁 | 钥匙锁链；优先两连；放在释放点之后 |
| **管道** | 永久占格 + 延迟供给 | 时间闸门 | 留空格；开局放置会死锁 | 供给按图层顺序排；出口时机就是卡点 |
| **数字冰** | 全局倒计时锁 | “再撑几步”的倒计时 | 冰在单车颜色上 = 不可通关；冰会被绕开 | 锁住门外的替代供给；倒计时与卡点进度对齐 |
| **问号** | 隐藏颜色 | 信息不确定 | 不能替代卡点；增加不可归因 | 少用；不放在钥匙上 |
| **黑块** | 塑形 | 窄通道 | 黑墙；补位黑块 | ≤5%，不成墙 |
| **棋盘尺寸** | 可点宽度 | 选择数量 | 方形边框天然全暴露 | 维持 7×7 为主 |

## 5. 游戏理解：什么随玩家变、什么不变

| 不随顺序变化（不变量） | 随顺序变化（可变量） |
|---|---|
| 目标图层次：X 被 Y 挡住，谁都得先吃 Y | 第几步拿哪辆车 |
| 每种颜色的总供给 | 某一步的暂存状态 |
| 数字冰按“拿走车数”倒计时 | 哪些车已暴露 |
| 锁链需要 N 个空格、整组离场 | 某辆车进暂存时能吃多少 |
| 管道出车顺序 | 同色车谁先吃 |

**v5 的核心设计原则**：**卡点只用不变量造**。最可靠的形式是“**供给卡口**”：

> 进度到 X% 时，图上下一层需要颜色 Y；Y 的供给（容量）大部分在门后（锁链 / 管道队列 / 冰下）；门外的 Y 不够把这一层吃完。

不管玩家前面怎么走，到这一层都必须过门。检查时用**进度 %** 定位卡点（不用步数），用**一群玩家**统计覆盖率（不用一条路线）。

### 6.3 未证实（必须先验证）

- 随机玩家通关率在**带锁链 / 管道**的关上是否同样准（分组2 锁链不多）。
- “会玩的人的压力”是否等于用户感到的压力（只有 1 条真人路径）。

## 7. v5 的十条原则

1. **线上数据是唯一裁判**：任何指标进验收口径前，必须和线上失败率 / 失败流失 / 重玩次数之一相关 |ρ|≥0.6；否则只当诊断。
2. **卡点用不变量造**：供给卡口；不依赖“预期路线”。
3. **用群体检查，不用一条路线**：至少 100 局随机玩家 + 会玩的玩家 + 贪心玩家。
4. **用进度 % 定位，不用步数**。
5. **容错优先于压力**：先保证随机玩家通关率达标，再加压。
6. **锁链按节奏放**：在释放点之后拿，组里有钥匙，优先两连。
7. **一次只动一类旋钮**，改完全量复测，记录改前改后（AGENTS 红线 7）。
8. **成批上线**（约 10 关一组），每关上线前写下预测。
9. **负结果也记**（AGENTS §2）。
10. **规则层改动（三面墙、buffer 大小）放在最后**，用同一套尺子先在模拟里对比。

## 8. v5 指标体系

> 每个指标标：**模型**（用哪种模拟玩家）、**用途**、**验证状态**、**阈值**。阈值是起点，按 §13 校准。

### 8.1 模拟玩家群体（所有指标的基础）

| 玩家 | 规则 | 代表谁 |
|---|---|---|
| **随机玩家**（主） | 每步在“当步不会死”的选项里均匀随机 | 普通玩家：看得见当步死，看不见以后 |
| **会玩的玩家** | free-first：先选不加债的，再选吃得多的，再选债少的 | 认真玩的人 |
| **贪心玩家** | 每步选本步吃得最多的（避开当步死） | 冲动玩家；用来找“诱饵陷阱” |
| **（后续）像人的玩家** | 用用户点击路径拟合选择概率 | 用户自己；数据够了再做 |

### 8.2 合法性（硬门，不需要校准）

| 指标 | 阈值 |
|---|---|
| 可通关（用强搜索判，不再用 `runMinBuffer`） | 必须 ✓ |
| 容量守恒（含管道队列） | 必须相等 |
| 无空格（管道 / 黑块除外） | 0 |
| 开局可点 | ≥5 |
| 排版（`LayoutScore_v1`） | hard=0 |
| 锁链正交相邻 | 必须 |
| 交付格式（§19.9） | 0 违规 |

### 8.3 容错

| 指标 | 定义 | 状态 | 阈值 |
|---|---|---|---|
| **随机玩家通关率** | 100 局随机玩家（固定 3 个种子取平均）通关比例 | ✅ ρ=−0.86 | 前期关 ≥0.9；之后按难度设计（§13） |
| 延迟致死数 | 沿玩家路线，“当步没死、其实已无解”的选项数 | 诊断 | 0（目标） |
| 诱饵陷阱数 | 最诱人的选项就是延迟致死的步数 | 诊断 | 0 |

### 8.4 选择

| 指标 | 定义 | 状态 | 阈值 |
|---|---|---|---|
| **选择熵** | 每步选项后果签名的熵，取平均（`ChoiceSpaceCheck_v1` 口径） | ✅ 9 关 ρ=−0.83 | ≥1.45 |
| 没得选步数 | 合法选项 ≤1 或没有能吃的 | 诊断 | 连续 ≤2 |

### 8.5 压力（改成按进度窗口、按群体）

| 指标 | 定义 | 状态 | 阈值 |
|---|---|---|---|
| **压力曲线** | 进度每 10% 一个窗口，随机玩家（通关局）和会玩的玩家在该窗口 buffer≥3 的步数占比 | 待验证 | 卡点窗口高（≥0.5），卡点之间低（≤0.3） |
| 会玩的人压力 freeP3 | 会玩的玩家全程 buffer≥3 步数占比 | ⚠️ 只对上 1 次真人（0.35=“还行”） | 0.25–0.40（暂定） |
| 最长连续高压 | 连续 buffer≥3 的最长步数（随机玩家中位数） | 诊断 | ≤8（防长磨） |

### 8.6 卡点（新）

每个规划的卡点单独输出：

| 指标 | 定义 | 阈值（暂定） |
|---|---|---|
| **覆盖率** | 到达卡点进度窗口的玩家里，真的“被卡住”的比例（buffer≥3，或被迫付门的代价） | ≥0.7 |
| **通过率** | 被卡住的随机玩家里，过了这个卡点的比例 | ≥0.85 |
| **窗口宽度** | 门可拿的连续步数（中位数） | ≥3 步 |
| **过法数** | 过这个卡点的不同方式（比如先拿钥匙 / 先清格子 / 走贵的替代） | ≥2 |

### 8.7 失败与归因（新）

| 指标 | 定义 | 阈值（暂定） |
|---|---|---|
| **归因距离** | 随机玩家每次死亡：从“最后一个还有解的状态”到死亡隔了几步，取中位数 | ≤3 |
| **死在卡点比例** | 死亡的“最后还有解”状态落在卡点窗口里的比例 | ≥0.6 |
| **死亡进度** | 死亡时的目标图进度，中位数 | 60–90% |

> 归因距离需要“这个状态还有没有解”的判断 = 强搜索。目前 `FatalOptionCheck_v0` 每关 15–20 分钟，必须提速（§11 T6）。

### 8.8 预测

| 指标 | 定义 |
|---|---|
| **预测失败率** | 随机玩家通关率按换算线换算；每关上线前写进交付清单 |

### 8.9 指标准入规则

- 新指标先在已有线上数据（分组2 L2–L13，以后加分组3 和每一批）上算相关性。
- 和失败率 / 失败流失 / 重玩次数之一 |ρ|≥0.6，且不比已有指标差 → 进验收口径。
- 否则只当诊断，写进日志（负结果也记）。

## 9. v5 制作流程（S0–S11）

> 每一步写清：**做什么 / 为什么 / 输入 / 输出 / 完成标准 / 谁来做**。
> “人”= 策划（用户）；“便宜模型”= 按任务单执行的低成本模型；“高级模型”= 只用于设计评审和结果判断。

### S0 选图与图分析

- **做什么**：
  1. 用 `ImgFeature_v781` 体检：色数 11–17、中位块 ≥2px、最大色占比 ≤35%。
  2. 生成**颜色层次表**：用“全图逐层剥离”的方式（任何顺序都成立的部分），算出每种颜色**最早什么进度能开始吃**、**什么进度之前必须吃完才能露出别的颜色**。
  3. 生成**颜色需求曲线**：按进度 0–100%，每个窗口里“下一层需要哪些颜色、各需要多少像素”。
  4. 标出**卡口候选色**：在进度 30–85% 之间才被需要、需求量适中（够做一两辆门后车）、被挡关系在图上看得清的颜色。
- **为什么**：卡点必须建立在图的层次上（不变量）。没有这张表，就只能靠预期路线。
- **输入**：目标图 TXT / 关卡 JSON 的 `blocks`。
- **输出**：`图分析_<图名>.json`（层次、需求曲线、卡口候选色及理由）。
- **完成标准**：每张图至少 2 个卡口候选色；否则换图。
- **谁来做**：工具（T1，可复用 `ColorSpread_v788`、`TargetReachCurve`、`ImageDebtScan_v1` 的部分逻辑）；人看一眼候选色是否“看得懂”。

### S1 卡点规划

- **做什么**：为每关写 2–3 张**卡点卡片**：

```text
卡点 #1
  进度窗口：35%–45%
  卡口颜色：Y（这一层需要 Y 共约 120px）
  门：两连锁链 [钥匙 Y×40 + 代价 Z×30]，另有冰锁住门外 Y×30
  钥匙为什么看得见：Y 的像素在图左下大面积露出；门在盘第 1 行
  代价怎么回收：Z 在进度 50% 前大量露出（释放者：Z 盘上另有 2 辆）
  第二种过法：门外 Y 车（冰 8）等冰化后也能过，但要多撑几步
  卡点前喘息：进度 25%–35% 压力 ≤ 0.3
```

  - 前 10% 不设卡；卡点之间留喘息；最后一个卡点在 70–85%（“可惜”在后段）。
- **为什么**：把“卡点有道理”在建造之前写清楚，后面每一步都对着卡片做，检查也对着卡片查。
- **输入**：S0 的图分析。
- **输出**：`卡点规划_<图名>.json`（机器可读的卡片）。
- **完成标准**：每张卡片的 7 项都填了；人认可“有道理”。
- **谁来做**：**人主导**（这是策划的核心价值）；工具可以给出默认草案（T2）。

### S2 切车（容量）

- **做什么**：
  1. **卡口颜色**：按卡片把容量分成“门后”（锁链 / 管道 / 冰下）和“门外”。门外的量 **不足以**吃完卡点那一层（例如 ≤40%）。
  2. **钥匙车**：容量设成进场当步就能吃满（≤ 那时该色可达像素数）。
  3. **代价车**：容量设成在“回收进度”之前能吃满（≤ 回收时可达像素数）。
  4. **普通颜色**：车容量接近均匀（目标离散度 ≈0.25，最大车 ≤55），避免 >60 的大车和 ≤5 的碎车。
  5. 校验：逐色守恒。
- **为什么**：卡点必经靠“门外不够”；钥匙必须立刻见效，代价必须收得回来——这是“卡点有道理”的容量条件。均匀车容量来自人做关卡的统计（212 张 G8 离散度 0.25、最大 54；分组2 离散度 0.42、最大 82）。
- **输入**：图分析 + 卡点卡片。
- **输出**：车列表（颜色、容量、角色：钥匙 / 代价 / 门外 / 普通）。
- **完成标准**：逐色守恒；角色条件全部满足。
- **谁来做**：工具（T3 的切车部分，可复用 `SplitLevel_v722` 的守恒逻辑）。

### S3 摆放

- **做什么**：
  1. **外圈（先暴露）放早期颜色**，内圈放后期颜色（按 S0 的“最早可吃进度”排）。
  2. **门**放在“到卡点进度时，门已经暴露或下一步暴露”的位置。
  3. **锁链**放在“压力刚释放、格子空出来”的时间点附近能暴露的位置；组员正交相邻。
  4. 门外的卡口色替代供给放深一点（或交给 S4 加冰）。
  5. 开局第 0 行 ≥5 辆可点，且至少一半能当步吃到东西（corner 色在第 0 行，B 线 R1 规则）。
- **为什么**：位置决定“什么时候能拿到什么”；门的时机必须和图的需求对齐，否则卡点要么提前（死在前段）要么错过（卡点消失）。
- **输入**：车列表 + 卡点卡片 + 图分析。
- **输出**：初版 `spools`。
- **完成标准**：合法性全过（S5）。
- **谁来做**：工具（T3 的摆放部分）。

### S4 放障碍

- **做什么**：按卡点卡片放锁链、管道、冰；**不按配额加障碍**。
  - 锁链：优先两连；三连只放在后段或压力低的地方；组里必须有一辆进场当步吃满。
  - 管道：队列按图层需求排序（先吐出的车，颜色就是下一层要的）；不放开局主路口。
  - 冰：锁门外的替代供给；倒计时（按拿车总数）对齐卡点进度；不加在“单车辆颜色”上。
  - 问号：可选，不放在钥匙上。
- **为什么**：障碍是卡点的实现，不是装饰；按配额加的障碍会制造不可归因的死。
- **输出**：完整关卡 JSON。
- **完成标准**：合法性全过。
- **谁来做**：工具（T3）。

### S5 合法性检查

- **做什么**：§8.2 的全部硬门。可通关用强搜索判（T6）。
- **为什么**：不合法的关后面的指标都没意义。
- **完成标准**：全过；不过就回 S2–S4（多数是守恒或空格问题）。
- **谁来做**：工具（现有 `ArlCheck_v793` 的合法部分 + `LayoutScore_v1` + 格式检查 T9 + 强搜索 T6）。

### S6 群体模拟检测

- **做什么**：跑 §8 的全部指标：随机玩家通关率、选择熵、压力曲线、每个卡点的覆盖率 / 通过率 / 窗口宽度 / 过法数、归因距离、死在卡点比例、死亡进度、延迟致死、诱饵。
- **为什么**：用群体代替预期路线；每个指标对应策划的一个目标。
- **输出**：`检测报告_<关卡>.json` + 一页可读的 md（每个卡点一行）。
- **谁来做**：工具（T4 群体模拟、T5 卡点检查、T6 归因）。

### S7 诊断与修复

- **做什么**：按 §10 的对照表，从**最上面一个不达标项**开始，选优先级最高的旋钮修；**一次只动一类旋钮**；修完回 S5–S6 全量复测。
- **为什么**：过去“同时调很多东西”导致不知道哪个改动起作用（AGENTS 红线 7）。
- **输出**：每次修改一条记录：症状、改了什么、改前改后的数字。
- **完成标准**：全部达标，或同一症状连续 3 轮修不好 → 回到 S1 改卡点规划（问题在设计，不在参数）。
- **谁来做**：工具给候选修改（T7，复用 `KnobPlan_v1` 的框架）；便宜模型执行；人只看“回 S1”的情况。

### S8 节奏微调

- **做什么**：卡点之间用换位（`PressureBuild_v5`，锁链 / 管道 / 门不动）把喘息段和小压力段调到目标；约束：不能降低卡点指标和随机玩家通关率。
- **为什么**：卡点之间完全没压力会平，一直有压力会磨。
- **谁来做**：工具。

### S9 人工试玩

- **做什么**：用户在编辑器里玩，**导出点击路径**；记录：卡点在哪感到、死在哪、死的时候知不知道为什么、想不想再来。
- **为什么**：模拟只能代表“普通玩家”；“卡点有道理”“想再来”最终要人判断。点击路径也是校准“像人的玩家”的数据。
- **输出**：试玩记录 + 点击路径 JSON。
- **完成标准**：人认可；否则写下哪一个卡点不对，回 S1 或 S7。
- **谁来做**：人。

### S10 交付

- **做什么**：格式规范化（§19.9）；交付清单：每关的预测失败率、随机玩家通关率、卡点表、版本号；成批（约 10 关）。
- **为什么**：预测写在上线前，才能事后对账。
- **谁来做**：工具（T9）+ 人确认组号。

## 10. 诊断 → 修复对照表

**旋钮优先级**（越靠前越安全）：
1. **摆放**（换位；不改总量，守恒自动成立）
2. **同色容量重分配**（同一颜色的车之间挪容量；守恒自动成立）
3. **障碍参数**（冰值、锁链组员、管道队列顺序）
4. **增删障碍**
5. **卡点规划**（回 S1）
6. **规则 / 棋盘**（最后）

| 症状（指标） | 常见原因 | 修法（按优先级） |
|---|---|---|
| **卡点覆盖率低**（玩家绕开了） | 门外还有足够的卡口色供给 | ① 把门外卡口色的车往深处挪；② 把门外车的容量转给门后的同色车；③ 给门外车加冰（倒计时到卡点之后）；④ 把门外供给改成“贵的替代”（放进三连锁） |
| **卡点通过率低 / 随机玩家通关率低**（门太窄） | 锁链窗口短；格子不够；代价车太大 | ① 锁链挪到释放点之后（换位）；② 降低代价车容量（同色重分配）；③ 三连改两连；④ 确保钥匙当步吃满；⑤ 门附近放一辆“恢复车”（能一次吃满、腾出格子） |
| **窗口宽度 <3** | 锁链组员暴露时间不一致；冰化太晚 | ① 让组员在相近时间暴露（换位）；② 冰值减小；③ 减少组员 |
| **延迟致死 >0 / 归因距离长** | 某笔债要很久以后才能还；锁链里有很晚才释放的颜色 | ① 债车容量减小，让附近露出的像素就能吃满；② 把释放它的颜色往外圈挪；③ 锁链里不放“晚释放”的颜色 |
| **诱饵陷阱 >0** | 最诱人的选项（吃最多）后面是死路 | ① 把这辆车的容量减小或挪深；② 让它吃不到那么多（换到同色更晚的车） |
| **死在前段**（死亡进度 <50%） | 开局太紧，门来得太早 | ① 开局多放能吃满的车；② 第一个门往后挪；③ 前 10% 不放锁链和冰 |
| **死不在卡点上**（死在卡点比例低） | 卡点之外还有暗坑 | 用 `FatalOptionCheck` 找出死点，按“延迟致死”行修 |
| **卡点之间没压力**（太平） | 免费选项太多 | ① 换位：后期颜色往外圈；② 同色容量稍调大，制造小额债 |
| **压力太长**（长磨） | 连续高压步数多 | ① 中间插一辆“大释放”车；② 一个卡点拆成两个 |
| **选择熵低**（没得选 / 假选择） | 可点的车太少，或后果都一样 | ① 去掉边缘的冰；② 拆大车；③ 边缘颜色多样化 |
| **过法数 <2** | 钥匙只有一把 | 加“贵的替代路线”：另一处也有卡口色，但在更贵的锁链里或冰更久 |
| **开局可点 <5** | 第 0 行有锁链 / 冰 / 不可吃的车 | ① 换位；② 第 0 行去冰 |
| **守恒失败 / 有空格** | 构建 bug | 回 S2–S4；不允许用缩放容量“修”（红线 1） |

**修不好的判断**：同一症状连续 3 轮修不好，说明是卡点规划本身不成立（比如卡口色需求量太大、图层次不支持），回 S1，而不是继续调参数。

## 13. 上线与校准闭环

1. **上线前**：每关写下随机玩家通关率、预测失败率区间、卡点表；交付清单入库。
2. **上线后**（数据稳定后，进入人数 ≥30 的关）：把失败率、关流失、失败流失、重玩次数、关总耗时加进校准表（T10）。
3. **对账**：预测 vs 实际；偏差大的关单独看：是哪个卡点出问题（试玩记录 + 模拟死因）。
4. **更新**：换算线（随机玩家通关率 → 失败率）；指标阈值；必要时修改“随机玩家”的定义（例如加入“像人的玩家”）。
5. **第一次外部检验**：分组3 L2–L5 数据出来后，先检验随机玩家通关率能否预测它们。
6. **难度曲线**（用户说先不考虑）：等有 2–3 批数据后，再讨论不同关卡位置的目标失败率。

**为什么这样能“精准”**：精准不是一次做对，而是每批都缩小“预测 vs 实际”的误差。每批约 10 关，就是 10 个新的校准点。

## 14. 规则层实验：三面墙 / 底边入口

- **目的**：降低吃像素顺序的不确定性（失败更可归因）、加强目标感（从底部往上吃）、入口变窄（天然压力）。
- **风险**：入口变窄 → 选择和容错下降；v4 停止的原因见 `实验关/产线v4/失败报告_20261111.md`，复活前必须先读。
- **做法**：不改客户端；在模拟器里对同一批图，分别用“四边 + corner”和“三面墙 + 底边”走完 S0–S6，比较：随机玩家通关率、选择熵、卡点覆盖率、**归因距离**。
- **放行门**：三面墙在归因距离上明显更好（中位数小 ≥1 步），且随机玩家通关率不低于四边版 0.05 以上 → 才提给程序改客户端。
- **时机**：M4 之后（需要卡点工具）。

## 15. 风险、未知与不做清单

### 15.1 风险

| 风险 | 后果 | 对策 |
|---|---|---|
| 随机玩家在锁链关上不准 | 容错预测失效 | M6 优先检验；必要时加入“会为锁链清格子”的玩家 |
| 校准样本太少（12 关） | 换算线不稳 | 每批上线就补；进入人数 <30 的关只参考 |
| 卡口设计让关卡同质化 | 关卡像一个模子 | 卡点四种类型轮换；不复用骨架（日志结论：骨架复用会让黑块 / 门永远在老地方） |
| 强搜索太慢 | 归因指标进不了批量 | T6 是第一优先 |
| 用户试玩代表性不足（专家玩家） | 手感偏“太简单” | 试玩用来判“有道理”，难度交给随机玩家 + 线上 |

### 15.2 未知（需要用户或数据回答）

- 用户心中“有道理的卡点”的具体正例（有一个正例，卡片模板就能从它反推）。
- 客户端里还能改什么（buffer 大小、复活、道具）。
- 程序能否加最小埋点（每次失败死在第几步）。

### 15.3 不做

- 不复活 v1 的 15 项作为质量判官（只保留合法性部分）。
- 不按配额加障碍。
- 不用单条预期路线检查卡点。
- 不在没有线上验证时把新指标写成硬门。
- 不改客户端 bin（红线 6）；三面墙先在模拟里比较。
- 不再继续 v1.5 / v4 的产物。
