## 0. 一页纸总结

**这个游戏的本质**：玩家在一个 5 格暂存区的约束下，决定“先拿哪种颜色的车、什么时候拿”。每辆车进暂存后去目标图上吃同色、且已暴露的像素；吃不满的车留在暂存里，就是“债”。5 格被吃不满的车占满，就死。

**过去冲突的根源**：
- 压力 = 暂存里有吃不满的车；
- 容错（旧定义）= 总有一辆能吃满的“免费车”可以点；
- 玩家只要有免费车就不会欠债 → **安全就平，有压力就脆**；
- 锁链要占空格、而且整组吃完才离场 → **压力越大，锁链越拿不了** → 锁链关容错低。

**v5 的做法**：
1. **用线上数据校准尺子**：只有和线上失败率相关（|ρ|≥0.6）的指标才进验收。目前已证实：**随机玩家通关率**（ρ=−0.86，12 关）、**选择熵**（9 关 ρ=−0.83）。
2. **卡点用“不变量”造，不用“预期路线”造**：卡点 = 进度到 X% 时，下一层需要颜色 Y，而 Y 的供给大部分在“门”（锁链 / 管道 / 冰）后面。所有玩家都必经，不会因为换顺序而消失。
3. **用一群模拟玩家检查，不用一条路线**：卡点覆盖率、通过率、死亡归因距离、死亡进度。
4. **不达标按“症状 → 原因 → 旋钮”修**：摆放 → 同色容量 → 障碍参数 → 增删障碍 → 规则，一次只动一类。
5. **成批上线，用失败率 / 失败流失 / 重玩次数校准**，每批都缩小预测误差。

> **跨版本的结论总表见 §23**（难度、有效做法、已证伪清单、还没解决的）。

**策划的五个目标在 v5 里的位置**：合理（合法性 + 无暗死）、有卡点（卡点规划）、卡点有道理（钥匙可见 + 代价可回收）、失败能归因（归因距离短 + 死在卡点上）、可惜想再来（死在后段 + 卡点有多种过法 + 线上失败流失低）。

### 0.1 核心思想：游戏的三层“可计算性”

规则确定的游戏可以被数学控制，但要分清每一层能算到什么程度：

| 层 | 能算到什么 | 难点 | v5 怎么做 |
|---|---|---|---|
| **关卡层**（规则本身） | **完全精确**：任一局面有没有解、哪个选项是延迟致死、卡点是否必经 | 计算量（顺序组合爆炸），靠剪枝 / 缓存 / 等价局面合并 | 强可通关判定（T6）；卡点用不变量造（§5） |
| **玩家层**（人怎么走） | **分布精确、个体不精确**：一群玩家里多少比例被卡、死、通关 | 需要线上数据校准 | 模拟玩家群体（§8.1）；随机玩家通关率 ρ=−0.86；每批上线校准（§13） |
| **价值层**（合不合理、有没有道理） | 规则里没有，要策划定义；**一旦定义清楚，就变回前两层可算的条件** | 把“有道理”说清楚 | 卡点卡片（S1）把策划判断翻译成可计算条件 |

过去“控制不住”的三个原因：**算错了东西**（15 项没对照真实玩家）、**算得不准**（求解器弱）、**算的对象不对**（单条路线而不是玩家群体）。v5 的每一部分都是在修这三点之一。

## 1. 游戏理解：规则（精确到代码）

> 出处：`02_工程/游戏主bin/bin/js/simulator.js`（corner 规则；分组2/3 均为 corner，分组1 不是）。

### 1.1 两块板

| 板 | 是什么 | 数据 |
|---|---|---|
| **目标图** | 像素画，每格一个颜色号，0=空 | `blocks[toprow][宽]`，常见 40×40=1600 像素 |
| **车盘** | `maprow × mapcol`（常见 7×7），每格一辆车或障碍 | `spools`，每格 `{id, type, param, count}` |

- 车：`id`=颜色，`count`=容量（能吃多少像素）。
- **容量守恒**：每种颜色所有车的容量和 = 该颜色像素数（含管道队列里的车）。这是硬约束（AGENTS 红线 1）。

### 1.2 能点哪辆车（车盘侧）

- 可达区域：从车盘**第 0 行**开始，经已经空出来的格子 4 邻接扩散（`computeReach`）。
- 车“暴露” = 在第 0 行，或与可达空格相邻（`isExposedAt`）。暴露过一次就一直算激活（单调）。
- 可点 = 已激活 + 不被数字冰锁 + 不被锁链锁（`isPickable`）。
- 锁链：组内**所有成员都已激活、且都没被冰锁**，整组才可点；点任意一个，整组一起离场（`isChainLocked` / `applyPick`）。
- 管道出口一旦被拿过车，就成为新的可达源（`markPipeOpenedIfExit`）。

### 1.3 车进暂存后发生什么（目标图侧）

- 暂存上限 **5**（`bufferLimit`）。
- 车进暂存后，去目标图上吃**同色、且与外界连通**的像素（外界 = 图边或已消除的、与图边连通的空格）。
- 吃的顺序（corner）：同色可达像素里，按 `D = 行(从底数) + 列` 从小到大，即**从左下角往外**。
- 吃满 `count` 就离场；吃不满就留在暂存里，之后其他颜色被吃掉、露出新像素时，它会**自动继续吃**（`autoReleaseBuffer`）。
- 同色多辆车同时在暂存：**剩余容量少的先吃**（`contendOrder`）。
- **锁链组整组都吃满才一起离场**（`releaseCompletedBuffer`）：一辆已经吃满的锁链成员，会一直占着格子等同伴。

### 1.4 死亡

- 暂存满 5，且暂存里**没有一辆还能吃**（无可达同色像素）→ 死（`isDeadEnd`）。
- 盘上没有任何可点的车，且未通关 → 死。
- 锁链组进场时暂存 + 组员数 > 5 → 这一步不可点（视为阻塞）。

### 1.5 障碍

| 障碍 | type | 规则 |
|---|---|---|
| 锁链 | 5，param=组号 | 同组正交相邻；整组同取；整组吃满才离场 |
| 问号 | 6 | 颜色对玩家隐藏；相邻格被拿走或本格激活后揭示（`isRevealed`） |
| 数字冰 | 7，param=剩余数 | **按全局拿走的车数倒计时**（锁链一次拿 N 辆就扣 N）；归零后变普通车（仍需暴露） |
| 管道 | 11–14（方向） | 永久占格、阻挡通行；出口格空了就吐出队列下一辆；拿过一次出口，出口就是可达源 |
| 黑块 | id=−1 | 永久占格、阻挡通行 |

### 1.6 交付格式

见 `工程说明 §19.9`：`type` 是数组时 `param` 必须同序同长；纯问号写 `type:6, param:0`；不写 `q`。（v5-1 发现安全版原件有 `[0,6]`+`q` 违规。）

## 2. 游戏理解：玩家实际在做什么

### 2.1 每一步的决策

玩家每一步看到：盘上能点的几辆车（颜色、数字）、目标图当前露出的像素、暂存里压着的车。他要决定：**点哪辆**。

每个选项的后果可以分成三类：

| 类型 | 定义 | 玩家感受 |
|---|---|---|
| **免费** | 点了之后暂存里吃不满的车不增加 | 安全、爽 |
| **代价** | 会多压一辆吃不满的车，但之后还有路 | 紧张、在“投资” |
| **致命** | 点了之后不可能通关；分“当步就死”（看得见）和“当步没死、其实已无解”（看不见，**延迟致死**） | 前者是正常的失败；后者是“死得莫名其妙” |

### 2.2 真人不是贪心，也不是最优

- 用户真人路径（ZC_18_safe，`点击路径_2026-11-11T07-11-34.json`）：经常点第 3–11 个“最诱人”的车，长期背着 2–3 辆吃不满的车，buffer≥3 共 17/49 步（日志 §1095）。
- 现役求解器 `runMinBuffer`（depth3）偏弱：同一 corner 规则下，宽度 4–16 的束搜索能解的关，它判“不通”（日志 §1094）。
- “每步吃最多”的贪心玩家（P3=0）和“free-first”玩家都不像真人。
- **“在看得见的死之外随机点”的随机玩家**，其通关率和线上失败率高度相关（§6）。
  → 解读：普通玩家**能看见当步就死的选项并避开**，但**看不见几步之后的后果**。这正是“延迟致死”伤害最大的原因。

### 2.3 玩家理解关卡靠什么

- 目标图上**看得见的颜色**：哪种颜色露出来了、哪种被挡住。
- 盘上**看得见的车**：颜色和数字。
- 吃的顺序（corner：从左下往外）**难以预判**：玩家不容易知道这辆车会吃到哪几格、能不能吃满。这是失败难以归因的来源之一（也是三面墙 / 底边入口想解决的问题，见 §14）。

## 3. 游戏理解：压力、容错、卡点从哪来

### 3.1 压力

- **压力 = 暂存里吃不满的车的数量**（以及剩余格子数）。5 格里压 3–4 辆，就是紧张。
- 压力的来源：可点的车里，“现在吃不满”的占多数；或者玩家为了别的目的（拿钥匙、清路）主动接受了债。
- 压力不是越多越好：长时间 buffer≥3 是“磨”（分组2 L7：中段压力 87%，长磨型高流失）。

### 3.2 容错

- **v5 的定义**：一个“看得见当步死、看不见以后”的普通玩家，有多大概率能通关 → **随机玩家通关率**。
- 次级定义：**没有延迟致死**，尤其是“最诱人的选项是延迟致死”（诱饵陷阱）。

### 3.3 为什么过去压力和容错打架

- 旧的容错 = “总有免费车可点”。有免费车，玩家就不欠债，压力消失（ZC_18_safe：每步都有强免费选项，安全但平）。
- 去掉免费车，剩下的都是债选项，其中只要有一个是陷阱就死（ZC_181：弱免费 + 不可恢复 → 死局）。
- A 方案六种杠杆全部 mid 0–6（日志 §1093）：容量 / 位置只改变“如果拿它会怎样”，不改变“玩家会不会拿它”。

### 3.4 为什么锁链关容错低（机制）

1. 锁链进场要 N 个空格；压力越大空格越少 → **压力和锁链在抢同一样东西：格子**。
2. 锁链**整组吃满才离场** → 已吃满的成员继续占格子，等吃不满的那个。
3. 锁链只在“组员全部暴露、没被冰锁、暂存 ≤5−N”时可点 → **可拿窗口窄**。
4. 如果当下需要的颜色恰好在锁链里，压力又高，就会出现“想拿拿不了、不拿解不开” → 死锁（ZC_18：4 组锁链共 11 车，第 36 步死）。
5. 普通玩家不会“提前清空格子准备拿锁链”，随机玩家更不会 → 窄窗口 = 低容错。

**结论**：锁链不能少放了事（锁链是唯一能“强制”玩家的机制），而要**按节奏放**：在压力释放、格子空出来时拿锁链；锁链里放“钥匙”，用它触发下一次释放。

### 3.5 卡点

- **卡点** = 一段进度窗口里，玩家必须完成某个特定动作（拿到钥匙 / 打开管道 / 等冰化）才能继续，而这段时间暂存压力高。
- **卡点有道理** = 钥匙看得见（已暴露或下一步暴露），为什么需要它从目标图上看得懂（被挡住的颜色就在那），付的代价之后能收回来。
- **卡点会消失** = 卡点建立在“随顺序变化”的东西上，玩家换顺序就绕开了（§5）。

### 3.6 失败、归因与“可惜”

- **能归因的失败**：错误决定和死亡之间只隔 1–3 步，而且错误发生在卡点上。
- **不能归因的失败**：延迟致死；死在非卡点的地方；因为吃像素顺序预判不了而死。
- **可惜想再来**：死在后段（进度 60–90%）、差一点；卡点有不止一种过法，下次换个打法就能过。线上对应**失败流失**（CSV 列，按字面是“失败后离开的比例”，口径待确认）低、**重玩次数**适中。

## 4. 游戏理解：每种机制的作用与风险

| 机制 | 主要作用 | 能制造什么 | 主要风险 | v5 用法 |
|---|---|---|---|---|
| **车的位置** | 决定什么时候能拿到什么颜色 | 日常压力、节奏 | 随顺序变化，单独造不出必经卡点 | 卡点之间调节奏（`PressureBuild_v5`） |
| **车的容量** | 决定吃不吃得满 | 债的大小 | 大车（>60）制造长期债；碎车（≤5）排版否决 | 卡口颜色把容量集中到门后；普通颜色接近均匀（离散度≈0.25） |
| **锁链** | 强制一起拿 | 钥匙 + 代价的卡点 | 抢格子、整组离场、窗口窄 → 死锁 | 钥匙锁链；优先两连；放在释放点之后 |
| **管道** | 永久占格 + 延迟供给 | 时间闸门 | 留空格；开局放置会死锁 | 供给按图层顺序排；出口时机就是卡点 |
| **数字冰** | 全局倒计时锁 | “再撑几步”的倒计时 | 冰在单车颜色上 = 不可通关；冰会被绕开 | 锁住门外的替代供给；倒计时与卡点进度对齐 |
| **问号** | 隐藏颜色 | 信息不确定 | 不能替代卡点；增加不可归因 | 少用；不放在钥匙上 |
| **黑块** | 塑形 | 窄通道 | 黑墙；补位黑块 | ≤5%，不成墙 |
| **棋盘尺寸** | 可点宽度 | 选择数量 | 方形边框天然全暴露 | 维持 7×7 为主 |

## 5. 游戏理解：什么随玩家变、什么不变

| 不随顺序变化（不变量） | 随顺序变化（可变量） |
|---|---|
| 目标图层次：X 被 Y 挡住，谁都得先吃 Y | 第几步拿哪辆车 |
| 每种颜色的总供给 | 某一步的暂存状态 |
| 数字冰按“拿走车数”倒计时 | 哪些车已暴露 |
| 锁链需要 N 个空格、整组离场 | 某辆车进暂存时能吃多少 |
| 管道出车顺序 | 同色车谁先吃 |

**v5 的核心设计原则**：**卡点只用不变量造**。最可靠的形式是“**供给卡口**”：

> 进度到 X% 时，图上下一层需要颜色 Y；Y 的供给（容量）大部分在门后（锁链 / 管道队列 / 冰下）；门外的 Y 不够把这一层吃完。

不管玩家前面怎么走，到这一层都必须过门。检查时用**进度 %** 定位卡点（不用步数），用**一群玩家**统计覆盖率（不用一条路线）。

## 6. 我们手里的证据

## 7. v5 的十条原则

1. **线上数据是唯一裁判**：任何指标进验收口径前，必须和线上失败率 / 失败流失 / 重玩次数之一相关 |ρ|≥0.6；否则只当诊断。
2. **卡点用不变量造**：供给卡口；不依赖“预期路线”。
3. **用群体检查，不用一条路线**：至少 100 局随机玩家 + 会玩的玩家 + 贪心玩家。
4. **用进度 % 定位，不用步数**。
5. **容错优先于压力**：先保证随机玩家通关率达标，再加压。
6. **锁链按节奏放**：在释放点之后拿，组里有钥匙，优先两连。
7. **一次只动一类旋钮**，改完全量复测，记录改前改后（AGENTS 红线 7）。**但一维找不到就做二维扫描**——耦合（A 单独无效、A+B 有效）不可能靠一维找到（§24.3）。
8. **成批上线**（约 10 关一组），每关上线前写下预测。
9. **负结果也记**（AGENTS §2）。
10. **规则层改动（三面墙、buffer 大小）放在最后**，用同一套尺子先在模拟里对比。
11. **先端到端跑通一张关，再扩工具**（2026-11-12）：任何新工具都必须先服务于“一张能给你试玩的关”。

### 8.5.1 高压出口占比（2026-11-12，诊断/建造约束）

用户 2026-11-12 的观察：暂存为 4 时，如果大部分下一步的车都“安全”（能当步吃完、把暂存降下来），那压力在、容错也在。

**定义**：在 `buffer≥3` 的步里，存在至少 1 个“点了之后 buffer 变小”的选项的步数占比。

| 关 | 出口占比 | 线上失败率 | 关流失 |
|---|---:|---:|---:|
| L9 | **0.67** | 28.0% | 14.3% |
| L13 | 0.59 | 25.0% | 7.7% |
| L5 | 0.51 | 60.2% | 35.0% |
| L4 / L10 / L12 | 0.47 | 46–48% | 19–23% |
| L8 | 0.45 | 27.9% | 16.7% |
| L6 | 0.37 | 46.8% | 16.9% |
| L2 / L11 | 0.35 | 44–65% | 30–48% |
| L7 | 0.24 | 49.2% | 22.2% |
| L3 | 0.22 | 63.9% | 36.7% |

相关：vs 失败率 ρ=−0.57 / r=−0.64；vs 关流失 ρ=−0.61；vs 失败流失 ρ=+0.53（n=7，方向与预期相反）。

**加权版本（2026-11-12 第二轮，12 关）**：

| 版本 | vs 失败率 | vs 关流失 | vs 失败流失 |
|---|---:|---:|---:|
| 高压出口占比（有任意降幅） | −0.57 | −0.61 | +0.53 |
| 平均最大降幅 per 步 | −0.64 | −0.68 | +0.53 |
| **有 ≥2 格降幅的步占比** | **−0.73** | **−0.74** | +0.60 |
| 平均降幅（所有选项） | −0.75 | −0.62 | +0.44 |
| 平均可吃完车数 | −0.03 | −0.02 | −0.05 |

**结论**：
1. “能吃完的车有几个”**完全没有信号**（−0.03）——重要的不是选项多，而是**有没有一次真正的松口气**（降 ≥2 格）。
2. 最强的版本（≥2 格降幅占比）ρ=−0.73 / −0.74，方向稳定，但**仍不如随机玩家通关率（−0.86）**，且对失败流失方向相反（+0.60，n=7）。
3. 反例仍在：L6 的 ≥2 降幅占比 0.169（接近 L8 的 0.163），失败率却 46.8% vs 27.9%——说明“有出口”还要和“压了多久”一起看（L6 是连续 10 步 4 格的长磨）。
4. **用法：建造约束，不是验收门槛**。目标：高压段里**定期**出现 ≥2 格的出口。

**节奏指标（2026-11-12 第三轮，12 关）——未通过**：定义“最长连续 buffer≥3 且没有一次 ≥2 格降幅的步数”，与线上失败率 ρ=**+0.16**、关流失 ρ=+0.14、失败流失 ρ=−0.27。**基本无信号**，假设被否。

反例：L5 的连续步数只有 5（最短档），失败率却 60%；L7 是 29（最长），失败率 49%。说明“压得久不久”不是决定因素。

**这一族（出口/降幅/节奏）到此为止**：最好的版本（≥2 格降幅占比）−0.73 仍不如随机玩家通关率（−0.86），且对失败流失方向相反。保留“≥2 格降幅占比 ≥0.1”作为建造时的**约束**（不要造出完全没有大出口的关），不再继续加变体。

### 8.5.2 开局代价车标定曲线（2026-11-12，第一个正面结果，但只标定“开局陷阱”）

在 106 平底座上，把“零收益 + 债务长”的后期色车（32/5/14）一辆辆换到开局可点处，每档 100 局 × 3 种子：

| 额外换入 | 通关率 | 熵 | 死亡数 | 死亡位置 |
|---:|---:|---:|---:|---|
| 0 | 1.000 | 1.25 | 0 | — |
| 2 | 1.000 | 1.23 | 0 | — |
| 4 | 0.997 | 1.23 | 1 | step 11 |
| 6 | 0.967 | 1.22 | 10 | 全部 step 11（进度 17%） |
| 8 | 0.947 | 1.16 | 16 | 75% 在 step 5 |
| **9** | **0.913** | — | — | 开局 |
| 10（3 种子） | 0.840 | 1.19 | 48 | **100% step 5，进度 2–5%** |
| 10（8 种子） | 0.818 | — | — | 开局 |

**结论**：
1. **能平滑标定**：6→9 辆是 0.967→0.947→0.913，每 1–2 辆约 −2~−3pp；0.913 落在目标带内。陡崖在第 10 辆——那辆把第 1 行最后一个安全格也换掉了（同样 10 辆但留 1 个安全格时是 0.893）。
2. **但它标定的是“开局陷阱”，不是中段压力**：所有死亡 progress <20%，中段/后段死亡为 0。
3. **“吃一半”不致命，“收不回来”才致命**：把 ratio=0.53 的早色 11 换到开局，800 局全 1.000；而 32/5/14 是后期色、零收益、长时间不释放，才致死。**债务时长 > 首次可吃比例**。
4. 熵没有一起崩（最大 −0.09，未过 §24.4 的退回线）。

**用法**：位置 + “后期色车”是第一个能连续调节随机通关率的旋钮；但**开局陷阱不是我们要的难度**（L2 的高流失正是早死）。下一步要把同样的代价挪到中段（可点时机 30–60%），看曲线是否保留。

**中段验证（2026-11-12，C5）——曲线消失，且原因拆清楚了**：

| 变体 | 中段代价车 | 通关率 | 熵 | 死亡 |
|---|---:|---:|---:|---:|
| M0 底座 | 0 | 1.000 | 1.25 | 0 |
| M2 | 2 | 1.000 | 1.42 | 0 |
| M4 | 4 | 1.000 | 1.45 | 0 |
| M5（最大可凑数） | 5 | 1.000 | 1.43 | 0 |

两个关键对照：
1. **剂量不足**：106 上“中段可点（30–60%）+ 零收益 + 债务长”的车只有 5 辆，而开局曲线要 8–10 辆才到 0.913。**同样的 5 辆放回开局，也全是 1.000**（M5_open）。所以“中段无效”不能单独归因于位置。
2. **代价属性会消失**：C3 里 6 辆 32/43 放开局是 0.967，放到中段后首点 gain 中位 43（吃满）、零收益点击只占 0.7–4.3%，通关 1.000。

**当前唯一被真人认可的配方（2026-11-12，用户试玩 17/20/21）**：`PressureBuild_v5` 换位加压 + **7–9 个数字冰 + 2–4 个问号，0 锁链、0 管道**；熵 1.54–1.67，随机通关 0.96–1.00。用户反馈：17（图 91）"挺不错"、20（图 18）两次都死、"可塑"、21（图 23）偏简单（该图最大同色块占 32%）。
> 注：这与 §6.5 “冰是熵杀手”不矛盾——C1 里致死的是**高冰值（8–27）**；低剂量（7–9 格、小值）与熵 1.5+ 可以共存。

**结论**：中段代价车在 106 上**不能当标定旋钮**；要当中段旋钮，底座至少需要 8–10 辆中段零收益 + 长债务的车，这在 106 上不存在。

**开局网格（2026-11-12，C7）——同样不成立**：开局可点 4/5/6 × 代价车 0/1/2，共 9 组，全部 **1.000、0 死亡**（合并对照 0/3600），熵 1.25–1.44。

两个机制原因：
1. **只有第 0 行在开局暴露**，第 1 行开局不可点；降开局可点只能给第 0 行加冰，而冰 n=1–3 只锁 1–3 步，3 步内就恢复成 7 个选项。
2. 代价车放在第 0 行会被点（A4_B2 首点 49.7% 落在零收益车），但仍然全胜——**一两辆吃不饱的车填不满 5 格**。

**至此，位置/容量/门/开局宽度都试完**：唯一能把通关率压进 0.85–0.92 的，是 C3 的 8–10 辆零收益后期色车铺满开局，而它的死亡 100% 在进度 <20%——**只能造开局陷阱，没有“适中且不死在开局”的证据**。


### 8.5.3 颜色体检：总量 × 连通性（2026-11-12 用户补充）

“纯色联通太大”这句话里的两个量要分开看——**总像素占比**和**最大连通块**。同一个颜色的两种极端，造成的效果相反：

| 象限 | 判据（coloredPx 为分母） | 效果 | 例子 |
|---|---|---|---|
| **大且联** | 占比 ≥10% 且最大块 ≥100px | **顺手色**：车一进场就吃满，关卡变平 | 23 的橙色：32.1% / 513px（第 21 关“完全没压力”） |
| **大但碎** | 总量 ≥80px 且最大块 <40px | **死债色**：永远吃不满，容易憋死人 | 106 的色 11：230px 被切成 71 块、最大 13px |
| 小且联 | 总量 <80px，但块完整 | 一口吃完，影响小 | — |
| 小且碎 | 总量 <80px 且碎 | 噪音，基本不影响 | — |

**可用的张力色**在中间：总量够大（≥5%），但最大块不足以让一辆车一口吃完（<100px）；这种颜色才需要“先开一片、再拿一辆”。

**用法**：选图 / 建造后做一次逐色体检——出现“大且联”的色就预期关卡偏平；出现“大但碎”的色就预期有挫败点；两种情况同时出现，就是 C11 里 ρ≈0 的原因（两个方向互相抵消）。

## 9. v5 制作流程（S0–S11）

> 每一步写清：**做什么 / 为什么 / 输入 / 输出 / 完成标准 / 谁来做**。
> “人”= 策划（用户）；“便宜模型”= 按任务单执行的低成本模型；“高级模型”= 只用于设计评审和结果判断。

### S0 选图与图分析

- **做什么**：
  1. 用 `ImgFeature_v781` 体检：色数 11–17、中位块 ≥2px、最大色占比 ≤35%。
  2. 生成**颜色层次表**：用“全图逐层剥离”的方式（任何顺序都成立的部分），算出每种颜色**最早什么进度能开始吃**、**什么进度之前必须吃完才能露出别的颜色**。
  3. 生成**颜色需求曲线**：按进度 0–100%，每个窗口里“下一层需要哪些颜色、各需要多少像素”。
  4. 标出**卡口候选色**：在进度 30–85% 之间才被需要、需求量适中（够做一两辆门后车）、被挡关系在图上看得清的颜色。
- **为什么**：卡点必须建立在图的层次上（不变量）。没有这张表，就只能靠预期路线。
- **输入**：目标图 TXT / 关卡 JSON 的 `blocks`。
- **输出**：`图分析_<图名>.json`（层次、需求曲线、卡口候选色及理由）。
- **完成标准**：每张图至少 2 个卡口候选色；否则换图。
- **谁来做**：工具（T1，可复用 `ColorSpread_v788`、`TargetReachCurve`、`ImageDebtScan_v1` 的部分逻辑）；人看一眼候选色是否“看得懂”。

### S1 卡点规划

- **做什么**：为每关写 2–3 张**卡点卡片**：

```text
卡点 #1
  进度窗口：35%–45%
  卡口颜色：Y（这一层需要 Y 共约 120px）
  门：两连锁链 [钥匙 Y×40 + 代价 Z×30]，另有冰锁住门外 Y×30
  钥匙为什么看得见：Y 的像素在图左下大面积露出；门在盘第 1 行
  代价怎么回收：Z 在进度 50% 前大量露出（释放者：Z 盘上另有 2 辆）
  第二种过法：门外 Y 车（冰 8）等冰化后也能过，但要多撑几步
  卡点前喘息：进度 25%–35% 压力 ≤ 0.3
```

  - 前 10% 不设卡；卡点之间留喘息；最后一个卡点在 70–85%（“可惜”在后段）。
- **为什么**：把“卡点有道理”在建造之前写清楚，后面每一步都对着卡片做，检查也对着卡片查。
- **输入**：S0 的图分析。
- **输出**：`卡点规划_<图名>.json`（机器可读的卡片）。
- **完成标准**：每张卡片的 7 项都填了；人认可“有道理”。
- **谁来做**：**人主导**（这是策划的核心价值）；工具可以给出默认草案（T2）。

### S1.5 卡片可行性核对（2026-11-12 新增）

- **做什么**：卡片写定之前，先用 20 局随机玩家统计**每种颜色每辆车的“首次可点进度中位数”**；门的窗口必须落在这批车的可达范围内。
- **硬规则**：
  1. **门只能延迟供给，不能提前**——门色车最晚的可点进度 ≥ 窗口终点，否则该窗口放不了门。
  2. **卡片容量只能写实际车的容量或区间**（容量是硬输入，红线 1）。
  3. 每个门至少要有一辆“窗口内可点”的门色车，并且有一辆**正交相邻**的其他颜色车当代价；否则先换位，换位不行就改窗口或换图。
- **为什么**：106 的卡片写 14@65–70%，底座的 14 色车最晚在 79% 才可点、其余 ≤34.8%——窗口不可达，造完才发现；23 的卡片写钥匙 31×40，实际只有 32。两张图连续撞上同一问题。
- **完成标准**：每张卡片逐门填写“用的哪辆车（位置/容量/可点进度中位数）”；填不出来就是卡片不成立。

### S2 切车（容量）

- **做什么**：
  1. **卡口颜色**：按卡片把容量分成“门后”（锁链 / 管道 / 冰下）和“门外”。门外的量 **不足以**吃完卡点那一层（例如 ≤40%）。
  2. **钥匙车**：容量设成进场时**吃不满**——约等于当时该色可达像素的 **60–80%**，留 1–2 步的债，再由门后/后续的释放者补足（2026-11-12 修正：原来写“当步吃满”，那等于门免费）。
  2b. **代价车必须是稀缺色**：开门那一刻，该色可达像素 < 车的容量。背景色 / 到处可达的颜色不行——链组里先吃的那辆会当步吃完，门就免费了。找不到稀缺色，就先把“后期才需要的颜色”的车挪到外圈再成链（S3 的范畴）。
  3. **代价车**：容量设成在“回收进度”之前能吃满（≤ 回收时可达像素数）。
  4. **普通颜色**：车容量接近均匀（目标离散度 ≈0.25，最大车 ≤55），避免 >60 的大车和 ≤5 的碎车。
  5. 校验：逐色守恒。
- **为什么**：卡点必经靠“门外不够”；钥匙必须立刻见效，代价必须收得回来——这是“卡点有道理”的容量条件。均匀车容量来自人做关卡的统计（212 张 G8 离散度 0.25、最大 54；分组2 离散度 0.42、最大 82）。
- **输入**：图分析 + 卡点卡片。
- **输出**：车列表（颜色、容量、角色：钥匙 / 代价 / 门外 / 普通）。
- **完成标准**：逐色守恒；角色条件全部满足。
- **谁来做**：工具（T3 的切车部分，可复用 `SplitLevel_v722` 的守恒逻辑）。

### S3 摆放

- **做什么**：
  1. **外圈（先暴露）放早期颜色**，内圈放后期颜色（按 S0 的“最早可吃进度”排）。
  2. **门**放在“到卡点进度时，门已经暴露或下一步暴露”的位置。
  3. **锁链**放在“压力刚释放、格子空出来”的时间点附近能暴露的位置；组员正交相邻。
  4. 门外的卡口色替代供给放深一点（或交给 S4 加冰）。
  5. 开局第 0 行 ≥5 辆可点，且至少一半能当步吃到东西（corner 色在第 0 行，B 线 R1 规则）。
- **为什么**：位置决定“什么时候能拿到什么”；门的时机必须和图的需求对齐，否则卡点要么提前（死在前段）要么错过（卡点消失）。
- **输入**：车列表 + 卡点卡片 + 图分析。
- **输出**：初版 `spools`。
- **完成标准**：合法性全过（S5）。
- **谁来做**：工具（T3 的摆放部分）。

### S4 放障碍

- **做什么**：按卡点卡片放锁链、管道、冰；**不按配额加障碍**。
  - 锁链：优先两连；三连只放在后段或压力低的地方；组里必须有一辆进场当步吃满。
  - 管道：队列按图层需求排序（先吐出的车，颜色就是下一层要的）；不放开局主路口。
  - 冰：锁门外的替代供给；倒计时（按拿车总数）对齐卡点进度；不加在“单车辆颜色”上。
  - 问号：可选，不放在钥匙上。
- **为什么**：障碍是卡点的实现，不是装饰；按配额加的障碍会制造不可归因的死。
- **输出**：完整关卡 JSON。
- **完成标准**：合法性全过。
- **谁来做**：工具（T3）。

### S5 合法性检查

- **做什么**：§8.2 的全部硬门。可通关用强搜索判（T6）。
- **为什么**：不合法的关后面的指标都没意义。
- **完成标准**：全过；不过就回 S2–S4（多数是守恒或空格问题）。
- **谁来做**：工具（现有 `ArlCheck_v793` 的合法部分 + `LayoutScore_v1` + 格式检查 T9 + 强搜索 T6）。

### S6 群体模拟检测

- **做什么**：跑 §8 的全部指标：随机玩家通关率、选择熵、压力曲线、每个卡点的覆盖率 / 通过率 / 窗口宽度 / 过法数、归因距离、死在卡点比例、死亡进度、延迟致死、诱饵。
- **为什么**：用群体代替预期路线；每个指标对应策划的一个目标。
- **输出**：`检测报告_<关卡>.json` + 一页可读的 md（每个卡点一行）。
- **谁来做**：工具（T4 群体模拟、T5 卡点检查、T6 归因）。

### S7 诊断与修复（2026-11-12 改：按 §24 的搜索阶梯）

- **做什么**：
  1. 按 §10 的对照表定位症状，选该症状的候选旋钮；
  2. **L1 一维扫描**：该旋钮的每一档都测（每个点 30 局 × 3 固定种子）；
  3. 一维全都不达标 → **L2 二维扫描**：任取两个候选旋钮，做 3×3 到 5×5 的格子，**不许回退后再单独试第二个**；
  4. 二维仍不行 → **L3 正交表或随机 100–200 个组合**（并行跑，固定种子）；
  5. L3 也扫不进区间 → 判“这套图 + 容量下可行域为空”，回 S1 换卡点或换图，不再调参。
- **为什么**：过去“同时调很多东西”导致不知道哪个改动起作用；但反过来“一次只动一个”会系统性漏掉耦合解（A 单独无效、A+B 有效）。两级都要。
- **输出**：每次修改一条记录：症状、旋钮与档位、改了什么、改前改后的数字、**影响面检查**（非目标指标有没有动）。
- **完成标准**：全部达标；或 L1–L3 都扫不进区间 → 记“可行域为空”并回 S1。
- **谁来做**：工具（T7）按 §24 生成扫描表并批量评估；便宜模型执行；人只看“回 S1”的情况。

### S8 节奏微调

- **做什么**：卡点之间用换位（`PressureBuild_v5`，锁链 / 管道 / 门不动）把喘息段和小压力段调到目标；约束：不能降低卡点指标和随机玩家通关率。
- **为什么**：卡点之间完全没压力会平，一直有压力会磨。
- **谁来做**：工具。

### S9 人工试玩

- **做什么**：用户在编辑器里玩，**导出点击路径**；记录：卡点在哪感到、死在哪、死的时候知不知道为什么、想不想再来。
- **为什么**：模拟只能代表“普通玩家”；“卡点有道理”“想再来”最终要人判断。点击路径也是校准“像人的玩家”的数据。
- **输出**：试玩记录 + 点击路径 JSON。
- **完成标准**：人认可；否则写下哪一个卡点不对，回 S1 或 S7。
- **谁来做**：人。

### S10 交付

- **做什么**：格式规范化（§19.9）；交付清单：每关的预测失败率、随机玩家通关率、卡点表、版本号；成批（约 10 关）。
- **为什么**：预测写在上线前，才能事后对账。
- **谁来做**：工具（T9）+ 人确认组号。

### S11 上线与校准

- 见 §13。

## 10. 诊断 → 修复对照表

**旋钮优先级**（越靠前越安全）：
1. **摆放**（换位；不改总量，守恒自动成立）
2. **同色容量重分配**（同一颜色的车之间挪容量；守恒自动成立）
3. **障碍参数**（冰值、锁链组员、管道队列顺序）
4. **增删障碍**
5. **卡点规划**（回 S1）
6. **规则 / 棋盘**（最后）

| 症状（指标） | 常见原因 | 修法（按优先级） |
|---|---|---|
| **卡点覆盖率低**（玩家绕开了） | 门外还有足够的卡口色供给 | ① 把门外卡口色的车往深处挪；② 把门外车的容量转给门后的同色车；③ 给门外车加冰（倒计时到卡点之后）；④ 把门外供给改成“贵的替代”（放进三连锁） |
| **卡点通过率低 / 随机玩家通关率低**（门太窄） | 锁链窗口短；格子不够；代价车太大 | ① 锁链挪到释放点之后（换位）；② 降低代价车容量（同色重分配）；③ 三连改两连；④ 确保钥匙当步吃满；⑤ 门附近放一辆“恢复车”（能一次吃满、腾出格子） |
| **窗口宽度 <3** | 锁链组员暴露时间不一致；冰化太晚 | ① 让组员在相近时间暴露（换位）；② 冰值减小；③ 减少组员 |
| **延迟致死 >0 / 归因距离长** | 某笔债要很久以后才能还；锁链里有很晚才释放的颜色 | ① 债车容量减小，让附近露出的像素就能吃满；② 把释放它的颜色往外圈挪；③ 锁链里不放“晚释放”的颜色 |
| **诱饵陷阱 >0** | 最诱人的选项（吃最多）后面是死路 | ① 把这辆车的容量减小或挪深；② 让它吃不到那么多（换到同色更晚的车） |
| **死在前段**（死亡进度 <50%） | 开局太紧，门来得太早 | ① 开局多放能吃满的车；② 第一个门往后挪；③ 前 10% 不放锁链和冰 |
| **死不在卡点上**（死在卡点比例低） | 卡点之外还有暗坑 | 用 `FatalOptionCheck` 找出死点，按“延迟致死”行修 |
| **卡点之间没压力**（太平） | 免费选项太多 | ① 换位：后期颜色往外圈；② 同色容量稍调大，制造小额债 |
| **压力太长**（长磨） | 连续高压步数多 | ① 中间插一辆“大释放”车；② 一个卡点拆成两个 |
| **选择熵低**（没得选 / 假选择） | 可点的车太少，或后果都一样 | ① 去掉边缘的冰；② 拆大车；③ 边缘颜色多样化 |
| **过法数 <2** | 钥匙只有一把 | 加“贵的替代路线”：另一处也有卡口色，但在更贵的锁链里或冰更久 |
| **开局可点 <5** | 第 0 行有锁链 / 冰 / 不可吃的车 | ① 换位；② 第 0 行去冰 |
| **守恒失败 / 有空格** | 构建 bug | 回 S2–S4；不允许用缩放容量“修”（红线 1） |

**修不好的判断**：同一症状连续 3 轮修不好，说明是卡点规划本身不成立（比如卡口色需求量太大、图层次不支持），回 S1，而不是继续调参数。

## 13. 上线与校准闭环

1. **上线前**：每关写下随机玩家通关率、预测失败率区间、卡点表；交付清单入库。
2. **上线后**（数据稳定后，进入人数 ≥30 的关）：把失败率、关流失、失败流失、重玩次数、关总耗时加进校准表（T10）。
3. **对账**：预测 vs 实际；偏差大的关单独看：是哪个卡点出问题（试玩记录 + 模拟死因）。
4. **更新**：换算线（随机玩家通关率 → 失败率）；指标阈值；必要时修改“随机玩家”的定义（例如加入“像人的玩家”）。
5. **第一次外部检验**：分组3 L2–L5 数据出来后，先检验随机玩家通关率能否预测它们。
6. **难度曲线**（用户说先不考虑）：等有 2–3 批数据后，再讨论不同关卡位置的目标失败率。

**为什么这样能“精准”**：精准不是一次做对，而是每批都缩小“预测 vs 实际”的误差。每批约 10 关，就是 10 个新的校准点。

## 14. 规则层实验：三面墙 / 底边入口

- **目的**：降低吃像素顺序的不确定性（失败更可归因）、加强目标感（从底部往上吃）、入口变窄（天然压力）。
- **风险**：入口变窄 → 选择和容错下降；v4 停止的原因见 `实验关/产线v4/失败报告_20261111.md`，复活前必须先读。
- **做法**：不改客户端；在模拟器里对同一批图，分别用“四边 + corner”和“三面墙 + 底边”走完 S0–S6，比较：随机玩家通关率、选择熵、卡点覆盖率、**归因距离**。
- **放行门**：三面墙在归因距离上明显更好（中位数小 ≥1 步），且随机玩家通关率不低于四边版 0.05 以上 → 才提给程序改客户端。
- **时机**：M4 之后（需要卡点工具）。

**实测（2026-11-12，R1_三面墙）**：口径 = 目标图上/左/右为墙、只有底边出口，corner 顺序不变；`--bottom-only`（PopulationSim / Solvable 新加，默认关；默认回归逐字节一致）。

| 关 | 四边 | 三面墙 | 熵 | 开局暴露像素 |
|---|---:|---:|---:|---|
| ZC_106_v1 | 1.000 | 1.000 | 1.25→1.31 | 164→92（−44%） |
| ZC_23_safe | 1.000 | 1.000 | 1.58→1.58 | 32→32 |
| ZC_18_v5p | 1.000 | **0.290** | 1.67→1.53 | 80→63（−21%） |
| ZC_91_v5p | 0.960 | 0.963 | 1.54→1.57 | 102→83（−19%） |

- **只变难或不变**，但效果高度依赖图：4 张里 2 张零变化、1 张可忽略，**1 张从 100% 打到 29%**（ZC_18 的供给路径被墙切断，最小暂存路线直接不通）。
- **没有更“可控”**：种子极差未缩小（ZC_18 0→0.11），死亡也没有更集中（进度 std 0.0057→0.0298）。
- 开局暴露面稳定压缩 19–44%，这是它唯一稳定的效果。
- **结论**：三面墙**只当可选关型**（做个别高难关 / 强目标感关），**不作为 v5 规则前提**。

## 15. 风险、未知与不做清单

### 15.1 风险

| 风险 | 后果 | 对策 |
|---|---|---|
| 随机玩家在锁链关上不准 | 容错预测失效 | M6 优先检验；必要时加入“会为锁链清格子”的玩家 |
| 校准样本太少（12 关） | 换算线不稳 | 每批上线就补；进入人数 <30 的关只参考 |
| 卡口设计让关卡同质化 | 关卡像一个模子 | 卡点四种类型轮换；不复用骨架（日志结论：骨架复用会让黑块 / 门永远在老地方） |
| 强搜索太慢 | 归因指标进不了批量 | T6 是第一优先 |
| 用户试玩代表性不足（专家玩家） | 手感偏“太简单” | 试玩用来判“有道理”，难度交给随机玩家 + 线上 |

### 15.2 未知（需要用户或数据回答）

- 用户心中“有道理的卡点”的具体正例（有一个正例，卡片模板就能从它反推）。
- 客户端里还能改什么（buffer 大小、复活、道具）。
- 程序能否加最小埋点（每次失败死在第几步）。

### 15.3 不做

- 不复活 v1 的 15 项作为质量判官（只保留合法性部分）。
- 不按配额加障碍。
- 不用单条预期路线检查卡点。
- 不在没有线上验证时把新指标写成硬门。
- 不改客户端 bin（红线 6）；三面墙先在模拟里比较。
- 不再继续 v1.5 / v4 的产物。

## 18. 实验规程：每个实验怎么开展

> 适用于 v5 的每一个实验（新指标、新工具、新建造方法、规则对比）。目的：结论可复现、可比较，失败也有价值。

### 18.1 开工前（写在实验目录的 `结果.md` 开头，跑之前写）

1. **问题**：一句话，例如“归因距离能否预测线上失败流失？”
2. **假设**：期望看到什么，例如“归因距离中位数越短，失败流失越低”。
3. **放行门（数字）**：例如“分组2 L2–L13 上 |ρ|≥0.6，且不比随机玩家通关率差”。**门槛一旦写下，不许在看到结果后修改**；想改，就另开一个实验。
4. **数据与样本**：用哪些关（文件路径）、随机种子（至少 3 个）、模拟局数（随机玩家 ≥100 局）。
5. **对照**：改前 / 基线是什么（例如原关、安全版、现有指标）。
6. **成本上限**：计算时间或迭代次数的上限（例如单个实验总计算 ≤2 小时；建造器迭代 ≤500）。超出就停，记录为“未完成”。

### 18.2 运行中

1. 命令必须可复制，写进 `结果.md`。
2. 并行时中间文件带 pid / uuid（红线 9）。
3. 改 js 先 `node --check`（红线 5）。
4. **一次只动一类东西**（红线 7）：要比较两个改动，就跑两个实验。
5. 发现工具 bug：立即停，修 bug，**整个实验从头重跑**，不拼接修前修后的结果。

### 18.3 结束后

1. **结果表**：每关一行，改前 / 改后 / 线上（如有）。
2. **结论只能三选一**：
   - **通过**：达到放行门；
   - **未通过**：没达到（这是负结果，同样要记）；
   - **不确定**：样本不够（例如进入人数 <30 的关太多）或种子间结论不一致。
3. **记录**：日志一节（五段：问题原话 / 证据 / 改动 / 验证改前后 / 遗留）+ `结果.md` + 三处状态页 + `git commit`（红线 10）。
4. **登记**：工具进 `03_工具/工具索引.md`；实验进 `实验关/索引.md`。

### 18.4 禁止

- 看到结果后改门槛；
- 用单条路线的结果代表“玩家”；
- 用推理代替实测（红线 4）；
- 混用口径（例如把噪声求解器的数当随机玩家的数）；
- 把“模拟通过”写成“好关”——模拟通过只是“可以拿去试玩 / 上线验证”。

## 19. 失败处理：通用规则与各里程碑的分支预案

### 19.1 先判断是哪一类失败

| 类型 | 判断方法 | 处理 |
|---|---|---|
| **A. 实现错了** | 结果明显违反常识（例如守恒失败、两个种子差异巨大、复测不一致） | 修 bug → 从头重跑 → 日志记录 bug 本身 |
| **B. 指标不准** | 指标与线上不相关（|ρ|<0.6） | 降为诊断，不进验收；记录负结果 |
| **C. 设计不成立** | 工具正确、指标可信，但造不出达标的关（同一症状 3 轮修不好） | 回到上一层设计（S7 → S1；M4 → M3） |
| **D. 数据不够** | 样本太少、结论在种子间翻转 | 标“不确定”，等数据或加种子，不做决定 |

**原则**：先排除 A，再判断 B/C/D。过去多次把 A（实现 bug、用错文件）当成 C（设计不行），导致方向反复（例如日志 §1094 的分组1 文件错误）。

### 19.2 各里程碑的分支预案

| 里程碑 | 失败情况 | 预案 |
|---|---|---|
| **T6 提速** | 达不到 ≤0.2 秒 / 次，或与宽束搜索一致率 <98% | ① 只在关键处做强搜索（卡点窗口内、随机玩家死亡局的最后 10 步）；② 缓存已判定状态；③ 仍不行就把归因类指标限定为“抽样诊断”，不进批量 |
| **M2 新指标** | 归因距离 / 死亡进度都过不了 |ρ|≥0.6 | 验收只用已证实的“随机玩家通关率 + 选择熵”；归因指标降为诊断；**不阻塞 M3** |
| **M2** | 随机玩家通关率在新数据上掉到 |ρ|<0.6 | 停止用它做门槛；回到“像人的玩家”方向（用点击路径拟合）；在此之前上线只能依赖试玩 |
| **M3 卡口候选** | 某张图卡口候选 <2 | 换图（正常关卡池 212 张） |
| **M3** | 大多数图都 <2 | 说明“供给卡口”对这类图不适用 → 卡点改用“冰倒计时 + 位置”组合；同时提前做 §14 三面墙对比 |
| **M4 覆盖率低** | 卡点被绕开 | 按 §10 修；3 轮不行回 S1 改卡片；所有图都不行 → 记录“供给卡口不成立”的负结果，召集评审（人 + 高级模型） |
| **M4 加锁链后通关率掉出 0.85** | 锁链让容错掉 | 依次：两连代替三连 → 锁链后移到释放点之后 → 加恢复车 → 锁链只放在 70% 以后或作为“贵的替代路线”。每一步都记录“锁链数量 / 位置 vs 通关率”的数字，最终形成“锁链和容错的边界表” |
| **M4 延迟致死去不掉** | 修一个冒一个 | 检查是否有“很晚才释放的颜色”被放进锁链或大车；仍不行回 S1 换卡口色 |
| **M5 试玩不认可** | 用户觉得卡点没道理 / 太难 / 太平 / 死得冤 | 按原因分类记录；看对应指标有没有捕捉到：捕捉到了就是阈值问题（调阈值）；没捕捉到就是缺指标（作为新指标候选，进 M2 流程） |
| **M6 预测偏差大** | 线上失败率和预测差很多 | 先分：**整体偏移**（排序对、数值偏）→ 平移换算线，正常；**排序错**（尺子失效）→ 暂停上线新关，回 M2 重新验证尺子 |
| **M6** | 进入人数太少 | 标“不确定”，等数据，不据此改尺子 |
| **分组3 外部检验** | 随机玩家通关率预测不了分组3 L2–L5 | 只有 4 关，先记“不确定”；与下一批合并再判 |

### 19.3 全局熔断

- **连续两个里程碑失败**，或**同一个问题换了三种方法都不行**：停止开发新工具，做一次复盘（人 + 高级模型），回答三个问题：
  1. 失败是哪一类（A/B/C/D）？
  2. 有没有违反本文的原则（例如单路线检查、改门槛）？
  3. 是否需要动规则层（三面墙、buffer 大小），或者换目标？
- 复盘结论写进日志和本文 §6（证据）/ §15（风险），再决定是否继续。

### 19.4 失败也要留下的东西

- 负结果的数字（例如 v5-0：诱饵陷阱 ρ=+0.64，不如选择熵）；
- “什么条件下失败”（例如“无锁链时压力和容错可以拆开”只在无锁链条件下成立）；
- 下一个人不要再试的做法（进 `新会话启动 §5 已知的坑`）。

## 21. 图不行还是产线不行：判定方法

> 问题：一张图怎么都造不出满意的卡点时，是图本身做不出（例如只有一种颜色、或者一个巨大的联通色），还是产线不够好？
> 原则：**先算图的“上限”（只看图、不依赖产线），再看产线离上限多远。** 上限只需要分析图，计算很便宜，不需要“烧服务器”去搜。

### 21.1 为什么有些图天生做不出卡点

- 卡点（供给卡口）的前提：**某种颜色在进度 X% 之前，无论玩家怎么走都吃不到**（被别的颜色挡着），而它的量足够做门后的车。
- 极端例子：整张图只有一种颜色 → 任何时刻都有可达像素 → 每辆车进场都能吃满 → 暂存永远不会压债 → **任何产线都造不出压力和卡点**。
- 一个巨大的、大面积贴边的联通色同理：它从开局就可吃，几乎不会被挡；挡住它的“层”太薄。
- 结论：**卡点的上限由图的“层次深度”决定**，产线只能逼近这个上限，不能超过它。

### 21.2 图的上限指标（只看目标图，与产线无关）

| 指标 | 定义 | 怎么算（思路） | 含义 |
|---|---|---|---|
| **最早可吃进度 E(c, a)** | 颜色 c 的第 a 个像素，在“对 c 最有利的顺序”下，最早在多少进度时能被吃到 | 网格最短路：从图边出发，经过其他颜色像素的代价 = 必须先吃掉的像素数；对 c 的像素按代价排序 | E 很大 = 不管玩家怎么走，c 的这部分都得晚吃 → 天然的卡口候选 |
| **可卡量 G(X)** | 在进度 X 之前，**所有顺序下都吃不到**的像素总量，按颜色分 | 由 E(c, a) ≥ X 的像素计数 | G 大 = 进度 X 处能做必经卡点 |
| **层次深度** | 能形成卡口的颜色数（例如在 30–85% 区间、可卡量 ≥ 一辆门后车的容量） | 由 G(X) 统计 | 0 = 这张图做不出供给卡口 |
| **最大贴边联通块占比** | 最大的同色联通块里、开局就可达的像素占全图比例 | 洪泛 | 越大越“平” |

> 这些都是**不变量**（§5）：与玩家顺序、与产线怎么切车摆车都无关。它们是 `ImageDebtScan_v1` 的 rich / ok / flat 分类的升级版——从经验分类变成有定义的上限。

### 21.3 判定流程（三选一）

1. **算图上限**（§21.2）。
2. **上限判“不行”**：层次深度 = 0（或只有 1 个、且在前 30% 或后 15%）→ **图不行**。这张图只能做“无卡口”的关（例如教学关、轻松关），或者换图；不再让产线浪费算力。
3. **上限判“可以”，但产线造不出达标卡点** → 先怀疑产线：
   - **加预算对照**：同一张图、同一张卡片，给建造器 3–5 倍的迭代 / 搜索预算。加预算后能达标 → **产线效率问题**（搜索不够）；
   - **对照卡片**：换一张卡片（另一个卡口色 / 另一种门）。换卡片能达标 → **卡片设计问题**（S1），不是图的问题；
   - 都不行 → 看是哪个指标卡住（§10），按“修不好”的规则回 S1；同一张图三张卡片都失败 → 标“不确定”，记录下来用于修正上限指标（说明上限估高了）。
4. **结论写进 `图分析_<图名>.json`**：`图不行 / 产线不行 / 卡片不行 / 不确定`，以及依据的数字。

### 21.4 用对照组校准“上限”本身

上限指标本身也要验证，不能只靠推理（红线 4）：

| 对照 | 预期 | 如果不符合 |
|---|---|---|
| **阴性对照**：单色图、两色左右平分图 | 层次深度 = 0；产线也确实造不出卡点 | 上限指标有 bug |
| **阳性对照**：人工做一张“明确分层”的图（外圈 A、中圈 B、内圈 C） | 层次深度 ≥2；产线必须能造出达标卡点 | 产线有问题（不是图） |
| **存在性对照**：正常关卡池 212 张（别人做的、带锁链 / 冰 / 问号的成品关） | 对这些成品关直接跑 §8.6 卡点指标：如果人做的关在这张图上有达标卡点，说明**图可以** | 我们的产线在同一张图上造不出 → **产线不行**（有人做到了） |
| **一致性**：上限判“不行”的图，产线成功率应接近 0；判“可以”的图，成功率应明显更高 | 两组成功率差异明显 | 上限指标区分力不够，修正定义或阈值 |

> 存在性对照最有说服力：**同一张图，别人做到了而我们没做到，就是产线的问题**；所有人都做不到、且上限也判不行，才是图的问题。

### 21.5 放进流程的位置

> **2026-11-12 更正：本节以下 §21.6 取代 §21.1–§21.5 的“图挡住”口径。**

- S0（选图）之后立刻算上限：上限不行的图不进 S1。
- S7 修复“3 轮修不好”时，先回看上限：上限勉强（层次深度 = 1）的图优先换图，而不是继续调。
- 工具：作为 T1（`ImageLayerMap`）的一部分实现；验收用 §21.4 的四种对照。

### 21.6 更正（2026-11-12，A1 实测）：图“挡住”不了卡点，卡点只能靠供给

> 本节 §21.1–§21.5 的前提被实测推翻，保留原文作历史；以下为现行口径。

**实测**：按“逐格 4 邻接、经过的中间格数 = 必须先吃的像素”算，E(p) 的上限是 H+W 格（40×40 图最多 79 格 ≈ 4.9%，实际约 2.4%；45×45 约 2.2%）。因为**一条很窄的通道就够了**——不需要吃完整块背景，只需要沿一条颜色通道吃过去。所以：

- **“某种颜色在进度 30% 前无论如何都吃不到”在数学上几乎不存在**。图的“层次深度”不是卡点的来源。
- 卡点只能靠**供给**：某色在进度 X 成为主要需求，而它的车大多是门后的（锁链 / 管道队列 / 冰下）。供给是我们自己摆的，图上没有这个约束。
- 图能提供的只有**需求**：进度到 X% 时，图上正在吃的是哪些颜色、吃了多少。这决定“门卡在哪一色、哪个进度”是合理的。

**因此 §21.2 的指标作废**（`最早可吃进度 E`、`可卡量`、`层次深度`、`最大贴边联通块占比` 作为“图能不能做卡口”的判据）。替代口径 **T1 v2 · corner 消融序列**（只看图，不含车）：

1. 从空开始，每步在“与图边或已吃格相邻”的彩色格里，选 `D = (行数−1−r) + c` 最小的吃掉（与游戏 corner 顺序一致），记录 (进度, 颜色)。
2. 输出**需求曲线**：每 5% 窗口中各色被吃的像素数；每色的进度分位数。
3. **需求峰**：某色在某窗口占该窗口像素 ≥30% 且 ≥40px。
4. **门候补**：在 20–90% 区间有需求峰、且总量 ≥60px 的颜色。
5. 判定：≥2 个不同窗口的门候补 → “图可以”；1 个 → “图一般”；0 个 → “图不行”。

**v1 的“212 张里只有 4–6 张能做卡口”不能用作选图结论**：那是按“挡住”算的，而挡住不存在。T1 v2 的全量结果出来后以 v2 为准（见 `实验关/产线v5/A1_图分析/说明.md`）。

## 23. 结论总表：从搜关卡到造关卡（v1→v5，2026-11-12）

> 这一节把 v1–v5 之间**能站住的结论**收在一处。每条标“已证实 / 推断 / 已证伪”；没标出处的是本工程长期观察。新结论往这里加，旧的被推翻就移到 §6.5。

### 23.0 一句话

> **造关是标定，不是搜索。** 固定图和容量，用少数几个旋钮把随机玩家通关率扫到目标区间；结构指标负责筛掉废关，不负责定义好关。

### 23.1 关于“难度”

| # | 结论 | 状态 | 依据 |
|---|---|---|---|
| 1 | 难度不是关卡的属性，是**人群的属性**。同一张关，最优解 100%、随机玩家 100%、专家觉得“较简单”，而线上同类关失败 48% | 已证实 | ZC_18_safe、分组2 |
| 2 | 流失主要由**失败率**驱动：失败率 × 关流失 r=0.85，重玩次数 × 关流失 r=0.91 | 已证实 | CSV 34 关-组，日志 §1094 |
| 3 | 普通玩家**看得见当步就死、看不见几步之后**。随机玩家通关率因此能预测线上失败率（ρ=−0.86） | 已证实 | 日志 §1095 |
| 4 | 压力和容错**不是天生对立**；只在“容错=总有免费选项”的旧定义下对立。改成“没有会害死你的选项”后可以并存 | 已证实（模拟口径） | v5-1，日志 §1095 |
| 5 | “迟延致死”（当步没死、其实已无解）是最伤的设计，因为它直接打中“看不见后果”这一点 | 推断 | v5-0 与随机玩家解读 |
| 6 | **“死在后段”本身不伤；开局窄 + 没得选才伤**。L9 与 L2 都是多数死在后段（89% vs 83%），L9 流失 14.3%、L2 48%；差别是开局 6 vs 4、熵 1.46 vs 1.01 | 已证实 | 2026-11-12 实测 |
| 7 | **“适中”是一个窄带**：通关率 0.85–0.92 对应线上失败 20–30%。我们过去要么产出 1.0（平）、要么 ≤0.5（崩），很少落在带内——这才是“做不出适中”的直接原因 | 已证实 | G2 12 关 + 安全版 |

### 23.2 关于“怎么造”（有效）

| # | 做法 | 为什么有效 | 证据 |
|---|---|---|---|
| 6 | **用一群人检查，不用一条路线** | 单条预期路线会让卡点因换顺序而消失 | 用户观察 + 全部 v5 工具 |
| 7 | **图只决定需求，供给由我们摆** | 像素最早可吃进度上限 = 行数+列数（40×40≈2.4%），一条通道就够——图挡不住卡点 | A1，日志 §1096 |
| 8 | **换位是最安全的加压手段** | 不改容量、不改总量、守恒自动成立 | v5-1：freeP3 0→0.35，通关 1.00 |
| 9 | **门可以做到“必经”** | 链组被拿率可到 100% | C1 23 |
| 10 | **门还没做到“有代价”** | 钥匙当步吃满 = 门免费；代价要来自“拿了之后占格几步” | C1 23，S2 规则已改 |
| 11 | **卡点要按进度 % 定位、按颜色供给建** | 步数随人群变，进度窗口才稳定 | A1/B3 |

### 23.3 关于“流程”（吃了亏才学会）

| # | 结论 |
|---|---|
| 12 | **结构指标只能筛废，不能定好**：分组2 里 15 项全过的关照样高流失；16 个相关格只有 1 个过线 |
| 13 | **只有两个指标能当门槛**：随机玩家通关率（ρ=−0.86）、选择熵（ρ=−0.83）；其余全是诊断（§8.0） |
| 14 | **门槛必须跑之前写下**（B1 是第一个这么做的实验，也因此没把方向相反的指标当成果） |
| 15 | **一次只动一类旋钮**，改完全量复测，记录改前改后 |
| 16 | **先端到端跑通一张关，再扩工具**：六个工具做完还没一张认可的关，说明瓶颈在设计假设，不在工具 |
| 17 | **先核事实再下结论**：用错分组1 文件、把“图可以”数重、卡片写在车之前——三次都是流程问题 |

### 23.4 已证伪（不要再试）

| 做法 | 结论 | 出处 |
|---|---|---|
| 按配额加障碍（冰/链） | 死锁或选择熵下降 | 长期 |
| 用数字冰延迟供给 | **熵杀手**：1.55 → 1.06–1.15 | C1 23 |
| 把容量调大制造中段债 | 玩家总能绕开 | 日志 §1093 |
| 拆链救死锁 | 救不回（ZC_18 mid 45→26，仍死） | B 线 |
| 延后闸门解锁 | 直接死锁 | 长期 |
| 末段冰 / 末段大车 | 不产生债务 | 长期 |
| 打碎目标图 | 画面不可辨认 | 用户否决 |
| 纯随机搜索 + 指标爬山 | 优化的是指标，不是体验 | v1–v4 |
| “图有层次、能挡卡点” | 图挡不住（§6.5） | A1 |
| “先写卡片再造关” | 窗口常不可达（S1.5） | C1 106 |
| “归因距离 ≤3” | 未通过、方向相反 | B1 |
| “覆盖率 ≥0.7” | 对平底座也报 1.0 | C1 23 |

### 23.5 还没解决的

1. **门的代价**：怎么让过门真的欠债，而不砍掉选择。还没试过的机制是**管道当门**（占格，但不像冰那样直接砍选项）。
2. **可归因的失败**：目前没有任何经过线上验证的指标。
3. **“适中”的锚点**：20–30% 是从分组1（14%）和分组2（48%）推出来的，没有普通玩家样本。
4. **图的可行域很窄**：212 张里只有 3 张能放两个门、23 张能放一个门。
5. **难度曲线/关卡位置**：用户暂不考虑，但“适中”本身离不开位置。

### 23.6 对下一步的含义

- 只做能直接产出“一张你可试玩的关”的事；工具按需补。
- 每张关的放行 = 合法 + 随机玩家通关率 0.85–0.92 + 门被拿率 ≥0.9 + **会玩的人在门段峰值 ≥3** + 你试玩认可。
- 每次上线前写预测，上线后对账；每批都会让“标定”更准一点。

## 24. 建造层：从指标到具体车（2026-11-12）

> 这一节回答：已知指标、已知卡点规则，建造层到底怎么动“容量/位置/障碍”？为什么不能“随机改一点 + 爬山”？

### 24.0 先承认蝴蝶效应（有实测）

| 例子 | 改动 | 结果 |
|---|---|---|
| 106 `guard0_rx` | 一辆 22px 碎车放在 late 位置 | 随机通关 20/20 → **2/20** |
| 23 的门 | 同一套容量，链组从尾段挪到中段 | `chainFillSteps` **6 → 0**（有代价 → 免费） |
| 23 的冰 | 给 4 辆车加冰（8–27） | 选择熵 **1.55 → 1.06–1.15** |

所以建造层的第一条设计目标是**控制影响面**，不是“搜索得聪明”。

### 24.1 五个聚合量（真正的设计变量）

不在“几十辆车”上搜，而在这五个数上搜；它们落地成哪几辆车，由 24.2 的编译规则决定。

| 代号 | 聚合量 | 定义 | 影响什么 |
|---|---|---|---|
| **A** | 门前需求 | 门色在窗口起点前的累计已吃像素 | 门外要留多少供给 |
| **B** | 门后供给 | 该色总容量 − 门外容量 | 门的强度 |
| **C** | 开门时机 | 会玩 / 随机两条路线第一次能点门的进度 | 卡点在进度的哪一段 |
| **D** | 免费余量 | 开局可点数；前 10 步每步的免费选项数 | 前段难度、开局宽窄 |
| **E** | 高压步数 | 卡点窗口内 buffer≥3 的步数占比 | 压力有没有被玩家真的背上 |
| **F** | 代价时长 | `chainFillSteps`（拿了链组到它离场的步数） | 门有没有代价 |

> 这五个数近单调：B↑ 难度↑；D↑ 难度↓；F↑ 代价↑。这是它们能“标定”的前提。

### 24.2 编译：聚合量 → 具体车

| 聚合量 | 编译规则 |
|---|---|
| B 门后供给 | 门后车辆数 = ⌈B ÷ 该色单车容量⌉；选**激活进度最接近 C** 的那几辆 |
| A 门前需求 | 门外容量 ≈ A × 1.1，多出的一律进 B |
| C 开门时机 | 选激活进度中位数落在窗口内的车格；随机与会玩差 >10pp 时，以**会玩**为准（随机会被拖偏） |
| D 免费余量 | 第 0 行 ≥5 辆可点；若要压低 D，把后期色车放外圈、前期色车放内圈 |
| E 高压步数 | 由 B、C、D 共同决定，不单独调；不达标就回 B/C |
| F 代价时长 | 代价车必须是**稀缺色**（开门时可达 < 容量）；没有稀缺色，就先把后期色车换到外圈再成链 |

**容量不能改**（硬输入）：唯一合法的“改容量”是**同色车之间的重分配**。切分本身不支持设计时，回 `SplitLevel` 重切，这是粗决策，一次做完。

### 24.3 搜索阶梯（含预算）

| 层 | 做什么 | 点数 | 预算（每点 ~20 秒，8 核并行） |
|---|---|---|---|
| **L0 可行性** | 五个聚合量在这张图上有没有解（S1.5） | 1 | 分钟级 |
| **L1 一维** | 每个旋钮逐档扫 | 5 旋钮 × 3–5 档 ≈ 20 | ~7 分钟 |
| **L2 二维** | 一维失败时，任取两个旋钮做格子 | 9–25 | ~5 分钟 |
| **L3 正交/随机** | 5 旋钮、3–5 档：正交表 25–27 点，或随机 100–200 | 25–200 | 10–60 分钟 |
| **L4 判定** | L3 都扫不进区间 → 可行域为空 | — | 回 S1 / 换图 / 重切 |

> **关键**：L1 失败**不是**“回退再单独试下一个”，而是直接进 L2。这是与旧流程最大的差别。

### 24.4 每次改动的三条纪律

1. **等价类交换**（把维度锁死）：
   - 同色两辆车互换 → 只改“时机”；
   - 同容量两辆车互换 → 只改“颜色时机”；
   - 同色车容量重分配 → 只改“这一色切成几辆”；
   - 障碍参数 → 只改“这一处门槛”。
2. **配对种子**：所有对比用同一批种子（977/4242/31337）；差异 <0.03 视为无变化。噪声不压下去，小效应会被淹掉。
3. **影响面检查**：每次接受一个改动，除了目标指标，还要看：
   - 选择熵掉 >0.1 → 退回；
   - 开局可点变了 → 退回；
   - 任何颜色的需求峰消失 → 退回；
   - 守恒 / 可通关 / 排版坏了 → 退回。
   **只允许目标指标动，其他必须在噪声带内。**

### 24.5 障碍是手段，不是要求

- 合格标准是**聚合量与指标**，不是障碍数量。
- **0 冰、0 管道、0 锁链，只要难度在区间，就是合格关。**
- 反过来，加了障碍但难度没动 → 应该撤掉（它只降低选择熵）。
- 需要“时间闸门”时才用管道；冰已证伪（熵杀手）。

### 24.6 失败的判定

| 情况 | 判定 | 处理 |
|---|---|---|
| L0 不通过 | 这套图 + 容量做不出目标结构 | 换图 / 重切 |
| L1–L3 全扫不进区间 | 可行域为空 | 换图 / 重切；**不要继续调参** |
| 扫进了区间但熵 <1.45 | 用选择换压力 | 按 §10 “选择熵低”那行修，或在 L2 里加“熵”作为第二目标 |
| 区间内但你看不上 | 设计判断 | 记下来，作为下一张卡片的约束 |

### 24.7 耦合的证据（我们自己的）

| 耦合 | 单独调一个为什么没用 |
|---|---|
| 门有没有代价 = 稀缺色 × 位置 × 链员 | 只挪位置（中段）→ 免费；只换代价色（背景色）→ 免费；两者同时才成立 |
| 22px 碎车 × buffer4 | 只看车容量没问题，只看 buffer 也没问题，同时在 late 才崩 |
| 冰 × 选择熵 | 冰单独看“只延迟了供给”，和熵一起看才发现用选择换了时间 |

### 24.8 与指标层的关系

- **指标是裁判，不是目标函数**：目标是**区间**（随机玩家通关率落带、熵有下限），不是最大/最小。
- 只有两个指标当门槛（§8.0）；其余是约束与诊断。
- 建造器不许自己改指标口径、不许调门槛来“通过”。
