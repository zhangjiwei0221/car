> 生成日期：2026-11-12　工具：`03_工具/正式版/PopulationSim_v1.js`
> 本目录的产物全部由该工具真实跑出；命令与数字见下。

## 1. 实现来源（与 PressureBuild_v5.js 的对应关系）

工具里的三个玩家是**逐行抽取**，判据、随机数、洗牌顺序、排序键均未改；只额外记录了路线与每步选项计数（纯观测，不参与决策）。

| PopulationSim_v1.js | PressureBuild_v5.js | 说明 |
|---|---|---|
| `isWon()` 第 80 行 | 第 40 行 | `eliminatedPixels >= totalPixels` |
| `isDead()` 第 81 行 | 第 41 行 | `overflow || buffer>limit || Sim.isDeadEnd` |
| `expand()` 第 84 行 | 第 43 行 | cloneState + applyPick 枚举全部非 blocked 车 |
| `freePath()` 第 101 行 | 第 60 行 | **skilled**：free-first，排序键 `[dead, 吃完, gain, -bufAfter, -debtPx, -r, -c]` 原样 |
| `lurePath()` 第 131 行 | 第 90 行 `playPath('lure')` | **greedy**：`gain` 降序、平手 `buffer` 升序 |
| `runRandom()` 第 153 行 | 第 90 行 `playPath('rand')` | **random**：LCG 洗牌整张合法车列表，再按序 cloneState+applyPick，取第一个“当步不死” |
| `lcg()` 第 219 行 | 第 123 行 `evaluate()` 内 | `rs = (rs*1103515245+12345) & 0x7fffffff; rs/0x7fffffff`，表达式逐字符相同 |

要点：
- random 每步的随机数消耗 = `合法车数-1`，与 PressureBuild 相同（不是“不死选项数-1”）；因此同种子下**每局路线逐步相同**。
- PressureBuild 的 LCG 乘法会超出 2^53（浮点精度损失），本工具保留同一表达式，所以序列逐位相同（不是换成了更“正确”的 RNG）。
- `freePath` 只额外记录了终态进度与 maxBuffer；选路逻辑未动。
- 本工具**没有调用/修改** `PressureBuild_v5.js` 或任何现有工具。

## 2. 命令

```bash
# 单关（本目录三个子目录即由下面三条命令生成）
node 03_工具/正式版/PopulationSim_v1.js 测试版本/2026_11_05/分组2/G2_bq_level_2.json \
  --random 100 --seeds 977,4242,31337 --skilled --greedy --out 实验关/产线v5/A3_群体模拟/G2_bq_level_2

# 参考实现（对比用）
node 03_工具/正式版/PressureBuild_v5.js 测试版本/2026_11_05/分组2/G2_bq_level_2.json \
  --eval-only --nrand 100 --pseed 977
```

目录输入：`--out` 下每个关卡一个子目录（`routes_seed<种子>.json` + `summary.json`），另写 `summary_all.json`。

## 3. 输出格式（固定）

`routes_seed<种子>.json`：

```json
{ "level": "...", "seed": 977, "player": "random", "games": [
  { "won": false, "steps": 42, "deathStep": 42, "deathProgress": 0.8625, "maxBuffer": 4,
    "route": [ { "step": 1, "r": 0, "c": 3, "buffer": 0, "progress": 0,
                 "gain": 59, "M": 4, "C": 1, "F": 1, "D": 3 } ] } ] }
```

口径：
- `steps`：实际点了多少步；`route.length` 与之相等。
- `deathStep`：死亡时已点步数（= `steps`）；通关为 `null`。
- `deathProgress`：死亡态 `eliminatedPixels/totalPixels`（0–1）；通关为 `null`。
- `buffer`：该步**点之前**的暂存车数（与 PressureBuild 的 `bufs` 同口径，因此 freeP3 可直接对齐）。
- `progress`：该步**点之前**的消除进度（0–1，6 位小数）。
- `gain`：该步消除的像素数。
- `M`：合法可点车数（`Sim.listMoves` 且 `!blocked`）。
- `C`：至少吃 1px 的选项数。
- `F`：不增加暂存车数（`bufferAfter <= bufferBefore`）的选项数。
- `D`：增加暂存车数、但“当步不死”的选项数（死判据 = random 玩家的 `isDead`）。
- 注意：C 与 F/D 是**两个不同维度**（C 按“吃没吃到”，F/D 按“暂存增不增加”），C 的选项可以同时计入 F 或 D；`F+D` 可能小于 `M`——暂存增加、但当步就死的选项既不算 F 也不算 D。这是定义本身的结果，不是漏算。
- `maxBuffer`：全程最大暂存车数（含每步点之前与终态）。

`summary.json`：每个种子一行 `{seed,games,wins,winRate}`；`randomWinRate` 给 `mean/min/max/range`；`skilled` 给 `won/freeP3/steps`；`greedy` 给 `won/steps`。

## 5. 局限与已知问题

1. **速度不达标（最重要）**：每步要给出 M/C/F/D，就必须对**每个合法选项**各跑一次 `applyPick`；本引擎一次 `applyPick` 里 `processAntBox`/`autoReleaseBuffer` 约 1–2.6 ms（实测 `processAntBox` 1.675 ms、整次 `applyPick` 2.39 ms）。平均 M≈4.7–6.5，因此 100 局 × ~35–44 步 × ~5 个选项 ≈ 2 万次结算，必然落在 20–60 s。
   - 对照：**只跑 random 玩家、不做逐选项统计**时是 8.2/8.7/6.7 s——已经贴着 10 s。所以“100 局 ≤10 s”这条要求与“每步输出精确 M/C/F/D”在同一引擎上不可兼得。
   - 已把统计做成“与玩家共用同一次展开”（每步只展开 M 次，不重复 apply），这已是精确统计的理论下限；没有为提速改判据或抽样。
   - 若后续只要通关率/路线，可加“不统计”开关再测；本次未擅自改验收口径。
2. **随机玩家的验证面**：只在 G2 的 L2/L9/L11 上与 PressureBuild 做了逐局核对；这三关各只有 6–8 个锁链格（无管道，5–11 个数字冰格），**锁链多/管道多/整组锁链大的关未验证**。玩家实现本身逐行复制，但极端关（满暂存+锁链整组入场、管道释放）建议补 2–3 关核对。
3. **skilled/greedy 只各跑 1 条确定性路线**（与 PressureBuild 的 `freePath`/`lure` 相同）；它们不进 `routes_seed*.json`，只进 `summary.json`。
4. **`progress`/`deathProgress` 是比率**（0–1），不是像素数；`gain` 是像素数。
5. `routes_seed*.json` 体积约 300 KB/100 局；目录输入时会按关卡分子目录，避免同名覆盖。
