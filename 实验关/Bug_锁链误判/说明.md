# G3 第 2 关「二锁链误判」复现序列搜索说明

## 1. 目标

复现用户 2026-11-13 在客户端「分组3 第 2 关」看到的形态：

- 暂存区为 3 时点击二锁链（组 2：`(4,6) 32/22` + `(5,6) 26/21`）；
- 客户端立刻弹出「失败，存储区域已满」；
- 但随后目标区像素继续消除、腾出了空位，实际并没有失败。

本目录只做**客户端 bug 的复现素材**，不造关、不改产线、不改客户端。

## 2. 关卡与模拟口径

- 关卡：`/Users/red/Desktop/ParkPassenger.app/Contents/Resources/bin/G3_bq_level_2.json`
  （7×7 棋盘，40×40 目标图，1600 像素，暂存上限 5）
- 模拟器：`03_工具/正式版/Build006Thickness_v688.js`
  - `loadSolver('corner')`
  - `createState({ useSlotStart: true, instantChain: false })`
  - `listMoves` 过滤 `!blocked`
  - `applyPick` 串行结算
- 链组：
  - 组 1（三连）：`(0,6) 50px`、`(1,6) 24px`、`(2,6) 18px`
  - 组 2（二连，本 bug 目标）：`(4,6) 32/22`、`(5,6) 26/21`

## 3. 命中条件（按用户后续收窄后的版本）

1. 点击前 `buffer.length == 3`；
2. 链组 2 的两格在 `listMoves` 中都存在且 `blocked == false`；
3. 点击链组 2 后：
   - 入场瞬间 `bufEnter == 5`（3 + 2）；
   - 结算后 `bufAfter <= 4`（至少一辆车吃满腾位）；
   - `applyPick` 后 `overflow == false`、`gameOver == false`、`isDeadEnd == false`。
4. **结算后仍为 5 的一律丢弃**——那是真输，不是误判样本。

每条序列在写入前都会从初始状态重放前缀 + 触发点击，核对 `bufEnter / bufAfter / 未判死`；`sequences.json` 中 `replay.ok` 全部为 `true`。

## 4. 搜索方法

### 4.1 随机轮（摸底 / 估命中率）

- 5000 局随机对局，LCG 种子 `1000..5999`。
- 每一步在当前 `!blocked` 的 `listMoves` 中均匀随机取一个，最多 90 步；死局/溢出/通关即停。
- 结果：
  - 链组 2 变为可点的对局：**107 / 5000（2.14%）**；
  - 链组 2 可点的状态：320 个；
  - 其中点击前 `buffer == 3`：166 个；
  - 去重后满足全部命中条件：**93 条**。
- 另有开发期小规模探针用于校验脚本与筛选逻辑（每轮 ≤500 局），不计入上面的正式统计。
- 正式随机轮为 5000 局，在 6000 局预算内。

随机轮的命中率与用户实测（200 局约 2 局链组 2 可点、其中 1 局 buffer=3）一致。

### 4.2 定向 beam search（最终清单来源）

随机轮路径太发散，短前缀很少。最终清单改用**多根 beam**：

- 6 个开局可点各起一条 beam（`(0,0)..(0,5)`），强制首步分化；
- 每根每层保留 160 个状态，深度 18，每状态最多扩展 8 个非阻塞取盒；
- 打分：链组 2 成员激活数、周围格清空数、第 6 列/第 5-6 行清空进度、暂存长度离 3 的距离；`buffer==3 且链组 2 可点` 给最高分；
- 去重键：棋盘占位 + 已消除像素数 + 暂存组成（色号/容量/进度）+ 数字冰剩余（另含管道剩余指针）。

结果：

- 原始命中 5831 条，去重后 4797 条；
- 其中入场=5 的尝试 31885 次，结算后仍为 5 的 **26054 次已丢弃**（约 81.7%），保留 5831 次；
- 结算后 buffer 分布：0 → 48、1 → 494、2 → 1431、3 → 3399、4 → 459；
- 最终按「前 5 步点击组合互不相同」筛选出 **30 条**，前缀长度 7–17 步，覆盖 6 个不同开局根；30 条的前 5 步组合全部不同（前 4 步有 23 种）。

## 5. 命中率小结

| 阶段 | 规模 | 链组2可点 | buffer=3 | 去重命中 |
|---|---|---|---|---|
| 随机 | 5000 局 | 107 局 / 320 状态 | 166 状态 | 93 条 |
| 多根 beam | 6 根 × 160 × 18 层 | — | — | 4797 条（最终选 30） |

随机轮平均约 **1.9%** 的对局能产出至少一条有效序列；链组 2 可点后约一半状态正好 buffer=3。但即使满足前两条，仍有约 **82%** 的点击在结算后 buffer 停在 5（真输），所以三条条件同时成立才是稀有事件——这也是最终用定向搜索提高产出的原因。

## 6. 局限（重要）

1. **模拟器是同步结算，客户端是动画结算。**
   `applyPick` 在一步内把消除推到完成；客户端按“每秒 5–8 只蚂蚁”逐步出蚁，暂存占用和失败判定发生在动画过程中。
   因此这些序列只能复现「点击前状态 + 入场 5 + 结算后腾位」的**状态形状**，不能直接证明客户端 bug；需要在客户端按序列手点验证。
2. **失败判定的客户端实现未知。**
   我们推断客户端在 autoRelease 之前就按“3 + 2 ≥ 5”或“> 4”判失败；本搜索只保证存在“入场 5、随后腾位”的局面，不证明客户端的具体判据。
3. **beam 前缀是机器生成的。**
   不保证是最短或最自然的人类路线；但每一步都是合法取盒，且已通过重放校验。
4. **链组可点要求两格都激活。**
   序列里链组 2 出现前，必须已清掉 `(3,6)` 以及 `(5,5)`/`(6,6)` 之一；清单中的前缀都满足。
5. **去重口径。**
   状态键包含占位、消除像素数、暂存组成、冰剩余；理论上可能把“消除像素数相同但图案不同”的状态合并，但本关 7×7 小盘、且键含全部棋盘占位，实际风险极低。
6. **预算。**
   正式随机轮 5000 局（≤6000 局）、多根 beam 约 205 秒（总时长 ≤40 分钟）；开发期的小规模探针（每轮 ≤500 局）用于校验脚本，另计。未到预算上限即产出 30 条，未放宽任何命中条件。

## 7. 文件

- `search_sequences.js`：随机 + 多根 beam 搜索主脚本（`node --check` 通过）。
- `finalize_outputs.js`：把随机轮与 beam 轮统计合并、重生成清单。
- `probe.js`：关卡加载 / 链组位置 / 随机命中率探针。
- `sequences.json`：30 条序列的机器可读版本；每条含前缀逐步点击、每步 buffer、点击前暂存明细、`bufEnter`、`bufAfter`、腾位车辆、状态键、复跑校验。
- `序列清单.md`：人读版，可直接照着点。
